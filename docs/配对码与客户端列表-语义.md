## 2. 查实的三条缺陷

### 2.1 本机自动配对的码冒充「待用」（已修）

**机制**：`server/localpair.py::publish()` 在后端**每次启动**都
`issue_pairing_code(created_by="local-pair")` —— 往配对码表插一行，同时写进
`local-pair.json`。而客户端那边 `app/backend_setup.py::pair_if_needed()` 一旦判定
"已配对到本机回环地址"就**直接跳过**，**永远不会来兑换**这张码。于是：

* 每启动一次后端多一张"发出但没人用"的码 → dev 攒到 **16 张**；
* 它一直挂在「待用配对码」页上（TTL 7 天），看起来像有 16 张码等人用，**其实一张都不会被用**。

**两处修复**：

1. **不再累积**：`localpair._reusable_code()` —— 上一张还在库里且没过期时**复用它**，
   于是同一时刻至多一张（实测：连发 4 次，库里始终 1 行；被兑换后补一张新的）。
2. **不再冒充待用**：`ops.pending_pairing_codes()` 排除 `created_by == LOCAL_PAIR_CREATED_BY`
   的那张。判据落在**服务端看得见的那一侧**。

⚠️ **一个被我否掉的方案（留作教训）**：一开始我让 `publish()` 去读**客户端那侧**的
`{DATA}/backend.json` 来判断"是否已配对"，从而干脆不发码。这在单机形态成立，但
**后端可以跑在容器里**（另一套文件系统）—— 那时它永远读不到，判据恒为 False，
问题会**在容器形态下原样复现**且更难查。所以改成在 `pending_pairing_codes` 里判。
`localpair._local_client_already_paired()` 作为反面教材留在代码里（不再被调用）。

### 2.2 客户端列表把"配对动作的历史"平铺出来（**已修**）

用户的原话给了判据：*"这里应该是 **client_id 作为主键**而不是配对码"* +
*"客户端下列出的应该是**成功配对的客户端**列表，不是配对动作"*。

**两张表的职责**（这是理解这件事的关键）：
* `clients` —— 主键就是 `client_id`（`client_id TEXT PRIMARY KEY`），一行 = 一个已配对客户端；
* `pairing_codes` —— 主键是 `code_hash`，一行 = 一次握手动作，另有 `client_id` 列
  **目前恒为空**（设计上留给"这张码是发给哪个已知客户端"）。

**真正的问题不在主键，在"一行对应一次配对动作"**：`Auth.redeem()` 里
`cid = new_client_id()` —— **每兑换一次就生成一个新 client_id**。本机每重新配对一次
就多一个客户端行（dev 实测 **12 行全叫「本机客户端」**），而列表把它们和"现在在用的"
平铺在一起。**点"撤销"也解决不了**：撤销只是 `token_version + 1`，行还在、列表照样显示
（`store.revoke()` 的注释写明"那一行是管理员的账，不能删"）。

**修法（不删行、可回退）**：
1. `_ADDED_COLUMNS` 加一列 `clients.revoked_at`（走既有的最小补列迁移）；
2. `store.revoke()` 顺手盖上 `revoked_at`；新增 `store.revive()` 可复位
   （**不动** `token_version` —— 标记只是"从列表里收起来"，不是判决，也不该让凭据失效）；
3. `store.clients()` 默认**只返回未撤销的**，`include_revoked=True` 时照旧全返回
   —— 管理面、`--list-clients`、`/admin/api/clients` 三处自动跟着变干净；
4. 管理面那句说明补上"本机自动配对那张不算待用"。

**实测效果**（dev）：列表从 **13 行 → 2 行**（`cli-aa07c1` 在用的 + `cjy-hw` 同事的）；
稳定版 **7 行 → 1 行**。行都还在库里（带 `revoked_at` 时间戳），
"这台机器配过几次"照旧查得到。

**这一步只是"把历史的收起来"**，根治见 §2.4 —— 那里让 `redeem()` 复用同一个身份。

### 2.4 「一台机器一个身份」的根治（**已做**）

§2.2 做的只是把积压的历史收起来。源头在 `Auth.redeem()`：

```python
cid = new_client_id()      # 每兑换一次就新建一个 —— "越配越多"的根源
```

而 `pairing_codes.client_id` 那一列**建表时就有、一直空着**，它就是为这件事留的。

**实现（三步，都用既有机制）**：

| 步 | 位置 | 做什么 |
|---|---|---|
| ① 发码时记下"这张码属于谁" | `store.put_pairing_code(client_id=…)` / `Auth.create_pairing_code(client_id=…)` / `ops.issue_pairing_code(client_id=…)` | 只是把那一列填上 |
| ② 本机配对带上自己的身份 | `localpair._current_client_id()` → `publish()` | 读客户端那份 `{DATA}/backend.json` 的 `client_id`。**尽力而为**：读不到就返回空串（容器形态读不到客户端的文件系统，自然退化成旧行为）——**不能因为读不到就让配对失败** |
| ③ 兑换时复用身份 | `Auth.redeem()` 的 reuse 分支 | 码上有 `client_id` 且那个客户端**还在** → `store.rotate_secret(cid, hash)`（只换 secret、不新建行）；**不在** → 回落新建 |

**安全边界**：能拿到这张码的人本来就能换到一份凭据，复用身份**不扩大**这个面
（换来的仍然只是那一个客户端的凭据），而码依然是"一次性、按 TTL 过期"的。
`rotate_secret` 会把 `token_version + 1`，所以**旧令牌立刻失效** ——
复用身份**不等于**沿用旧凭据。

**判据**：
* `test_a_code_carrying_a_client_id_reuses_that_identity`
  —— ① client_id 与原来相同；② 客户端行数不增；③ 新 secret 能用、**旧 secret 不能用**；
* `test_a_code_for_a_missing_client_falls_back_to_creating_one`
  —— 码上指的客户端不存在时**必须还能配上对**（复用是优化，不是前提）。

### 2.3 `last_seen` 是死字段（**已修**）

`store.touch()`（唯一写 `last_seen` 的地方）**全仓没有任何调用点** —— 注释还写着
"刻意不每请求写 —— **由调用方节流**"，但那个"调用方"从来没被接上。于是：

* 管理面「最后活跃」那一列永远显示 `—`；
* `--show-client` 的"最后活跃"同样是空的；
* 看起来像"这些客户端从没活动过"，而本机客户端其实刚调用了几十次。

**修法**（用户给的口径：*"既然列表以客户端为单位，那就需要最后活跃时间，发起调用时更新"*）：
在**唯一的认证入口** `Auth.authenticate()` 里按间隔节流地调 `store.touch(cid)`：

```
auth.touch_interval_s   默认 60 秒 —— 管理面看的是"分钟级"活跃度，
                        没必要每个请求抢一次 Store._lock
```

* 节流表是**进程内**的（`Auth._touch_at` + 一把锁）：多实例各写各的，最后一次写入赢，
  对"最后活跃"这个语义完全够用；
* 写失败**绝不**让一次已经通过的认证变成 500（那是把附带动作升级成可用性问题）。

**判据**：`tests/test_server_contract.py::AuthTokenTests::test_a_request_updates_last_seen_but_throttles_the_write`
—— ① 走一次 `authenticate()` 后 `last_seen` 真的变了；② 节流窗口内第二次**不写库**；
③ 过了窗口必须再写（否则"最后活跃"会永远停在第一次）。

**真机核验**（带合法令牌打一次 HTTP）：

```
GET /v1/health  Authorization: Bearer <token>   → 200
之后 clients.last_seen = 13:37:59
```

⚠️ **一个差点误判的坑（留作教训）**：我第一版验证脚本用 `server.settings.load()`（无参）
建 Auth，拿到的是 `auth.jwt_secret` 为空的配置 → `authenticate()` 走"鉴权关着"那条早退分支
直接返回 `anonymous`，**根本不会触达 `_touch()`**，于是"验证失败"。正确做法是
`settings.load(<后端 server.yaml>)` —— **验服务端行为必须用服务端那份配置**。

## 4. 顺带说明：为什么"清理"这件事本身很少真的发生

`store.sweep_pairing_codes()` 会被 `ops.issue_pairing_code()` 顺手调用 —— 也就是
**每次发码时清一次过期的**。所以积压的从来不是过期码，而是**未过期但没人会用**的
本机码（TTL 7 天）。这也解释了体检时"已过期 0 条"却攒了 16 张的反直觉现象。
