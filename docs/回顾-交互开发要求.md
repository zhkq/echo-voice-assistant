# 回顾交互 · 开发要求（App 优化任务书）

> 版本：v1.0（2026-10-24）
> 目标客户端：Android App（`android/`）
> 目标：把「开始回顾 → 提示回顾准备已开始 / 本次回顾的主要内容 → 同时给智能体发布准备任务 → 等准备结束给用户反馈 → 按用户交互不断完善 → 最后结束」这一套交互，完整实现到 App；并补齐 ECHO 侧**让手机能触发与观测准备任务**的最小契约。
> 依据：
> - 用户 2026-10-24 口径（见 §1 需求原文）
> - 现状实现：`app/daily_review.py`（`preflight` / `pre_state`）、`app/assistant.py::_review_worker`、`app/api.py` 的 `/api/daily-review/*`、`android/app/src/main/java/com/echo/contact/ui/MainViewModel.kt`、`ReviewTab.kt`
> - 现有设计：`docs/AI手机-ECHO-App-设计.md` §4.4 / §5.3 / §6.6；`docs/AI手机-App-P0开发清单.md` M4
> - 仓库纪律：`AGENTS.md`（失败必须可见、假成功比报错更坏、缓存/状态原子性、不静默）

## 1. 需求原文与一句话目标

用户 2026-10-24 原话（断句后）：

> 开始回顾后，提示用户「回顾准备已经开始」「回顾的主要内容」等信息提示，
> 同时给 agent 发布「开始回顾」任务，
> 然后等准备任务结束后给用户反馈，
> 随后根据用户交互不断完善回顾内容，直到最后结束。

一句话目标：

**手机点「开始回顾」后，先让用户立刻看到「回顾准备已开始 + 本次回顾会梳理什么」，同一时刻把准备任务交给智能体；准备结束（完成/超时/失败）后用一句人话反馈；之后一轮轮说/打字，让回顾内容被整理、核对、补全；用户点结束时给一个如实的收尾。**

## 2. 现状（先读这一节，别重复造轮子，也别假装已有）

| # | 现状（代码事实） | 对本期的影响 |
|---|---|---|
| 1 | 手机点「开始回顾」**只调** `POST /api/daily-review/start`：建/取回当天会话，**不碰麦克风**（`MainViewModel.startReviewSession`，2026-10-19 起）。 | 这一条保持不变，继续作为第一步。 |
| 2 | 手机现在开始后**直接进入「回顾进行中」**，没有「准备」阶段，也没有准备提示。 | 本期新增 `PREPARING` 阶段。 |
| 3 | ECHO 的 `daily_review.preflight()` **已实现完整准备流程**（技能第 0 步：扫当天文件、归档会议纪要、汇总计数、完成标记、3 次追问、900 秒上限、可中止）。 | 准备逻辑不用重写，只需包一层 REST + 后台线程。 |
| 4 | 但这个 `preflight()` **只有 PC 语音回顾会调**：`/api/daily-review/go` → `assistant.start_review()` → `_review_worker` → `preflight()`。 | **手机目前无法触发准备**；这是必须补的 A 部分。 |
| 5 | `GET /api/daily-review` **已经**返回 `pre`（`daily_review.status()` → `pre_state()`），但 App 的 `DailyReviewState` DTO 没有这个字段，被 Gson 丢弃。 | App 补字段即可；服务端再补齐 `ack/topics/reply` 等。 |
| 6 | `POST /api/daily-review/stop` 只停 PC 语音回顾（`assistant.stop_review()`），**不停准备任务**。 | 结束时要能一起停准备，响应加 `preStopped`。 |
| 7 | 手机每轮已走 `/api/daily-review/turn`（语音）或 `/submit`（文字），与 PC 回顾同一条 `daily_review.submit()`，只进回顾历史。 | 保持不变。 |
| 8 | 手机结束已区分「本地结束 / 主机 stopped 三态」。 | 保持不变；再补「准备是否被停」。 |
| 9 | PC 面板有准备流程，但只有「念一句开场」，**没有可视化准备卡/主要内容/进度**。 | 本期不做 PC 视觉升级；同一契约以后可复用。 |

**结论：** 只改 Android 改不出真准备——必须同时做 A 部分（ECHO 契约）。若 App Agent 无权改 ECHO 侧，先把 A 部分转给 ECHO 侧并等它合入；否则 App 只能做「假提示」，**明令禁止**。

## 3. 角色与职责边界

| 角色 | 负责 | 不负责 |
|---|---|---|
| **App（Android）** | 开始/结束、准备提示与进度、轮次录音/上传、播报与登记核实展示、失败原因、导航与状态。 | 不直连 DSH；不执行回顾技能；不生成回顾内容；不判断「已完成/已登记」。 |
| **ECHO API** | 建会话、发准备任务、维护准备状态、转写、调用 `daily_review.submit()`、落库、历史查询。 | 不替 App 做 UI 状态机；不向手机推送语音。 |
| **配置的智能体（DSH）** | 执行 `daily-review` 技能：第 0 步收集素材；每轮整理/登记/追问；回复含 `【播报】`。 | 不直接和手机通信。 |
| **PC 面板** | 现有 PC 语音回顾（`/go`）不变。 | 本期不新增准备可视化。 |

**铁律：**

1. **所有推理只发配置的智能体**（`AGENTS.md` 2026-10-22 硬约束）。App 不能直连 LLM/DSH。
2. **`/api/daily-review/go` 是禁区**：它内部 `assistant.start_review()` 会真的打开**电脑**的麦克风。手机在车里说什么都听不到，还会把电脑的麦占住。
3. **准备任务不占麦克风**：服务端准备路径上不许出现 `assistant.start_review` / `record_command` / `recorder.*` / `providers.speak_text`。
4. **回顾轮次不走指令空间**：只走 `/turn` 与 `/submit`，不调 `voice-command` / `assistant/command`。
5. **单一事实源**：回顾内容最终落在 ECHO 的 `commands(source='review')` 与笔记库工作日志；App 只呈现，不在本地维护可编辑副本。

## 4. 目标交互（用户视角，五个阶段）

```
手机（用户）                        ECHO API                         配置的智能体（DSH）
   │ 点「开始回顾」                    │                                  │
   ├─ POST /api/daily-review/start ──▶ 建/取今天会话（不碰麦）            │
   │ ◀─ sessionId ────────────────────┤                                  │
   │                                                                      │
   │ ① 立刻显示「回顾准备已开始」+「本次回顾会梳理」+ 预计约 1 分钟         │
   │    （本地兜底文案先上屏，不等 /pre 返回）                             │
   ├─ POST /api/daily-review/pre ─────▶ 确保会话 → 起后台准备线程          │
   │ ◀─ ack / topics / eta（立即返回）─┤ ── prompt（技能第 0 步）────────▶ 扫文件、
   │                                    │                                  │ 归档纪要、
   ├─ GET /api/daily-review/pre（2.5s）▶ 只读准备状态                       │ 汇总计数
   │ ◀─ phase=pre, elapsed=42 ─────────┤                                  │
   │                                    │ ◀── 回复「前置环节完成 + 计数」──┤
   │ ◀─ phase=done, reply=计数 ─────────┤                                  │
   │ ② 显示「准备完成：…」+ 念一句「扫完了，现在开始说今天的工作吧」        │
   │                                                                      │
   ├─ 按住说话 → POST /turn ──────────▶ 转写 → daily_review.submit() ────▶ 整理/登记
   │ ◀─ text / spoken / reply / registered / seconds ────────────────────┤
   │ ③ 追加两条消息 + 播报（念）+ 登记核实 + 整理详情                       │
   │ ④ 重复 N 轮（打字 → /submit），内容不断累积                            │
   │                                                                      │
   ├─ 点「结束回顾」→ POST /stop ─────▶ 停准备（若有）+ 停 PC 语音回顾      │
   │ ◀─ { stopped, preStopped } ───────┤                                  │
   │ ⑤ 收尾卡：本场 N 轮 / 去向 / 电脑端三态 / 准备是否被停                 │
```

### 4.1 阶段 0：开始前（IDLE）

**入口（两处，必须同一状态机）：**

- 首页「回顾」卡 → `开始回顾`（`HomeCards.reviewCardButtons` / `SuperAssistantTab.ReviewCardBody`）。
- 回顾页「开始回顾」卡（`ReviewTab.ReviewStartCard`）。

**要求：**

1. 未配对 → 只写原因、**一个请求都不发**（现有 `REVIEW_NOT_PAIRED` 语义保持）。
2. `GET /api/daily-review` 读到 `ready=false` → 开始按钮禁用，并显示 `reason` 原文（不要只说「今天还没回顾」）。
3. 读到 `running=true`（电脑正在用电脑麦克风做回顾）→ 允许开始，但开始卡/首页卡必须先显示一行：
   「电脑上还有一场回顾在跑（用的是电脑麦克风）；两边同时录会混。」（不阻止，只提示；是否做成确认弹窗由实现自定，但提示必须可见）。
4. 读到 `pre.phase=pre`（电脑上已有一场准备在跑）→ 点开始后**加入**这一场（`/pre` 回 `already=true`），不要重新发任务、不要显示“准备已开始”两次。
5. 同一场已在进行 → 重复点开始显示 `REVIEW_ALREADY_RUNNING`，**不许清空会话/消息**。

### 4.2 阶段 1：开始（STARTING，通常 1–3 秒；网络差会更久）

**触发：** 点「开始回顾」。

**要求：**

1. 按钮立刻进入 loading（`正在开始回顾…`，禁用）。此时**不要**说「准备已开始」——还没确认。
2. 调 `POST /api/daily-review/start`（无 body，保持现有契约）。
3. 成功（`ok=true` + `sessionId` 非空）后，**在同一个 UI 帧/下一帧**：
   - 建立本场 `ReviewSession`（现有逻辑保留）；
   - 置 `reviewPreparing=true`；
   - **立即**显示准备卡（先用 App 本地兜底 `ack` + `topics` + 「约 1 分钟」，标题 `正在开始准备…`；等 `/pre` 确认后再换成 `回顾准备已开始`，见 §6.2）；
   - 若用户是从首页开始的，**自动切到「回顾」页**（`vm.selectTab(EchoTab.REVIEW.ordinal)`），保证提示真的被看见；从回顾页开始则不动；
   - **同时**异步发 `POST /api/daily-review/pre`（不等待它返回才显示卡片；见 §8.2）。
4. 失败（非 2xx / `ok=false` / `sessionId` 空 / 网络异常）→ 现有三条失败路径全部保留，写进 `reviewSessionNote`，**停在 IDLE**，不发 `/pre`。
5. `/pre` 回 `done=true`（今天已经准备过）→ 不重新扫：直接按 §4.4 显示上一次的完成反馈（`pre.reply` 可能为空，用兜底），进入 ACTIVE。
6. `/pre` 回 `already=true`（电脑上已有一场准备在跑）→ 不重复发任务，直接进入轮询并显示当前 `pre`。
7. `accessOk=false` → 保留现有「权限没准备好，整理可能变慢」提示。

### 4.3 阶段 2：准备中（PREPARING）

**目标：** 用户知道「准备已经开始、在准备什么、大概多久、现在能做什么」；准备任务在电脑上跑，用户可以随时结束。

**界面（准备卡，见 §8.5 线框）：**

1. 标题：**`/pre` 已确认 → `回顾准备已开始`**；还没确认（`/start` 成功、`/pre` 在途）→ `正在开始准备…`（有 spinner）。**不许在 `/pre` 失败后仍显示「准备已开始」**。
2. `ack`（服务端或本地兜底）：说明在扫什么 + 预计时长。
3. **「本次回顾会梳理」**：`topics[]` 逐条显示（最多 4 条；没有则用本地兜底 4 条，见 §6.2）。这是需求里「回顾的主要内容等信息提示」的落点。
4. 进度：`已用时 0:42 · 预计约 1 分钟`；每秒更新；超过 120 秒追加一句「比预计久一点，还在收集素材…」。
5. 下一步提示：`准备期间可以先想想要说的：今天做了什么、卡在哪、明天计划做什么。`
6. 操作：
   - `结束回顾`（始终可用；点了会同时停准备）；
   - 准备超过 **60 秒**后出现 `先开始说（不等准备）`（调 `POST /api/daily-review/pre/stop`）；
   - 准备失败/超时后出现 `重试准备`（重新 `POST /pre`）。
7. **不显示可点的「按住说话」/输入框**（准备没完就不该让人以为能说）。若产品要求显示，必须禁用并附原因（见 §6.2 `REVIEW_PRE_GATE`）。

**等待逻辑：**

1. 每 **2.5 秒**打一次 `GET /api/daily-review/pre`（轻量只读；见 A2），页面不可见/App 进后台时暂停，回前台立刻刷新一次。
2. `phase=pre`：继续等；`elapsed` 以服务端为准，本地秒表做平滑（见 §8.1）。
3. `phase=done` 且 `finished=true`：进入阶段 3。
4. `phase=timeout`：显示「准备没跑完（原因），这场回顾照常进行…」，进入 **ACTIVE（降级）**，允许说话；不重试除非用户点「重试准备」。
5. `phase=failed`：显示「准备没跑起来（原因）…」，进入 ACTIVE（降级），给「重试准备」。
6. `phase=stopped`（用户跳过）：显示 `REVIEW_PRE_SKIPPED`，进入 ACTIVE。
7. 轮询本身失败（网络/中继）：不清准备状态，显示一行 `暂时读不到准备进度（电脑那边还在跑）`，按 2.5→5→10 秒退避重试；恢复后继续。
8. 本地兜底：即使服务端一直 `phase=pre`，到 **900 秒**（服务端上限）必须已经进入可说话状态；App 在 **120 秒**时就把「先开始说」提到显眼位置，避免干等。
9. **不许**因为「过了预计时间/没报错/GET 一直成功」就宣布准备完成。

**结束（准备中）：** 允许点「结束回顾」→ 走 §4.6；结束卡必须说明准备是否被停（见 §6.2 `REVIEW_PRE_STOPPED_ON_END`）。

### 4.4 阶段 3：准备完成 → 给用户反馈

**判据：** `pre.phase == "done"` 且 `pre.finished == true`。只看这个，不看时间、不看轮询次数。

**要求：**

1. 停止轮询（只停准备轮询，不影响会话）。
2. 准备卡切换为「准备完成」态：
   - 标题 `准备完成`；
   - **反馈正文** = `pre.reply`（服务端给的「前置环节完成：文件 N 份…会议归档 M 场」）；为空则用本地兜底 `今天的素材已经收集好了，现在开始说今天的工作吧。`；
   - 一行 `现在可以按「按住说话」，或直接打字。说一轮，ECHO 整理一轮。`；
   - 保留可展开的「今天的会议」等 `topics`（不要求重画）。
3. **念一句**（沿用现有 TTS 失败不阻塞的规则）：`扫完了，现在开始说今天的工作吧。`（不念计数；计数在屏幕上）。无 TTS/朗读关闭时静默，但 UI 必须可见。
4. 进入 **ACTIVE**：输入条出现；`reviewPreparing=false`；`_reviewSessionNote` 清空旧准备错误。
5. 完成反馈**不许一闪而过**：至少保留到用户第一次开始一轮，或 10 秒后折叠成一行可点开的「准备完成 · 展开」；折叠后仍能看到 `reply`。
6. 若用户在准备期间切到了别的页：首页回顾卡的状态行同步为 `准备完成`；不新增系统推送（App 后台/关闭时收不到是已知边界，写进说明）。

### 4.5 阶段 4：多轮完善（ACTIVE ⇄ SUBMITTING）

**每一轮的固定链路：**

```
用户说/打字 → [语音 /turn | 文字 /submit] → 服务端转写 → daily_review.submit()
→ 智能体整理/登记/追问 → 返回 reply + spoken + registered + seconds
→ App：追加「我」「ECHO」两条消息 + 显示/朗读 spoken + 登记核实 + 整理详情
```

**要求：**

1. **一轮两条、只追加不覆盖**（现有 `appendReviewRound` 语义不变；两轮 = 4 条）。
2. 轮次入口与闸门：
   - 语音：现有唯一录音路 `startRecording(asCommand=false, reviewRound=true)`；
   - 文字：现有 `submitReviewText`；
   - 闸门顺序：**准备未完成 → 这场不在 → 没权限 → 已经在录 → 会议占麦 → 一直听着占麦 → 上一轮还没整理完**。每一条原因都必须不同且可见（复用 `dictationGate` + `reviewRoundGate`）。
   - 准备未完成时：`REVIEW_PRE_GATE`（含「先开始说」提示）。
3. **整理中反馈**：
   - 显示 `正在整理这一轮…（通常 2–3 分钟）` + 已用时；
   - 60 秒时追加（并只念一次，若 TTS 可用）：`这一轮还在整理，快好了…`；
   - 120 秒时追加：`这一轮比较久，还在整理，别急。`；
   - 按钮防双击；同一时刻只允许一轮在路上。
4. **结果呈现**：
   - 最新 `spoken` 作为「ECHO 播报」突出显示，并**朗读**（现有行为保留）；
   - `reply` 全文放在「整理详情」可展开（不要只显示截断的播报）；
   - `registered` 三态：`true` → 「已写进工作日志」；`false` → 如实提示「没检测到工作日志更新（可能技能没装/这轮没内容）」；`null` → **不说话**（老记录，不猜）；
   - 显示 `整理完成（N 秒）`；失败显示 `error` + 原因（HTTP 200 + ok=false 也按失败处理）。
5. **「不断完善」的呈现方式**：
   - 消息列表本身就是内容视图，**不另造一份可编辑副本**，也不把整段对话在「刚才那一场」里重画；
   - 顶部维持 `本场 N 轮 · 今日历史 M 轮`；
   - 每轮结束后刷新 `GET /api/daily-review`（今日轮数）与 `GET /api/daily-review/history`（历史列表）；
   - 最后一轮播报即当天总结；不新增「结束总结」接口。
6. 失败/没听清：**不落一轮**、原因可见、会话不结束、可直接重说；**不自动重试** `/turn` / `/submit`。
7. 准备失败/跳过的那场仍可正常多轮（服务端背景素材可能缺一部分，文案如实说，不许假装准备过）。

### 4.6 阶段 5：结束（ENDED）

**要求：**

1. 结束前置条件（保留现有）：
   - 正在录这一轮 → `REVIEW_STILL_RECORDING`（先点「说完了」）；
   - 这一轮还在整理 → 阻止，并说明「等它出结果再结束」；
   - 已在结束态 → `REVIEW_ALREADY_ENDED`；
   - **读到 `running=true`（电脑上那场回顾在跑）→ 结束前必须二次确认**：`结束会同时停掉电脑上正在进行的回顾，确定？`（现有 `/stop` 会 `assistant.stop_review()`；不确认就不许悄悄停掉电脑那场）。
2. 结束序列：
   1. 本地先置 `reviewEnded=true`（先给用户反馈，不等网络）；
   2. 取消准备轮询与本地秒表；
   3. 调 `POST /api/daily-review/stop`（服务端同时停准备与 PC 语音回顾），读 `stopped`（三态）与 `preStopped`（可空）；
   4. 结束卡文案 = 现有 `reviewEndedLine(rounds, stopped)` + 准备补充：
      - 准备完成：`准备完成：<pre.reply 摘要>`（可选一行）；
      - 准备没完成且 `preStopped=true`：`准备也一起停了：这一场没有完成素材收集。`；
      - 旧服务端没有 `preStopped` → **不说**准备是否被停（不猜）。
3. 结束之后：
   - 保留「刚才那一场」只读卡（现有去向句，不重画对话）；
   - 刷新历史列表，今天这一场应出现在「历史回顾」；
   - 输入条消失；「再开始一场回顾」重新走 §4.2（当天会话复用；若当天准备已完成，`/pre` 应回 `done=true`，App 直接显示「今天的素材已经准备过了」并进入 ACTIVE，不重新扫）。
4. 结束时若准备还在跑：`/stop` 必须停掉它（服务端 `preStopped=true`），App 结束卡如实说；不允许准备线程在后台继续跑。

## 5. 状态机（App）

### 5.1 状态定义

| 状态 | 进入条件 | UI | 允许操作 | 退出 |
|---|---|---|---|---|
| `IDLE` | 无会话，或上一场已结束且已复位 | 开始卡 | 开始回顾 | 点开始 → `STARTING`；开始成功 → `PREPARING` |
| `STARTING` | 已点开始，`POST /start` 在途 | 按钮 loading | 无（禁止双击） | 成功 → `PREPARING`；失败 → `IDLE` |
| `PREPARING` | 会话已建 + 准备任务已发/在跑 | 准备卡（§8.5），无输入条 | 结束、跳过（>60s）、重试（失败后） | `done` → `ACTIVE`（先显示完成反馈）；`timeout/failed/stopped/legacy` → `ACTIVE`（降级） |
| `ACTIVE` | 准备终态（或旧版 ECHO 直接进入） | 进行中卡 + 消息 + 输入条 | 说一轮 / 打字 / 结束 | 一轮开始 → `SUBMITTING`；结束 → `ENDED` |
| `SUBMITTING` | 一轮上传/整理在途 | 输入禁用 + 进度文案 | 无（可取消录音，不含已上传） | 结果回来 → `ACTIVE`（追加消息）；失败 → `ACTIVE` + 原因 |
| `ENDED` | 用户结束（本地已置） | 收尾卡 + 只读「刚才那一场」 | 再开始一场 | 再开始 → `STARTING` |

> 与 P0 清单的 `IDLE→PREPARING→ACTIVE→SUBMITTING→ACTIVE→ENDED` 对齐；`PREPARING` 不再只是 `/start` 的几秒钟，而是**包含准备任务**的完整阶段。

### 5.2 迁移表（含失败去向）

| 当前 | 事件 | 下一状态 | 必须做的事 |
|---|---|---|---|
| IDLE | 点开始（未配对） | IDLE | 写 `REVIEW_NOT_PAIRED`，不发请求 |
| IDLE | 点开始（`/start` 失败） | IDLE | 写失败原因（现有三条路径） |
| STARTING | `/start` 成功 | PREPARING | 建会话 → **立即**准备卡 + 切回顾页 + 异步 `/pre` |
| PREPARING | `pre.phase=done & finished` | ACTIVE | 显示完成反馈 + 念一句 + 输入可用 |
| PREPARING | `pre.phase=timeout` | ACTIVE | 如实原因 + 输入可用 |
| PREPARING | `pre.phase=failed` | ACTIVE | 如实原因 + 重试按钮 |
| PREPARING | `pre.phase=stopped` | ACTIVE | 跳过说明 |
| PREPARING | `/pre` 404/405 | ACTIVE | 旧版降级一行 |
| PREPARING | `/pre` ok=false | ACTIVE | 原因 + 重试；**不要**死等 |
| PREPARING | 结束 | ENDED | `/stop`；结束卡说明准备被停 |
| ACTIVE | 开始一轮（闸门过） | SUBMITTING | 录音/上传；60s/120s 里程碑 |
| SUBMITTING | 成功 | ACTIVE | 追加两条 + 播报 + 登记三态 + 刷新历史 |
| SUBMITTING | 失败/没听清 | ACTIVE | 原因可见；不落轮次；可重说 |
| ACTIVE | 结束 | ENDED | 同 PREPARING 结束 |
| ENDED | 再开始一场 | STARTING | 复用当天会话；`/pre` done 则直接 ACTIVE |

## 6. 文案与信息提示（硬要求）

### 6.1 通用规则

1. **不静默**：每个分支都要写进界面读的字段（`reviewPreNote` / `reviewSessionNote` / `reviewRoundNote` 三者按语义分开，不混用）。
2. **不假成功**：
   - 没拿到 `phase=done&finished=true` 不说「准备完成」；
   - 没拿到 `registered=true` 不说「已登记/已写进工作日志」；
   - 没拿到 `stopped`/`preStopped` 不替服务端下结论。
3. **不说没发生的事**：准备失败就说失败，不写「素材还在扫」（除非服务端明确仍在 pre 状态）。
4. **一句一个下一步**：失败文案必须包含「现在能做什么」（直接开始说 / 重试准备 / 去设置配对 / 等一会儿）。
5. **错误分档**：未配对、未就绪、电脑忙、准备超时、准备失败、旧版不支持、网络不通、整理失败、没听清——**互不混用**。
6. **长度**：主行 ≤ 2 行（小屏不折行爆炸），原因 ≤ 4 行 + 可展开；`pre.reply` 超过 120 字折叠，保留全文可展开。
7. **中文字符串集中成常量**，放 `ReviewPrep.kt`（或 `ReviewConversation.kt` 同风格），JVM 可断言。

## 7. 接口契约

### 7.1 现有接口（语义保持不变）

| 接口 | 用途 | 本期注意 |
|---|---|---|
| `GET /api/daily-review` | 状态：enabled/ready/reason/running/pre/sessionId | 保留；`pre` 字段按 A5 扩展（只增不改） |
| `POST /api/daily-review/start` | 建/取当天会话，不碰麦 | **不改请求/响应语义**；不塞准备逻辑 |
| `POST /api/daily-review/turn` | 手机语音一轮（裸 wav） | 不变；阻塞，用长读客户端 |
| `POST /api/daily-review/submit` | 手机文字一轮（JSON） | 不变；阻塞 |
| `POST /api/daily-review/stop` | 结束 | 增加 `preStopped`；`stopped` 语义不变 |
| `GET /api/daily-review/summary`、`/history`、`/history/{date}` | 历史 | 不变 |
| `POST /api/daily-review/go` | PC 语音回顾（会开电脑麦） | **App 永不调用** |

### 7.2 A 部分：ECHO 服务端必须补的最小改动

#### A1 `POST /api/daily-review/pre` —— 启动（或加入）今天的准备任务

**语义：** 确保今天的回顾会话 → 把 `daily-review` 技能第 0 步（素材收集）作为**一条 prompt** 发给配置的智能体 → 立刻返回（后台线程跑，不阻塞 HTTP）。

**绝不：** 开麦克风、调 `assistant.start_review()`、`record_command`、`providers.speak_text`、写 `commands(source='review')`。

**请求：** 无 body（或 `{}`；忽略未知字段，老服务端兼容靠 404/405 降级）。

**响应：HTTP 200**（业务失败也 200，遵循本仓库「人话错误」约定）：

```json
{
  "ok": true,
  "started": true,
  "already": false,
  "done": false,
  "sessionId": "…",
  "etaSec": 60,
  "ack": "好，回顾准备开始了。我先扫今天的素材：企微、微信、桌面和 WPS 的当天文件，还有今天的会议纪要；大概一分钟。扫完我就提示你。",
  "topics": [
    "今天的会议（2 场）：10:00 周会 · 15:30 需求评审（纪要已生成）",
    "今天收到或改过的文件：企微 · 微信 · 桌面 · WPS 缓存",
    "笔记库里今天的工作日志与待办",
    "昨天没说完的、明天要做的"
  ],
  "pre": { "phase": "pre", "elapsed": 0.0, "seconds": 0.0, "finished": false,
           "etaSec": 60, "error": "", "nudges": 0, "ack": "…", "topics": ["…"], "reply": "" }
}
```

**失败（HTTP 200 + `ok=false` + `error` 人话）：**

| 情形 | `error` 示例 | App 行为 |
|---|---|---|
| 回顾未启用/未就绪 | `ready.reason` 原文 | 准备失败态 + 「重试准备」；可直接说 |
| 取智能体客户端失败 | `取智能体客户端失败：…` | 同上 |
| 建会话失败 | `没能建立回顾会话…` | 同上 |
| 电脑正忙（另一条指令/会议录音） | `电脑正忙（<owner>），准备没开始` | 同上 |
| 准备已在跑 | **不是失败**：`ok=true, started=false, already=true` | 继续轮询 |
| 今天准备已完成 | **不是失败**：`ok=true, started=false, done=true` | 直接显示完成反馈 |

> 判定顺序：**先看今天已有的准备状态**（`_PRE.phase`）——已在跑回 `already`、已完成回 `done`；只有都不成立时才去判「电脑忙/未就绪」。否则 PC 那场回顾刚跑过准备时，手机点开始会被误报成「电脑忙」。

**幂等与并发：**

- 同一天同一时刻**只允许一个准备任务**；第二次调用返回 `already=true`（并带当前 `pre`），**不重复发 prompt**。
- 跨天自动重置。
- 多次调用不得造成 `ensure_session` 建出第二条当天会话。
- 全局锁 + 状态快照原子替换（见 A6）。

**`ack` / `topics`：**

- `ack` 用**手机版**文案（新函数，例如 `pre_phone_ack_text(eta)`），**不要改 PC 正在用的 `pre_ack_text()`**（PC 那句是「扫完就开始录你说的内容」）。
  - 现有 `preflight()` 内部把 `out["ack"]` 写死成 `pre_ack_text()`。实现上给它加一个**可选**参数 `ack_text`（默认 `pre_ack_text()`，PC 行为不变），手机路径传 `pre_phone_ack_text(...)`；或由 `start_pre()` 在起线程前先把 `_PRE["ack"]` 写好自己的那句。两条都行，但**不许改 PC 的播报文本**。
- `topics` 用新函数 `pre_topics(now)` 在启动时算好并缓存（不要每次 GET 都扫盘）：
  1. 今天的会议（`today_meetings()`；有则「今天的会议（N 场）：HH:MM 标题 · …」+ 纪要是否已生成；没有则「今天 ECHO 里没有会议记录」）；
  2. `今天收到或改过的文件：企微 · 微信 · 桌面 · WPS 缓存`；
  3. `笔记库里今天的工作日志与待办`；
  4. `昨天没说完的、明天要做的`。
- 每条 ≤ 60 字，最多 4 条。

#### A2 `GET /api/daily-review/pre` —— 轻量只读轮询

**语义：** 只读准备状态；**不建 client、不建会话、不触发任何动作**。供 App 每 2.5 秒轮询。

**响应：**

```json
{
  "ok": true,
  "day": "2026-10-24",
  "sessionId": "…",
  "pre": {
    "phase": "idle|pre|done|timeout|failed|stopped",
    "day": "2026-10-24",
    "startedAt": 1790000000.0,
    "elapsed": 42.3,
    "seconds": 0.0,
    "finished": true,
    "etaSec": 60,
    "error": "",
    "nudges": 0,
    "ack": "…",
    "topics": ["…"],
    "reply": "前置环节完成：文件 12 份（专项 3）、会议归档 2 场"
  }
}
```

- `phase=pre` 时 `elapsed` 实时计算；终态 `elapsed = seconds`。
- 旧字段（`phase/startedAt/seconds/finished/etaSec/error/nudges/elapsed`）**一个都不能少**，只增不减。
- `phase` 初值用 `"idle"`；App 同时容忍 `""`/未知值，按 `idle` 处理。
- 不返回 `running`（那是 PC 模式，职责分开）。

#### A3 `POST /api/daily-review/pre/stop` —— 只停准备（跳过）

**语义：** 用户点「先开始说（不等准备）」时调用；停准备线程，**不结束回顾会话**。

**响应：** `{ok: true, preStopped: true|false, pre: {…}}`

- `preStopped=false` = 本来就没在跑（不是失败）。
- 准备已完成 → 返回 `pre.phase="done"`、`preStopped=false`。
- 停止必须 ≤3 秒生效（`preflight(should_stop=…)` 每轮轮询检查）。
- 停后 `phase="stopped"`，`error="用户跳过了准备"`（给 App 显示）。

#### A4 `POST /api/daily-review/stop` —— 结束会话时一并停准备

**响应：** `{ok: true, stopped: <bool>, preStopped: <bool>}`

- `stopped` 语义**保持不变**（PC 语音回顾是否真的停掉）。
- `preStopped`：`true` = 这次调用**确实停掉了一个正在跑的准备**；`false` = 本来没在跑 / 已完成（不是失败）。
- 实现顺序自定，但两件事都要做，结果如实回。

#### A5 `GET /api/daily-review` 的 `pre` 扩展

与 A2 的 `pre` **同一份结构**（`status()` 的返回里 `pre` 直接复用 `pre_state()`）。老 App 忽略新字段；新 App 一次 GET 也能拿到。

#### A6 服务端行为约束（逐条写进代码注释/测试）

1. **不碰麦**：准备路径不出现 `assistant.start_review` / `record_command` / `recorder.*` / `providers.speak_text`。
2. **不写轮次**：准备不是一轮，不进 `commands`、不进回顾历史。
3. **完成判据唯一**：只认 `PRE_DONE_MARK`（`"前置环节完成"`）；「本轮结束/没报错/时间到了」都不算完成（沿用现有 `preflight` 语义）。
4. **可停止**：`should_stop` 每轮检查；停止 ≤3s；最长 900s 自动收尾（`PRE_MAX_S`），如实 `phase=timeout`。
5. **状态原子性**：`_PRE` 用锁保护；对外 GET/POST 一律读**完整快照**（先在局部建好 dict，最后一次性替换；不要「先挂空 dict 再逐键填」——`AGENTS.md` 2026-09-29 的并发 bug 就是这个）。
6. **忙判据复用现成的**：`assistant._busy_owner`、`meeting.meeting_status().active`、`assistant.review_running()`；不要新造一套「忙」。
7. **后台线程**：daemon thread；进程退出不阻塞；线程句柄/stop event 存在模块状态里，可被 A3/A4 找到。
8. **日志**：`db.add_log` 记录启动/完成/超时/停止（category=`daily_review`），与 PC 同一类。
9. **PC 与手机共用同一个准备任务**：现在 `assistant._review_worker`（PC 语音回顾）是**直接**调 `preflight()` 的。本期必须让它也走同一个单例入口（例如 `daily_review.ensure_pre_started()`：已在跑就**加入/等**，不新起线程），否则 PC `/go` 与手机 `/pre` 同时触发时会各跑一份准备、互相覆盖 `_PRE`、重复扫盘。判据：两边同时触发时，智能体只收到 **1 条**准备 prompt。
10. **中继**：新路径都在 `/api/` 下，`app/relay.py` 的 `ALLOWED_PREFIX="api/"` 已放行；但要在验收文档补一条「经中继调 /pre」的证据（见 §10.6）。

#### A7 服务端验收 / 测试

新增 `tests/test_daily_review_pre.py`（可复用 `_FakeClient` 与现有 preflight 测试手法），至少覆盖：

1. `POST /pre` **立即**返回 `ack/topics/etaSec`，不阻塞；后台线程随后把 phase 推进到 done。
2. 第二次 `POST /pre` → `already=true`，**prompt 次数不增加**。
3. 完成标记出现后：`GET /pre` → `phase=done, finished=true, reply` 含计数；`GET /api/daily-review` 的 `pre` 是同一份。
4. 模拟探测异常/超时 → `phase=timeout|failed` + 人话 `error`，**不抛 500**。
5. `POST /pre/stop` → `phase=stopped`、`preStopped=true`；再调一次 → `preStopped=false`。
6. 准备中 `POST /stop` → 响应 `preStopped=true`；准备线程退出。
7. 未就绪 → `ok=false` + `reason`，不抛异常。
8. 全程**没有**调用 `assistant.start_review`、没有开麦、没有写 `commands`（打桩断言）。
9. 现有 `tests/test_daily_review.py` 全绿；`/go` 行为不变；PC 的 `pre_ack_text` 不变。
10. `GET /pre` 在 idle 时也可读（不建 client、不建会话）。
11. PC worker 与手机 `/pre` 同时触发 → 只发 **1 条**准备 prompt（单例）。注意：现有 `test_the_worker_runs_the_preflight_before_it_starts_recording` 断言 worker 源码里有 `preflight(`——如果改成单例入口，要同步更新这条断言（它真正守的是「准备在录音之前」，不是函数名）。

> 业务失败统一 **HTTP 200 + `ok=false`**（与 `/submit`、`/turn` 一致），不要用 4xx 表达「准备没跑起来」。401/422 等传输/形状错误除外。

### 8.1 状态与数据流（ViewModel）

### 8.2 开始序列（伪代码）

```kotlin
fun startReviewSession() {
    if (reviewStarting) return
    if (session != null && !reviewEnded) { note = REVIEW_ALREADY_RUNNING; return }
```

`launchPrep()`：

```kotlin
suspend fun launchPrep() {
    try {
        val resp = api().dailyReviewPre()
        when {
            resp.code() == 404 || resp.code() == 405 -> degradeLegacy()      // 旧 ECHO
            !resp.isSuccessful -> degradeFailed(parseError(resp))            // 网络/传输
            body?.ok != true -> degradeFailed(body?.error)                   // 服务端人话
            body.done -> finishPrepFromServer(body.pre)                      // 今天已完成
            else -> { applyServerAck(body); startPrepPolling() }             // 正常
        }
    } catch (e: IOException) {
        // 请求可能已到服务端：先 GET 一次确认；确认真没开始再降级
        reconcilePrepAfterNetworkError(e)
    } catch (e: Exception) { degradeFailed("准备请求出错：${e.message}") }
}
```

**关键：** 卡片先上屏（阶段 1 第 3 步），`/pre` 失败只把「准备」降级，**不撤销会话、不结束回顾**。

### 8.3 准备轮询

```kotlin
fun startPrepPolling() {
    prepJob?.cancel()
    prepJob = viewModelScope.launch {
        var intervalMs = 2_500L
        while (isActive && reviewPreparing && !reviewEnded) {
            if (!appForeground || !reviewScreenVisible) { delay(1_000); continue } // 后台/离页暂停
            try {
                val resp = api().dailyReviewPreState()
                if (resp.code() == 404 || resp.code() == 405) { degradeLegacy(); return@launch }
                if (!resp.isSuccessful || resp.body() == null) {
                    reviewPreNote = REVIEW_PRE_POLL_LOST
                    intervalMs = minOf(intervalMs * 2, 10_000L)
                } else {
                    reviewPreNote = null
                    intervalMs = 2_500L
                    applyPre(resp.body().pre)
                    when (resp.body().pre?.phase) {
                        "done" -> if (resp.body().pre.finished) { finishPrep(); return@launch }
                        "timeout" -> { finishPrepDegraded(REVIEW_PRE_TIMEOUT); return@launch }
                        "failed"  -> { finishPrepDegraded(REVIEW_PRE_FAILED); return@launch }
                        "stopped" -> { finishPrepSkipped(); return@launch }
                        else -> Unit // idle/pre/"" 继续等
                    }
                }
            } catch (e: Exception) {
                reviewPreNote = REVIEW_PRE_POLL_LOST
                intervalMs = minOf(intervalMs * 2, 10_000L)
            }
            delay(intervalMs)
        }
    }
}
```

**要求：**

- 首次轮询**立即**执行（不要先等 2.5s）。
- 页面不可见（切页）暂停；App 进后台暂停（在 `MainActivity.onStart/onStop` 通知 VM，或在 `ReviewTab` 的 `DisposableEffect` + `repeatOnLifecycle` 里做，二选一但必须覆盖后台）。
- 回前台/回页立刻刷新一次。
- 终态后 `reviewPreparing=false`；取消 job；不再轮询。
- 轮询失败**不结束会话**、不把 `reviewPre` 清空（继续显示最后状态）。

### 8.7 失败与重试策略

| 场景 | 处理 | 是否重试 |
|---|---|---|
| `/start` 失败 | 写原因，停留 IDLE | 用户手点 |
| `/pre` 404/405 | 旧版降级，ACTIVE | 否 |
| `/pre` 业务失败 | 降级 + 「重试准备」 | 用户手点 |
| `/pre` 网络异常 | GET 一次核对；确认真没开始才降级 | 用户手点 / 轮询 |
| 准备 `timeout` | 如实原因，ACTIVE | 用户手点「重试准备」 |
| 准备 `failed` | 如实原因 + 重试按钮，ACTIVE | 用户手点 |
| 轮询失败 | 保留状态 + `REVIEW_PRE_POLL_LOST`，退避 2.5→10s | 自动（仅轮询） |
| `/turn`/`/submit` 失败 | 追加失败消息 + 原因；不落轮次 | **不自动重试** |
| `/stop` 失败 | 本地已结束；显示「已请求结束，但没确认到电脑」 | 不自动 |

### 8.8 性能与体量

- 准备轮询：2.5s；只打轻量 `GET /pre`；终态即停。
- 单场消息上限：按现有实现；不新增全量轮询。
- 文案截断：`pre.reply` >120 字折叠；`reply` 详情可展开；不要一次性把长文塞进首页。
- 网络请求并发：同一时刻最多 1 个准备轮询 + 1 个轮次请求；结束/重置时取消。

## 10. 验收

### 10.1 真机 E2E 剧本（必须逐条留证据）

1. **正常链路（局域网）**
   - 点开始 → 立即按钮 loading；`/start` 返回后立即出现准备卡（局域网体验目标 ≤3 秒，这里不该有固定延迟）。
   - 同时：ECHO 日志出现 `/api/daily-review/pre` 与准备 prompt；**电脑麦克风没有被打开**（系统麦指示不亮；服务端日志无 `start_review`）。
   - 准备完成 → 卡片显示 `准备完成` + 计数；手机念一句；输入条出现。
   - 说一轮 → 进度 + 60s 提示 → 两条消息 + 播报 + `registered` 说明 + 秒数。
   - 再说一轮 → 4 条消息（追加），最新播报更新。
   - 结束 → 收尾卡（本场 2 轮 + 去向 + 主机三态 + 准备状态）；历史回顾出现今天 2 轮；**指令历史没有这两轮**。
2. **准备超时/失败**：准备卡显示 `准备没完成` + 原因；输入可用；后续轮次正常；不出现「准备完成」。
3. **旧版 ECHO**：`/pre` 404 → 一行 `REVIEW_PRE_LEGACY`，直接可说话，不轮询、不死等。
4. **电脑忙**：准备 `ok=false` + `电脑正忙（…）` 可见；可直接开始说；「重试准备」可用。
5. **准备中结束**：`/stop` 返回 `preStopped=true`；收尾卡写「准备也一起停了」；服务端准备线程退出。
6. **准备中切页/切后台 2 分钟**：服务端继续跑；回前台/回页刷新出当前 `elapsed`；不重复 `POST /pre`。
7. **重复点开始**：不新建会话、不清空消息；提示「这场回顾已经在进行了」。
8. **准备期间按「按住说话」**：被挡，原因可见，并指出「先开始说」。
9. **网络断开后恢复**：轮询显示「暂时读不到准备进度」；恢复后继续；准备完成后反馈正常。
10. **无 TTS / 朗读关闭**：完成反馈与播报只显示不念，不崩；不影响后续轮次。

### 10.2 负例矩阵

| 场景 | 期望 |
|---|---|
| 未配对点开始 | 不发请求 + 指路设置 |
| `ready=false` | 开始禁用 + `reason` 原文 |
| `/start` 400（未就绪） | 原因可见，停留 IDLE，不发 `/pre` |
| `/pre` 200 ok=false | 原因可见 + 重试 + 可直接说；**不**说准备完成 |
| `/pre` 网络超时但服务端已开始 | GET 核对后按 `phase=pre` 继续，不重复发送 |
| 准备 `timeout` | 不假完成；可开始说；原因可见 |
| 准备 `failed` | 原因 + 重试；可开始说 |
| `/turn` 422（非音频） | 与「没听清/整理失败」分开提示 |
| `/turn` 200 ok=false | 追加失败消息 + 原因；不落轮次；可重说 |
| `/stop` 返回 `stopped=false` | 如实说「电脑上没有可停的回顾」，不报错 |
| `/stop` 缺 `preStopped`（旧服务端） | 不提准备是否被停 |
| 旧 ECHO | 降级；现有流程可完成一场回顾 |
| 抓包 | **没有任何** `/api/daily-review/go` 请求；没有 `voice-command` 回顾轮次 |
