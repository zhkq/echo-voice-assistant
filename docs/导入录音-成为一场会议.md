# 导入录音 → 一场会议（接口 / 能力边界 / 状态语义）

> 2026-09-25 新增。起因是用户一句话：**"导入录音是个需要的功能"** ——
> 场景是"我有一段录音（会议/访谈/手机录的），丢给 ECHO，它变成一场带文字稿的会议"。
> 在此之前 ECHO **没有**这条路：只有单文件 `POST /api/stt/transcribe`（转完只回一段文字，
> 不进会议链路），用户做实测时只能靠 `delivery/ECHO-meeting-fixture/导入.ps1`
> 把 wav 硬塞进会议目录再手工建库记录。

## 1. 一条命令看懂

```bash
curl -F "files=@第一段.wav" -F "files=@第二段.mp3" \
     -F "title=季度评审" -F "start=2026-09-20 10:48" -F "notes=手机录的" \
     http://127.0.0.1:8970/api/meetings/import
```

```json
{"ok": true, "name": "2026-09-20_10-48-00", "id": 12,
 "files": 2, "seconds": 1777.4, "message": "已导入 2 段音频（29.6 分钟），正在转写"}
```

面板：**会议 → 导入录音** → 选文件（可多选，列表里能上下移动）→ 填可选标题 → 开始导入。

## 2. 端点与字段

`POST /api/meetings/import`（`multipart/form-data`）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `files` | ✅ | 1..N 个音频文件。**表单里出现的顺序 = 分段顺序**（第 1 个 → `01.wav`） |
| `title` | | 会议标题（写 `meetings.title`） |
| `start` | | 会议时间：`YYYY-MM-DD [HH:MM[:SS]]` / ISO。只影响目录名与显示时间；认不出就用"现在"（**不报错**） |
| `notes` | | 备注（写 `meetings.notes`） |
| `block_frames` | | 转码分块大小（0=默认 65536 帧）。**留这个口子是为了可验**：用例传一个小值就能断言"分块解码真的发生了" |

返回（成功，HTTP 200）：`{"ok", "name", "id", "files", "seconds", "message"}`。
`id` 就是 `GET /api/meetings/{id}` 与 `GET /api/transcribe/status` 用的那个，
面板据此**接着用既有的转写进度显示**。

失败（HTTP 400）：`{"detail": "<一句人话的原因>"}`，原因是**后端给的**，面板原样显示
（本项目硬规矩：界面不许自己编原因）。超过上限是 413，缺 `files` 是 422。

两条**前置拒绝**（都带能照做的一句话）：

* 正在录音中（`meeting.active`）→ "正在录音中，不能同时导入录音；请先停止录音，再导入"
  （导入完会立刻起转写，那会跟正在录的这场抢 CPU/GPU）；
* 已有一次导入在跑 → "已有一次录音导入正在进行，请等它结束"
  （两场并发会抢 `01.wav/02.wav` 这批段号，而"谁的 01.wav 是谁的"事后查不出来）。

## 3. 支持 / 不支持哪些格式（**实测**，不是估计）

本机实测（2026-09-25，venv：`soundfile 0.14.0` + `libsndfile 1.2.2`）：

| 格式 | 能不能直接导入 | 说明 |
| --- | --- | --- |
| `wav` | ✅ | 16/24/32-bit、任意采样率、单/多声道都行 |
| `flac` | ✅ | 无损，手机与录音笔常给这个 |
| `mp3` | ✅ | libsndfile 1.2.x 起内建读 MP3 |
| `ogg` | ✅ | Vorbis |
| `m4a` / `aac` / `mp4` | ❌ **明确拒绝** | 需要 **ffmpeg** 解码，而 ECHO **不依赖 ffmpeg**（装它要多上百 MB，还得管跨平台二进制）。所以这里**响亮报错**，不是静默失败 |
| `wma` / `amr` / `ac3` / `opus` | ❌ 同上 | 本机 libsndfile 编进来的编解码器不保证，一律当"读不了"报 |

拒绝时的原文（面板直接显示这句）：

> 音频「录音.m4a」的格式 M4A 本机读不了：它需要 ffmpeg 解码，而 ECHO 不依赖 ffmpeg。
> 请先把它转成 wav 或 mp3 再导入（例如 `ffmpeg -i 输入.m4a -ac 1 -ar 16000 输出.wav`）。
> 本机**可以**直接导入的格式：wav、flac、mp3、ogg。

**"不许假装支持"是怎么落地的**：`m4a`/`aac` 这一族在**读字节之前**就按扩展名挡掉
（省掉一次白传几百 MB），报错里点名格式 + 说清为什么 + 给出一条能照抄的命令。
剩下的容器一律**以内容判定**：读不出来就报 `libsndfile` 自己说的话
（`Format not recognised.`），不编"导入失败"这种空话。

## 4. 归一化：为什么只能是 16 kHz / 单声道 / 16-bit PCM WAV

会议链路的每一环都只认这一种：

* `_transcribe_impl` / `_seg_duration_map` / `retranscribe_meeting` 全按 `^\d+\.wav$` 找段；
* **sherpa 只吃 RIFF/WAV** —— 喂 flac/ogg 直接报 `file does not start with RIFF id`；
* whisper/faster-whisper 那条路也按 16 kHz 读。

所以导入的每一步都固定成：**解码 → 单声道（多声道取平均）→ 重采样到 16 kHz → 写 16-bit PCM WAV**。

重采样走哪条路，**按顺序**试，并且**写进日志与 `meta.json`**：

| 顺序 | 实现 | 特点 |
| --- | --- | --- |
| ① | `soxr.ResampleStream` | **首选**：分块重采样，内存恒定。实测与一次性 `soxr.resample` **逐样本相同** |
| ② | `soxr.resample` | 次选：质量同级，但要整段在内存里（只有在①的依赖出问题时才走到） |
| ③ | `scipy.signal.resample_poly` | 既有依赖，整数比（44100→16000 = 160/441） |
| ④ | 线性插值 | **兜底**：会丢高频（不做抗混叠），日志里会出现 warn |

`meta.json` 里逐文件记着 `{"file", "how", "srcRate", "srcChannels", "srcFormat"}`，
日志里是一条 `音频导入：<原名> → 01.wav（源 FLAC 44100 Hz 2 声道 PCM_16；重采样=soxr 流式重采样（分块，内存恒定））`。
**为什么要这么啰嗦**：用户问"这段录音转得准不准"、或排障问"这台机器上到底用了 soxr 还是兜底插值"，
除了这里没有第二个地方有答案。

## 5. 大文件：分块，不整段进内存

* **上传侧**：按 1 MB 一块写进 `%TEMP%` 的临时文件（`MAX_UPLOAD_BYTES = 512 MB` 是明面上限，
  超了当场 413）。任何一刻内存里只有一块。
* **转码侧**：`sf.SoundFile.blocks(blocksize=65536)` 一块一块解码，`soxr` 流式一块一块重采样，
  再按块攒批写目标文件。
* **怎么验的**（`tests/test_meeting_import.py::ChunkedConversionTests`）：
  * 每一次底层读取请求的帧数都必须 `0 < n ≤ block_frames`（**没有任何一次"把整个文件给我"**）；
  * `tracemalloc` 看 60 秒 44.1 kHz 立体声（> 5 MB）转码时 Python 峰值增量 < 16 MB。

> **踩过的坑（写在代码里了）**：`sf.SoundFile.blocks()` **不能传 `fill_value`** ——
> 传了之后最后一块会被补齐到整块大小，读到的总帧数比文件实际帧数多。
> 实测：16 kHz 的 1 秒文件（16000 帧）配默认块大小会报出 **65536 帧**，
> 也就是往导入的会议里塞进 4 倍静音、时间轴全错。见 `app/audio/importer.py:iter_mono_blocks`。

## 6. 导入后会议的状态落点：`imported`（「待转写」）

库里的状态词：`recording` / `transcribing` / `transcribed` / `imported` / `interrupted` / `error`。

导入的流程与状态是**一条线**：

```
（校验 + 转码，全在会议目录落地之前）
   ↓ 全部转码成功
create_meeting()            → 建记录（此刻起"这场会存在了"）
update_meeting(imported)    → 「待转写」：音频在、还没有文字
update_meeting(transcribing)→ 立刻排上转写（面板进度条据此出现）
   ↓ 后台线程
transcribed / error
```

**为什么不复用别的词**（同事的夹具脚本当初只能用 `interrupted`，并在交付文档里
写明了那是妥协）：

| 候选 | 为什么不用 |
| --- | --- |
| `transcribed` | **谎称完成**：库里一行转写都没有，面板却显示"已转写" |
| `error` | 面板把它读成"录音失败（没录到音频）"，而音频明明躺在磁盘上 |
| `interrupted` | 这个词已经被"录音中断"占住了（进程崩了/设备断了）。用它表达"导进来还没转"，两种完全不同的状况在列表里长得一模一样 |

`imported` 只多一个词，却把语义说准了：**音频在、还没有文字**。面板两侧都加了这一档文案
（`web/app.js` 与 `web/meeting.html`：徽章「待转写」，用 `idle` 色而不是红的）。

注意：`imported` 是**瞬时**状态（导入函数返回前就切成 `transcribing`）。
转写**失败**仍然落 `error` 并带真原因 —— 那一档才有原因可查，
这正是"待转写"和"转写失败"必须分开的理由。

## 7. 失败时不留垃圾（原子性）

顺序是刻意的：**先把每个文件转码成功，再建库记录、再写 `meta.json`**。
任何一步失败：

* 会议目录（可能已经有 `01.wav`）整个删掉；
* 不起转写线程；
* 库里**没有**记录；
* `%TEMP%` 里的上传临时文件清掉；
* 接口返回 400 + **真原因**。

覆盖的失败面：空文件（0 字节）、解码失败（改了扩展名的假音频）、不支持的格式、
读不到采样率、重采样实现全缺失、转写引擎驱动不了（这一条落 `error`，音频**保留**）。

## 8. 与既有链路的关系（都没动）

| 既有能力 | 受影响吗 |
| --- | --- |
| 会议**录音**（`POST /api/meeting/start` / `stop`） | ❌ 没动。导入只写新的会议目录 |
| **重新转写**（`POST /api/meetings/{id}/retranscribe`） | ❌ 没动。导入出来的场次照样能重转（段名就是 `01.wav/02.wav`） |
| **说话人分离**、声纹识别 | ❌ 没动。转写时按设置走，与导入来源无关 |
| **能力后端路由** | ❌ 没动。导入只是把音频塞进会议目录；整场转写仍按 `capabilityMeetingAsrBackend` 走 |
| `delivery/ECHO-meeting-fixture/导入.ps1` | ❌ 没动，照旧能用（它是"离线硬塞"那条路；现在面板里有了正路，但脚本没被删也没被改） |
| `POST /api/stt/transcribe`（单文件转写） | ❌ 行为没变（它自己的 `_audio_to_wav16k` 保持原样） |
