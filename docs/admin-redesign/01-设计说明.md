## 1. 背景与目标

当前管理面是 `server/admin.html`（约 1.2k 行，深色单页），由 `server/admin.py` 提供。
收费/账号能力已经落在 `integration/billing-vibepay`：套餐、订单、权益、账号、设备、邀请码、
支付回调都有后端接口，但页面上全部塞在「收费 / 账号」一个页签里，运营每天查单、退款、
看用户权益/设备要在一张很长的页面里翻。

本设计要解决三件事：

1. **视觉统一**：管理面（含登录页）改成与官网 `site/` 同一套浅色、蓝色主色、卡片、字体、
   按钮、表格、响应式；但保留管理面应有的信息密度。
2. **运营优先**：把订单、用户/账号、权益、邀请码、支付回调拆成独立、可搜索筛选的操作界面；
   订单/用户详情可用，退款/冻结/解绑/查询等操作有确认与审计。
3. **不丢能力、不动安全边界**：模型、客户端/发授权、调用、性能、存储继续保留（重新分组）；
   管理面仍只走回环/SSH 隧道；CSRF / Origin / `X-ECHO-Admin` / 审计不变；页面不出现私钥/密钥。

**非目标（本次第一版不做）**：

- 不做多管理员/RBAC、不改「新增/删除管理员只在命令行」的现状；
- 不做导出 CSV / 对账报表下载（现有 `billing/summary` 只作为只读数据来源保留）；
- 不做部分退款、换套餐/升降级（沿用现有「同套餐续费」规则）；
- 不做扫码授权白名单（`authorized_open_ids` / `scan_sessions` 仍是建表未接逻辑）；
- 不改官网公开页面，只复用它的视觉 token。

## 2. 现状盘点（设计输入）

### 2.1 现有页签与页面职责

| 现页签 | 内容 | 本次去向 |
|---|---|---|
| 概览 | 并发、调用、错误码、各端点 | 重做「概览」，增加收入/订单/用户/到期/异常 |
| 模型 | 模型状态、显存 | 原样保留，归「运行」 |
| 客户端 / 发授权 | 发配对码、客户端列表、scopes/配额/撤销/轮换、对外公布地址 | 原样保留，归「运行」 |
| 调用 | 客户端 × 端点聚合、最近调用 | 原样保留，归「运行」 |
| 性能 | 4 张图 + 运行参数 | 原样保留，归「运行」 |
| 收费 / 账号 | 收费概览、套餐、订单、回调、权益、账号、邀请码（一页 7 张卡） | **拆成 6 个独立页面** |
| 存了什么 | 表/列、目录、管理员账号、最近审计 | 保留「存储」；「操作审计」独立 |

### 2.2 现有后端能力（不需要重写）

- 订单：`GET /admin/api/billing/orders`（仅 `status`、`userId`、`limit`）、
  `GET /admin/api/billing/orders/{id}`（含 `order_events`）、
  `POST /admin/api/billing/orders/{id}/refund`（`confirm` + 审计）。
- 用户：`GET /admin/api/account/users?q=`（工号/姓名/openId）、
  `GET /admin/api/account/users/{id}`（设备+权益+订单）、
  `POST /admin/api/account/users/{id}/reset-devices`（全部解绑 + `confirm`）。
- 权益：`GET /admin/api/billing/entitlements`、`POST .../{uid}/adjust`
  （`extend/freeze/activate/internal/set`，要求 `confirm`）。
- 邀请码：`GET/POST /admin/api/account/invites`、`DELETE .../{code}`（`confirm`）。
- 回调：`GET /admin/api/billing/notifies`（最近 100 条，含 conflict）。
- 套餐：`GET/POST /admin/api/billing/plans`、`PUT/DELETE .../{code}`。
- 审计：`admin_audit` 表已在写；页面只在「存了什么」里显示最近若干条。

**结论：不需要改表。** 本次后端只补「查询参数、聚合视图、三个缺失的写动作」，
以及一个只读的系统状态端点。

### 2.3 一个必须说明的数据事实：没有 email 字段

issue 写的是「用户按邮箱/工号/userId 搜索」。当前 `users` 表是：

```
user_id, name, employee_no, invite_code, phone, alipay_open_id,
status, token_version, created_at, updated_at
```

**没有 email**，官网账号页也是「邀请码 + 工号」登录。所以第一版用户搜索覆盖
`userId / 工号 / 姓名 / 手机号 / 支付宝 openId`；邮箱搜索需要先给账号体系加字段
（注册/登录/唯一性/迁移都要动），不属于这次管理面重设计。详见 §11 待确认。

## 3. 设计原则

1. **运营优先**：第一屏先回答「今天收了多少钱、有没有异常、最近谁注册/下单」；
   查单、退款、冻结账号最多两次点击。
2. **视觉统一但不照搬官网密度**：颜色/字体/圆角/阴影与 `site/assets/site.css` 同一套；
   管理面正文 14.5px、表格 13px、按钮 36px（官网营销页是 16px/46px）。
3. **状态先说清楚**：每个列表都有加载、空、失败、无权限四种状态；状态用「文字 + 颜色」，
   不能只靠颜色。
4. **危险动作两步**：退款、冻结账号、解绑设备、作废邀请码、撤销客户端都要二次确认；
   请求里继续带 `confirm`，前端弹窗只挡手滑，后端字段挡构造请求。
5. **安全边界不因为好看而放宽**：仍单文件、无 CDN/框架、无 `type="module"`；
   写请求继续走 `wpost`/`wdelete`（`X-ECHO-Admin` + CSRF + 同站 Origin）；
   所有用户数据/订单号/回调原文继续 `esc()`，只有显式 `raw()` 能插 HTML。
6. **现有测试锚点尽量保留**：`data-tab="perf"`、4 张 SVG、`#pwCard/#pwCur`、
   「待用的配对码（能用的 n 张）」、`table()` 的 `? c.__raw : esc(c)` 等继续成立；
   结构性断言按新导航更新，安全断言一条不改。

## 4. 信息架构

左侧分组侧栏（替代横向页签），三组共 14 个入口：

```

  概览            / #overview
  订单            / #orders            ← 第一优先级
  用户 / 账号      / #users             ← 第一优先级
  权益            / #entitlements
  套餐            / #plans

运行
  模型            / #models

  性能            / #perf

  操作审计         / #audit

- 导航用 hash 路由（`#orders`）实现可刷新、可深链；生产页面仍是 `server/admin.html` 单文件，

  无横向溢出。
- 「修改口令」仍跳到「存储」页的账号卡并聚焦 `#pwCur`（保留现有测试与入口习惯）。

## 5. 视觉规范（与官网对齐）

从 `site/assets/site.css` 直接取 token：

| 项 | 值 |
|---|---|
| 主色 | `#2563eb`，hover/深色 `#1d4ed8`，浅底 `#eaf1ff` |
| 辅助色 | `#0ea5a4`（渐变尾色） |
| 正文/次级 | `#0b1220` / `#1e293b`；muted `#5b6b84` / `#7c8ca6` |
| 背景/卡片/线 | `#f6f8fc` / `#fff` / `#e3e9f3` |
| 成功/警告/危险 | `#0f9d58` / `#b45309` / `#dc2626` |
| 圆角/阴影 | 卡片 18px、控件 10–12px；`0 6px 22px rgba(15,23,42,.06)` |
| 字体 | `-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif` |

组件复用官网的视觉语言：白色卡片 + 细边、蓝色渐变主按钮、浅色徽章、表格行 hover、
输入框聚焦蓝环、空状态虚线框。**不引入**外部字体、图标库、CSS 框架；图标用内联 SVG
sprite（生产页面同样内联，不请求 `site/assets/icons.svg`，因为管理面与官网是两个服务）。

密度调整：正文 14.5px、表格 13px、按钮 36px、输入 38px、卡片内边距 18–20px。
登录页可更大（官网营销感），登录后以运营效率优先。

## 6. 页面设计

> 下列「草图」为信息结构说明；实际视觉见 `docs/admin-redesign/*.png`。
> 截图是静态 mockup（假数据），不是生产页面。

### 6.1 登录页

```
┌───────────────────────────────┬──────────────────────┐
│  ECHO 管理面                   │  登录管理面            │
│  把订单、账号与运行状态         │  仅限管理员            │
│  放进同一张运营台。             │  [用户名]              │
│  · 订单与用户优先               │  [口令]                │
│  · 安全边界不变                 │  [登录]                │
│  · 现有运维能力保留             │  静态预览说明           │
└───────────────────────────────┴──────────────────────┘
```

- 左侧品牌区：浅色渐变背景 + 三条能力说明（不是营销文案，是管理面定位）。
- 右侧登录卡：用户名、口令、错误提示（同一句「用户名或口令不对」）、登录按钮。
- 768/375：左侧隐藏，登录卡居中；仍不引用外部资源。
- 失败退避、登录审计、会话 Cookie、CSRF 都不变，只改外观。

### 6.2 概览

- 4 张 KPI：今日收入、今日订单（已支付/待支付）、活跃用户（24h / 总数）、7 天内到期。
- 异常条：支付回调 conflict / 验签失败 / 支付失败，点「去处理」到支付回调页。
- 最近订单（5 笔，行可点开订单详情）；最近注册（4 人，行可点开用户详情）。
- 右栏：即将到期（7 天内，点开用户）、系统状态摘要、快捷入口。
- 金额口径：**服务端按 `billing.timezone` 自然日算**，页面不自己算日界。

```

列：用户（头像/姓名/userId）、工号、账号状态、权益（套餐+状态）、到期、设备 n/m、注册、操作。

- 搜索第一版覆盖现有字段，**不含 email**（见 §11）。

### 6.5 权益

- 筛选：用户搜索、状态（全部/有效/冻结/已到期/已退款）、到期范围（全部/7 天/30 天/已过期）。
- 列：用户、套餐、状态（后端计算后的状态，过期不能显示绿色）、到期、每日音频、TTS、
  QPS/设备、操作（+30 天、冻结/恢复、设 internal）。
- 「调整权益」走现有 `adjust`，仍要求 `confirm`；页面显示“退款动钱、这里动权限”的提示。

### 6.6 套餐

- 卡片式（月卡/试用/内部账号），显示价格、天数、每日音频、TTS、设备/并发、已售笔数、上下架。
- 编辑/新建表单：code、名字、价格（分）、天数、额度、QPS、设备、并发、上架。
- 只读规则卡：续费/换套餐/退款规则（与官网同源，避免两处文案漂开）。
- 改价/下架只影响以后订单；已卖出订单金额与权益不变。

### 6.7 邀请码

- 列表：code、名额、已用/名额、到期、谁发的、备注、操作（作废）。
- 生成卡：code（留空随机）、名额、到期、备注；生成后明文**只显示这一次**，当场复制。
- 明确写清：邀请码只决定注册名额；已注册用户登录不因作废失效。

### 6.8 支付回调

- 异常条：conflict / 验签失败数量 + 「去处理」。
- 筛选：订单号/tradeNo、状态（paid/closed/pending/conflict）、验签、时间范围。
- 列：tradeNo（截断+复制）、订单、状态、验签、时间、原文（截断+展开）。
- 「展开原文」用新只读端点拿完整 `raw`，弹窗展示；不显示签名密钥（原文里本来也只有
  回调表单字段，后端不把密钥写进去）。
- conflict 行标红；说明「订单已关闭/已退款后才到达的成功支付，需人工核对」。

### 6.9 操作审计

- 筛选：管理员/动作/对象、结果（成功/失败）、时间范围；分页。
- 列：时间、管理员、动作（`billing-refund` 等）、对象、结果。
- 失败动作显示 `.failed`；新增的 `billing-order-sync`、`account-user-status`、
  `account-device-revoke` 都会出现在这里。
- 「存储」页保留最近的审计摘要；独立页给筛选与分页。

### 6.10 系统状态

- 只读：支付 provider、是否配置、网关模式（sandbox/prod）、notify_url、计费闸门、
  版本、运行时长、TLS、在线会话数、advertised host、state/tmp 目录。
- **不读、不显示** app_id、私钥、公钥、签名串、任何 token；修改这些仍走配置文件/命令行。
- 管理面安全边界四条写在页面上（回环/隧道、四道写闸门、转义、两面隔离）。

### 6.11 运行五页（保留并重绘）

- 模型：表格式状态（模型、槽、状态、常驻、估显存、并发、向量空间）。
- 客户端/发授权：发码表单、待用配对码、对外公布地址、客户端列表与操作，文字与判据保持现有。
- 调用：客户端×端点聚合 + 最近调用，只有元数据。
- 性能：仍是 2×2 四张 SVG 折线图 + 运行参数卡；轮询、启停、`pagehide` 停轮询都保留。
- 存储：表/列、白名单、目录、管理员账号/改口令、最近审计摘要。`#pwCard/#pwCur` 等保留。

### 7.2 写接口（必须走 `as_write`：会话 + 同站 Origin + `X-ECHO-Admin` + CSRF + 审计）

|---|---|---|---|---|
| `POST /admin/api/billing/orders/{id}/refund` | 现状 | `orderId` | `billing-refund` | 调网关退款 + 订单 `refunded` + 重算权益 |
| `POST /admin/api/billing/orders/{id}/sync` | **新增** | 不需要（只读转发 + 幂等入账） | `billing-order-sync` | 仅 `created/paying` 查询支付宝；`paid` 走同一 `apply_notify`；终态回库视图 |
| `POST /admin/api/billing/entitlements/{uid}/adjust` | 现状 | `uid` | `billing-entitlement-adjust` | extend/freeze/activate/internal/set |
| `POST /admin/api/account/users/{uid}/status` | **新增** | `uid` | `account-user-status` | `{status: active|disabled}`；冻结时 `token_version+1`；设备由 fail-closed 立即 403 |
| `POST /admin/api/account/users/{uid}/devices/{client_id}/revoke` | **新增** | `clientId` | `account-device-revoke` | 单设备解绑（revoke + 清缓存 + 禁用 client） |

> `BillingConsoleReviewTests.READS` 要同步加新读端点。这是有意的“加端点必须显形”。

### 7.3 Store 层新增（不改表 / 不加列）

- `search_orders(q, status, user_id, since, until, limit, offset) -> (rows, total)`
  - `LIKE` 参数化；订单号/`alipay_trade_no`/`user_id` 直查；姓名/工号 join `users`。
  - 现有索引 `idx_orders_user(user_id, created_at)`、`idx_orders_status(status, created_at)`
    覆盖主要筛选；`trade_no` 模糊查在内部规模下可接受。
- `count_users(...)` / `users_page(...)`（或沿用 `users()` + Python 过滤，规模 < 千人）。
- `active_users_since(since_ts)`：**按 `clients.last_seen` 算**（认证路径会按
  `auth.touch_interval_s` 节流更新），join `user_devices` 取人：

  ```sql
  SELECT COUNT(DISTINCT d.user_id)
  FROM user_devices d JOIN clients c ON c.client_id = d.client_id
  WHERE d.status='active' AND c.last_seen >= ?
  ```

  **不要用 `user_devices.last_seen`**：它只在绑定/重新配对时写一次，不是“最近活跃”。
- `orders_created_since(since, status=...)`：概览的“今日订单/已支付”计数
  （在现有方法上增加可选 status）。
- `notifies_for_order(order_id, limit)`。
- `audit_records(q, action, admin, result, since, until, limit, offset) -> (rows, total)`。
- `count_orders(...)`（分页 total 用）。

### 7.4 契约与兼容

- 所有新参数可选，缺省行为与现在一致；现有 `/billing/orders?status=&userId=&limit=` 继续可用。
- 所有时间参数是 unix 秒（与服务端现有 `createdAt/paidAt` 一致）；页面用 `<input type="date">`
  转成当天 00:00 与次日 00:00（本地时区），服务端仍按传入值过滤。
- 「今日」金额/订单用 `billing.day_start(cfg)`（服务端时区），页面不自己算。
- 返回体新增字段只增不改；`status` 仍用现有字符串。

## 8. 安全不变项

- 管理面仍只监听回环 / SSH 隧道；**不新增任何公网端点**。
- 两个 FastAPI app 的路径不交叉：`/v1/*` 与 `/admin/*`；新端点全部在 `/admin/api/*`。
- 写请求四道闸门不变：会话、同站 Origin、`X-ECHO-Admin`、CSRF；`as_write` 统一审计。
- 新增写端点必须登记 `WRITE_ENDPOINTS` 并有对应的 `WriteGuardTests` 覆盖（未登录 401、
  错 Origin 403、缺标志头 403、缺 CSRF 403、值不变）。
- 页面不展示私钥/密钥/token/secret；「系统状态」只读白名单字段。
- 所有用户数据/订单号/plan 名/邀请码备注/回调原文/错误信息都 `esc()`；
  `table()` 只对显式 `raw()` 放行；新增渲染点必须过同一 helpers。
- 邀请码明文只在生成结果里显示一次；配对码/新 secret 仍只显示一次。
- 管理面与能力面仍是两套身份；客户端 JWT 不能进管理面。
