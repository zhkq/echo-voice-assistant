# ECHO 能力后端 —— 容器部署（GPU 宿主 + Docker）

> **这份文档要解决的那件事**：把能力后端跑成容器之后，**管理端页面仍然打得开**。
> 出厂默认管理面是关着的（`server.admin_listen: ""`），而容器里"绑回环"等于只有容器自己
> 进得去 —— 所以必须同时做两件事：容器内绑通配地址 + 宿主只把端口发布到回环。
>
> **诚实声明（先读这一段）**：这份文档与 `scripts/prepare-backend.sh` 是照着**源码、
> 配置与单测**写出来的，**没有在任何真机上跑过 `docker build` / `docker compose up`**
> （写它的这台机器是 Windows 开发机，没有 Docker、也没有 GPU 直通）。
> 凡是"代码已证"的结论，下面都给了文件与行号；凡是"待真机确认"的，都标了
> **【待真机】**。最后一节把没验的东西逐条列出来了 —— 别把这份文档当成"跑过了"。
>
> 一键准备：`sudo bash scripts/prepare-backend.sh --from user@源机:/path/to/echo --server-host gpu-01`

## 0. 这套东西长什么样

| | 地址（宿主） | 容器内绑定 | 谁能连上 | 鉴权 |
|---|---|---|---|---|
| 能力面 | `0.0.0.0:8900` | `0.0.0.0:8900` | 客户端网段 | `auth.enabled`（**上网必须打开**） |
| 管理面 | **只发布到宿主回环** `127.0.0.1:8901` | `0.0.0.0:8901` | 宿主本机 / `ssh -L` | 管理员账号 + 会话 + 同站 Origin + CSRF |
| `/v1/health`、`/v1/ready`、`/v1/capabilities` | 跟着 8900 | 同上 | 同上 | **免鉴权**（探针/清单端点，只有模型与槽的元信息） |

> 那三个端点**刻意不打鉴权**：探针要在没凭据时也能用，而 `capabilities` 只暴露
> "这个后端有哪些槽与模型"，没有业务数据（`server/main.py:161-166` 也是按这条把它们
> 归成一类的）。真正的调用端点（`/v1/asr`、`/v1/diarize`、`/v1/speaker/embed`）
> 一律要凭据，见 `server/routes.py:ENDPOINT_SCOPES`。

卷（保留策略**相反**，别合并）：

| 宿主 | 容器内 | 内容 | 能不能换 tmpfs |
|---|---|---|---|
| `/srv/echo/models`（只读挂） | `/opt/echo/models` | 几 GB 权重 | 只读，无所谓 |
| `/srv/echo/tmp` | `/var/echo/tmp` | 临时文件（跑完就删） | **能**（丢了没关系） |
| `/srv/echo/state` | `/var/echo/state` | **鉴权库**（客户端凭据 / 审计） | **绝对不能**（换了所有客户端要重新配对） |
| `/srv/echo/cache` | `/var/echo/cache` | ModelScope 的**运行期缓存**（SenseVoice 要的那个 VAD 模型，约 2 MB） | **能**（下次加载模型时自动重下）——但**别并进 tmp 卷**，理由见 §2.4 |

根文件系统 `read_only: true`：程序想往磁盘写东西会**直接报错**，而不是静默发生。


`scripts/prepare-backend.sh` 会把上面这几条都跑一遍，并且**缺什么就直说要装什么**
（含上面那几条发行版命令），而不是等到 `compose up` 报一句不好懂的错。

**磁盘**：模型卷按 ~6 GB 准备（qwen3asr 0.6B + 对齐器 0.6B + pyannote 三件套；

**还要先想清楚一件事：这块卡是什么架构。** 它决定**镜像里的 torch 从哪个源装**

见第 10 节「按显卡选规格」。`prepare-backend.sh` 会读 `compute_cap` 并自动给出结论。

## 2. 模型卷（`/srv/echo/models`，只读挂载）

### 2.1 容器里的目录布局是**固定的**（不是随便放的）

```
/srv/echo/models/
├── hub/
│   ├── models--Qwen--Qwen3-ASR-0.6B/snapshots/master/          ← 转写（qwen3asr）
│   │     ├── config.json
│   │     └── model.safetensors
│   └── models--Qwen--Qwen3-ForcedAligner-0.6B/snapshots/master/ ← **强制对齐器**
│         ├── config.json
│         └── model.safetensors
├── sensevoice/snapshots/master/                                 ← SenseVoice（**老卡推荐**，可选）
│     ├── config.yaml
│     └── model.pt
└── pyannote/
    ├── pyannote-segmentation-3.0-local/pytorch_model.bin
    ├── pyannote-wespeaker-local/pytorch_model.bin
    └── pyannote-plda-local/plda/{plda.npz,xvec_transform.npz}
```

**为什么 Qwen 那两份必须放 `hub/` 下**：`app/audio/stt.py` 在 import 时把 `HF_HOME`
定成模型根（`stt.py:38`），解析走 `_resolve_hf_cache()`（`stt.py:390-406`）——
它就找 `{模型根}/hub/models--<owner>--<name>/snapshots/<任意一个子目录>/`
（用 `master` 只是跟 ModelScope 的命名对齐，**目录名本身不参与判断**）。
而 ModelScope 的默认缓存落在 `~/.cache/modelscope/models`（`app/modelinfo.py:51`）——
容器里那是 `/root`，在 `read_only: true` 下**既不可写、也不在模型卷里**。
SenseVoice 同理：它认 `{模型根}/sensevoice`（递归找 `model.*`，见
`app/modelinfo.py:_sensevoice_model_dir` / `_first_stem_dir_with_files`），
所以上面那个 `sensevoice/snapshots/master/` 布局是对的（多一层 `snapshots/master` 也认）。

> 这条判据不是"看着像"：`tests/test_server_contract.py::ContainerDeploymentTests::
> test_the_documented_model_volume_layout_is_the_one_the_loader_resolves`
> 会造一份假权重树，让加载器自己去解析一遍（不加载模型），
> 并检查对齐器在位时 `qwen3asr_aligner()` 真的给出那个名字。

> 想省事不重新摆布局的替代方案（**没写成默认**）：把 ModelScope 缓存目录原样拷到
> `/srv/echo/models/` 的**根**（`Qwen--Qwen3-ASR-0.6B/snapshots/master/...`），
> 再给容器加一条只读挂载把同一个宿主目录挂到 ModelScope 的缓存点上：
> `- /srv/echo/models:/root/.cache/modelscope/models:ro`。
> 这样 `_resolve_ms_cache()` 也能命中。代价是"同一份数据挂在两个位置"，
> 排查时容易看错地方 —— 默认还是走上面那一种。

### 2.2 两种来源

> **还有第三种：拿到的是"含权重"的后端包**（包根有 `models/` 与 `MODELS-INCLUDED.txt`，
> 2026-09-28 起的档位，见 `docs/3.0-离线最小包与快路安装.md` §5.1.1）——
> 那就不用拷任何东西：把 `ECHO_HOST_MODELS_DIR` 指向**解包目录下的 `models/`** 即可。
> 含权重包按变体给了它真正需要的那几棵子树（cu118 只有 SenseVoice；cu126 还带 qwen3asr、
> 强制对齐器与 pyannote），所以下面第 4.1 节"该放哪些"的表可以直接跳过。

**① 从源机拷（推荐，内网快）** —— 源机就是一台**已经跑起来过**的 ECHO（开发机或旧服务器）：

```bash
sudo bash scripts/prepare-backend.sh --from user@源机:/home/user/echo
```

脚本会按顺序在两处找每个模型（先 HF 布局、再 ModelScope 缓存），
用 `rsync -aL`（**`-L` 是关键**：把符号链接实体化，否则读缓存里的软链会断）
拷到容器布局。也可以指本地路径（`--from /mnt/usb/echo`）。

**② 联网从 ModelScope 下**：

```bash
sudo python3 -m pip install modelscope        # 宿主上要装（脚本会检查并提示）
sudo bash scripts/prepare-backend.sh --from-modelscope
```

`--from-modelscope` 用 `snapshot_download(..., local_dir=...)` 直接把文件落进容器布局。
**【待真机】**：这条路没有在本机实测过（本机没有 Linux 宿主、也不该在这台机器上下 6 GB）。

### 2.3 ⚠️ 缺**强制对齐器**不是"降级一点"，是让能力声明变成假话

`asr-long` 那个模型宣告的是 `supports: [asr.text, asr.timestamps]`
（`server/engines.py:default_specs`）。句级时间戳**只有**带上强制对齐器才有：
没有它时 `return_time_stamps=True` 只换回 funasr 的一句
`"return_time_stamps requires forced_aligner. Skipping timestamps."`，
一个时间戳都没有（`server/engines.py:_stt_loader` 与 `app/audio/stt.py:299-312`）。

而 `stt.qwen3asr_aligner()` 在**本地找不到权重时返回空串并且不联网**
（离线机器上那是一次加载失败，所以刻意不试）—— 于是：

* 结果看起来"跑通了"，只是 `timestamps` 一路退化成 `none`（客户端再自己 estimated 兜底）；
* 服务端的 `/v1/capabilities` 与 `/v1/health` **不会**因此变红。

所以 `prepare-backend.sh` 把"对齐器缺失"当成**失败**（退出码 3），并打印上面这段原因；
确实要接受降级就显式加 `--allow-missing-aligner`（那样它降级成一条**警告**，
但仍然会出现在最后的汇总里，不会静默通过）。

**pyannote 缺失**（说话人分离）只算**警告**：`/v1/diarize` 会如实报模型不可用
（`model_failed`），不会假装成功。

### 2.4 ⚠️ 容器里还必须有**一个可写的 ModelScope 缓存**（2026-09-28 真机踩的坑）

**症状**：模型卷摆对了、SenseVoice 权重也读到了（日志里 `Loading ckpt: .../model.pt,
status: <All keys matched successfully>`），但**每一个 `/v1/asr` 都 `model_failed`**：

```
Building VAD model.
Download: iic/speech_fsmn_vad_zh-cn-16k-common-pytorch failed!:
  [E1022] Failed to create SDK directories: [Errno 30] Read-only file system: '/root/.modelscope'
[stt] SenseVoice 加载失败，回退 CPU: model 'fsmn-vad' is not registered.
```

**为什么**：SenseVoice 那条加载路径不只读我们放进模型卷的那份权重 ——
`app/audio/stt.py:_get_sensevoice` 传的是 `vad_model="fsmn-vad"`，那是一个
**ModelScope 模型名**（约 2 MB 的 VAD 权重），funasr 会去 ModelScope 现拉它。
而根文件系统是 `read_only: true`，默认落点 `~/.modelscope` 与 `~/.cache/modelscope`
**都写不了** → 下载失败 → funasr 注册不出这个模型 → 加载整体失败。
模型卷是**只读**挂的，所以"把缓存塞进模型卷"也不行。

**修法**（`server/compose.yaml` 里已经是这样了，`/srv/echo/cache` 由
`prepare-backend.sh` 建）：

```yaml
    environment:
      MODELSCOPE_CACHE: /var/echo/cache/modelscope    # 缓存落点
      HOME: /var/echo/cache                           # modelscope 还要在 ~/.modelscope 建 SDK 目录
    volumes:
      - /srv/echo/cache:/var/echo/cache
```

* **为什么不放进 tmp 卷**：`/v1/health` 的 `tmp.files/bytes` 是**泄漏判据**
  （空转时必须为 0），而 `server/tmp.py:sweep` 还有一条"超 `max_bytes`（默认 4 GB）
  就从最老的开始删"的分支会遍历到非日期目录的**子目录** —— 缓存放那儿既污染判据，
  又可能被清掉。单独一个卷最干净。
* **离线也能用**：这个缓存只有约 2 MB，可以先在有网的机器上跑一次模型加载，
  把 `.../cache/modelscope` 原样拷到 `/srv/echo/cache/` 预置好；
  不预置的话，第一次加载模型时容器会自己去 ModelScope 拉（内网能通 ModelScope 就行，
  2026-09-28 实测 `www.modelscope.cn` 可达；**huggingface.co 在这台机器上不通**）。
* 判据：加载成功的日志里有 `Loading pretrained params from
  /var/echo/cache/modelscope/models/iic--speech_fsmn_vad_zh-cn-16k-common-pytorch/snapshots/master/model.pt`。

## 3. 状态卷与密钥（`/srv/echo/state`、`echo-backend.env`）

```bash
sudo install -d -m 700 /srv/echo/state          # 鉴权库在这里：**持久**，别放 tmpfs
openssl rand -hex 32                            # 生成 ECHO_JWT_SECRET
```

脚本会把这些写进 `/srv/echo/echo-backend.env`（`chmod 600`，`*.env` 已被 `.gitignore` 忽略）：

```
ECHO_JWT_SECRET=<openssl rand -hex 32>          # 用 auth.mode=jwt 时必需
ECHO_AUTH_ENABLED=true
ECHO_AUTH_MODE=jwt
ECHO_HEALTH_SCHEME=http|https                   # 开了容器内 TLS 就是 https（探针用）
```

**幂等承诺**：这个文件已经存在时，脚本**绝不重新生成密钥**。
重新生成会让**所有客户端立刻 401**，而现象看起来像"客户端坏了"。

**缺 `ECHO_JWT_SECRET` 的真实症状**（2026-09-27 在本机用 `TestClient` 复现过）：
服务端**照常启动**、`/v1/health` 照常 200 —— 但客户端"配对成功"之后
`POST /v1/token` 回 **503 `auth_misconfigured`**（`server/auth.py:352-357`），
detail 是"auth.mode=jwt 但没配 auth.jwt_secret"。所以这三项要么一起配，要么都别开。

### 3.1 本机自配对文件（`ECHO_LOCAL_PAIR`，2026-09-28）

**单机装法**（后端与客户端同一台机器，也就是设计里的方案 ①）不该让人抄配对码。
开了这一项，后端启动会在**状态卷**里写一份 `local-pair.json`：

```
ECHO_LOCAL_PAIR=true            # compose 默认就是 true；只跑后端（客户端在别的机器）可设 false
```

* 文件落在**鉴权库旁边**（显式 `auth.db` 的目录，否则 `server.state_root`）——
  容器里就是 `/srv/echo/state`，宿主侧是 `${ECHO_HOST_STATE_DIR:-/srv/echo/state}`。
* 里面**只有一张一次性配对码**（`echo://pair?…`，与 `--new-client` 打印的同一个拼法），
  TTL 默认 **7 天**（`auth.local_pair_ttl_s`），**每次启动重发一张**覆盖旧的；
  `0600`，容器内也只让运行用户读。**没有 clientId/secret** —— 凭据仍然只落客户端。
* **客户端要能读到它**：把宿主侧那个 state 目录填进客户端的
  **设置 → 能力 → 本机配对文件路径**（或设环境变量 `ECHO_LOCAL_PAIR_PATH`）。
  Docker 的宿主路径猜不出来，所以这一步是**要人填一次的**；不填时客户端会如实说
  "找不到 + 看过哪些位置"，并提示改用配对串。
* 代价要知道：它**每次启动会往鉴权库发一张码**（`created_by=local-pair`，
  在管理面的"待用配对码"里能看到、过期会被顺手清掉）。这也是它默认只在交付路径
  （`compose.yaml` / 后端包）打开、代码默认关的原因。

## 4. TLS

### 4.1 容器内自签（默认 `--tls self-signed`）

脚本生成 `/srv/echo/tls/server.{crt,key}`（幂等：已存在就沿用），写法等价于：

```bash
# <server-host> 默认自动探测（hostname -I 的第一个地址），也可以用 --server-host 指定。
# SAN 按它的形状二选一：看着像 IP 就写 IP:…，否则写 DNS:…（脚本里的 case 就这一条判断）。
openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout /srv/echo/tls/server.key -out /srv/echo/tls/server.crt \
  -subj "/CN=<server-host>" -addext "subjectAltName=IP:<server-host>"
```

> 客户端连的是 IP（`https://10.0.0.7:8900`）时，SAN 必须是 `IP:…` 而不是 `DNS:…`，
> 否则**严格的 TLS 客户端会报证书不匹配**。两种都想要就自己改成
> `subjectAltName=DNS:<名字>,IP:<地址>` 再删掉证书重跑。

因为**没有环境变量能设 `server.tls.*`**，容器里启用 TLS 必须挂一份配置 + `--config`。
脚本会写两个文件（内容都是绝对路径，不依赖 compose 的相对路径解析）：

`/srv/echo/config/server.yaml`（只写"必须按环境定"的项，其余仍走默认值 + 环境变量）：

```yaml
server:
  tls: {certfile: /etc/echo/tls/server.crt, keyfile: /etc/echo/tls/server.key}
  vram_budget_mb: 7000            # 只有你给了 --vram-budget-mb 才有这一行
```

`/srv/echo/compose.local.yml`（compose override，接上配置 / 打开鉴权）：

```yaml
services:
  backend:
    command: ["python", "-m", "server.main", "--config", "/etc/echo/server.yaml"]
    environment:
      ECHO_AUTH_ENABLED: "${ECHO_AUTH_ENABLED:?...}"   # 没配就**报错退出**，不静默不鉴权
      ECHO_AUTH_MODE: "${ECHO_AUTH_MODE:?...}"
      ECHO_JWT_SECRET: "${ECHO_JWT_SECRET:?...}"
    volumes:
      - /srv/echo/config/server.yaml:/etc/echo/server.yaml:ro
      - /srv/echo/tls/server.crt:/etc/echo/tls/server.crt:ro
      - /srv/echo/tls/server.key:/etc/echo/tls/server.key:ro
```

> ⚠️ **启用容器内 TLS 时探针也要跟着换 scheme**：`compose.yaml` 的 healthcheck
> 打的是容器自己的 `127.0.0.1:8900/v1/health`。不换就会一直显示 `unhealthy`，
> 而服务其实是好的。所以 healthcheck 里的 scheme 走了编排层变量
> `ECHO_HEALTH_SCHEME`（在 `echo-backend.env` 里写 `https` 即可；它**不是**容器里的
> 运行时配置，所以不在 `environment:` 里）。

客户端**不需要装自签根**：配对串里带证书指纹（`fp=`），客户端按指纹固定证书。

### 4.2 前面放 TLS 终结（`--tls proxy`）

Nginx / HAProxy / 云负载均衡上做 TLS，容器里就是明文 http：

* `server.tls.certfile` 与 `server.tls.keyfile` **都留空**（这就是默认值，什么都不用配）；
* 只填一个的话服务端**启动就报错**，绝不静默按 http 起（`server/main.py:_tls_kwargs`）——
  那是"你以为连的是 https"的最坏结果；
* 终结层要**原样转发** `X-Forwarded-For`（审计与登录退避按它识别来源，
  `server/admin.py:_source_of`），并把 8901 管理面也一起终结（或干脆不给它开外部路由）。

**两种方式都不要削弱什么**：管理面的会话 cookie 是 `HttpOnly + SameSite=Strict`
且**刻意没有 `Secure`**（因为管理面自己是明文 http；设了 `Secure` 浏览器根本不存，
典型症状是"登录成功但下一个请求 401"）。放在 https 反代后面时 cookie 也照发。

## 6. 建管理员（**只能在命令行建**）

```bash
docker exec echo-backend python -m server.main --new-admin ops
```

* 口令**只打印这一次**，当场存进密码管理器；库里只有哈希。
* 管理面**仍然不开账号管理**：面板上那份管理员清单**是只读的**，
  新建 / 删除 / 禁用 / 启用、改**别人**的口令都只在命令行。
  改账号 = 改"谁能进这扇门"，而面板本身就在这扇门里 —— 让面板改账号，
  等于给一次会话劫持配一个提权出口（`server/main.py:502-509` 的那段注释）。
* 唯一的例外（2026-09-29 起）是**改"自己"的口令**：`POST /admin/api/password`
  **必须同时给出当前口令**（所以"一次会话劫持"不足以改掉它），改成功后别的会话失效、
  当前会话保留。页面上如实写着这件事，文案就在后端下发的
  `GET /admin/api/admins` 的 `note` / `selfServiceNote`（`server/admin.py`，页面渲染它们，
  不在 HTML 里另抄一份）；用例见 `tests/test_admin_console.py::PasswordChangeConsoleTests`。
* **幂等**：`--new-admin` 会把同名账号的**口令重置**，所以脚本会先
  `docker exec echo-backend python -m server.main --list-admins`，
  已经有账号就跳过（并告诉你"要重置就自己删账号再跑"）。

打开管理面：宿主上直接 `http://127.0.0.1:8901/admin/`。
**远程运维**用 SSH 端口转发（比把 8901 摊给网段稳得多）：

```bash
ssh -L 8901:127.0.0.1:8901 <gpu-host>
# 然后本地浏览器开 http://127.0.0.1:8901/admin/
```

同站判定为什么在容器里仍然成立（**这条是"管理端页面仍可用"的技术核心**）：
`allowed_origins()` 从 `server.admin_listen` 取**端口**，白名单里是
`http://127.0.0.1:<port>` / `http://localhost:<port>` / `http://[::1]:<port>`
（`server/admin.py:689-712`）；通配地址 `0.0.0.0` **不会被当成 hostname** 加进去，
也不会把回环名挤掉。所以浏览器发 `Origin: http://127.0.0.1:8901` 时**判为同站**，
而 `Origin: http://evil.example:8901` 仍然 403。
契约由两条用例钉住：`test_server_contract.ContainerDeploymentTests::
test_a_wildcard_admin_listen_still_accepts_the_loopback_origin`（纯函数）
与 `test_admin_console.WildcardAdminListenWriteTests`（真打一次写请求）。

> 直接访问 `http://<宿主IP>:8901/admin/` 会**登录得进去但写动作 403**
> （Origin 是那个 IP，不在白名单里）。**这是有意的窄** —— 走 `ssh -L`。

## 8. 回滚 / 排错


起不来的三个最常见原因与**看哪一行**：

| 现象 / 日志 | 真因 | 怎么办 |
|---|---|---|
| `compose up` 阶段就报 `could not select device driver "" with capabilities: [[gpu]]` | 宿主没装/没配 nvidia-container-toolkit | 见第 1 节那两条命令，然后 `docker info` 里确认有 `nvidia` runtime |

| 日志有 `[stt] 强制对齐器 ... 不在本机`，`timestamps` 一路 `none` | 对齐器权重没进模型卷（或放错目录） | 回到第 2 节：放在 `hub/models--Qwen--Qwen3-ForcedAligner-0.6B/snapshots/master/` |
| `model_failed` 且日志里是 `No such file` / `Can't load` | 模型卷没挂对（宿主路径不存在时 Docker 会**建一个空目录**，不报错） | `docker exec echo-backend ls /opt/echo/models/hub`；`docker inspect` 看 `Mounts` 的 Source |
| 管理面打不开（宿主上 `curl 127.0.0.1:8901/admin/` 拒绝） | 忘了 `ECHO_ADMIN_LISTEN`，或者 8901 没发布 | `docker exec echo-backend env \| grep ADMIN_LISTEN`；`docker compose -f server/compose.yaml config \| grep -A2 ports` |
| 容器一直 `unhealthy` 而服务是好的 | 容器内启用了 TLS，探针还在打 http | `echo-backend.env` 里加 `ECHO_HEALTH_SCHEME=https`，重新 `up -d` |

## 9. 显存与并发：**按卡校准**，别把小卡的数带到别的卡上

`server.vram_budget_mb`、每个 spec 的 `est_vram_mb`、`limits.max_concurrent` 是
**同一台机器的同一套标定**，换卡就得重算。

| | 出厂样例（`server/echo-server.example.yaml`） | 本机 8 GB 卡实测（2026-09-27） |
|---|---|---|
| `vram_budget_mb` | `20000`（24 GB 卡参考） | **`7000`**（不是 8000：桌面+显示留 1 GB 左右） |
| `asr-long.est_vram_mb` | `4700`（原为 3900 = 只算 ASR） | **`4700`**（qwen3asr + 对齐器**实测峰值 4.6 GB**） |
| `max_concurrent` | `6` | `2`（8 GB 卡上**两路**长音频就会互相挤显存 —— **按卡估的校准值，没压测过**；要调就在管理面里调） |

⚠️ **并发（`limits.max_concurrent`）与另外两个数不一样：它是"运行时可配"的。**
优先级是 **管理面配置 > 环境变量 > 出厂默认**（`server/limits.py`）：
管理员在管理面「性能」页签的「运行参数」里改过的值**盖过** `ECHO_MAX_CONCURRENT`，
写的值存在 state 卷里（**重启后还在**）、**改完即时生效**（不用重启）；
环境变量（`server/compose.yaml` 与两个交付包 compose 里的 `ECHO_MAX_CONCURRENT`）
**只在"空 state 卷首启、还没被管理面配过"时决定起点**。
所以"文件里写 6、上面 8 GB 卡那格写 2"并不矛盾：**全新部署先按出厂 6 起，
小卡在管理面里按自己的显存调到 2**。env 在场面却被管理面盖住时，
`GET /admin/api/limits` 的 `notes` 与启动日志会**如实说一句**
（"环境变量 `ECHO_MAX_CONCURRENT=…` 已设，但当前以管理面配置的 … 为准"）——
那是给现场"我改了 env 怎么没变"准备的，不是配错了。
⚠️ `per_client_concurrent` **仍然是 1**，且它是**刻意的**：单个客户端不许同时占两路（公平性）。

**怎么按自己的卡算**：

1. 列出**可能同时驻留**的模型（本清单里 `resident: false` 的按需加载 ——
   池子靠 LRU 腾地方，所以最省事的一条是"两个模型别同时常驻"）；
2. 把 `est_vram_mb` 加起来（**对齐器算进 qwen3asr 那一项**）；
3. 再留出桌面/显示占用（8 GB 卡约 1 GB+，24 GB 卡也要留一点）；
4. 剩下的写进 `vram_budget_mb`；超预算时服务端**拒绝**（`gpu_oom`）而不是 OOM，
   也**绝不回退 CPU**（`server/pool.py:_make_room_locked`、`server/engines.py:_assert_device`）；
5. `max_concurrent`（出厂 6）用真机压测校准：按**你打算填的通道数**同时打满时，
   单段耗时相对 1 路涨得少 = 还有余量；**要调就在管理面「运行参数」里改，改完即时生效**（不用重启）；
6. **把实测数字写回注释**，下一个换卡的人才不用从头猜。

⚠️ **容器里没有 `ECHO_VRAM_BUDGET_MB` 这种环境变量** —— 要设就得挂一份配置 +
`--config`（`prepare-backend.sh --vram-budget-mb 7000` 会替你写好那一行）。
不设就是默认 `0` = 不限（24 GB 卡上无所谓；8 GB 卡上建议设）。

## 10. 按显卡选规格（torch 源 / bf16 / 三类配法）

**一句话**：`est_vram_mb`、`vram_budget_mb`、`max_concurrent`，以及**镜像里的 torch 是哪个
CUDA 版本**，都是"按这块卡定的"；换卡要重算，**torch 源换错则根本跑不起来**。

### 10.1 先认清自己的卡：算力等级（sm_xx）

```bash
# ① 宿主上（不需要装 torch）
nvidia-smi --query-gpu=name,compute_cap --format=csv

# ② 容器里（顺便验"镜像里的 torch 真的认识这块卡"）
docker run --rm --gpus all echo-backend:0.1.0 python -c \
  "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_device_capability())"

# ③ 任何装了 torch 的地方（6.1 = Pascal）
python -c "import torch; print(torch.cuda.get_device_capability())"
```

| 算力 | 架构 | 例子 | bf16 | 新 CUDA 还支持吗 |
|---|---|---|---|---|
| sm_50 | Maxwell | GTX 9xx、M40 | ✗ | ✗ |
| **sm_61** | **Pascal** | **GTX 1070/1080、P4/P40/P100、MX150** | ✗ | ✗ |
| sm_70 | Volta | V100、Titan V | ✗ | ✗ |
| sm_75 | Turing | GTX 16xx、RTX 20xx、T4 | ✗ | ✓（bf16 仍然没有） |
| sm_80/86/89 | Ampere/Ada | RTX 30xx/40xx、A100 | ✓ | ✓ |
| sm_90/100/120 | Hopper/Blackwell | H100、**RTX 50xx**（本机实测的那块） | ✓ | ✓ |

判据来源：PyTorch 开发者邮件列表 2026-09-04 的公告 —— **PyTorch 2.15 起不再发布 CUDA 12.6 的
wheel，Maxwell / Pascal / Volta 一起被丢下**；CUDA 13.x 更是只支持 sm_75 及以上
（[公告](https://dev-discuss.pytorch.org/t/notice-cuda-12-6-wheels-will-no-longer-be-published-from-pytorch-2-15-drops-maxwell-pascal-volta/3432)、
[RFC #190385](https://github.com/pytorch/pytorch/issues/190385)）。
`prepare-backend.sh` 会在宿主上把算力读出来（`nvidia-smi --query-gpu=compute_cap`，
读不到就按型号名兜底），并按下面这套规则给出结论。

### 10.2 老卡（Pascal / Volta）**必须**换 torch 源：两个构建期参数

`server/Dockerfile` 里 torch 那一层现在是：

```dockerfile
ARG ECHO_TORCH_INDEX=https://download.pytorch.org/whl/cu126   # 默认：Turing 及以后
ARG ECHO_TORCH_VERSION=""                                      # 留空 = 该源上最新的一版
RUN ... pip install torch --index-url "$ECHO_TORCH_INDEX" ... && pip install funasr qwen-asr ...
```

老卡要换成 cu118 并**一起钉版本**：

```bash
# 直接 build
docker build -f server/Dockerfile -t echo-backend:0.1.0-full \
  --build-arg ECHO_EXTRA=1 \
  --build-arg ECHO_TORCH_INDEX=https://download.pytorch.org/whl/cu118 \
  --build-arg ECHO_TORCH_VERSION=2.7.1 .

# 或者 compose（这两行也可以写进 build.args；prepare-backend.sh 在 sm_<7.5 时会自动写）
docker compose -f server/compose.yaml build \
  --build-arg ECHO_EXTRA=1 \
  --build-arg ECHO_TORCH_INDEX=https://download.pytorch.org/whl/cu118 \
  --build-arg ECHO_TORCH_VERSION=2.7.1
```

* **为什么是 cu118**：cu118 的 wheel 里带着 sm_61 / sm_70 的 kernel；cu126/cu128 从 CUDA 12.8
  起就不带了。**2026-09-27 实地核过** `https://download.pytorch.org/whl/cu118/torch/`：
  目前最新是 **`torch-2.7.1+cu118`**（cp311 有 manylinux 轮子），所以 2.7.1 是现在能钉的上限。
* **为什么必须钉版本**：不钉就是"那个源上最新的一版"，而装 `funasr` / `pyannote.audio` 时
  **可能顺手把 torch 升级**成不含 Pascal 的版本 —— 镜像构建成功、容器里却跑不了那块卡。
  Dockerfile 里为此加了一步**版本校验**：钉了版本而最终 torch 不是它，**构建直接失败**
  （宁可构建失败，也别交付一个跑不了的镜像；构建日志里会打印实际装到的 torch / cuda 版本）。
* **另一条路（我们没走）**：官方对 2.15+ 的建议是从源码编译
  （`TORCH_CUDA_ARCH_LIST="5.0;6.0;7.0"`）。镜像里不做 —— 构建时间从分钟级变小时级，
  而且在这台开发机上无法验证。

### 10.3 老卡吃不了 bf16：这是我们实测路径的**硬限制**，不是"慢一点"

我们跑通的 qwen3asr 路径用的是 **bf16**（`app/audio/stt.py:_get_qwen3asr`：
`dtype = "bf16" if use_cuda else "fp32"`，**写死的**）。Pascal / Volta / Turing **都没有 bf16**：

* 请求 bf16 → 要么报错、要么走低效路径 —— 两种都不该拿去上生产；
* 退回 fp32 会把显存**翻倍**：qwen3asr 0.6B + 强制对齐器 0.6B 在 fp32 下约 4.8 GB + 激活 ——
  8 GB 卡上很容易再踩回我们刚修好的那个坑（**溢出换页 → 慢十倍、600 秒音频只出几十个字**）。
* 想在老卡上试 qwen3asr，得先把 `app/audio/stt.py` 里那个 dtype 改成 fp16 ——
  **那是客户端引擎层的改动，本次没做、也没在真机验过**。所以文档的立场很直接：
  **老卡别跑 qwen3asr，用 SenseVoice。**

### 10.4 三类配法（`models.specs` 直接抄）

**A. 8 GB 新卡（sm_80+，能吃 bf16）** —— 本机实测的那条路：

```yaml
server:
  vram_budget_mb: 7000          # 不是 8000：桌面/显示还要留 ~1 GB
models:
  device: cuda                  # 要 cuda 而看不到 CUDA 时**直接失败**，绝不回退 CPU
  specs:
    - id: asr-long
      slot: asr.long
      impl: qwen3asr
      resident: false           # 8 GB 上**不要**常驻（它会让 diarize 加载失败）
      max_concurrency: 1
      est_vram_mb: 4700         # qwen3asr + 对齐器实测峰值 4.6 GB（3900 是只算 ASR 的旧值）
      modelVersion: qwen3-asr-0.6b
      supports: [asr.text, asr.timestamps]   # 对齐器在位，这两项才是真的
    # diarize / speaker-embed 照 server/echo-server.example.yaml 抄，别改 vectorSpaceId
```

实测（2026-09-27，8 GB 卡）：峰值 **4.6 GB**；600 秒音频 **30~45 秒**
（切片 60 秒 / 批 4，见 `app/audio/stt.py:QWEN3_CHUNK_S` 与 `QWEN3_BATCH` —— 这两个值就是
为 8 GB 卡定的）。⚠️ 对齐器与 qwen3asr 是**同一个进程里的两份权重**，
`est_vram_mb` 必须把两份都算进去。

**B. 8 GB 老卡（Pascal，例如 GTX 1070）** —— **SenseVoice + pyannote，把 qwen3asr 让给新卡**：

```yaml
server:
  vram_budget_mb: 7000
models:
  device: cuda
  specs:
    - id: asr-long
      slot: asr.long
      impl: sensevoice           # 非自回归、不吃 bf16、显存小得多
      resident: false
      max_concurrency: 1
      est_vram_mb: 1800          # GTX 1070 **实测**：90 秒音频峰值 1.7 GB（1800 是校准后的值，
                                 # 原来的 1200 是占位估算，已按 /v1/health 的 vram.usedMb 写回）
      modelVersion: sensevoice-small
      supports: [asr.text]       # 注意：**没有** asr.timestamps
    # ⚠️ **老卡上不要写 diarize / speaker-embed**。这一行原文是"pyannote 也是 torch 系，
    #   sm_61 上能跑，但慢"——那句话是**错的**。（2026-09-28 在 GTX 1070 上实测：
    #   pyannote.audio 4.x 要求 torch>=2.8，而带 Pascal(sm_61) 的 torch 最高只到
    #   2.7.1+cu118，**装不上**；退回 3.4.0 又没有 `app/audio/diarize.py` 要用的 `plda=`
    #   形参。镜像里因此没有它，宣告这两档 = 宣告一个永远 model_failed 的槽，与"缺强制
    #   对齐器却宣告 asr.timestamps"是同一种假话。）本小节标题里的 "+ pyannote" 是同一句
    #   旧结论的残留，按上面这条读。后端交付包的 cu118 变体就是照这条写的：
    #   `delivery/backend-cu118/server.yaml`（只有 sensevoice 一档）。
```

* **代价**：`supports` 里**没有** `asr.timestamps`（SenseVoice 不给句级时间戳，服务端**不编**
  `estimated`），所以老卡上会议时间轴会退化成"按字数均摊"（客户端兜底）。
  `prepare-backend.sh` 对"缺强制对齐器"报警，说的就是这件事。
* **权重必须在模型卷里**：`/srv/echo/models/sensevoice/snapshots/master/model.pt`
  （同目录还有 `config.yaml`）。容器里的 ModelScope 缓存
  （`/root/.cache/modelscope/models`）**不在只读模型卷上**，别指望它；
  `prepare-backend.sh --from 源机` 会把源机的 `models/sensevoice` 一起拷过来。
* 镜像要带 torch：`--extra`（或 compose 里 `ECHO_EXTRA: "1"`）**并且**用 cu118 那个源（见 10.2）。
* **实测速度（GTX 1070 / 8 GB / 2026-09-28）**：一段**真会议录音的 90 秒切片**
  （16 kHz 单声道，`/v1/asr`，`variant=long`）——
  **冷启动 9.7~15.7 秒**（含 SenseVoice + VAD 加载）、**热 1.17 秒 → RTF 0.013（约 77× 实时）**，
  输出 490 字、`timestamps: none`；显存峰值 **1701~1737 MiB**，`/v1/health` 的
  `vram.usedMb` 转写完显示 **1800**（所以 `est_vram_mb` 记 1800）。
  这台机器上它是**够用的**：一段 10 分钟会议 ≈ 热转写 8 秒。
* `est_vram_mb: 1200` 是**估算**，没在 8 GB 卡上实测过 —— 第一次部署请用
  `/v1/health` 的 `vram.usedMb`（跑一段真音频之后看）校准，然后写回配置与注释。
  （2026-09-28 已按上面那条实测改成 **1800**。`scripts/prepare-backend.sh --asr-est-vram-mb`
  就是干这件事的，别手改生成的配置文件 —— 那份文件每次重跑都会被重写。）

**C. 24 GB 卡（sm_86+）** —— 出厂样例那套：

```yaml
server:
  vram_budget_mb: 20000
models:
  device: cuda
  specs:
    - id: asr-long
      slot: asr.long
      impl: qwen3asr
      resident: true            # 24 GB 上可以常驻预热（8 GB 上不行）
      max_concurrency: 1

      modelVersion: qwen3-asr-0.6b

```

`asr-long` + `diarize` 可以同时在位（4700 + 2600 ≈ 7.3 GB）；**8 GB 上不行**（已有结论）。
`limits.max_concurrent` 仍要用真机压测校准（见上一节第 5 条）。

### 13.2 真机上发现并**已改**的问题（每条都在这台机器上复现过）

1. **SenseVoice 在容器里加载不了**（`fsmn-vad` 下不下来，只读根）→ 新增 `cache` 卷 +
   `MODELSCOPE_CACHE` / `HOME`，见 §2.4。**这是本次最要紧的一条：不改就一个 `/v1/asr` 都跑不通。**
2. **`pyannote.audio` 把 torch 换成 cu13 的**：`pip install ... pyannote.audio` 现在会拿到
   4.0.x（`Requires-Dist: torch>=2.8, torchaudio>=2.8, torchcodec>=0.6`），pip 于是卸掉
   `torch 2.7.1+cu118` 与 `triton 3.3.1`、装 `nvidia-*-cu13`。Dockerfile 里那条版本校验
   **真的把它拦住了**（这条校验以前只在纸上）。修法：老卡那一档只装
   `funasr transformers` + 把 `torchaudio` 与 torch **一起钉**（`server/Dockerfile`，见 10.4 B）。
3. **普通依赖的 pip 慢 170 倍**：同一个宿主机上 `curl` 拉 PyPI 有 17 MB/s，而构建里的
   `pip install` 每个 wheel 只有 85~190 kB/s；清华镜像同一时刻的真实 wheel 是 **26 MB/s**。
   新增构建期开关 `ECHO_PIP_INDEX`（Dockerfile）与 `--pip-index`（脚本），默认仍是 PyPI。
   torch **不**走它（cu118 索引自带它要的依赖：sympy 1.14 / typing-extensions 4.16 /
   filelock / networkx / jinja2 / fsspec / nvidia-*-cu11，2026-09-28 逐条核过）。
4. **老卡 + SenseVoice 那条路走不到退出码 0**：脚本一边打印"缺 qwen3asr/对齐器只算警告"，
   一边把它们记进错误计数 → 汇总报"有 N 处错误"并以 **1** 收场（`--allow-missing-aligner`
   同样如此）。现在这类错误单独计数，在两条"允许缺"的路线上统一降级为警告。
5. **老卡没有地方写 `impl: sensevoice`**：生成的 `server.yaml` 每次重跑都会被重写，
   照着文档手改一行会被抹掉（然后就变成"按 qwen3asr 加载 → asr 一路 model_failed"）。
   新增 `--asr-impl sensevoice`（写整份 `models.specs`）与 `--asr-est-vram-mb`。
6. **开了鉴权时冒烟验收必然失败**：脚本默认开鉴权，却给冒烟**不带凭据** —— 拒绝路径那
   5 项全拿 401，退出码 4。现在脚本会现发一张一次性配对码给冒烟（`--pair-code`），
   并且冒烟里那条"乱填令牌 → 401"改打**受保护**的 `/v1/asr`（原来打在免鉴权的
   `/v1/capabilities` 上，永远 200）。
7. **一个没凭据的请求能把连接挂死**（`Content-Length: 999MB` + 只发几 KB）：
   鉴权先失败 → `_reject` 去 `drain` 那个永远发不完的 body → 客户端在自己的超时前
   **拿不到任何响应**（实测 12 s 超时；冒烟的 600 s 超时表现为"卡住十分钟"）。
   修法：`server/routes.py:_reject` **不再抽干"声报超限"的 body**（新增
   `_declared_over_limit()`，与 `/asr` 里 `payload_too_large` 那条特例同一个道理：
   声报超大的请求只回状态码就够，绝不能为了发一个错误去读一个可能永远发不完的 body）。
   修完实测：无凭据 **401 0.01 s**、有凭据 **413 0.01 s**。
   （`scripts/smoke-echo-backend.py` 里那条"声报超限 → 413"因此**必须带凭据**才测得到 413，
   所以脚本现在会给冒烟发一张配对码 —— 见第 6 条。）

### 13.3 真机上发现但**没改**的问题（要用户拍板）

1. **容器里发出来的配对串带的是 Docker 网桥地址**：
   `echo://pair?host=https://172.18.0.2:8900&code=…&fp=…`。`ops.advertised_host()`
   （`server/ops.py:72-99`）把通配监听换成 `socket.gethostbyname(socket.gethostname())`，
   容器里那就是 `172.18.0.x`；而 `ECHO_LISTEN=0.0.0.0:8900` 是**环境变量**，
   优先级高于配置文件（`server/settings.py:166-167`），所以配置文件里写死监听地址也压不住它。
   返回里那句 `note` 会说"同事连不上就换成他们能访问到的那台机器的主机名或 IP" ——
   对用户来说就是**必须手工把 host 换成 `192.168.1.30`**。
   （要根治得给"对外地址"一项配置，属于产品决策，本次没动。）
2. **容器里的 CLI 不带 `--config` 就没有证书指纹**：`docker exec echo-backend python -m
   server.main --new-pairing-code` 打出来的是 `host=http://172.18.0.2:8900&code=…`
   （**没有 `fp=`、而且 scheme 是 http**，因为 CLI 读不到 `server.tls`）。
   必须写成 `--config /etc/echo/server.yaml` 才带 `fp=`。
   `prepare-backend.sh` 里发码那处已经是带 `--config` 的写法。
3. **`ssh -L 8901:127.0.0.1:8901` 在"本机 8901 已被占用"时绑不上**：开发机上正好跑着
   另一份后端（`python -m server.main --config data\backend-dev\server.yaml`），
   所以本次用 `-L 18901:127.0.0.1:8901` + 显式 `Origin: http://127.0.0.1:8901` 验的
   （同站判定看的是**服务端**的 8901，不看隧道本地端口）。
4. **转写结果不是逐字可复现的**：同一段音频两次调用，文本长度 490 / 493 字，个别词不同
   （funasr 的 VAD 切分与批处理会引入这点差异）。这不是本次部署引入的，但值得知道。
5. **`sm_6.1` 这个显示**：脚本把 `compute_cap=6.1` 拼成 `sm_6.1`（文档里写的是 `sm_61`）。
   纯显示问题，判断逻辑用的是数值比较。
