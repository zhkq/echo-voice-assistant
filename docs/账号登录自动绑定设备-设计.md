# 账号登录后自动绑定设备（登录即用）· 设计

对应 issue #23。目标分支 `integration/billing-vibepay`（**不合 main**）。

本文是第一版设计，覆盖三件事：**接口**、**凭据模型**、**旧配对兼容与迁移**。
写代码前请先确认第 11 节的几个决策点；确认后按本文实现。

> 本文会取代 `docs/后端收费与自动配对-设计.md` §5.0.1 / §5.0.4 / §5.2 里
> "登录 → 服务端发设备绑定码 → 客户端再调 `/v1/pair`"那一段。
> 旧的 pairing 协议本身**不删**，只是客户端新用户默认不再走它。

---

## 0. 结论（先看这段）

1. 新增 **`POST /v1/account/devices/bind`**：带 `userToken` 直接换
   `clientId + clientSecret + accessToken`，**不再需要配对码/二维码**。
2. 设备身份用客户端稳定生成的 **`deviceId`**；同一账号重复绑定**复用同一个
   `clientId`**、只轮换 secret，**不重复占设备数**。
3. 账号态（`userToken`）与设备态（`clientId`/`secret`）**继续分离**：
   `userToken` 不能调能力端点（现有 `typ=user` 边界不变），设备 secret 可以轮换。
4. 旧 `/v1/pair` 与 `/v1/account/devices/code` **原样保留**，旧客户端一个字节不受影响；
   新客户端默认不展示配对码，已有 `backend.json` 的设备**不重复绑定**。
5. **本票范围**：服务端（bind/设备列表/解绑）、客户端账号与绑定服务
   （`app/account_admin.py` + `/api/account/*`）、账户页设备列表、测试与迁移说明。
   **安装向导 UI 归 #22**；#22 的"登录/注册 → 自动绑定"步骤调用本票的 API。
   验收项"安装向导首次登录自动绑定"要等 #22 合入后联调（依赖关系写在 issue 正文里）。

## 1. 现状与差距

| 现在有什么 | 位置 | 差在哪 |
|---|---|---|
| 邮箱注册/登录、`userToken`（30 天） | `server/account.py::register/login` | 登录只发账号令牌，**没有能力后端凭据** |
| 设备绑定码（一次性、10 分钟、绑定到 user） | `POST /v1/account/devices/code` → 客户端走 `/v1/pair` | 要人工把码/二维码交给客户端，**这就是"手动配对"** |
| 配对码 → `clientId` + `secret` → 短期 JWT | `server/auth.py::redeem/token_for`、`app/capabilities/pairing.py` | 协议本身可用，只是入口仍是码 |
| user ↔ 设备、`max_devices`、解绑 | `user_devices`、`/v1/account/devices/unbind`、管理面 | 数据模型已有；**缺一条"登录态直接建/复用设备凭据"的服务端路径**，账户页也看不到设备列表 |
| 能力请求的收费/设备闸门 | `BillingService.user_for_client/check_access` | 已有；账号冻结、设备禁用立即 403 的语义可复用 |
| 旧客户端兼容 | `/v1/pair`、`clients`/`user_devices` | 必须原样保留 |

**核心结论**：不需要新造一套凭据，也不需要改 `/v1/pair`。
缺的是"**用 `userToken` 证明是谁，然后由服务端直接把 `/v1/pair` 兑换那一步做掉**"的接口，
以及客户端"登录态存哪、绑定走哪"的那一层。

## 2. 目标流程

```
安装 / 首次启动
  │
  ├─ 登录 / 注册邮箱账号            POST /v1/account/login（或 register）
  │     └─ 得到 userToken（30 天，续期靠重新登录；不做 refresh token）
  │
  ├─ 自动绑定设备                  POST /v1/account/devices/bind（Bearer userToken）
  │     入参：deviceId / clientName / deviceName / platform
  │     校验：账号 active + 有效权益 + 设备数未超限 + 同一 deviceId 幂等
  │     返回：clientId + clientSecret + accessToken + expiresIn
  │     └─ 客户端把 clientId/secret 落 {DATA}/backend.json（DPAPI/0600，复用现有信封）
  │
  └─ 完成：客户端从 backend.json 读设备凭据
        └─ 之后和今天完全一样：/v1/token（Basic）→ Bearer /v1/asr、/v1/diarize、/v1/tts
```

- 登录失败/过期：提示"请重新登录"，**不自动回退到配对码**。
- 已有 `backend.json`：跳过 bind（不重复占设备数），继续用现有凭据。
- 账号冻结/设备解绑：能力请求立即 403（现有语义，见 §4.4）。
- 本机自配对（`localpair`）继续走自己的路：本机后端不需要账号，也不应被自动绑定顶掉。

## 3. 服务端接口

### 3.1 `POST /v1/account/devices/bind`

**鉴权**：`Authorization: Bearer <userToken>`（`typ=user`、账号 `status=active`、`ver` 与
`users.token_version` 一致）。**这是账号端点，不是能力端点**；`userToken` 不会被当成设备凭据。

**请求**：

```json
{
  "deviceId": "9f2c…（客户端生成的稳定设备 id，必填）",
  "clientName": "张伟的办公本",          // 可选，管理面/客户端列表里的名字
  "deviceName": "DESKTOP-ABC",          // 可选，账户页显示的主机名
  "platform": "windows",                // 可选：windows/macos/linux/...
  "clientVersion": "3.0.2",             // 可选，只用于排障/审计
  "existingClientId": "cli-…"           // 可选：把已有配对凭据"认领"到账号下（见 §8.3）
}
```

**响应 200**：

```json
{
  "clientId": "cli-1a2b3c",
  "clientSecret": "…（只出现这一次）",
  "accessToken": "…",                  // 短期客户端 JWT，等价于马上调一次 /v1/token
  "expiresIn": 3600,
  "scopes": ["asr", "diarize", "embed", "tts"],
  "serverName": "",
  "protocol": 1,
  "rebound": false,                    // true = 复用了已有 deviceId 的 clientId
  "device": {
    "clientId": "cli-1a2b3c",
    "deviceName": "DESKTOP-ABC",
    "platform": "windows",
    "boundAt": 1762500000.0,
    "lastSeen": 1762500000.0,
    "status": "active"
  },
  "devices": 1,
  "deviceLimit": 3
}
```

字段名说明：

- 本接口用 **`clientSecret`**（issue 里写的就是这个名字）；旧的 `/v1/pair` 继续用 `secret`，
  **不改老协议**。客户端绑定函数按各自协议读字段。
- `accessToken` 是**便利字段**：客户端可以立即用它，也可以丢掉后走 `/v1/token`；
  它**不落盘**（与现有 `BackendCredentials.access_token` 的约定一致）。

**错误**（沿用现有 `errors` 结构：`{code, detail}`）：

| HTTP | code | 场景 |
|---|---|---|
| 401 | `unauthorized` | 缺 `userToken`、过期、签名不对、`typ != user`、`userToken` 版本不对 |
| 403 | `forbidden` | 账号已停用/冻结 |
| 402 | `entitlement_missing` / `entitlement_expired` / `entitlement_inactive` | 没有有效权益 |
| 403 | `device_limit_reached` | 有效设备数已达套餐 `max_devices` |
| 409 | `device_bound_to_other_account` | 同一 `deviceId` 已绑定到**另一个账号** |
| 409 | `client_not_yours` | `existingClientId` 在**本服务端**存在且属于另一个账号 |
| 409 | `device_mismatch` | `existingClientId` 已有非空 `deviceId`，且与本次请求的不是同一台设备 |
| 400 | `bad_request` | `deviceId` 缺失或格式不对、名字/平台字段不合规 |
| 429 | `rate_limited` | bind 限流 |
| 404 | `billing_disabled` | 服务端没开收费 |
| 503 | `auth_misconfigured` | 收费开着但 `auth.enabled=false` 或 `auth.mode != jwt` |

> `device_limit_reached` 继续用**403**（现有错误、现有客户端提示都认这个）；
> 不新造 409 表示"设备满了"，409 只留给"设备已属于别的账号"这种冲突。

### 3.2 幂等：同一台设备重复绑定

判据是 **`deviceId`**（不是名字，也不是 IP）：

- 客户端首次运行时生成一次 `deviceId`（32 hex 随机），存在 `{DATA}/device-id`；
  重装/升级保留数据目录时不变，所以"重装后重新登录"能认出同一台设备。
- 服务端 `user_devices.device_id` 存这个值；**全局只允许一条 active 行**（见 §5）。
- 绑定算法：

```
用户 = userToken 解析出的 user（active）
限流（按 user）
若 deviceId 非法/缺失 → 400

row = active_device_by_device_id(deviceId)
若 row 存在且 row.user_id != 用户 → 409 device_bound_to_other_account
若 row 存在且 row.user_id == 用户：
    cid = row.client_id；轮换 secret（token_version + 1）；不增加设备数
若 row 不存在、给了 existingClientId：
    client = store.client(existingClientId)
    若 client 存在且 user_devices 归属另一个账号 → 409 client_not_yours
    若 client 存在且 user_devices 归属当前账号：
        已有非空 deviceId 且与本次不同 → 409 device_mismatch（不能拿另一台设备顶替）
        否则 → 认领：cid = existingClientId；轮换 secret；把 device_id 补到这条绑定行
    若 client 不存在（换了后端/已被删）→ 当作没给，继续下面的新建
否则：
    若 count_devices(用户) >= max_devices → 403 device_limit_reached
    新建 cid + secret
创建/更新 clients 行（名字、scopes、secret hash、revive/解除 disabled）
upsert user_devices（user, cid, deviceId, deviceName, platform, status=active）
并发兜底：再数一次，若超过上限 → 撤销刚建的设备并 403（与 after_pair 同语义）
签发 accessToken
记一条 order_events（device-bound / device-rebound）
返回
```

**"幂等"的准确含义**：同一个 `(user, deviceId)` 重复调用**返回同一个 `clientId`、设备数不变**；
但 **secret 会轮换**（服务端只存哈希，无法把旧明文再给一次）。客户端拿到新 secret 后覆盖
`backend.json`；正常流程里客户端已有有效 `backend.json` 时**根本不会重复调用 bind**，
所以轮换只在"客户端丢了凭据/重装"和"用户主动重新绑定"时发生。

并发：v1 是单进程，`AccountService` 里用一把 `threading.Lock()` 把"查重 + 建行 + 数数"串起来；
多实例部署要改成 DB 事务，本轮如实记为限制。

### 3.3 限流

- 新增绑定令牌桶（按 `user_id`，与能力面的 1 QPS 完全分开）：
  `billing.device_bind_rate_per_min`（默认 6）、`billing.device_bind_burst`（默认 5）。
- 超了回 429 + `Retry-After`。3 台设备 + 少量重试在 burst 内，不会误伤。
- 未认证请求在 `authenticate` 就 401，不进入桶；登录本身已有 `PairThrottle`。

### 3.4 设备列表视图（`GET /v1/account/me` / 登录响应）

`device_view` 增加：

- `platform`（新列）
- `lastSeen`：取 `max(user_devices.last_seen, clients.last_seen)`（管理面/账户页要看"最近活跃"，
  现在只取绑定时间，会永远显示绑定那一刻）
- `boundAt`、`status` 不变。

`/v1/account/me` 已返回 `devices`；账户页直接渲染，不再新增列表接口。

### 3.5 解绑（`POST /v1/account/devices/unbind`）不变

现有实现已经做到：设备行置 `revoked` + `clients.disabled=1` + 清 `_device_cache`；
能力请求立即 403（`forbidden`/`device_revoked`），并且**不推 token_version**
（保持"认得出这台设备，但不许用"的语义）。本轮只补测试与账户页入口。

### 3.6 旧"设备绑定码"接口保留

`POST /v1/account/devices/code` 继续存在（换机/人工兜底/旧客户端），
`/v1/pair` 继续按它兑换，`BillingService.after_pair()` 继续落 `user_devices`。
新客户端默认不调用它；如果服务端还是旧版（没有 bind 接口），客户端明确报
"服务端未升级，可手动配对"，**不自动回退**。

### 3.7 轮换 secret

不新增"轮换"端点：**对同一 `(user, deviceId)` 再 bind 一次 = 轮换**（`token_version + 1`，
旧 accessToken 立即失效）。管理面已有的 `--rotate-secret` 不受影响。
这样少一个端点、少一条权限面；如果以后要"设备自己换 secret 而不重新绑定"，再加。

## 4. 凭据模型

### 4.1 三层，各管一段

| 凭据 | 谁签发 | 生命周期 | 存哪 | 能做什么 |
|---|---|---|---|---|
| `userToken`（JWT `typ=user`） | `/v1/account/login/register` | 30 天（配置 `billing.user_token_ttl_s`） | 客户端 `{DATA}/account.json`，DPAPI/0600 | 账号 API：bind、me、订单、设备解绑、退出 |
| `clientId` + `clientSecret` | bind 或 `/v1/pair` | 长期，直到解绑/撤销/轮换 | 客户端 `{DATA}/backend.json`，DPAPI/0600 | 只用于 `POST /v1/token`（HTTP Basic） |
| `accessToken`（客户端 JWT） | bind 或 `/v1/token` | 1 小时（`auth.token_ttl_s`） | **只在内存**，不落盘 | 能力端点 `Authorization: Bearer` |

### 4.2 硬边界

1. `userToken` **不能**调能力端点：`Auth.authenticate()` 继续拒绝 `typ=user`（已有用例钉着）。
2. `clientSecret` **不能**调账号端点：账号端点只认 `typ=user`。
3. `userToken` **不**被当作长期设备凭据存进 `backend.json`；bind 只把它当"这次授权"的证明。
4. `clientSecret` 只出现一次；服务端只存 PBKDF2 哈希（现有 `hash_secret`）；bind 重复调用时轮换。
5. `accessToken` 不落盘；进程重启后重新 `/v1/token`。
6. `backend.json` 的信封（Windows DPAPI / POSIX 0600）与证书固定逻辑**完全复用**现有
   `app/capabilities/credentials.py`；`account.json` 复用同一套原语（§6.1）。

### 4.3 userToken 失效 / 设备凭据失效，分别怎么办

| 情况 | 客户端 | 服务端 |
|---|---|---|
| `userToken` 过期/被登出（`users.token_version+1`） | 账号页与 bind 回 401 → 提示重新登录；**已绑定设备的能力调用照常**（设备凭据独立） | 账号端点 401；能力端点不受影响 |
| 设备被解绑（账户页/管理面） | 能力请求 403 → 提示"这台设备已被解绑，请重新登录绑定"；不自动换成配对码 | `clients.disabled=1`，立即 403 |
| 设备 secret 被轮换 | 旧 accessToken 失效 + 旧 secret 换不到令牌 → 用新 secret 覆盖 `backend.json` | `token_version+1`，`/v1/token` 只认新 secret |
| 账号冻结 | bind/me 403；能力请求 403 | `users.status != active`：`AccountService.authenticate` 403；`BillingService.user_for_client` fail-closed 403 |
| 权益到期/退款 | bind 402；能力请求 402 | `require_entitlement` / `check_access` |

### 4.4 为什么"撤销设备"能立即生效

- 同进程：`auth.set_disabled()` 直接改缓存 + 落库，下一个请求就 403。
- 跨进程（CLI 撤销）：`RevocationWatcher` 轮询 `max(updated_at)`，≤5 秒发现（现有设计，如实保留）。
- 设备 secret 撤销之后**不能再换令牌**：`Auth.token_for()` 看 `disabled`/`revoked_at`
  （2026-11-03 真机事故的修法），不会出现"401 自动续命"。

## 5. 数据模型与迁移

### 5.1 `user_devices` 增列

```sql
ALTER TABLE user_devices ADD COLUMN device_id TEXT NOT NULL DEFAULT '';
ALTER TABLE user_devices ADD COLUMN platform  TEXT NOT NULL DEFAULT '';

-- 一台设备同一时刻只能在一个账号下 active（防止同一台机器跨账号占名额/串权益）
CREATE UNIQUE INDEX IF NOT EXISTS idx_user_devices_device
    ON user_devices(device_id) WHERE device_id <> '' AND status = 'active';
```

- 放在 `store.py` 的 `_ADDED_COLUMNS` + `_migrate_locked()`（与 `users.email` 同一套做法）。
- `device_id = ''` 的历史行**不参与**唯一索引，也不匹配任何 bind；行为与升级前完全一样。
- `clients.client_id` 与 `user_devices.client_id` 的现有唯一索引不动。

### 5.2 `upsert_device` / 查询

- `upsert_device(user_id, client_id, device_name, device_id="", platform="")`：
  `ON CONFLICT(client_id)` 时同时更新 `device_id/platform/device_name/status='active'/last_seen`，
  **保留 `bound_at`**（重复绑定不算新绑定）。
- 新增 `device_by_device_id(device_id)`：只查 `status='active'`。
- `devices()` 左连 `clients` 取 `last_seen`（§3.4）。
- `billing.after_pair()` 继续用空 `device_id`（旧 pairing 路径不要求客户端有 deviceId）。

### 5.3 迁移语义

- **不强制迁移**：升级后已配对用户的 `backend.json` 原样可用，设备行原样保留。
- **旧设备行（`device_id=''`）**：继续占设备名额；用户可在账户页看列表并解绑。
- **认领**：如果用户显式"改用账号后端"，客户端把当前 `backend.json.client_id` 作为
  `existingClientId` 传上来，服务端把这条旧绑定行补上 `device_id`（不新建、不占第二个名额）。
  **只认同一台设备**：旧行已有非空 `device_id` 且与本次不同 → `409 device_mismatch`；
  没有 `user_devices` 行的 client 不认领（归属不明确）。
  这需要客户端有当前凭据；没有凭据（重装且数据丢了）就按新设备算，旧行由用户自己解绑。
- **回滚**：关掉客户端自动绑定即可；服务端新增列/端点是惰性的，旧客户端不调用。
  服务端也可以回滚到不含 bind 的版本（多出的列不影响旧代码）。

## 6. 客户端改造

### 6.1 新模块 `app/account_admin.py`

职责只有三件：**账号会话落盘**、**代理账号 API**、**登录态绑定设备**。

- `{DATA}/account.json`：`{serverUrl, userId, email, userToken, expiresAt, savedAt}`，
  用 `app/platform.protect_secret()` 加密（Windows DPAPI / POSIX 0600）。
  为了不复制信封代码，把 `credentials.py` 里的 `_seal/_open` 提成可复用的
  `seal_json/load_json`（名字待实现时定），`backend.json` 与 `account.json` 共用。
- 读取失败/损坏 → 当作未登录（不抛，面板能起来）。
- `login(email, password, serverUrl?)`：
  - `serverUrl` 取参数 → 隐藏设置 `accountServerUrl` → 报错"还没配置账号服务地址"。
  - 调 `POST {serverUrl}/v1/account/login`，存 `account.json`，返回
    `{userId, email, expiresAt, devices}`（**不返回 userToken**）。
- `register / send_code / reset_password`：同上的薄代理，错误原样映射成人话。
- `logout`：调 `/v1/account/logout`（尽力而为），清 `account.json`。
- `me()`：`GET /v1/account/me`，返回用户 + 权益 + 设备列表。
- `bind_device(force=False)`：
  1. 没有会话 → `AccountError("请先登录")`；
  2. `credentials.load()` 有有效凭据且 `force=False` → **跳过**，返回 `skipped=True`；
  3. `deviceId()` 取/生成 `{DATA}/device-id`；
  4. `pairing.bind_with_account(serverUrl, userToken, deviceId=…, clientName=…,
     deviceName=hostname, platform=sys.platform 归一化, existingClientId=当前 client_id（仅 force）)`；
  5. `credentials.save()`（原子替换 + DPAPI/0600）；
  6. 返回 `{ok, pair, devices, deviceLimit, skipped:false}`。
- `unbind_device(clientId)`：调账号端点；如果解绑的是本机 `backend.json.client_id`，
  同时删除本机凭据（否则界面会一直显示一台已失效的后端）。
- **错误映射**（必须逐条写清，避免"登录失效"被误报成网络问题）：
  - 401 → "登录已失效，请重新登录"（**不自动走配对码**）；
  - 402 → "账号没有有效权益/已到期，请续费"；
  - 403 `device_limit_reached` → "设备数已满（N 台），请先在账户页解绑旧设备"；
  - 409 `device_bound_to_other_account` → "这台设备已绑定到另一个账号，请先在原账号解绑"；
  - 404 `billing_disabled` → "该服务端未开通账号计费"；
  - 429 → "操作太频繁，请稍后再试"；
  - 连不上/证书失败 → 复用 `pairing.PairingError` 的现有文案。

### 6.2 `app/capabilities/pairing.py`：只加一个函数

```python
def bind_with_account(base_url, user_token, *, device_id, client_name="",
                      device_name="", platform="", existing_client_id="",
                      timeout=PAIR_TIMEOUT_S, save=True) -> BackendCredentials
```

- 与 `pair()` **逐字同一套** TLS 固定 / `_post_json` / 错误模型：
  https 先 `pin_certificate()` → `pinned_context()`，POST 时带
  `Authorization: Bearer <userToken>`，路径 `/v1/account/devices/bind`。
- 读 `clientId/clientSecret/accessToken/expiresIn`，构造 `BackendCredentials`，
  把 accessToken 写进内存对象（不落盘），`save=True` 时落 `backend.json`。
- **不新增第二套 HTTP 客户端**；`echo_server` 完全不用改（它只认 `backend.json` + `/v1/token`）。

### 6.3 本机 API（`app/api.py`）

给 #22 的向导/面板用，全部走本地进程（免 CORS、TLS pin 在进程里）：

```
POST /api/account/login            {email, password, serverUrl?}
POST /api/account/register         {email, code, password, inviteCode?}
POST /api/account/email/code       {email, purpose: register|reset}
POST /api/account/password/reset   {email, code, newPassword}
POST /api/account/logout
GET  /api/account/session          → {signedIn, userId, email, expiresAt, serverUrl}
GET  /api/account/me               → 用户 + 权益 + 设备
POST /api/account/devices/bind     {force?} → {ok, pair, devices, deviceLimit, skipped}
POST /api/account/devices/unbind   {clientId}
```

- 错误回 400/401/402/403/409/429 + `detail`（中文），不把后端 `code` 原样丢给界面。
- 绑定成功后**不自动改** `capabilityPrivacy`；路由设置由向导/面板在用户确认后写
  （`capabilityMeetingAsrBackend=echo-server`、`dailyReviewSttBackend=echo-server`、
  `ttsEngine=echo-server`；`capabilityEchoServerUrl` 留空走凭据）。这条沿用现有隐私纪律。

### 6.4 设备 id 与登录态落盘

- `{DATA}/device-id`：32 hex，一次生成、原子写、0600。不是秘密，但要求稳定；
  删数据目录 = 新设备（旧设备由用户在账户页解绑）。
- `{DATA}/account.json`：见 §6.1；退出登录/401 时清。
- **已有 `backend.json` 不重复绑定**：`bind_device` 的默认分支；要换后端时走显式 `force`。
- **登录失效不自动回退配对码**：客户端没有任何"401 后去发设备绑定码"的分支；
  手动配对只保留在"后端设置"卡的显式入口（排障/管理员给码）。

### 6.5 配置

- 新增隐藏设置 `accountServerUrl`，默认 `https://echoserver.zhkq.online:8443`
  （官方 HTTPS 口，见 `scripts/tls/`），可被向导/运维覆盖；dev/内网用 http 时也走同一个键。
- 登录/注册的密码只走本地进程 → 后端 HTTPS，不写日志；`account.json` 只存 userToken（不存密码）。

### 6.6 中继（手机 / 手表）兼容

`app/relay.py` 复用同一份 `backend.json`：`backend_endpoint(slot="relay")` 读 base_url/凭据、
`hostId` 就是认证后的 `client_id`、主机靠 `/v1/relay/host/poll` 取手机请求。

- bind 写的就是**同一个** `{DATA}/backend.json`、同一套字段（base_url/client_id/secret/
  cert_fingerprint/cert_pem），所以 relay 的读取路径**一个字节不用改**。
- 登录绑定后：hostId 变成新的 `clientId`（或重复绑定时**保持同一个** `clientId`），
  poll 用的 accessToken 由新 secret 换得；手机/手表经 `/v1/relay/<hostId>/` 的调用不回归。
- 旧 `/v1/pair` 配好的 `backend.json` 仍然能读（形状不变），升级后 relay 不会突然没有 hostId。
- 判据：`tests/test_relay_host.py::RelayAfterAutoBindTests`
  （登录 → bind → 真的起 relay worker → poll 回 `hostId=cli-bound` → 交回结果；
  旧凭据另有一条用例）。

### 8.2 旧入口保留

- 客户端"后端设置"卡的手动配对/本机自动配对**保留**；默认路径不再经过它。

  但 pairing 协议章节不改。

### 8.3 迁移动作

1. 服务端升级：加列 + 唯一索引，旧数据不动。
2. 客户端升级：已配对用户继续用 `backend.json`；`bind_device` 发现凭据就跳过。
3. 想"从手配迁移到账号"的用户：显式点"改用账号后端" → 登录 → bind（带

4. 找不到旧凭据的重装：新 `deviceId` 会新建一台；旧行在账户页解绑（或管理面重置设备）。
5. 回滚：关客户端自动绑定；服务端可回滚到无 bind 的版本（多出的列/索引不影响旧代码）。

### 8.4 不做的迁移

- **不自动把旧 `clients` 行挂到某个 user**：没有可靠证据，乱挂等于把别人的设备送给账号。
- **不删除旧 `user_devices` 行**：解绑只置 `revoked`，保留审计。

## 9. 安全与滥用

- 绑定必须带有效 `userToken`；`userToken` 只用于账号端点，不能调能力端点。
- 设备数按套餐 `max_devices` 硬上限；同一 `deviceId` 幂等；同一设备全局只能 active 在一个账号下。
- 限流（§3.3）+ 账号登录已有的失败退避；bind 不往外泄漏"某个邮箱是否存在"之外的信息。
- 设备 secret 只出现一次、只存哈希、可轮换；日志/异常里绝不打印明文
  （`BackendCredentials.__repr__` 已有遮罩）。
- 伪造 `deviceId` 只能给自己账号多占名额，受 `max_devices` + 邀请码/权益 + 限流约束；
  多账号绕过属于账号治理问题（管理面可停用/查设备），不在本接口单独解决。
- 账号页展示的设备列表不含任何凭据；只有 `clientId/设备名/平台/绑定时间/最近活跃/状态`。
- 本机 `/api/account/*` 的写操作（登录/注册/发码/重置/退出/绑定/解绑）登记进
  `app/api.py::_NETWORK_DENIED`：手机/手表即使拿着 API 令牌，也不能改这台电脑登录的是谁、
  绑的是哪台设备；本机面板（回环）不受影响。
- TLS：登录用系统 CA 校验；bind 首次固定服务端证书（TOFU，与 `/v1/pair` 一致），
  之后能力调用只认固定证书；证书变更时明确报错，不静默跳过。
