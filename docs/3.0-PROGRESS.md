### 3.1 待拍板：降级原因词汇表不够用（2026-09-24 落地客户端时发现）

权威词汇（`统一路由` §2）只有十个：`absent / blocked / busy / circuit-open / offline /
open-failed / quota / unsupported / vector-mismatch / error`。但服务端 §6.3 的错误模型里
有几档它**明确要求分开**的：

| 服务端坚持要分开的 | 权威词汇里有对应词吗 |
|---|---|
| `client_busy`（自己占着，重试永远没用） vs `server_busy`（系统忙，该退避重试） | ❌ 只有一个 `busy` |
| `model_loading`（该等一会儿） | ❌ 没有"正在加载"这一档 |
| `unauthorized` / `forbidden`（凭据/权限） | ❌ 没有 `auth`（`能力路由` §5.2 那版**有**，权威版没有） |

**服务端那句话是**："合并成一个码，客户端就只能盲目重试" —— 而权威词汇把它们合并了。

**当前的做法（信息一点没丢，也没擅自扩词汇）**：两套词各管一件事 ——
* `reason`（权威词汇）只回答"**这一轮换不换这个后端**"；
* `code` + `retryable`（本层自己那张表）回答"**客户端该干什么**"
  （`client_busy` → 不重试；`server_busy` → 退避重试）。

**建议拍板**：要么给权威词汇加 `loading` / `server-busy`（`auth` 那档也补回来），
要么在 `统一路由` §2 里写死一句"**词汇表只管候选筛选；行为一律看 `code`**"。
两条都行，但**得选一条** —— 现在这个含糊是四域统一词汇这件事本身漏出来的。
契约由 `tests/test_capabilities_contract.py::ServerCodeCoverageTests` 钉着
（服务端每个错误码都必须有 reason + retry 策略，加了码不跟就红）。

### 2.6 配对与凭据（2026-09-24，客户端侧的"这一步现在真能走了"）

| 文件 | 干什么 | 用例 |
|---|---|---|
| `credentials.py` | 落盘：Windows **DPAPI**（用户作用域）/ POSIX `0600`；`accessToken` **不落盘**；读坏了返回 `None` 不抛 | `tests/test_backend_credentials.py`（19 条，含"直接读文件字节"的断言） |
| `pairing.py` | `pair()` / `fetch_token()` / `ensure_token()` / `unpair()` / `state()`；错误是**一句人话** + 服务端 code | `tests/test_backend_pairing.py`（25 条，分"线路形状"与"真 uvicorn"两层） |

三条设计取舍（都写进了服务端设计 §7.5 ⑥）：

1. **地址与令牌的来源顺序**：地址用设置里填的（显式配置该赢），没填才用配对记下的；
   令牌**手填的优先**（排障时能把凭据那一路整个绕开），手填的**不自动续期**（不知道它的期限）。
   "只配对、什么都没配"是一种能用状态。
2. **401 之后换一次再试一次**：令牌没到点上就被拒（`--rotate-secret` 或时钟偏差），
   再换一个就好。**只试一次** —— 真失效的话再换也换不来，无限重试会把一次失败变成转不出来的循环。
3. **两层的错误模型不合并**：能力调用要的是路由能用的 `reason`（十词表），
   配对是一次性交互、要的是一句人能看懂的话。所以 `pairing.py` 不 import `echo_server.py`
   （反向 import 是有的，方向单一不成环）。

### 2.8 配额（2026-09-24，施工顺序 step 4 的前半）

`server/quota.py` + `clients.daily_audio_minutes` 列 + `--set-quota`。
用完回 **429 `quota_exceeded`**，`Retry-After` 指到**本地明天 0 点**。

四条实现时才定下来的语义（都写进服务端设计 §7.2 那张表，别读成"精确的日额度"）：

1. **先占通道、再记账**（`State.billing`）：被 409/503 顶回去的请求不扣额度；
   通道拿到、模型要开跑了，即使推理失败也扣 —— 那段 GPU 时间真花了。
2. **只看"已经用完"，不预测**：预测量要等解码出秒数，而那时 body 已收完，
   正是要避免的"先落盘再说不行"。边界上允许最后一次略微超额。
3. **`0 = 不限`**，剩余量在响应里**不给字段**（回 -1 或大数，界面都会当成"有额度"）。
4. **`/v1/capabilities` 只给全局上限**（它免凭据，给个人用量等于泄露别人的）；
   客户端自己的剩余量在推理响应的 `quotaRemainingMinutes` 里。

### 2.11 轮换宽限期（2026-09-24）

`--rotate-secret ID --grace-hours 24`：宽限期内**旧 secret 仍可换令牌**，
`/v1/token` 回 `X-Echo-Secret-Rotated: 1` + `X-Echo-Secret-Expires`，客户端写一条 warn 日志
提醒人重新配对；命令行顺带再发一张配对码（运维手上有东西可交）。

**设计里那句话照字面实现不了，已更正**：原文写"服务端回 `X-Echo-Secret-Rotated: 1`
+ **新 secret**，客户端自动落盘"—— 但服务端**只存 `secret_hash`、手上没有新 secret 的明文**
（这正是"secret 只出现这一次"的代价）。所以"自动换新"做不到，只能做成上表那三件事。

**另一条边界写进了命令行的输出**：**宽限期不能用于 secret 泄漏** ——
宽限期内持有旧 secret 的人照样进得来，它换不掉一个已经泄出去的秘密；
它只解决"例行轮换不想打断客户端"。泄漏请用默认轮换（旧 secret 立刻失效、
`prev_*` 一并清空，把之前开的门也关上）。

**两种模式下 `token_version` 都 +1**：宽限期给的是旧 **secret** 一条活路，不是旧**令牌** ——
泄漏时最先想断掉的就是那些已经发出去的 JWT。8 条用例里有 3 条专门钉"它不是什么"。


### 2.12 TLS（2026-09-24）

服务端：`server.tls.certfile` / `keyfile` 两个都填才起 https，**只填一个启动就报错**

### 2.4 管理动作（2026-09-24 补齐到命令行）

`server/main.py` 的命令行入口现在齐了，**运维不需要网页也能干活**：

```bash
--new-client "张三的办公本" --scopes "asr diarize"   # 新建 = 发一张带名字与 scope 的码
--new-pairing-code                                 # 只发码（名字/scope 由对端自报）
--list-clients / --list-codes / --show-client ID   # 看
--revoke ID                                        # 撤销（版本号 +1，立即失效）
--disable ID / --enable ID                          # 禁用（403）/ 启用（原令牌直接能用）
--set-scopes ID --scopes "asr"                      # 改权限，**下一个请求**就生效
--rotate-secret ID                                  # 换 secret；旧令牌与旧 secret 立刻全失效
--set-quota ID --daily-audio-minutes 120            # 每日音频上限（0 = 用全局默认；不清零已用量）
```

三条容易搞错的语义（都已写进用例）：

1. **名字 / scope 跟着码走**，而且**码上带的盖过对端自报的** ——
   自报的能改名，那份清单就不算清点了。为此 `pairing_codes` 加了 `name` / `scopes` 两列。
2. **`--rotate-secret` 同时 bump `token_version`**：v1 没有宽限期，客户端本来就要重新配对，
   所以不给"旧 JWT 还能再用一小时"的窗口（留着反而让人以为轮换没生效）。
3. **`--enable` 之后不需要重新换令牌**（`disabled` 与 `token_version` 是两回事）。

`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，所以加了一段**最小的补列迁移**
（已存在的库自动补上，数据不丢）。再多就得换真正的迁移工具。
