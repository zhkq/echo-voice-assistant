### 3.1 待拍板：降级原因词汇表不够用（2026-09-24 落地客户端时发现）

权威词汇（`统一路由` §2）只有十个：`absent / blocked / busy / circuit-open / offline /
open-failed / quota / unsupported / vector-mismatch / error`。但服务端 §6.3 的错误模型里
有几档它**明确要求分开**的：

| 服务端坚持要分开的 | 权威词汇里有对应词吗 |
|---|---|
| `client_busy`（自己占着，重试永远没用） vs `server_busy`（系统忙，该退避重试） | ❌ 只有一个 `busy` |
| `model_loading`（该等一会儿） | ❌ 没有"正在加载"这一档 |
| `unauthorized` / `forbidden`（凭据/权限） | ❌ 没有 `auth`（`能力路由` §5.2 那版**有**，权威版没有） |

**服务端那句话是**："合并成一个码，客户端就只能盲目重试" —— 而权威词汇把它们合并了。

**当前的做法（信息一点没丢，也没擅自扩词汇）**：两套词各管一件事 ——
* `reason`（权威词汇）只回答"**这一轮换不换这个后端**"；
* `code` + `retryable`（本层自己那张表）回答"**客户端该干什么**"
  （`client_busy` → 不重试；`server_busy` → 退避重试）。

**建议拍板**：要么给权威词汇加 `loading` / `server-busy`（`auth` 那档也补回来），
要么在 `统一路由` §2 里写死一句"**词汇表只管候选筛选；行为一律看 `code`**"。
两条都行，但**得选一条** —— 现在这个含糊是四域统一词汇这件事本身漏出来的。
契约由 `tests/test_capabilities_contract.py::ServerCodeCoverageTests` 钉着
（服务端每个错误码都必须有 reason + retry 策略，加了码不跟就红）。

### 2.6 配对与凭据（2026-09-24，客户端侧的"这一步现在真能走了"）

| 文件 | 干什么 | 用例 |
|---|---|---|

| `pairing.py` | `pair()` / `fetch_token()` / `ensure_token()` / `unpair()` / `state()`；错误是**一句人话** + 服务端 code | `tests/test_backend_pairing.py`（25 条，分"线路形状"与"真 uvicorn"两层） |

三条设计取舍（都写进了服务端设计 §7.5 ⑥）：

1. **地址与令牌的来源顺序**：地址用设置里填的（显式配置该赢），没填才用配对记下的；
   令牌**手填的优先**（排障时能把凭据那一路整个绕开），手填的**不自动续期**（不知道它的期限）。
   "只配对、什么都没配"是一种能用状态。
2. **401 之后换一次再试一次**：令牌没到点上就被拒（`--rotate-secret` 或时钟偏差），
   再换一个就好。**只试一次** —— 真失效的话再换也换不来，无限重试会把一次失败变成转不出来的循环。
3. **两层的错误模型不合并**：能力调用要的是路由能用的 `reason`（十词表），
   配对是一次性交互、要的是一句人能看懂的话。所以 `pairing.py` 不 import `echo_server.py`
   （反向 import 是有的，方向单一不成环）。

3. **`Settings.all()` 把 `hidden` 整行剔掉**，而能力路由这批设置**全是 hidden**；

   `include_hidden`。选了后者：**同一形状的行由同一个函数出**，面板直接复用
   `renderSettingRow`。默认值不变，`/api/settings` 行为一个字没改。
4. **卡片的接线要能用静态断言钉**：门禁里没有浏览器，而这块界面出问题的方式是
   "安静的空白"（id 拼错、忘了调它、卡片被放到没人切过去的页签里）。
   `cap*` / `btnCap*` 那一片的 id 引用、事件绑定、载荷字段名对 `PairBackendIn`
   都钉住了；跨语言那处（JS 送的 key ↔ pydantic 的字段）最容易悄悄断 ——
   字段名写错时 pydantic 用默认值兜住，按钮点下去毫无反应。

**没做**：这块界面的**视觉验证**（无头 Edge 截图，配方见 `docs/面板布局-窄边条.md`）。
门禁不引浏览器，所以这一步得人来做 —— 布局那几条硬约束（`min-width: 0` 之类）
已经被 `test_panel_layout.py` 钉着，但"长得难不难看"它管不了。

### 2.8 配额（2026-09-24，施工顺序 step 4 的前半）

`server/quota.py` + `clients.daily_audio_minutes` 列 + `--set-quota`。
用完回 **429 `quota_exceeded`**，`Retry-After` 指到**本地明天 0 点**。

四条实现时才定下来的语义（都写进服务端设计 §7.2 那张表，别读成"精确的日额度"）：

1. **先占通道、再记账**（`State.billing`）：被 409/503 顶回去的请求不扣额度；
   通道拿到、模型要开跑了，即使推理失败也扣 —— 那段 GPU 时间真花了。
2. **只看"已经用完"，不预测**：预测量要等解码出秒数，而那时 body 已收完，
   正是要避免的"先落盘再说不行"。边界上允许最后一次略微超额。
3. **`0 = 不限`**，剩余量在响应里**不给字段**（回 -1 或大数，界面都会当成"有额度"）。
4. **`/v1/capabilities` 只给全局上限**（它免凭据，给个人用量等于泄露别人的）；
   客户端自己的剩余量在推理响应的 `quotaRemainingMinutes` 里。

### 2.11 轮换宽限期（2026-09-24）

`--rotate-secret ID --grace-hours 24`：宽限期内**旧 secret 仍可换令牌**，
`/v1/token` 回 `X-Echo-Secret-Rotated: 1` + `X-Echo-Secret-Expires`，客户端写一条 warn 日志
提醒人重新配对；命令行顺带再发一张配对码（运维手上有东西可交）。

**设计里那句话照字面实现不了，已更正**：原文写"服务端回 `X-Echo-Secret-Rotated: 1`
+ **新 secret**，客户端自动落盘"—— 但服务端**只存 `secret_hash`、手上没有新 secret 的明文**
（这正是"secret 只出现这一次"的代价）。所以"自动换新"做不到，只能做成上表那三件事。

**另一条边界写进了命令行的输出**：**宽限期不能用于 secret 泄漏** ——
宽限期内持有旧 secret 的人照样进得来，它换不掉一个已经泄出去的秘密；
它只解决"例行轮换不想打断客户端"。泄漏请用默认轮换（旧 secret 立刻失效、
`prev_*` 一并清空，把之前开的门也关上）。

**两种模式下 `token_version` 都 +1**：宽限期给的是旧 **secret** 一条活路，不是旧**令牌** ——
泄漏时最先想断掉的就是那些已经发出去的 JWT。8 条用例里有 3 条专门钉"它不是什么"。


### 2.12 TLS（2026-09-24）

### 2.4 管理动作（2026-09-24 补齐到命令行）

`server/main.py` 的命令行入口现在齐了，**运维不需要网页也能干活**：

```bash
--new-client "张三的办公本" --scopes "asr diarize"   # 新建 = 发一张带名字与 scope 的码
--new-pairing-code                                 # 只发码（名字/scope 由对端自报）
--list-clients / --list-codes / --show-client ID   # 看
--revoke ID                                        # 撤销（版本号 +1，立即失效）
--disable ID / --enable ID                          # 禁用（403）/ 启用（原令牌直接能用）
--set-scopes ID --scopes "asr"                      # 改权限，**下一个请求**就生效
--rotate-secret ID                                  # 换 secret；旧令牌与旧 secret 立刻全失效
--set-quota ID --daily-audio-minutes 120            # 每日音频上限（0 = 用全局默认；不清零已用量）
```

三条容易搞错的语义（都已写进用例）：

1. **名字 / scope 跟着码走**，而且**码上带的盖过对端自报的** ——
   自报的能改名，那份清单就不算清点了。为此 `pairing_codes` 加了 `name` / `scopes` 两列。
2. **`--rotate-secret` 同时 bump `token_version`**：v1 没有宽限期，客户端本来就要重新配对，
   所以不给"旧 JWT 还能再用一小时"的窗口（留着反而让人以为轮换没生效）。
3. **`--enable` 之后不需要重新换令牌**（`disabled` 与 `token_version` 是两回事）。

`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，所以加了一段**最小的补列迁移**
（已存在的库自动补上，数据不丢）。再多就得换真正的迁移工具。

|---|---|---|

**挖出来的八件事**（前四件是"只有真机才会现形"的那一类，后四件是顺着手往下走时
在**同一条链**上撞出来的）：

1. **回环转发把 `context=` 透传给了 `open()`** ——
   `OpenerDirector.open() got an unexpected keyword argument 'context'`，
   现象是"后端明明活着、能力层却一个请求都发不出去"（`capsError`）。
   根因：`context`/`cafile` 是 **`urlopen()` 的形参**（它内部拿去建 `HTTPSHandler`），
   `open()` 不认；而能力层每个请求都带着它（http 时带 `None`），回环那条分支原样透传。
   **为什么 1477 条用例没拦住**：全局转发只在 `app/main.py` 里装，测试里没人一起走
   "装了转发 + 带 context"这条路。补齐：`netlocal._open()` 统一分派（回环把 TLS 形参交给
   opener 承载，外部交回标准库），`tests/test_netlocal.TlsKwargsThroughBypassTests`（5 条，
   含真 https 握手 + 别人的证书必须被拒），并做了一次**变异测试**验证它有牙
   （把 `kwargs.pop` 退回 `kwargs.get` → 4 errors + 1 failure，还原后全绿）。
2. **配对串里的 `fp=` 一直没有出口** —— `pairing.pair(cert_fingerprint=…)` 与它那批
   用例都在，但 `PairBackendIn` 没这个字段、面板也无处可填，于是"防中间人"那一步
   从界面上根本走不到（这正是 §三第一行那种"有没有消费方"的问题，只是发生在参数上）。
   补齐：接口 + `capability_admin.pair()` + 面板（**认整串** `echo://pair?host=…&code=…&fp=…`，
   `parsePairString`）。
3. **服务端打出来的配对串有两处"抄过去连不上"**：不带 scheme（https 后端要 `https://`，
   否则客户端按 http 连）、以及出厂默认监听 `0.0.0.0` 时**把通配地址抄给客户端**。
   现在按"有没有配 TLS"写 scheme；通配地址换成探测到的地址并附一句怎么改。
4. **`capabilityDiarizeBackend` / `capabilityEmbedBackend` 在会议链路上还没有消费方**
   （见 §三第一行）：设置是真的、路由表认识，但会议只对 `asr.text` 问过路由。
   这条**没修**，是 step 4 的正题；写在这里是因为"面板上有的开关"最容易被当成已完成。
5. **门禁里有一条用例依赖"这台机器没配过对"** —— 这台机器真配对一次之后
   `test_not_configured_is_absent_and_says_so` 立刻红了（`refresh()` 返回 True）。
   根因不是一个测试写漏了打桩，而是 `EchoServerClient(creds=False)` **名不副实**：
   注释说"就当本机没配对"，实际只挡住了 `self._creds`，地址照旧从凭据文件读出来。
   现在是**地址也不看凭据**（`_base_url_from_settings(use_credentials=…)`），
   并加了一条用例把两种读法都钉住（默认 = 只配对就能用；`creds=False` = 真的当没配对）。
   —— 与 §2.3 那几条是同一族：**测试读到真实机器状态**，而在开发机上那种状态会变。
6. **退回本机那条路是"静默"的**（读代码时发现，用真机复现）：
   `_capability_asr_session` 里那句"仍走本机引擎 —— 原因：…"只在
   `capabilityEchoServerUrl` 非空时打，而"只配对、什么都没配"从 §2.7 起就是能用状态 →
   那种机器掉了后端**一句话都不留**。改成问 `echo_server.configured()`（设置或配对任一个）。
   真机复现：`privacy=none` → 日志里出现
   `配了能力后端，但本场仍走本机引擎 —— 原因：echo-server(blocked)；-(absent)`，
   这一场确实由本机转出 8 行。
   顺带把**语义**记清楚：配额用完（后端**调用时**才拒）**不会**退回本机 ——
   那一场是 `status=error` 且 0 行，日志写明 `reason=quota code=quota_exceeded`；
   退回本机只发生在**计划阶段**就用不上后端的时候。
7. **详情页会把上一场的路由结论显示成本场的** —— 真机现场抓到：`meta.json` 是同一场会
   反复重转时**覆盖写**的，而 `capability` / `timestampsKinds` 只在走能力层时才写。
   于是"上一次走 ECHO 后端、这一次退回本机"之后，页面上那行还是上一次的
   `转写文本 → ECHO 后端`。现在**没走能力层就把这两项删掉**（`_apply_capability_meta`），
   面板那块随之隐藏 —— `web/meeting.html` 自己那句注释是对的："页签说会走 GPU、
   实际走了本机"这种对不上，比不显示更糟。
   真机验证：`privacy=none` 重转后 `meta.json` 只剩
   `config/durationSeconds/end/segments/start/transcribed`，详情页的 `capability` 变成"没有"。
8. **`--set-quota` 的提示与实测不符**：原话是"上限的**下一个请求**就生效"，实测改完立刻打
   仍然 200，要等**鉴权缓存**（默认 60 s）过期才是 `429 quota_exceeded`
   （`Retry-After: 4648`，指到本地 0 点 ✓）。提示已改成"最多 N 秒后生效（要它马上生效就
   重启服务端）"，并加了一条用例禁止它再说"下一个请求就生效"。

### 2.20 qwen3asr 后端变慢的根因与修复（2026-09-26 凌晨，实测）

用户把后端的 ASR 从 `sensevoice` 换回出货清单的 **qwen3asr**（`server/engines.py:default_specs()` 那套：
`asr-long` / `qwen3-asr-0.6b` / `supports: [asr.text, asr.timestamps]`）后，发现**10 分钟音频要 4~5 分钟**，
且面板没有句级时间戳。排查结论（都有原始数据）：

**① 慢的真因是"整段喂"把显存撑爆，不是模型或设备配错。**
```
整段 600s 直接喂: {'extract_feat': 0.0, 'forward': '255.821', 'batch_size': '1', 'rtf': '1.000'}
                  peak_cuda_mb: 11399 MB  ← 超过这张 8151 MB 的卡 → 溢出到 Windows 共享内存、边换页边算
                  text_len: 35            ← 而且文本是坏的（10 分钟只出 35 个字）
分块 60s + 批 4 : forward 35.1 s / peak 3994 MB / text_len 3531  ← 文本正确、显存减半
```
GPU 侧证据：`device: cuda:0`、`dtype: bf16`、推理中 `util_mean 95.4%` —— **不是"没用上 GPU"**，
所以"换个设备就能快"这条路不存在；能改的是**喂法**。

**② 没有时间戳是接线缺口，不是缺权重。** 日志里那句
`return_time_stamps requires forced_aligner. Skipping timestamps.` 的原因不是权重缺失 ——
`Qwen--Qwen3-ForcedAligner-0.6B`（1.75 GB）**本机 modelscope 缓存与 `models/hub` 里都有**，
是服务端那条加载路径**没把 `forced_aligner` 传进去**。

**③ 修复把参数提到共用位置**（本地与后端同一套，`app/audio/stt.py`）：
```
QWEN3_CHUNK_S = 60.0
QWEN3_BATCH   = 4
_get_qwen3asr(..., forced_aligner=QWEN3_FORCED_ALIGNER)   # 默认接上对齐器
```
顺带解释了用户"单机版当年没这么慢"的印象：**客户端那条路本来就有分块参数，后端的加载路径没有** ——
同一个模型、一边分块一边不分块。

**④ 实测对照（同一段 600 秒真会议音频 `data/meetings/2026-09-20_10-48-26/01.wav`，同一权重、`cuda:0`/`bf16`）**

| 路径 | 墙钟（多次） | RTF | 文本 | 句级时间戳 |
|---|---|---|---|---|
| **本地 A**（客户端 `_qwen3asr_sentences`） | 40.2 / 36.4 / **33.2** s（中位 **36.4**） | 0.055–0.067 | 3508 字 | **205 句 ✓** |
| **后端 B**（`POST /v1/asr`，https+JWT） | 63.8（首次含预热）/ 42.1 / 46.9 / **44.4** s | 0.070–0.078 | 3508 字 | **205 句 ✓** |
| 后端·修复前（整段喂） | **236.6 s** | 0.394 | **35 字（坏的）** | 无 |
| 参照：SenseVoice（同一后端，修复前） | 0.16 s | ~0.003 | 有 | **无**（`supports` 只有 `asr.text`） |

**两条路的产出逐字节相同**（`ab-a.text` 与 `ab-b.text` 的 sha256 前 16 位同为 `84665722809b3919`；
`ab-a.sentences.json` 与 `ab-b.sentences.json` 同为 `6febaf250f175b82`，205 条逐条相同）——
也就是说"本地 vs 后端"如今**只差速度**：后端 **236.6 s → 44.4 s（快 5.3 倍）**，剩下的差距是
19 MB 音频上传 + 服务端落临时文件 + 首次预热。

**⑤ 参数定案**：后端用 `chunk 60 s + batch 4 + forced_aligner`（即出货清单那套 + 共用分块参数）。
`est_vram_mb: 3900` 是**按 24 GB 卡估的占位值**（`engines.py` 自己写明"上线前要用真机压测校准"），
本机 8 GB 卡上峰值约 4 GB，安全；但如果将来与 `diarize`（2600 MB）同时常驻仍需盯。

**⑥ 踩到的两个环境坑（都不是 ECHO 的 bug，但会让人误判）**
* **`schtasks /end` 不会杀子进程**：python 变孤儿继续占着 8900，于是"重启"后仍是**旧进程 + 旧配置** ——
  表现就是"配置改了却没生效"。正确做法：`Get-NetTCPConnection -LocalPort 8900 → OwningProcess → Stop-Process` 再起。
* **PowerShell here-string 里的反引号是转义符**：用它写含反引号的 YAML 注释会被拆行、直接把配置写坏。
  教训：**配置改动一律"Python 写 + `yaml.safe_load` 校验通过才落盘 + 先备份"**（本次靠校验拦住了一次）。



### 2.21 显存记账校准（2026-09-26 上午，dev 配置）

§2.20 那次实测暴露了一个**参数层**的坑：出厂占位值 `est_vram_mb: 3900` 比实测峰值（4.6 GB）小，
而 `vram_budget_mb: 8000` 又比这张卡的**可用**显存大 —— 于是池认为 `asr(3900) + diarize(2600) = 6500`
装得下，两个模型同时常驻，实际整卡跑到 **7.2 / 8.15 GB**，同一段推理从干净的 36–40 s 掉到 **62–74 s**、
GPU 利用率从 54–60% 掉到 **24–32%**（同一机制的小一号复现，见 §2.20）。

改法（只改 `data/backend-dev/server.yaml`，**它是 gitignored 的本机配置**，不进仓库）：
```yaml
server:
  vram_budget_mb: 7000        # was 8000 —— 让它 < asr(4700)+diarize(2600)=7300
models:
  specs:
    - id: asr-long
      est_vram_mb: 4700       # was 3900（出厂占位值）—— 按实测峰值记账
```
依据与权衡：
* `pool.py:311` 的语义是**预算不足时驱逐 LRU 模型**（不是拒绝加载），所以收紧预算会让
  "ASR 与说话人分离"**改为 LRU 串行**，各跑各的干净速度；两者单独都装得下（4700 / 2600 ≤ 7000）。
* **本机不给 ASR 设 `resident: true`**：常驻模型**不可驱逐**（`pool.py:47` 注释"不参与 LRU"），
  8 GB 卡上会让 `diarize` 加载失败。**≥12 GB 的卡上可以反过来**：保留实测 `est_vram_mb` +
  `resident: true`（启动预热，省掉首次请求的 30–60 秒）。
* 只改数值、不插注释 —— 上一版试图顺手插注释时**把 YAML 写坏被校验拦下**（`server:`/`tls:` 结构处），
  这再次说明"**Python 改 + `yaml.safe_load` 校验后才落盘 + 先备份**"这条纪律是必要的。

真实调用表里的对照（`--stats`，同一台后端）：

cli-50aa69   /v1/asr   9 次  音频  90.00 分钟  平均 44460 ms  p95  63724 ms  最慢  74293 ms   ← 修复后（分块+批+对齐器）

### 8.4 2026-09-29 续：后端包的两个档位（含权重）

**决定**（§11.1 第 21 条）：出**两档**，默认仍是纯代码包。

* `scripts/build_backend_kit.py --with-models`（`--models-from <模型根>`，默认 `<repo>/models`）
  才把权重打进包；变体各自声明要哪几棵子树（就是容器里找的那个路径）：
  * **cu118** —— 只要 `sensevoice`（老卡跑不了 qwen3asr，镜像里也没有 pyannote）；
  * **cu126** —— `hub/models--Qwen--Qwen3-ASR-0.6B` + `...ForcedAligner-0.6B` + `sensevoice` + `pyannote`。
* **缺一棵就失败**，不做"能拷多少拷多少"：含权重包的意义是拿来即用，缺子树的表现是
  "装完了某个 spec 一路 `model_failed`"，而那种故障要到同事的机器上才现形。报错会列出
  缺哪几棵、并给出"或者出纯代码包"的出路。
* 包根多一份 **`MODELS-INCLUDED.txt`**：里面是什么 / `ECHO_HOST_MODELS_DIR` 指哪 /
  别把 `models/` 拷进镜像 / 权重坏了不报错所以 `sha256sum -c SHA256SUMS.txt`。
* `is_excluded()` 加了 `allow_models`：**只放行 `models/` 这一层目录名**，
  后缀类排除（`.db`/`.log`/`.pem`…）在权重目录里照旧生效 —— 别把缓存垃圾或密钥打进包。
* `--check` 只比**源码**（`models/**` 是 payload，允许与当前机器不同），并如实标注"含权重"。
  超 2 GB 时出包会提醒一声（不是失败）。
* 用例：`tests/test_build_backend_kit.py::ModelsTierTests`（4 条：默认不带、按变体带对、
  缺子树响亮失败且不留半个包、含权重包不会被 `--check` 误报过期）。
* 本机实测：**cu118 的含权重包能出**；**cu126 的出不来**（本机 `models/hub/` 里没有
  `models--Qwen--Qwen3-ASR-0.6B`）—— 出包脚本响亮失败并指名缺哪一棵，这是设计行为。

### 8.7 2026-09-29 续：「在本机起一个能力后端」批 1a / 1b 落地（进程层）

依据是 `docs/后端容器-一键起-实施方案.md` §5 的拆解（**一次只做一小块**）。本轮做的是
**进程层**：谁是我们起的、怎么起、怎么停、端口被谁占着。配置生成/编排/面板（1c/1d）没动。

**① 1a `app/backend_pid.py`（归属记录：读/判/写）—— 落地时被门禁逮住一个真问题**

* 模块只做四件事：`pid_path()` / `log_paths()`（只给路径，不建文件）/ `read_pid()`（坏文件→`None`，
  永不抛）/ `is_ours_alive()`（**pid 文件在 + 那条 pid 确实活着**才 `True`，陈旧记录顺手清掉
  并在 note 里写明"已清掉"）。本轮补上 `write_pid()` / `clear_pid()`（写属于"起进程"那一半）。
* **门禁逮住的**：第一版把 Windows 探活写成了 `ctypes.windll.kernel32` 直接用，
  `tests/test_path_seam.py::test_no_windows_api_outside_app_platform` **红** ——
  D12 的规矩是"Windows API 只能出现在 `app/platform/<os>/`"，白名单只有 `app/platform/` 与
  `app/paths.py`。这不是形式主义：**`os.kill(pid, 0)` 在 Windows 上是"给那个进程组发 Ctrl+C"**
  （`signal.CTRL_C_EVENT == 0`），探活会把对端打断（实测：被探的 `time.sleep` 子进程当场
  KeyboardInterrupt）—— 所以探活必须是接缝里的原语，业务代码连"自己写"的机会都不该有。
* 修法：接缝新增两个原语 `pid_alive(pid)` / `process_label(pid)`，三平台同名同义
  （Windows = `OpenProcess` + `GetExitCodeProcess` / `QueryFullProcessImageNameW`，权限只要
  `PROCESS_QUERY_LIMITED_INFORMATION`；POSIX = `os.kill(pid, 0)` / `ps -o comm=`），
  并**登记进 `test_path_seam.EveryPlatformImplementsThePrimitives.PRIMITIVES`**
  （否则"Windows 上写好的调用"到 mac 上就是 AttributeError）。`app/backend_pid.py` 改为转发。
* 卫生：`tests/test_backend_pid.py` 在 `setUpModule()` 里把 `_logs_dir` 指到临时目录，
  并有护栏用例钉住"真实 `data/logs/backend.pid` 一个字节都没动"（照 harness 那次事故的教训）。

**② 1b `app/backend_proc.py`（起 / 停 / 端口占用者）**

* `spawn(argv, cwd, env, ports)`：两道闸不通过就**不起**（pid 记录里那条还活着 → "已经有一个在跑"；
  端口被**别人**占着 → 说出占用者是谁）。起的方式：`cwd` 默认后端自己的家、
  `platform.detach_console_kwargs()`（**不是**裸 Popen：uv venv 的 `python.exe` 是 trampoline，
  孙子进程会自己开一个可见控制台）、stdout/stderr **追加到文件**（管道要活读端，ECHO 重启后写满就卡）、
  pid 落盘。**落盘失败不留孤儿**：刚起的那个就地收掉再报错（否则它正占着 8900 而没人认得它）。
* `stop(reason, ports)`：判据只有 `backend_pid.is_ours_alive()`。没有记录 / 记录陈旧 → 如实说
  "没有可停的后端：…陈旧…"并**收手**；有记录 → 杀**整棵进程树**（`kill_process_tree`，trampoline
  的子进程才是真服务）、等它真的退出、清记录、收尸（`_proc.wait()`，否则 GC 会打
  "subprocess N is still running" 的 ResourceWarning）。端口没释放**如实附注但不补刀**
  （那时端口上的已不是记录里那条进程，归属不明 —— 猜着杀正是 harness 那类事故）。
* `port_owner(port)` / `describe_owner()` / `port_check(ports)`：占用的 pid 与 pid 记录**是同一条
  且它确实活着** → 那是我们自己的（"已经在跑，不再起第二个"）；否则是"别人"，只报告不动手。
  **同机 1:1** 这条口径由此有了代码依据。
* 位置：`paths.backend_root()` = `{echoBase}/backend`（老式扁平安装 = `{DATA}/backend`）。
  `BASE_DIRS` 从"设计 §2.2 的六个"变成七个（`backend` 刻意不在 `echo-core` 里：升级代码树不许动
  后端的 `state/`（auth.db、local-pair.json）与 `cache/`）。`pairing.py` 的候选列表一个字没动。

`privacy=none`（「不出机」）是**最保守**的许可，正是最在意隐私的人会选的那一档；而
「帮我起本机后端」起的恰恰是只绑回环那个（§8.8 的 1c）—— 旧口径让他**用不了自己刚装的后端**，
还逼他把许可放宽到「内网」，而许可一放宽，**真正的内网后端也跟着被放行**（方向正好反了）。
实证（真跑 router.plan，只读）：`privacy=none` 允许的来源 = `['local']`；回环客户端
`source=lan` → `picks={}` + `blocked`；改成按地址判之后
`127.0.0.1` / `localhost` / `[::1]` / `127.9.9.9` → `local`（`none` 放行），
`10.100.0.24` 与空地址 → `lan`（`none` 照旧挡住）。

**怎么改的**：`EchoServerClient.source` 从**类属性**变成**按 `base_url` 算的属性** ——
判据只一处（`app/netlocal.is_loopback()`，认 `127.0.0.0/8` 与 IPv6 方括号），
router 一行没动。**故意不给 setter**：赋值只会造出"字段说本机、地址其实是内网"的静默不一致
（要模拟别的档请换 `base_url`；用例钉着这条）。

⚠️ **已知边界（拍板时就摆明了，不是漏掉）**：**地址分不出"本机服务"与"本机隧道"** ——
把远端后端用 `ssh -L 18900:远端:8900` 映射到本机回环会被判成"没出机"（于是 `none` 放行），
而音频其实经隧道去了另一台机器。所以这条假设必须写在**用户看得到的地方**（配套 ②）。

**配套 ①：被许可挡住 ≠ 连不上（原来那句是错的）**
`privacy=none` 时后端**连得上、只是不被允许**，而会议侧记的是 `waiting-backend`，
面板把它翻成「等待能力后端（**连不上**，本步还没有离线队列）」—— 用户于是去查网络/端口/
后端进程，方向全错，而且这个组合**等多久都不会来**。现在：

  **`blocked-by-privacy`** 而不是 `waiting-backend`；分离那一档同理**不再标 `waiting=True`**

### 8.12 2026-09-30 续：批 3 落地（权重就绪 + **三层就绪**，含 L3 真音频自测）

新模块 `app/backend_ready.py`。它存在的**唯一理由**是那个真踩过的坑：
**`/v1/health` 全绿，但每个 `/v1/asr` 都 503 `model_failed`**（权重缺失 / torch 与 torchaudio
的 CUDA ABI 不符，见 `AGENTS.md`）—— 那种状态下面板会说"后端可用"，用户等到开会才发现
一个字都转不出来。所以三层缺一不可：

| 层 | 打什么 | 判据 |
|---|---|---|
| L1 | `GET /v1/health`（免鉴权） | 进程在 |
| L2 | `GET /v1/ready` | 服务端自己说"声明的模型都就绪了"；**503 时把 `failed[]` 原样报出** |
| L3 | `POST /v1/asr` | **一次真音频**：客户端现场生成 1 秒 16k 单声道 wav，走真鉴权真推理，**拿到非空文本**才算过 |
| L4（可选） | `POST /v1/diarize` | **失败不算失败**：老卡本来就"做不了分离"，如实说即可 |

* **L2 没过就不跑 L3**（模型没就绪时那一次必然 503，还会白等一次加载超时），结论里写明"为什么没跑"。
* **200 但文本空 = 没过**；**401/403 且手里没令牌**时那句话要把"被鉴权拒了"与
  "没有可用令牌（还没配对）"**一起**说出来 —— 否则用户会去查模型。
* 三层判据**用真 HTTP 服务端验**（stdlib 桩：health 200 / ready 200 / asr 503），
  有一条用例就叫 `test_a_green_health_is_not_enough`。
* 自测音频用 `wave` 现写（440 Hz + 880 Hz 低幅音调，**不是全零静音** —— 有的实现会把静音判成
  "无有效音频"，那时失败原因会被误读成"后端坏了"）。回环请求走 `app/netlocal`（**不经过系统代理**：
  这台机器上真发生过"代理把 127.0.0.1 的探活劫走 → 服务在跑却显示连不上"）。
* `token` 复用能力层那条已经验证过的路（手填令牌优先 → 本机配对凭据换短期令牌），
  **不自写第二套** —— 自测用的令牌与真实调用用的必须同一枚，否则测不出真问题。

**接进流程与界面**：

* `backend_setup.start(ready_probe=True)`（默认开）在**配对之后**多一步 `ready`：失败就按失败收口，
  并把那句结论原样作为 `message` —— 用户点"起后端"就该当场知道能不能用。
* `POST /api/capability/backend/ready`（面板「就绪自测」按钮）+ `view()["ready"]` 保留**最近一次**结论：
  L3 是一次真推理，面板每 1.5 秒轮询时**不许**现跑（那等于把后端打满），所以只在"一键起"与
  "人点按钮"时跑，其余时候显示上一次结论 + 时间。
* 权重那一格进计划：`renderBackendPlan` 显示 **`模型 N/M 就绪（看的是 <哪一处>）`** + 缺哪几棵
  （批 2 的 `weights`）—— 满足"`models.root` 指空目录 → 面板显示模型 0/3 + 缺哪几个 + 下一步"。

**验收**：`tests/test_backend_ready.py` 10 条（health 绿但 asr 503 → **不过**、三层全绿 → 过、
没应答 → not-running 且不再往下问、ready 503 带 `failed[]` 且不跑 L3、200 空文本不算过、
无令牌与模型故障分开说、L4 失败不算失败、坏 URL 不抛、自测 wav 真的是 16k 单声道 PCM 且非静音）
+ `test_backend_config.py` 3 条（多一步 `ready`、可关、失败即收口）
+ `test_backend_admin.py` 2 条（端点打的是本机那个后端、结论留在 `view()`；炸了也不抛）

**① `scripts/build_offline_pack.py --bundle`（D23 的第二方言）**

**起因（同事实测的一次误读）**：装完在「能力与智能体 → 设备选择」里看到「指令**播报**」
「会议**播报**」两行，以为它们是**麦克风**。查下来两件事叠在一起：

* 那两行其实是**扬声器**（`commandOutputDeviceId` / `meetingOutputDeviceId`）—— 线上实测候选项
  确实全是输出设备（`Dell S2716DG (NVIDIA HD Audio)`、`扬声器 (Realtek(R) Audio)`、
  `Microsoft 声音映射器 - Output`）；麦那三项的候选才是 `麦克风阵列 (Realtek(R) Audio)`、
  `Microsoft 声音映射器 - Input`。
* 会被绕是因为 `SET_SHORT_LABELS` 把"扬声器"三个字省掉了（「指令播报扬声器」→「指令播报」），
  而**三个麦的入口全在另一个页签**（业务配置 → 会议 / 语音指令），于是这张"设备选择"
  看起来只管播放。

**用户口径与最终落点**（"播放有默认路径就够，采集需要分别明确设备"）：

| 常用（3 行） | 高级（4 行） |
|---|---|
| **默认播放** `outputDeviceIds`、**指令采集** `commandInputDeviceId`、**会议采集** `meetingInputDeviceId` | **默认采集** `inputDeviceId`、**指令播放** `commandOutputDeviceId`、**会议播放** `meetingOutputDeviceId`、**计算设备** `device` |

* 卡片标题改「设备选择（采集与播放）」，hint 写清"采集在这张卡、播放默认跟随系统、要按用途覆盖去高级"；
* 短标签换成**对称的一组**（播放 / 采集）—— 旧标签缺的就是这个设备名词；
* 三个麦挪进来后，从「会议」「语音指令」两张卡里**删干净**（每个键恰好一处是硬规矩）；
* **键、取值、回退链、`app/audio/output.py` / `app/audio/stt.py` 的实现一个字节没动**，
  老配置照旧生效；收进高级只是界面让位（不能真删键：删了审计会判 DEAD、老值也没人读）。

**顺带回答用户当天的问题**（"客户端还需要 CUDA 吗，转写转入后端后"）：**默认路径不需要**。
`device` 只被"客户端自己跑引擎"那条路读（`app/audio/stt.py:resolve_device()`：whisper 走
ctranslate2 的 cuda/float16、sensevoice 走 torch 的 `cuda:0`，另有 qwen3asr / pyannote）；
默认档的指令引擎是 **sherpa-onnx（CPU）**，会议转写/分离在 3.0 里交给**能力后端**。
所以它从常用收进了高级，`description` 里也写明"只影响客户端自己跑的引擎"。
