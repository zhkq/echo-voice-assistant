# 跨平台约定（Windows 是主平台）

ECHO 的主平台是 **Windows**：热键、边条（`sidebar/`）、PowerShell 启动链
（`scripts\*.ps1`），都是 Windows 实现。
macOS 支持是**附加**能力，走独立入口，不能反过来影响 Windows。

这份文档把"怎么保证 Windows 一直可用"写成可执行的东西，而不是靠记忆。

## 一、硬约定（有测试兜着）

| # | 约定 | 谁在兜 |
|---|---|---|
| 1 | `app/`、`scripts/` **不得** import `mac` / `hotkey_mac` / `mac_runtime` / `notify_mac` / `tts_mac` | `tests/test_platform_contract.py` |
| 2 | `app/` 里**不得**出现 `darwin` 分支；跨平台差异用 `os.name` 判断 | 同上 |
| 3 | `app/config.py` 的 `DEFAULTS` 必须是 **Windows 值**（Mac 覆盖只能发生在 `mac/` 入口） | 同上 |
| 4 | Windows 上 import `app.main` 后，`sys.modules` 里**不得**出现任何 mac 模块 | 同上（仅 Windows 运行） |
| 5 | mac 入口必须是**注入式**的：`mac/run_mac.py` 在 `import app.main` 之前用 `sys.modules` 注入实现、覆盖 `DEFAULTS` | 同上 |

macOS 支持的正确形态（2026-09-15 合并的 PR #7 就是这个样子）：

```
mac/run_mac.py     ← 唯一入口：先改 DEFAULTS，再把 app.hotkey / app.runtime 换掉，
                     然后才 import app.main；TTS/通知用 monkeypatch 打补丁
mac/*.py           ← Mac 实现（hotkey_mac / mac_runtime / notify_mac / tts_mac）
mac/sidebar/*      ← Swift 原生浮动框（构建产物 mac/sidebar/build/ 已 ignore）
```

## 二、Windows 敏感面（改这些必须附冒烟证据）

`app/hotkey.py`、`app/runtime.py`、`app/audio/recorder.py`、`app/boot.py`、
`sidebar/`、`scripts/*.ps1`、`web/*`

改这些文件时，PR 描述里请附：本机（Windows）跑 `scripts\check-windows.ps1` 的输出，
若是交互/硬件相关（热键、录音、边条），再加一句人工验证结论。

## 三、本地门禁：`scripts\check-windows.ps1`

```powershell
powershell -ExecutionPolicy Bypass -File scripts\check-windows.ps1
powershell ... -Quick    # 只跑 编译 + 导入冒烟 + 平台契约（跳过单测）
powershell ... -Quiet    # 只在失败时输出细节
```

依次做四件事，任一失败即非 0 退出：

1. `python -m compileall -q app mac scripts`
2. **导入冒烟**：`import app.main, app.api, app.db, app.pathutil, app.modelinfo, app.llm_router, app.audio.tts, app.audio.wake, app.netguard`
   —— 专门抓"删了 import 还在用"这类会在真实运行时才炸的错
3. `python -m unittest -q tests.test_platform_contract`（跨平台契约）
4. `python -m unittest discover -s tests -t . -q`（仓库全部单测）
5. 若装了 ruff（`pip install -e .[dev]`，或本机有 uv 时自动回退 `uv tool run ruff`）
   再跑 `ruff check --select F821,E9 app mac scripts` —— 这条专抓"删了 import 还在用"
   （如 `np.sqrt` 少了 `import numpy`），模块级导入冒烟抓不到函数体内的这种错。

**推送前自动跑**：`scripts\gh-push.ps1` 会在 push 之前调用它；确认要跳过时用
`-SkipCheck`（仅在网络/环境异常时用，别当成常态）。

## 四、CI（`.github/workflows/ci.yml`）

| job | 平台 | 装什么 | 跑什么 | 触发 |
|---|---|---|---|---|
| `static` | ubuntu + **windows** + **macos** | ruff + numpy | compileall + `ruff --select F821,E9` + 平台契约测试 + 路径/接缝守卫（`test_path_seam` / `test_paths` / `test_platform_settings`） | 每次 push / PR |
| `macos-audio` | macos | 只有 numpy | 麦克风子进程隔离 + 占用/录音恢复/端口让位/浮动框（`test_mic_reliability` 等 5 个模块） | 每次 push / PR |
| `windows-smoke` | windows | 完整依赖（CPU torch + requirements） | `scripts\check-windows.ps1` 全量 | 手动 + 每周一 |

为什么这么分：契约与静态检查**不需要重依赖**，三平台几秒就绿，能覆盖绝大多数
"改坏 Windows / 改坏 mac"的情况；真实依赖的冒烟很重（数 GB），留给手动/每周，避免每次 PR 等十分钟。

**为什么要有 `macos-audio`（2026-09-20 补）**：麦克风子进程隔离（`app/audio/mic.py`，PR #5）
的测试是 **POSIX-only** 的（`@unittest.skipIf(os.name == "nt", ...)`，因为靠 `socketpair` +
`pass_fds` 传描述符）。在此之前**没有任何 job 跑到它们**：`static` 不选这些模块、
`windows-smoke` 在 Windows 上必跳 —— 于是"这次改动的核心行为"只在作者自己的 Mac 上验过。
该 job 只装 numpy（测试自带 `sounddevice` stub，不碰 PortAudio、不碰真麦克风），
并且**带一道守卫**：该模块在 macOS 上若出现 skip 就报错退出，防止它悄悄退化成空跑。

**为什么 static 也要装 numpy**：`tests/test_paths.py` 的"根跟着配置走"用例要 import 真实运行时
模块（`app.meeting` → `app.audio.recorder`、`app.audio.diarize`），这些模块顶层就 `import numpy`。
不装 numpy 时那两条用例在每个 runner 上都以 `ModuleNotFoundError` 挂掉，static 因此长期全红、
每个 PR 看起来都"不能合并"（2026-09-20 修）。numpy 是小体积通用 wheel，不算"重依赖"。

> 另外，那 3 条平台用例（`test_env_override_wins_and_roots_follow`、
> `test_current_platform_defaults_apply`、`test_existing_database_gets_platform_options_on_reseed`）
> 原先把 **Windows 基准值**写死断言，在 mac/linux runner 上必红；现已改为走平台接缝
> （`config.platform_default` / `platform_options` / `paths._platform_defaults()`）取期望值，
> 三平台一致通过（2026-09-20 修）。**新增平台相关用例时请勿再写死基准值。**
>
> **同一个坑的另一面（2026-09-21）**：用例也**不要读真实的 `data_root`**。
> `tests/test_runtime_hotkey.py` 里 3 条断言 URL 端口的用例只 patch 了 `settings.get`，
> 漏了 `ports.active_port` —— 而 `runtime` 用的是**活动**端口（让位后 `echo-port.txt`
> 才是权威，见 `app/ports.py::active_port` 里的 2026-09-20 事故）。于是它们读到开发机的
> `data/echo-port.txt`（18060），断言 8970 的三条在本地门禁变红；更隐蔽的是另外两条
> 写 18060 的用例**只是碰巧过**（开发机实际端口正好等于那个字面量）—— 那是环境泄漏，
> 不是覆盖。修法：`_patch_active_port()` 显式钉住接缝。
> **凡是要断言 URL / 端口 / 路径，先把对应接缝钉死再断言。**
>
> **临时目录不用自己登记清理（2026-09-21）**：用例里 `tempfile.mkdtemp(prefix="echo-...")`
> 造出来的目录，`tests/__init__.py` 会在进程退出时统一收尾（只删**本次运行新增**的
> `echo-` 目录，不碰运行前就存在的、也不碰文件 —— 文件可能属于同时跑着的别的 ECHO 进程）。
> 此前约 50 处 `mkdtemp` 只有 9 处登记了清理，全量跑一次漏几十个、TEMP 里积到 1120 个。
> 契约由 `tests/test_temp_hygiene.py` 兜着；要换前缀就改
> `tests/__init__.py::TEMP_PREFIXES`，别在别处另写一套判断。

## 五、合并外部 PR 的检查清单

```powershell
# 1) 拉到本地独立分支（不动工作区）
git fetch origin refs/pull/<N>/head:pr-<N>

# 2) 试合并 + 冒烟（临时 worktree，失败就根本别合）
git worktree add --detach ..\echo-merge main
cd ..\echo-merge; git merge --no-ff pr-<N>
powershell -File scripts\check-windows.ps1        # 用主仓的脚本对合并树跑
cd ..\ECHO-public; git worktree remove --force ..\echo-merge

# 3) 真合并（保留合并点，便于整体回滚）
git merge --no-ff pr-<N> -m "Merge PR #<N>: ..."

# 4) 合并后：重启 ECHO 跑一遍真实服务，再 push
powershell -File scripts\gh-push.ps1
```

**合并后的人工冒烟清单**（Windows 面）：

- [ ] 服务能起：`/api/status` 在线、组件无 error
- [ ] 面板：`/`、`/web/app.js`、`/web/meeting.html` 均 200
- [ ] 模型页：`/api/models` 条目正确（pyannote 就绪判定 / 复制命令）
- [ ] 会议：列表 + 详情 + 一次上传转写（`POST /api/stt/transcribe`）
- [ ] 归档：`/api/worklog/status` ready=true，能写进笔记库
- [ ] 交互硬件：录音、热键、边条（改动涉及这些时必须）
- [ ] `data/echo.db` 的 `logs` 表无新增 error

**回滚点**：合并前记下 `git rev-parse main`；出事就
`git revert -m 1 <merge-sha>` 再 push（合并点还在，历史清晰）。

## 六、本地分支/环境小抄

- 解释器：`$env:ECHO_PYTHON`（ASCII junction）→ 回退 `venv\Scripts\python.exe`，见
  `docs/DEPLOY.md` 的路径说明；中文路径下 **必须** 走 junction，否则 qwen3asr 的
  nagisa/dyNet 读不了模型文件。
- 依赖：`pip install -e .[dev]` 可拿到 `pytest` / `ruff`（`tests/test_llm_router.py`
  是 pytest 风格，用 `python -m pytest` 才能跑到它那两条用例）。

## 七、推送网络：DNS 污染与代理回退（2026-09-21）

公司内网把**裸域名** `github.com` 黑洞掉（子域名 `api.github.com` 正常），普通 `git push`
连解析都过不去。`scripts\gh-push.ps1` 按两级处理：

1. **直连**：先探测可连通的 GitHub 前端 IP，用 `http.curloptResolve` 让 git 直连 IP，
   同时 SNI/Host 仍是 `github.com`（TLS 端到端有效）。
2. **回退到本地代理**：这条网络路径经常"半通"——探测返回 401，真推送仍死在
   `Failed to connect to github.com port 443`。此时脚本起 `scripts\gh-proxy.py`
   （CONNECT 隧道：把原始 TCP 导到刚探到的 IP，TLS/SNI/证书不变），再用
   `-c http.proxy=http://127.0.0.1:<port>` 推。**每个候选 IP 起一个、端口随机** ——
   代理在启动那一刻就把 IP 钉死，旧 IP 中途失联只会一直 502，必须换端口重起。

**为什么不直推裸 IP**：GitHub 会 302 回规范域名，git 二次解析又撞 DNS。

**两条路径都会用 `ls-remote` 复核** `origin/<branch> == 本地 HEAD` 才算成功：
这个脚本 2026-09-12 就踩过一次 —— 把 git 的输出当成函数返回值，于是一次 no-op push
（"Everything up-to-date"）被误报成失败。退出码和输出在这条网络上都不适合当唯一依据。

同一套手法在用户级技能 `github-dns-bypass-push` 里另有一份 Node 版 `gh-proxy.js`。
仓库这边用 Python，是因为 ECHO 自己就是 Python 应用、解释器一定在，而 node 不是本仓依赖
（技能里那条 managed node 路径已随版本翻新失效过一次）。

> 推送走 `scripts\gh-push.ps1`（它会先跑第三节的门禁）；只有网络/环境异常时才 `-SkipCheck`。
