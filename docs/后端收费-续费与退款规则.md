# 续费 / 到期 / 退款 / 换套餐规则（2026-11-06 定稿）

> 本文是 `docs/后端收费与自动配对-设计.md` §4.5 的**续费细则补充**。两者冲突时，
> 以本文为准（旧文里“退款立即全额失效”的写法已被本文的“按剩余 paid 订单重算”取代）。
> 目标分支仍是 `integration/billing-vibepay`，**不合 main**。
>
> 一句话版本：**期内续费从到期日顺延；过期续费从支付成功时间起算；试用不叠加；
> 退款按剩余已支付订单重算；第一版只支持同套餐续费；不做自动扣款；
> 支付前必须能看见“支付后预计到期”。**

## 1. 先看别人怎么做（至少三类产品）

调研只提炼**通用机制**，不照抄任何一家平台的文案。下面每条都附了公开可查的官方入口，
方便以后复核；平台规则会变，本文引用的是 2026-11-06 能读到的版本。

### 1.1 内容会员（长视频 / 音乐）

代表：腾讯视频、华为视频连续包月等。

- **有效期叠加**：在会员有效期内续费，月数从**当前到期时间**往后累加；不是从付款日
  重新开始。腾讯视频的客服说明写得最直接：有效期内续费从当前到期时间向后累积，过期后
  重新开通则从开通/续费当天向后累积。
- **过期续费**：从**开通/续费当天**起算，一般不补历史空档。
- **升级/降级**：内容会员通常没有“补差价换档”的公开自助入口，常见做法是买联合会员/
  升级包，或等当前周期结束后再换；平台不会把“剩余天数”折成通用余额。
- **退款**：已充值/已开通的会员通常不支持按天退款；续费后想退，客服一般也是走
  “取消自动续费 + 协商”，而不是系统自动按未使用天数折算。
- **自动续费**：连续包月很常见，但它是**单独订购的选项**，到期前 1–2 天扣费；
  取消入口放在 App/支付渠道里，关掉后当前周期仍然有效。
- 另外，内容会员普遍给**总有效期上限**（例如 3 年 / 10 年），防止一次买几十年；
  本产品当前不需要这个上限，但“不能无限叠加”这个风险要知道。

### 1.2 云资源 / 包年包月

代表：阿里云 ECS 包年包月。

- **提前续费**：续费周期接在**当前到期时间**之后；不会因为提前付款而缩短。
- **过期续费**：云厂商为了保资源，通常给一段“到期未释放”的保留期；保留期内续费，
  到期时间从**原到期时间**顺延（相当于补上停机那几天）。这和内容会员“从支付日重算”
  不同，原因是云资源在保留期内仍然占着机器/磁盘，补费是合理的。
- **升级/降级**：按**剩余时长**折算差价：升级补差价，降配退差额；计算口径是
  “新配置单价 × 剩余时长 − 原配置单价 × 剩余时长”，不是按整月重买。
- **退款**：新购有“5 天无理由”这类窗口；**续费/升级订单通常不适用**。超过窗口的退款
  按“订单实付 − 已消费金额”计算；已生效的续费订单一般不能单独退，只能整台退订。
- **自动续费**：可选开启，到期前扣费；未生效的续费订单可以单独退。

参考：
- 阿里云 ECS《续费常见问题》：
  <https://help.aliyun.com/zh/ecs/renewal-faq>
- 阿里云《退订常见问题》（5 天无理由、升降配差价、未生效续费可退）：
  <https://help.aliyun.com/zh/user-center/support/faq-about-unsubscription>

### 1.3 SaaS / 软件订阅

代表：JetBrains 商业订阅、Notion。

- **升级/降级**：成熟的 SaaS 普遍做 **proration**（按比例折算）：JetBrains 切换方案时，
  把当前订阅未使用的时间折成抵用金，抵扣新方案；Notion 中途升级立即生效并开新账期，
  上一账期剩余时间按比例抵扣。
- **续费**：默认在周期结束时按同一周期自动续订（Notion 明确写了年度/月度自动续订）；
  JetBrains 也提供自动续订开关，可启用/禁用。
- **退款**：不是“随时按天退”。Notion 的政策是月付账单 3 天内、年付账单 30 天内可联系
  客服退款；已使用的积分不退。JetBrains 的“未使用时间抵用金”是换方案时的抵扣，
  不等于现金退款。
- **自动续费**：默认自动续订较常见，但都提供关闭入口；关闭后通常在当前周期结束时生效。
- **共同点**：proration 需要“按剩余价值折算”的完整计价模型，实现和客服成本都高；
  小规模产品第一版往往选择“只允许同档续费/到期后再换”，把歧义关掉。

参考：
- JetBrains《升级或降级商业订阅》（未使用时间折算为抵用金）：
  <https://sales.jetbrains.com/hc/zh-cn/articles/360010274879>
- Notion《管理账单》（中途升级按比例抵扣、自动续订）：
  <https://www.notion.com/zh-cn/help/billing>
- Notion《要求退款》（月付 3 天 / 年付 30 天窗口）：
  <https://www.notion.com/zh-cn/help/refunds>

### 1.4 三类产品的共同规律

1. **绝不缩短已付的时间**：提前续费一定接在当前到期之后；没有平台会把提前付的钱作废。
2. **过期后的起算点分两种**：内容会员从支付日；占用资源的云产品在保留期内从原到期日
   补起。选择哪一种，取决于“过期期间平台是否仍在为用户保留资源”。
3. **换套餐要么完整 proration，要么明确不支持**；最怕的是“看起来支持、算不清”。
4. **退款要能重算，不能拍脑袋减一个周期**；多笔订单叠加时，退其中一笔不能把别的单一起
   废掉。
5. **自动续费必须可见、可关**；默认静默扣款是最容易引发投诉的做法。

## 2. 本产品定稿规则

本产品是“按人授权的实时能力服务”（ASR/TTS/并发），过期后**不占用任何资源**，
也没有云主机那种“保留期”。因此选择内容会员的口径，而不是云产品的补费口径。

| 场景 | 规则 | 理由 |
|---|---|---|
| 期内续费 | 从当前 `paid_until` 顺延 `plan.days` 天；可连续多笔叠加 | 与内容会员一致，提前续费不吃亏 |
| 过期后续费 | 从**支付成功时间**起算，不补过期空档 | 过期期间没有提供服务，补费不合理；避免“过期越久越赚” |
| 试用 | 试用不叠加；试用期内买付费套餐从**支付成功时间**起算 | 试用是赠送权益，不能折现，也不能把付费周期往后推 |
| 连续多笔 | 按支付时间顺序逐笔叠加；每笔 `base = max(paid_at, 上一笔 paid_until)` | 与单笔规则一致，可重放、可测试 |
| 退款 | 管理面手工退款；退成功后把该单标 `refunded`，再按**剩余 `paid` 订单**重放计算；只剩退款单时 `status=refunded`、`paid_until=0` | 不是简单减 30 天；退第二笔不能把第一笔也废掉 |
| 退款后再续费 | 从新的支付成功时间起算（因为已无有效付费权益） | 与“过期后续费”同一条规则 |
| 换套餐 | 第一版**只允许同套餐续费**；有有效付费权益时买不同套餐 → `409 plan_change_unsupported`，文案明确“暂不支持升级/降级” | 不做 proration，避免算不清；等当前周期结束或联系管理员 |
| 无有效付费权益时换套餐 | 允许买任意上架套餐（含过期/退款/试用状态） | 没有重叠时间可“换”，本质是新购 |
| 内部账号 | 不降级、不产生购买；下单直接拒绝 | 内部账号本来就是长期有效，收钱没有意义 |
| 自动续费 | **暂不做自动扣款**；只做手动续费 | 与 issue 约束一致；以后若做，必须显式勾选、可随时取消、到期前提醒 |
| 展示 | 下单/订单详情返回 `projectedPaidUntil`；支付页展示“当前到期 / 本次天数 / 支付后预计到期”；账户权益卡展示一句规则 | 支付前把歧义说清，金额/天数/时间全部来自服务端 |

### 2.1 边界说明

- `plan.days <= 0` 视为“不过期”（内部账号/长期有效），`projectedPaidUntil = 0`，
  前端显示“长期有效”，不显示具体日期。
- 退款只退“钱”，不回收已消费的额度；当日已用的分钟/字符不退回。
- 退款由管理面发起（客户端没有退款入口），与旧设计一致；区别只在权益重算方式。
- 不提供“按未使用天数比例退款”。本产品客单价低，按天折算会引入大量客服争议；
  需要特殊处理时由管理员手工调整权益（`adjust_entitlement`）并留审计。
- 不提供“过期宽限期”。过期即停新请求（402 `entitlement_expired`），但保留账号、配对、
  设备与历史数据；续费后立即恢复。

## 3. 唯一计算口径

后端只允许有一份“这次支付后到期时间”的纯函数，预览和真正入账都调它，保证
`projectedPaidUntil` 与支付后的实际 `paid_until` 一致。

```text
base =
  paid_until                      若 status=active 且 plan_code != trial 且 paid_until > now
  now（支付成功时间）              其它情况（无权益 / 已过期 / 退款后 / 试用中）
paid_until_after = base + plan.days * 86400    （days <= 0 时为 0，表示长期有效）
```

退款重算的口径（与支付路径同一套叠加规则）：

```text
paid_until = 0
for order in 该用户 status=paid 的订单，按 paid_at 升序:
    base = max(order.paid_at, paid_until)
    paid_until = base + plan(order.plan_code).days * 86400
若没有任何剩余 paid 订单:
    status = refunded, paid_until = 0
```

补充：

- 只有 `paid` 订单增加时长；`created / paying / closed / refunded` 一律不增加。
- `trial` 不是订单，不进入上述重放；试用期间付款时 `base = paid_at`。
- 管理面手工 `extend` 仍然从 `max(now, paid_until)` 加天数；它是人工兜底，不参与退款重放。
- 同一订单重复回调只入账一次（既有幂等逻辑不变）。

## 4. 接口字段

### 4.1 订单视图（下单响应、`GET /v1/billing/orders/{id}`、`GET /v1/billing/orders`）

在现有字段之外增加：

| 字段 | 类型 | 含义 |
|---|---|---|
| `planName` | string | 套餐名，服务端读 `plans.name` |
| `days` | int | 本次套餐天数 |
| `currentPaidUntil` | number | 当前权益到期（unix 秒；无权益/长期有效为 0） |
| `renewalDays` | int | 本次续费天数（等于 `days`，单独给 UI 用） |
| `projectedPaidUntil` | number | 这次支付成功后预计到期（unix 秒；0 = 长期有效） |
| `renewalBasis` | string | `paid_until`（期内顺延）/ `payment_time`（从支付时间起算）/ `never_expires`（长期有效） |
| `renewalRule` | string | 一句规则说明，UI 直接显示，不在前端拼文案 |
| `planChangeRule` | string | “暂不支持升级/降级”的说明 |
| `refundRule` | string | 退款重算规则说明 |
| `autoRenew` | bool | 当前恒为 `false`（不做自动扣款） |

已支付订单的 `projectedPaidUntil` 按“该订单及之前所有 paid 订单重放”计算，因此它是
**这笔订单带来的到期时间**，不会因为后来又有新订单而变化；最新一笔 paid 订单的值
与 `entitlement.paidUntil` 一致。

### 4.2 权益摘要（`/v1/billing/entitlement`、`/v1/account/me`、`/v1/capabilities`）

增加同样的 `renewalRule / planChangeRule / refundRule / autoRenew`，以及当前套餐的
`renewalDays`。没有权益时也返回这些规则字段（UI 仍能显示“开通后怎么算”）。

### 4.3 错误

| 场景 | HTTP | code |
|---|---|---|
| 有有效付费权益时买不同套餐 | 409 | `plan_change_unsupported` |
| 内部账号下单 | 409 | `plan_change_unsupported`（detail 说明无需购买） |

这两个分支都在**落订单之前**拒绝，不产生 `closed` 孤儿订单、不调支付网关。

### 4.4 订单列表

`GET /v1/billing/orders` 返回当前用户全部状态的最近订单（`created / paying / paid /
refunded / closed`），不做“只显示 paid”的过滤；账户页按状态分别渲染。

## 5. 页面

- **支付页**（`site/pay.html`）：从订单响应读 `currentPaidUntil / renewalDays /
  projectedPaidUntil / renewalRule`，展示“当前到期”“本次续费”“支付后预计到期”和规则句；
  不写死天数或“支付成功后起算”。
- **账户页**（`site/account.html`）：权益卡显示 `renewalRule`（一句），保留“续费”入口；
  最近订单显示 `已退款 / 已关闭 / 待支付 / 已支付`，不只显示 paid。
- **管理面**（`server/admin.html`）：订单表继续显示全部状态；退款确认文案说明
  “按剩余未退款订单重算权益”，不写“立即失效”。
- **金额 / 天数 / 到期时间全部来自服务端**；前端只做格式化，不参与计算。

## 6. 测试判据

服务端（`tests/test_server_billing.py`）至少覆盖：

- 期内续费两笔叠加（第二笔 `= 第一笔 paid_until + 30d`）；
- 过期后续费从支付时间起算（不补空档）；
- 连续三笔续费；
- 退第二笔：第一笔保留，到期日回到第一笔 + 30d；
- 同时退两笔：`status=refunded`、`paid_until=0`；
- 退款后再续费：从新支付时间起算，权益恢复；
- 试用转月卡：从支付时间起算，不叠加试用；
- 换套餐：有效期内买不同套餐 → 409 `plan_change_unsupported`；同套餐允许；
  过期后买不同套餐允许（按新购）；
- `projectedPaidUntil` 与支付后实际 `paid_until` 一致（容差几秒）；
- 订单列表包含 `refunded / closed`，不是只返回 paid。

页面（`tests/test_vibepay_site.py`）至少覆盖：

- 支付页存在“当前到期 / 本次续费 / 支付后预计到期”的挂载点，且从订单字段渲染；
- 账户权益卡存在规则说明挂载点，且从 `entitlement.renewalRule` 渲染；
- 订单列表状态文案包含已退款/已关闭；
- 页面源码里不出现写死的“支付成功后起算 30 天”。

## 7. 明确不做（本轮）

- 自动扣款 / 连续包月；
- 升级/降级 proration、补差价；
- 按未使用天数退款；
- 过期宽限期；
- 总有效期上限（内容会员那种 3 年/10 年封顶）。
