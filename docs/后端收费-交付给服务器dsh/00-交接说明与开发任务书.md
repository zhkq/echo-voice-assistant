## 3. ⚠️ 一处架构冲突：动工前必须显式处理，不许静默绕过

`server/` 的旧铁律是 **"服务端不存业务数据"**（`store.py` 顶部、`tests/test_server_contract.py` 的多条断言都在钉它）。
而收费功能**必然**要在服务端存 `users / orders / entitlements` 这类"关于人和钱"的数据 —— 这是一次**架构决定**，`01` §4.1 只写了"遵循 `TABLE_WHITELIST` + 迁移惯例"，**没有**写这次评审结论。

> 注：`01` §4.1 引用的"`store.py` 两写卷约束"是**措辞漂移**（`store.py` 里没有"两写卷"这个词）。真实的约束是下面这三条用例。

**会红的护栏与正确改法（改，但必须留下理由）**

| 用例 | 拦什么 | 正确改法 |
|---|---|---|
| `test_only_the_documented_routes_exist` | 路由集合精确相等（现在只有 12 条） | 把 `/v1/account/*`、`/v1/billing/*` **逐条**加进 `allowed`，并在 docstring 里写清"这是收费功能定义的新端点，不是业务内容端点" |
| `test_the_whitelist_here_matches_the_one_in_the_code` | `TABLE_WHITELIST` 与设计 §8.5 精确一致 | 新表加进 `TABLE_WHITELIST` **和**这条断言，并补一行"哪张表、为什么、属于哪一类"的注释 |
| `NoBusinessCouplingTests`（业务词 / 业务 import） | `server/*.py` 里出现 `meeting/command/summary/voiceprint`、import `app.*` | **不许放宽**。写注释时避开这几个词；收费本来也不需要它们 |
| `AuthSchemaTests` 列名黑名单 | `text/transcript/content/body/audio/wav/embedding/vector/speaker_name/meeting/command/summary/voiceprint/prompt/reply` | **不许放宽**。新表只存**管理数据**（谁、买了什么、到什么时候、调用计数），不存**请求内容**（音频、文本、纪要）；列名避开黑名单 |

**分类口径（写进注释，供以后审计）**：`users/orders/entitlements` 属于"**关于谁、买了什么、还有多少**"的**管理数据**，不是请求内容；`alipay_notify.raw` 是**支付回调原文**（对账需要），也不含音频/转写内容。

**这一步需要用户拍板**：如果用户不接受"服务端存用户/订单"，替代方案是把这些表放进独立 SQLite 文件（`billing.db`）并只在 `billing.py` 里持有连接（不动 `store.py` 的白名单）。**默认按上表"扩白名单 + 显式改断言"做**，并在回复里把这条决定单独列出来。

## 4. 任务拆解（按顺序做，每个任务可独立提交）

### T1 表 + 迁移（`server/store.py`）
- 新表：`plans / users / user_devices / invites / authorized_open_ids / scan_sessions / orders / order_events / alipay_notify / entitlements`
- 扩展：`pairing_codes` 加 `user_id`、`kind`（`purchase` / `device-bind`）
- `TABLE_WHITELIST` + `SCHEMA` + 迁移（老库**幂等**补表补列）+ §3 的三处断言同步更新
- **判据**：`python -m unittest tests.test_server_contract` 绿；老库（现网 schema 快照）升级跑两次不炸、不丢 `clients`

### T2 账户（新增 `server/account.py` + 路由）
- `POST /v1/account/register`（邀请码 + 姓名 + 工号；工号唯一）、`login`、`me`、`devices/code`、`devices/unbind`、`logout`
- **userToken 独立域**：JWT claims 至少 `{sub: user_id, typ: "user", ver?}`，**与 client JWT 互不接受**（用例钉：client token 不能调 `/v1/billing/orders`，userToken 不能调 `/v1/asr`）
- 设备绑定码复用 `pairing_codes`（`kind=device-bind`、TTL 10 分钟、一次性），**不新造第二套码**
- **判据**：`tests/test_server_account.py`（邀请码错/过期/超次、工号重复、userToken 过期、设备上限 3、绑定码一次性）

### T3 套餐 / 订单 / 权益（新增 `server/billing.py`）
- `plans` 种子：月卡 `monthly` ¥10 / 30 天 / 每日 120 分钟 / TTS 5 万字符 / 1 QPS / 3 设备 / 并发 1；另 `trial`（7 天）、`internal`（不过期、9999 分钟/日）
- 订单状态机 `created → paying → paid → (refunded|closed)`，**只许前进**；`orderId` 不可猜（`secrets.token_urlsafe`）
- `GET /v1/billing/plans`、`POST /v1/billing/orders`、`GET /v1/billing/orders/{id}`、`POST /v1/billing/orders/{id}/cancel`、`GET /v1/billing/entitlement`
- **金额只从 `plans` 取**，客户端只传 `planCode`；未登录不许建单
- 续费：从 `max(now, paid_until)` 起 +30 天；支付成功**不发码、不换凭据**，直接延 `entitlements`
- **判据**：`tests/test_server_billing.py`（状态机、重复回调幂等、金额篡改被拒、续费叠加、试用/内部账号）

### T4 支付网关（新增 `server/payment.py`）
- 抽象：`create_pay(order) -> {payUrl, qrCode?}`、`verify_notify(headers|form) -> {tradeNo, outTradeNo, amountCents, status, buyerId?}`、`query(order)`、`refund(order)`
- **`MockGateway`**（配置 `payment.provider=mock` 才启用）：提供模拟支付端点（仅 mock 下注册、生产不注册）+ 可编程回调；**Mock 必须能产出与真网关同形的 `notify`**，让 T3/T5 的链路不用改就能切真网关
- `AlipayGateway` 骨架：读 `alipay.appId` / 私钥路径 / 支付宝公钥 / 沙箱开关；**未配置时明确报"支付未配置"**（新错误码，登记进 `errors.py` 与 `server/README.md`），不许崩、不许静默走 mock
- **判据**：mock 下 下单→回调→`paid` 全绿；`provider=mock` 的模拟端点在生产配置（`alipay`）下**不存在**（用例钉）

### T5 权益执行（改 `server/quota.py` + `server/routes.py` + 新 `server/ratelimit.py`）
- 闸门顺序：**配对鉴权 → `client_id → user_id` → 1 QPS → 准入/并发 → 计费**
- ASR：额度上限改读 `entitlements.daily_audio_minutes`；无权益 → 402；到期 → 402 `entitlement_expired`
- TTS：按字符记日额度（默认 5 万），超额 402/429（**按设计选一种并写清**）；TTS 不受并发闸门，只受 1 QPS
- 1 QPS：按 `user_id` 令牌桶（突发 1），多设备共用；超限 `429 rate_limited` + `Retry-After: 1`
- 并发：`plans.max_concurrent`（默认 1）**按 user**；第二台设备 → `409 client_busy` + detail "另一台设备正在转写"
- 日额度也按 user 累加（`client_id → user_id` 后再累加），避免换机重刷
- 设备被解绑/超限 → **复用现有禁用客户端路径**（401/403），不新造
- **判据**：沿用 `tests/test_server_contract.py::AdmissionTests` 的形状，补 user 级用例；`tests/test_capabilities_contract.py` 不红

### T6 `/v1/capabilities` 附权益摘要
- 新增 `entitlement: {plan, paidUntil, dailyMinutes, ttsCharsLeft, qps, maxDevices, maxConcurrent, devices, expiringSoon}`；**不破坏现有字段**；billing 未启用时该字段不出现或为 `null`
- **判据**：现有 capabilities 用例照绿；新增"到期前 7/3/1 天 `expiringSoon=true`"用例

### T7 管理面
- 页签/接口：`plans` 增删改、`orders` 列表+筛选、`refund`（二次确认 + 审计 + 调网关退款 + **立即失效权益**）、`entitlements` 手工调整（延长/冻结/设 `internal`）、`users` 列表/详情、`invites` 生成/作废、`reset-devices`、`summary`
- **必须走 `admin.py` 的七道闸**（尤其失败也要写 `admin_audit`）
- **判据**：`tests/test_admin_console.py` 形状一致；未带 CSRF/标志头的写请求 400/403；退款后权益立即失效

### T8 测试 + 文档
- 新增 `tests/test_server_account.py`、`tests/test_server_billing.py`、`tests/test_capability_billing_client.py`（**客户端不上，这个可以留空/跳过或只写契约级**）
- `server/README.md` 补一节：怎么开 mock、怎么跑收费自测；`server/echo-server.example.yaml` 补配置段（`billing.enabled`、`payment.provider`、`alipay.*`、`trial.enabled`、`invite.required`、`billing.daily_*` 默认值）
- **判据**：全量跑绿（见 §8）

## 5. 关键契约（从 `01` 摘出，别漏）

### 5.1 数据表
`plans`（`code` PK、`price_cents`、`days`、`daily_audio_minutes`、`tts_chars`、`qps`、`max_devices`、`max_concurrent`、`active`、`sort`）／
`users`（`alipay_open_id`、`name`、`employee_no` 唯一、`phone`、`status`）／
`user_devices`（`user_id`、`client_id`、`device_name`、`bound_at`、`last_seen`、`status`）／
`invites`（`code` PK、`max_uses`、`used`、`expires_at`、`created_by`、`note`）／
`orders`（`order_id` PK、`plan_code`、`amount_cents`、`status`、`user_id`、`client_id`、`pairing_code_id`、`alipay_trade_no`、`created_at`、`paid_at`、`expires_at`、`meta`）／
`order_events`／`alipay_notify`（`trade_no` **唯一索引**做幂等）／
`entitlements`（`user_id` PK、`plan_code`、`paid_until`、额度列、`status`、`order_id`）／
`authorized_open_ids`、`scan_sessions`（Phase 4 用，**建表可留、逻辑不做**）

### 5.2 错误码（新增，命名进 `errors.py`）
| 场景 | 状态 | code |
|---|---|---|
| 套餐到期 | 402 | `entitlement_expired` |
| 未开通/无权益 | 402 | 设计只写了"未开通"分支、**没给 code** → 建议 `entitlement_missing`（客户端按钮不同：去开通 vs 去续费），实现后列入"待确认" |
| 当日额度用完 | 429 | `quota_exceeded`（**保留现有语义**） |
| 1 QPS 超速 | 429 | `rate_limited` + `Retry-After: 1`（复用现有 code） |
| 同 user 另一台设备在转写 | 409 | `client_busy`（复用，detail 写明原因） |
| 支付未配置 | 503 | 新增（例如 `payment_unconfigured`），**不许让服务起不来** |

### 5.3 幂等 / 安全
- `alipay_notify.trade_no` 唯一；同一订单**只发一张码**（重复请求返回同一张；码过期才重发且**旧码作废**）
- 回调必须验签 + 校验 `out_trade_no`/金额/卖家 + `trade_status` 白名单
- 应用私钥只在服务端（env 或挂载文件），**绝不进客户端、仓库、日志、测试夹具**
- 管理面退款/改套餐写 `admin_audit`

### 5.4 时间
- "每日 0 点恢复"按 **`Asia/Shanghai`**；库里的时间表示**照 `store.py` 现有表**（动手前先看一行现有 `created_at` 存什么），别混两套

### 5.5 时序（三条，照 `01` §4.3 画）
A 新用户：注册 → 建单 → 付款 → notify → `paid` + 发 `echo://pair` 码 → 客户端轮询拿 `pairUrl` → 本机 `/api/capability/pair` 兑换 → 记 `user_devices` → 权益挂 user
B 续费：登录态建单 → 付款 → notify → 延长 `entitlements`（**不发码**）
C 换机：登录 → `devices/code` → 兑换绑定码 → 继承权益、不重复收费（超 3 台先解绑）
