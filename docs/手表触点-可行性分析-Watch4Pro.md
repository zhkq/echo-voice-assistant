# ECHO 手表触点（HUAWEI WATCH 4 Pro）可行性分析

> 起因（用户 2026-10-09 原话）：
> *"手机端暂时不考虑唤醒，你再分析一下，我的华为手表有可能作为触点吗，watch 4 pro"*
>
> 本文是**可行性分析**，不是设计承诺。每条事实都标了**可靠度**（官方 / 社区 / 未核实），
> 因为"华为手表能不能装第三方应用、能不能录麦克风"这类问题极容易想当然。
> 姊妹文档：[手机触点-App设计.md](手机触点-App设计.md)（那份是 Android APK 的设计）。

---

## 0. 结论（先给答案）

**能，但手表不该按"第二块屏幕"来做，应该按"手腕上的一个震动 + 一句话"来做。**

三档排期，性价比从高到低：

| 档 | 一句话 | 成本 | 什么时候做 |
|---|---|---|---|
| **A 只做输出** | ECHO → 手机通知 → 华为运动健康镜像到手表（震动 + 文字） | **手表端 0 行代码** | 手机触点的阶段 5 顺手做 |
| **B 手机借道** | 手机 APK 用 Wear Engine 用手表的能力（若"音频"能力存在，则**仍 0 行手表代码**） | 中（要申请接入） | 核实 §5-3/4 之后 |
| **C 手表原生应用** | 鸿蒙穿戴应用（ArkTS）：录音 → HTTP → 放音 | 高（新技能栈 + 真机调试 + 上架审核） | 兜底，最后做 |

**两条决定性未知**（都不在本文结论里，必须你自己验）：Wear Engine 的**能力清单**、
Watch 4 Pro 的**真机 API 版本**。§5 给了 10 分钟能跑完的清单。

## 1. 手表相对手机，"触点"这件事上差在哪

| 维度 | 手机（APK 设计里那个触点） | WATCH 4 Pro |
|---|---|---|
| 拿取成本 | 要掏出来、点亮 | **抬腕即用**（这是手表唯一不可替代的价值） |
| 输出 | 屏大，能看长文 | 屏小 → 只能"看一眼摘要" + **震动** |
| 输入 | 打字 / 按住说话 | 基本只有**语音**（+ 预设短回复） |
| 麦克风 / 扬声器 | 有，且第三方应用随便用 | **有**，第三方应用可用（见 §3-C 证据） |
| 摄像头 / 扫码 | 有 → 手机设计的"扫码配对"成立 | **没有** → §4-1 必须另设配对路径 |
| 联网 | wifi / 流量 | **eSIM + WLAN**，手表应用可独立联网 |
| 常驻监听 | 前台服务可做（耗电可接受） | **不可行**（续航会崩）→ 只能"点一下说一句" |
| 凭据保护 | Android Keystore | **没有对等物**，且"戴着就走" → 丢失风险更高 |
| 开发门槛 | 侧载 APK 即可 | 手表应用要 AGC 调试证书 + 设备 UDID，**上架还要过审** |

> 一句话：**手表拿不走手机的任何一件事，它只多给两件：震动、抬腕即说。**
> 所以手表触点的验收标准不应该是"能替代手机"，而是"**不用掏手机也能完成一轮**"。

## 2. 按手机设计的"四件事"逐条对表

手机设计 §1 把触点钉成四件事（收 / 放 / 显 / 连），手表逐条过一遍：

| 四件事 | 手表上怎么做 | 障碍 |
|---|---|---|
| **显**（显示这一轮文字） | 通知镜像 / Wear Engine 模板化通知 | 屏小 → 只能放**摘要**，长回复放不下（§4-4） |
| **放**（把回话念出来） | 路径 C 才需要：手表应用 `AVPlayer` 播 ECHO 的音频 | 语音播报在公共场合奇怪；"念"的价值主要是**车里** |
| **收**（录音） | 路径 B（借道 Wear Engine，若支持）或路径 C（手表应用 `AudioCapturer`） | **成本全在这一格**：要么申请接入，要么写手表应用 |
| **连**（可达 + 身份 + 重试） | 手表应用直连局域网 ECHO（eSIM/WLAN） | 配对不能扫码（§4-1）；重试逻辑要在表上重写一遍 |

**震动**是手机设计里**没有**的一格，而它恰好是手表最便宜、最有效的一格 —— 建议单独作为一条验收：
"ECHO 答完 / 需要确认时，手腕震一下"。

## 3. 三条路径

### 路径 A：只做输出（**今天就能用，推荐先拿这一档**）

```
ECHO 主机 → 手机 APK 发一条通知 → 华为运动健康把手机通知同步到手表 → 震动 + 文字
```

* **证据（官方）**：华为官网支持页有"WATCH 4 系列手表弦月窗无法同步手机消息"这类条目，
  说明**手机消息同步到手表**是该系列的既有能力；
  [华为 AI 消息随身功能适配情况](https://www.ithome.com/0/815/410.htm) 报道的适配机型包含 WATCH 4。
* **证据（官方）**：WATCH 4 系列**支持第三方手表应用**（
  [Watch3/4 系列应用市场支持的手表应用](https://consumer.huawei.com/cn/support/content/zh-cn15876316/)，
  适用产品明确列出 `HUAWEI WATCH 4 Pro`，名单首项是支付宝）。
* **做法**：手机 APK 的**阶段 5（体验期）**加一个通知渠道，通知标题/正文放 ECHO 回话的 `brief`。
  **手表端 0 行代码。**
* **判据**：手机发一条通知 → 手表 3 秒内震动并显示；手机息屏也能收到。
* **做不到**：**回话**。手表上只能"看"，把语音送回 ECHO 需要路径 B/C
  （第三方应用通知的"快捷回复/语音回复"在华为手表上是否可用，**我没能核实** —— 别默认能用）。

### 路径 B：手机 App 借 Wear Engine 用手表的能力（**可能完全不用写手表应用**）

* **是什么**：Wear Engine Kit 是华为官方"**手机侧应用** → 穿戴设备"的通道；
  官方文档有**Android 手机侧**的分支（
  [穿戴设备模板化通知 - Android 手机侧应用开发](https://developer.huawei.com/consumer/cn/doc/connectivity-guides/wearable-device-notification-0000001057412109)），
  说明**不要求手机是鸿蒙** —— 正好对上 ECHO 的 Android APK 计划。
* **已知能力**：设备管理、**模板化通知**（手机应用向手表发通知）；
  接入需走[申请接入 Wear Engine 服务](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/wearengine_apply)。
* ⚠️ **未核实但决定性**：Wear Engine 是否有**音频**能力（手机侧取手表麦克风 / 往手表扬声器播）。
  若有 → 手机 APK 里加一条"从手表收音"的通道，**0 行手表代码**就拿到双向触点（**最优路径**）。
* **门槛**：申请接入有资质要求；**个人开发者能否申请，我没能核实**。
* **核实位置**：开发者联盟 → 申请接入 Wear Engine 服务 → 页面上的**能力勾选项**（§5-3）。

### 路径 C：真正的鸿蒙手表应用（ArkTS，成本最高）

* **技术确定可行（官方样例）**：华为官方的穿戴样例组织里有
  [`Explore-In-HMOS-Wearable/audio-recorder`](https://github.com/Explore-In-HMOS-Wearable/audio-recorder)
  —— *"Record PCM/WAV microphone audio and play it with AVPlayer on HarmonyOS watches using AudioCapturer"*，
  另有同类样例 `how-to-build-voice-memo-recorder`。
  → **第三方手表应用能录麦克风、能放音**（这解决了"手表是不是只能读传感器"的疑问）。
* **联网可行（官方支持页）**：手表应用"完全不依赖手机同步时，可以使用 **eSIM/WLAN 联网独立使用**"
  （同上应用市场支持页的说明）→ 手表应用可以自己发 HTTP 到局域网 ECHO。
* **代价**：ArkTS/ArkUI 全新技能栈；真机调试要 AGC 调试证书 + 设备 UDID；
  分发要**过手表应用市场审核**（自用也绕不开"怎么装进去"这道门）。
* ⚠️ **Watch 4 Pro 的机型风险（本路径最大的坑）**：它是 2023 年机型，系统停在
  **HarmonyOS 4.x** —— 检索到多条社区提问（
  ["WATCH4Pro 至今没有升级 5.0/6.0 的计划"](https://developer.huawei.com/consumer/cn/forum/topic/0204208340721916134?fid=0102767778349500527)、
  ["Watch 4 Pro 后续有机会升级到鸿蒙 5/6/7 吗"](https://developer.huawei.com/consumer/cn/forum/topic/0208224510106319050?fid=0109140870620153026)），
  以及社区先例 **["GT3 是鸿蒙 4.0 却不支持 API 10"](https://developer.huawei.com/consumer/cn/forum/topic/0201224675730732088?fid=0104164651529951067)**。
  **教训是"设备系统版本 ≠ SDK/API 版本"** → 动手前必须先查真机 API 版本，
  否则会走到"写完装不上"，而那种错的现场表现往往不是"版本不对"（§5-1）。
* **结论**：只有当 A/B 都不够用（比如必须**脱离手机用 eSIM**）时才做。

## 4. 手表对 ECHO 侧设计的**连带影响**（这部分是本次分析真正要拿出来的东西）

手机设计不是"不用改"，手表给它提了 5 条要求：

1. **配对不能靠扫码。** 手机设计 §3 新增 1（`POST /api/pair/phone`）出的是二维码，
   而 Watch 4 Pro **没有摄像头** → 必须补一条"无摄像头"的配对形态：
   * **形态 1（推荐）**：手表显示/输入 **6 位一次性码** 向 ECHO 换 token ——
     与能力后端 `POST /v1/pair` 同一形态（那个接口本来就是"一次性码 → clientId/secret"）；
   * **形态 2**：**手机代传** —— 手机已配对，把"手表要用的地址 + 凭据"通过 Wear Engine 传给手表。
   > ✅ **2026-10-09：形态 1 已落地**，而且它顺手把"二维码 = 一把无寿命凭据"那个问题一起解决了：
   > `POST /api/pair/phone` 现在发 **6 位一次性码**（5 分钟寿命 / 用掉即删 / 错 20 次锁 5 分钟，
   > `app/phone_pair.py`），设备拿码去 `POST /api/pair/phone/claim` 才换到令牌；
   > 面板上的二维码**因此不必立刻做**（推迟到手机 App 那一期）。
   > 手机设计 §3 / §4 已按这个形态改写（含"为什么不把令牌放进二维码"的取舍）。
2. **"手机代传"会放权，所以 §6-A 必须先做。** 现在 `api_keys.scopes` **存了但从不校验**
   （手机设计 §6），手机 token 等于全权；让手机有权给手表发钥匙 = 授权面扩大。
   → **手表这条路反过来证明：手机设计的"白名单收窄"不是可选项，是前置条件。**
   > ⚠️ 2026-10-09 现状：本轮**没有**做"手机代传"（形态 2），所以这条前置条件**还没被触发**；
   > 已落地的只是**按发起点**判的那张拒收清单（网上来的令牌不能停服/重启/删会议/改设置，
   > 含批量版 `clean-short` 与 `settings/reset`）。**真做形态 2 之前，§6-A 的完整白名单必须先做。**
3. **手表凭据的保护等级天生更低**（没有 Keystore 对等物、戴着就走、丢失风险高）
   → 手表 token 必须**更窄 + 有期限**。而 `api_keys` 现在**没有过期时间**（`expiresAt` 空着）。
   → 手表提出一个**新增要求**：`api_keys` 加过期时间 + 真正按 scopes 判权（也就是手机设计 §6-B 提前做）。
   > 2026-10-09：仍未做。配对时已经给设备令牌写上 `scopes=["device"]`，那是给这一步留的锚点。
4. **播报要短。** 手机上可以念长文，手表上只该要 `brief`
   → `POST /api/tts`（手机设计 §3 新增 3）要支持"短播报"这个用法，别把长文本丢给手表。
5. **手表不能常驻听。** 手机设计 §7 那个可选 `ListenService`（持续听）在手表上**没有对应物**，
   手表交互固定为"点一下说一句"。→ **手机端设计不用为手表改。**
   （另：用户已定**手机端暂不做唤醒词**，手表端同理不做。）

## 5. 动手前的核实清单（**都是能自己跑的判据**，别跳过）

> **2026-10-09：用户已注册华为个人开发者账号**（入口
> [HarmonyOS 穿戴应用开发入门](https://developer.huawei.com/consumer/cn/multidevice/wearables/get-started/)）。
> 于是 #3 / #4 从"能不能查到"变成"**在你账号里点两下就有答案**"；
> #1 还多出一格**新的、更要紧的判据：应用形态**（见下表，这是本次新查出来的）。

| # | 要核实的 | 怎么验（都能在 10 分钟内做完） | 不过会怎样 |
|---|---|---|---|
| **1** | **应用形态**：Watch 4 Pro 走 **ArkTS 智能穿戴**（`wearable`）还是 **轻量级穿戴**（`Lite Wearable`，JS/FA） | ① 手表 `设置 → 关于 → 版本号`；② AGC 里**创建调试证书**时看设备类型给的是**智能手表**还是**轻量级穿戴** —— **能建哪种，你就能开发哪种** | 决定路径 C **怎么写**。两套 API 完全不通用：ArkTS 那套才有 `AudioCapturer`/`AVPlayer`；Lite Wearable 是另一套 JS 媒体 API，"能不能录音"要重新查。**社区证据（2023–2025，未官方确认）**：Watch 3/4 系列是 HarmonyOS 3.1/4.x，当年社区口径是"手表还不支持 ArkTS"，调试证书建的是 **Lite Wearable**；ArkTS 穿戴属于 HarmonyOS 5/6 那一代新表 |
| **1b** | 真机 **API 版本** | DevEco 连真机看 API 档位 | 社区先例：**系统版本 ≠ API 版本**（GT3 是鸿蒙 4.0 却不支持 API 10）——不查会"写完装不上"，而现场报错通常**不是**"版本不对" |
| 2 | 手表能否装第三方应用 | 手表自带应用市场搜"支付宝"（官方名单说支持），装一个 | 装不上 = 路径 C 直接死 |
| **3** | Wear Engine 有没有**音频**能力 | 开发者联盟 → **申请接入 Wear Engine 服务** → 看能力清单勾选项（登录后可见） | **分水岭**：决定路径 B 能不能"零手表代码" |
| 4 | 个人开发者的**资质**（接入 Wear Engine / 上架穿戴应用） | 同上一页的资质要求 + 实名认证状态 | 决定 B/C 是不是只剩"过不了审" |
| 5 | 手机通知能否镜像到手表 | 手机随便发一条通知，看手表是否震动显示 | 路径 A 死 → 手表暂时没路可走 |
| 6 | 手表与 ECHO 同网可达 | 手表连家里 wifi，访问 PC 的 IP | 不可达 → 只能靠手机中转（B 档） |
| **7** | 能不能**装进去**（自用，不上架） | `hdc shell bm get --udid` 取手表 UDID → 加进 AGC **调试证书的设备白名单** → DevEco `File → Project Structure → Signing Configs` 配签名 → Run 到手表 | 装不进去 = 路径 C 就只能靠上架过审 |

> 判据纪律照仓库惯例：**别信"应该可以"**。第 3 条是"**要不要**写手表应用"的分水岭，
> 第 1 条是"**写哪一种**"的分水岭（选错等于白写）。

## 6. 建议排期（**不改手机触点的排期**，只在后面挂两条）

* **手机触点阶段 0–4 照原计划做** —— 手表**不阻塞**它们（手表要调的是同一套接口，
  先有接口才有手表，顺序天然如此）。
* **阶段 5（体验期）顺手加通知** → 手表自动获得 **A 档**（震动 + 摘要），**手表端 0 行代码**。
* 阶段 5 之后按 §5 的结果二选一：**B 档优先**（成本低、可能零手表代码）→ **C 档兜底**。

> **2026-10-09 补充（用户已注册个人开发者账号之后）**：账号解锁的是"**能不能做**"这三件 ——
> 建调试证书（含 UDID 白名单）、申请 Wear Engine 接入、走审核上架；
> 它**不解锁**"哪种应用形态"和"有没有音频能力"（那两条只能去账号里 / 手表上看）。
>
> 而且这次新查到的**形态风险会改变 C 档的形状**：若 Watch 4 Pro 属 **Lite Wearable**，
> 则 §3-C 引的 ArkTS 证据（`AudioCapturer`/`AVPlayer` 官方样例）**不适用** ——
> 得先确认 Lite Wearable 那套 JS API 能不能录麦克风。若不能，C 档就只剩"看一眼 + 震动"，
> 于是**B 档（Wear Engine）的价值上升**。
> 建议核实顺序因此调整为：**3（音频能力，分水岭）→ 1（应用形态）→ 2/7（能不能装进去）**。

**不做的**（与手机设计 §9 同一口径）：
* 不做手表上的历史/设置/模型管理（管理仍在主机面板）；
* 不做手表端唤醒词、不做手表常驻监听；
* 不把 ECHO 暴露到公网（手表用 eSIM 也不改变这条）；
* **不为了手表去改手机侧的交互模型**（手表是增量，不是替代）。
