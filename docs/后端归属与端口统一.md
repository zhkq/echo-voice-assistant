# 后端归属与端口统一（2026-10-06）

> 起因：用户报"开发版重启后，后端显示**待启动**，但点上面的箭头能打开后端管理页面并登录，
> 当时会议转写确实失败了"。查下去发现这不是显示问题 —— 是一整条**归属链**缺了判据。

## 1. 现场与真因

**现象**（三条同时成立，看起来互相矛盾）：

| 看到什么 | 用户的理解 |
|---|---|
| 面板底部「后端：待启动」 | 后端没起来 |
| 点 ↗ 能打开 8901 的管理页并登录 | 后端明明在 |
| 会议转写失败，提示"等待能力后端（连不上）" | 后端连不上 |

**真相**：8900/8901 上跑的是**稳定版那棵树的后端**，而面板是 dev 的。

```
dev 看来：echo-server  ready=False  code=unauthorized
          后端凭据不能用：客户端不认识 —— 需要重新配对
```

`main -m server.main --config C:\echo-dev\data\backend\server.yaml` —— 端口通、管理页能进
（**凭据同源**），但那个后端的 `clients` 表里没有 dev 客户端 → 一律 `unauthorized`。

**所以三条现象的解释是**：后端确实"没起来"（**dev 那份没起来**）；能登录的那台是**别人的**；
转写失败的原因是**凭据不属于那台后端**，而不是连不上。

**为什么会出现这个现场**：开发版与稳定版轮流跑、**共用 8900/8901**，而切实例时
**后端不会跟着换**。仓库里 7 个启停/切换脚本，`grep backend` **一个都没有**。

## 2. 三条原则（本次据此收敛）

1. **端口统一，安装位置区分**：两棵树轮流跑，所以**共用同一套端口与相对路径**，
   只有安装位置不同。谁在跑由 `echo.pid` / 安装根判定，**不许靠端口区分**。
2. **归属由命令行证明**：判断"这个后端/实例属于哪棵树"**只能**看进程命令行的
   `-m server.main --config <目录>`（后端）与 `-m app.main` + 代码路径（ECHO 实例）。
   这正是 `AGENTS.md` 那条"唯一可靠判据"，桌面工具包 `Get-BackendPid` 也是这么写的。
3. **配对不重做**：本机客户端与后端的配对在安装/首次启动时完成，凭据落在
   `<数据根>/backend.json`。换后端**不需要用户重新配对** —— 只要起的是这棵树自己的后端，
   它的配对库里本就有这个客户端（实测 `cli-aa07c1` 在 dev 后端库里，`clients` 表 13→13 不变）。

## 3. 端口统一做了什么

| 项 | 统一前 | 统一后 |
|---|---|---|
| ECHO 面板端口 | dev **18060** / 稳定版 8970 | **两棵树都 8970**（出厂默认值） |
| 持久环境变量 `ECHO_PORT` | User 级 = `18060`（**对两棵树都生效**，压过稳定版自己的 `echo-port.txt`） | **已删除**（User/Machine 都空） |
| dev 库 `serverPort` | 18060（越轨覆盖值） | 8970（= 出厂默认） |
| `harness_proc.RESERVED_PORTS` | `{43120, 18060}` 写死 | `reserved_ports()` 运行时算（`[8970, 43120]`） |
| 桌面快捷方式 | 开发版 18060 / 稳定版 8970 | 两者都 8970 |
| 桌面工具包 `$Instances[].Port` | dev 18060 | 两者都 8970（`Get-Port` 仍优先 `echo-port.txt`） |
| 边条（rail） | 进程里缓存 `--url=…:18060` | 重启后指向 8970 |
| **端口由谁决定** | 环境变量 `ECHO_PORT` **优先** | **配置 `serverPort` 优先**（见 §3.3） |

### 3.3 端口解析顺序（已收敛到唯一一处）

**`scripts/echo-port.py` 是唯一解析器**，四个脚本（`start` / `startup` / `restart-echo` /
`launch-desktop`）都调它，`install-all.ps1` 例外（它是安装器，故意用 `ECHO_PORT` 钉死
自己装的那棵）。判定顺序：

```
1. 配置 serverPort        （库 <数据根>/echo.db 的 settings 表）—— 用户的显式选择，权威
2. echo-port.txt          （ECHO 启动时写的**实际**端口；首选被占/落保留段时会让位并重写）
3. ECHO_PORT 环境变量      —— **仅兜底**（库与端口文件都读不到时）
4. 8970                   —— 出厂默认
```

**为什么把 `ECHO_PORT` 从第一降到第三**（用户 2026-10-06 报的现场）：
面板上的**重启按钮**走 `restart-echo.ps1`，而它原来把环境变量排第一。那个变量会从
**任何父进程**继承进来（终端、计划任务、开发机上的持久用户变量），可能指着**另一棵树**
或一个早已废弃的端口 —— 日志里因此出现：

```
[09:53:19] port 18060 free          <- 修前：盯着环境变量里那个废弃端口
[11:31:34] resolved ECHO port=8970  <- 修后：配置优先
```

**为什么"配置优先"而不是"端口文件优先"**：端口文件是"它实际听了哪儿"，配置是"我要它听哪儿"。
两者不一致时（首选被占而让位），ECHO **下次启动仍会尝试配置值** —— 那才是用户的选择；
`port_check()` 会如实说出被占。把文件排第一会让"我改了端口"永远不生效。

解析器**同时容忍两种传法**（`paths.data_root()` 给的是含 `echo.db` 的那层，
脚本里的 `$base` 是安装根）—— 猜错就会静默回落到默认端口，正是这一类 bug 的形态。

**为什么 18060 会冒出来**：它是"两棵树曾同时跑"时为了错开端口手工设的。
`ECHO_PORT` 那个**持久用户变量**是根源 —— 它同时影响两棵树，而脚本的解析优先级是
`ECHO_PORT → echo-port.txt → 默认`，于是"稳定版自己的端口文件"被静默压过。
`install-all.ps1` 早就有一句"**先清掉继承来的 ECHO_PORT**"（注释：*开发机/CI 上它常常
指着别人的实例*），说明这个坑以前就露过头。

## 4. 归属与接管做了什么

### 4.1 新增的判据（都落在 ECHO 本体，脚本复用同一份事实）

| 原语 | 位置 | 干什么 |
|---|---|---|
| `platform.process_command_line(pid)` | 平台接缝（win32/posix/darwin） | 读进程完整命令行。Windows 走 ctypes 直读 PEB（**实测 1.0 ms**；`wmic` 已不可用，`Get-CimInstance` 要 **1244 ms**，面板每次刷新都付不起） |
| `backend_proc._backend_root_from_cmdline()` | `app/backend_proc.py` | 从命令行取 `--config <root>/server.yaml` → 后端目录 |
| `backend_proc.backend_owner()` | 同上 | `{is_ours, foreign, root, note}`：**本棵树的** / **另一棵树的** / 说不出来 |
| `backend_admin.usability()` | `app/backend_admin.py` | **配对的那台能不能用我**：`ready` + `code`（`unauthorized`/`blocked`/`forbidden`/`offline`） |
| `backend_admin.take_over()` | 同上 | 停掉**另一棵树**的后端 → 起本棵树自己的 → 配对复用（不重新配对） |

### 4.2 面板那格现在怎么显示

```
running 且是我们的      → 「本机」（online）
端口被另一棵树的后端占着 → 「别人的」（可点 = 接管）
后端在但 code=unauthorized → 「不可用」（tip 里写清"不认本机凭据"）
运行时在、后端没起      → 「待启动」
```

**`unauthorized` 必须有专门的措辞**：说成"连不上"会把用户引去查网络/启动，
而该做的是**换掉那台后端**（`_USABILITY_ADVICE` 那张表就是防这个的）。

#### 4.2.1 第四种归属：**本棵树的后端在跑，但 pid 记录不在**（2026-10-06 补）

**用户报的现场（原话）**：*"后端管理页面能进，语音能转写，但是仪表盘的状态显示待启动"*。

**真因**：**归属记录活不过 ECHO 那一次进程**。`data/logs/backend.pid` 写的是
"**这个 ECHO 进程**起的后端"，而 ECHO 重启之后端口上那个后端还活着
（父进程是旧 ECHO，已成孤儿），新 ECHO 手里没有 pid 记录。于是：

* `is_ours_alive()` → False → `view()["running"]` = False → 那格说「待启动」；
* 而**能力路由根本不看归属记录** → 转写照旧成功、管理页照旧能进
  —— 用户看到的就是这个自相矛盾；
* **更糟的是点"启动"还会被自己挡住**：这一类原来落进 `strangers`，面板说
  *"端口被占：…这不是 ECHO 起的后端…请先停掉它或换端口"*，而那明明是本棵树自己的。

**修法（判据早就有了，只是没用）**：`port_owner(with_root=True)` 会按**命令行**
（`server.main … --config <目录>`）算出 `is_ours` —— 与桌面工具包 `Get-BackendPid`
同一判据。`port_check()` 补上第四类：

```python
elif owner.get("is_ours"):        # 本棵树的，只是 pid 记录不在
    unmanaged.append(owner)
...
if unmanaged:
    for o in unmanaged:
        backend_pid.write_pid(int(o["pid"]))   # 就地认领（写不进去不算错）
    return True, "本棵树的后端已经在跑（…）…（归属记录原本不在 —— ECHO 重启过就这样，已认领它）"
```

放行是必需的：否则一定会去起第二个、或者把用户引去手工杀进程。消息里那句
"已经在跑"还是 `backend_setup.start()` 的**幂等闸**（它见到这句就把 `ok` 置真、
直接进入配对）。

⚠️ **`view()` 里的顺序要紧**：`port_check` 会**认领**（写 pid），所以 `is_ours_alive()`
必须**在它之后**读。反过来的话第一次刷新仍说「待启动」，用户得刷两次才自愈
—— 而那句"待启动"正是他报上来的问题。实现时就把归属读取挪到了 `port_check` 之后。

**判据**：`tests/test_backend_owner.py::PortCheckTests::test_our_own_backend_without_a_pid_record_is_claimed_not_blocked`
（① 放行；② 消息里说得出"已经在跑"；③ pid 记录被补上）。
真机复核（删掉 `backend.pid` 重现 → 重启 ECHO → **第一次**问面板接口）：
`running=True`、`pid=17588`、`usable.ready=True`，且 `backend.pid` 被自动认领为 `17588`。

### 4.3 脚本的改动

| 脚本 | 改动 |
|---|---|
| `scripts/switch-instance.ps1` | 停旧实例**之前**先让它停掉自己的后端（趁它还活着能调自己的 API）；起新实例**之后**调 `/api/capability/backend/take-over` |
| `scripts/stop.ps1` | 按 `-m server.main --config <本棵树 backend>` 认领并停掉**自己的**后端（别的树的不匹配，绝不误杀） |
| `scripts/restart-echo.ps1` | 起来后调 take-over（是别人的后端就接管，是自己的就不动）。⚠️ 它有 BOM，`edit` 会抹掉，改完必须按字节补回 |
| `scripts/echo-port.py` | **新增**：端口解析的唯一事实源（配置 → 端口文件 → 环境变量 → 8970） |
| `scripts/start.ps1` / `startup.ps1` / `launch-desktop.ps1` | `Resolve-EchoPort` 改调 `echo-port.py`（顺序由"环境变量优先"改成"配置优先"） |

| `1/2-启动-*.cmd` | 注释里的端口改成 8970 |

## 6. 仍未统一的一处（如实记录）

**模型路由端口**：dev `8899`、稳定版 `18061`（`dsh-failover/config.json` 的 `port`）。
按"端口统一"这条原则它也该统一，但它是**每棵树一份配置文件**、且改动要同时动
`config.json` 与面板设置，本次没动。**没有把它当成已完成**。

## 7. 教训

1. **"端口在听"不是"这棵树在跑"**。统一端口后，所有 `Test-Up <port>` 式的判据都会
   把两棵树都判成 UP（工具包的 `status` 真这么报了）。判归属必须看**进程**。
2. **"不是我的就不动"在"轮流跑"的场景里是错的**。工具包原来对别人的后端"leaving it
   alone"，结果是被停掉的那棵树一直占着端口，下一棵树起来就撞 `unauthorized`。
   正确的语义是：**停止实例 = 释放它占的资源**。
3. **说错原因比不说更坏**。「待启动」把用户引去查启动，而根因是凭据/归属。
   现在 `unauthorized` 有专门的措辞（"那台后端不认本机凭据" + "点接管"）。
4. **调不存在的端点不会报错，只会静默不做**。工具包的 `/api/control/sidebar` 就是例子 ——
   `Invoke-RestMethod` 被 `try/catch` 包着，失败返回 `$null`，于是"重启边条"一直是空转。
   凡是"调了接口什么都没发生"的地方，都该有一个**结果判据**（例如边条的 pid 端口）。
