## 0. 一句话结论（先看这里）

**不要换引擎。** 现在这条路的病根不在 sherpa-onnx，而在三个**实现层面的静默缺陷**加一个**过宽的匹配器**：
拼音容错层在客户端**根本没装**（`pypinyin` 从未写进任何依赖清单，`_pinyin` 用 `except` 吞掉导入失败）；
`wakeConfirmX/wakeConfirmN` 这两个确认帧设置**被代码显式绕过**；而一旦装上 `pypinyin`，
`_subseq`（允许任意插入）+ `_syl_match`（音节编辑距离 ≤ 1）会让「小李小李」「小蜜小蜜」「很牛哦」全都命中「小尼小尼 / 嘿尼欧」。
把匹配器收紧 + 补 VAD 前置（`silero_vad.onnx` **已经在交付包里**，零下载）+ 换掉叠词唤醒词，
预计能吃掉绝大部分误唤醒；引擎本身换不动也不必换（Porcupine 免费档 2026-06-30 失效；openWakeWord 官方只支持英文、预训练权重是 **CC-BY-NC-SA 4.0 非商用**）。

## 1. 现状核实（先对齐事实，这一节全部是【本机实测】）

### 1.1 出厂默认值（`app/config.py`）

| 设置 | 出厂值 | 备注 |
|---|---|---|
| `wakeEnabled` | `False` | 唤醒默认关闭 |
| `wakePaused` | `True` | 出厂即"勿扰" |
| `wakeEngine` | `"sherpa"` | **默认 = 流式 ASR + 文本匹配**（不是 KWS） |
| `wakeKeywords` | `["回声回声"]` | 注意：**不是**「小尼小尼」；「嘿尼欧」不在默认词表里 |
| `wakeAliases` | `[]` | 空 —— 题述的「嘿尼欧」若不在 `wakeKeywords`/`wakeAliases` 里，理论上永远不会命中 |
| `wakeThreshold` | `0.5` | **只被 KWS 路径消费**；默认的流式 ASR 路径完全不读它 |
| `wakeCooldownSec` | `3` | 命中后 3 秒不再触发 |
| `wakeConfirmX` / `wakeConfirmN` | `2` / `3` | **读了但没用**（见 1.2） |
| `wakeSilenceFloor` | `60` | int16 RMS 门控；60 ≈ -54 dBFS，**基本等于不设门控** |

### 1.2 默认路径（`wakeEngine=sherpa`）的真实行为（`app/audio/wake.py`）

- 用 sherpa-onnx **流式 transducer** 持续识别，`get_result()` 拿到的**是整个 stream 累积的文本**；
  只有静音约 **1.6 秒**（`silent_run > 20` × 80 ms 块）或命中时才会 `reset()`。
- 命中判定两级：① `kw in text` **子串精确匹配**（归一化后）；② 拼音**子序列**匹配 `_subseq`。
- `_subseq` 的宽松度（读代码）：`_syl_match` 允许**编辑距离 ≤ 1**，`_subseq` 允许**任意插入**。
- **代码里明确写着不做多帧确认**（wake.py 注释：*"命中即触发…不做多帧确认——流式检测器命中后会重置，单次命中无法凑够多帧"*），
  于是 `wakeConfirmX/wakeConfirmN` 在默认路径上**是死设置**。

### 1.3 三个"静默档"（本报告最重要的发现）

**【本机实测】发现 1：`pypinyin` 没有任何地方声明，客户端很可能没有它。**
`requirements-core.txt`（客户端装的那份）实际内容：`fastapi / uvicorn / pydantic / python-multipart / httpx / PyYAML /
ruamel.yaml / numpy / sounddevice / soundfile / soxr / sherpa-onnx / modelscope` —— **没有 pypinyin**；
全仓库 `requirements*.txt`、`server/requirements*.txt`、`*.toml`、`scripts/*.py` 里 grep `pypinyin` **零命中**。
而 `wake.py::_pinyin` 是 `try: from pypinyin … except Exception: return [全文小写]` —— **导入失败被静默吞掉**。
本机两个环境正好各是一半：

```
C:\echo-dev\.venv   -> pypinyin False, numpy False, sherpa False   （没装）
C:\echo-dev\venv    -> pypinyin True,  numpy True,  sherpa True    （装了）
```

后果：**拼音容错层在没装 pypinyin 的机器上是死代码**，`_subseq` 退化成"逐字全等"，
而 docstring 仍在宣称"容忍同音字与插入" —— 这解释了**"漏唤醒"**里最刺眼的一类：
ASR 只要把「嘿尼欧」转成「嘿你哦 / 黑牛哦」，就**永远不会命中**。
反过来，dev 机（有 pypinyin）与客户机（大概没有）**行为不一致**，这就是"我这能唤醒、他那不行"的典型形状。

**【本机实测】发现 2：装了 pypinyin 之后，匹配器宽到离谱。**
在 `C:\echo-dev\venv` 下直接调 `wake._pinyin / _subseq`（复现命令见附录 A）：

| 唤醒词 | 实测**会命中**的普通话语 | 说明 |
|---|---|---|
| 小尼小尼 | 小李小李、小蜜小蜜、**小李飞刀小李飞刀**、我叫小李，他叫小李、小丽，小李他来了 | `ni≈li≈mi≈bi≈pi≈di≈ti≈ne≈nu…`（编辑距离 1），且允许任意插入 |
| 嘿尼欧 | 黑牛哦、**很牛哦**、嘿你哦、黑泥藕 | `hei≈hen`、`ni≈niu`、`ou≈o` —— 全是编辑距离 1 |
| 回声回声 | 这瓶汇声汇声挺贵、回升升回回回升 | 汇声/回声是真同音（可接受）；但**任意插入**让它能命中一整句话 |

音节级的实测：`_syl_match("ni","li")=True`、`("hei","hen")=True`、`("ni","niu")=True`、`("o","ou")=True`
—— 拼音音节只有 2~3 个字母，**"编辑距离 ≤ 1"在中文里几乎等于"随便"**。

**【本机实测】发现 3：KWS 模型其实已经是最新的，但代码用的是"低精度那一档"，且没有 boosting/threshold。**
`models/wakeword/kws-zh-en-3m/` 的每个文件字节数与官方
`sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20` 发布清单**逐项一致**
（encoder int8 4,600,657 / encoder fp32 11,976,951 / decoder 759,829 / joiner 86,629 / en.phone 3,330,061 / tokens 1,928）
—— 也就是说 **ECHO 拿到的就是 2025-12-20 那版最新的中英 KWS 模型**，不是旧模型。
但是：
- 官方说 `chunk-8` **延迟 160 ms、精度更低**，`chunk-16` **延迟 320 ms、精度更高**；`wake.py` 写死了 **chunk-8**；
- 官方关键词文件支持**逐词** `:boosting`（越大越易触发）与 `#threshold`（**越小越易触发**）；
  `wake.py::_keywords()` 生成的行是 `x iǎo n í x iǎo n í @小尼小尼` —— **既没有 `:` 也没有 `#`**；
  于是全局回落到 `keywords_score=1.0` + `keywords_threshold=wakeThreshold(0.5)`。
  （对照：第三方一手工程记录里，中文 KWS 标定出来的是 **threshold 0.1 / score 1.5**，见 §3.2。）

### 1.4 交付包里已经有什么（很关键）

**【本机实测】** `dist/ECHO-kit-*/bundle/models/sensevoice-onnx/silero_vad.onnx`（**1.7 MB**）**已经在交付包里** ——
即"给唤醒加 VAD"这个动作**不需要新下载、不需要新依赖**：
sherpa-onnx 1.13.6（本机 venv）已内含 `VoiceActivityDetector` / `VadModelConfig` / `SileroVadModelConfig` / `TenVadModelConfig`，
且 `KeywordSpotter` 与 `OnlineRecognizer` 都在（全部 torch-free）。

**【本机实测】顺带发现一个交付风险**：`models/wakeword/` 里除了 KWS 模型，还躺着两个**没人引用**的
openWakeWord 产物 —— `niouniou.onnx`（14 KB）+ `niouniou.onnx.data`（856 KB）+ `niouniou.keywords.txt`。
用字符串扫描该 ONNX 可读到 `openwakeword.train.Model.__init__.<locals>.Net`、
导出路径 `\NEO\voice-bridge\venv\Lib\site-packages\openwakeword\train…`、`torch 2.10.0+cu128`、
输入 `x`（`[1,1536]`）、输出 `sigmoid`；本机 `venv\Lib\site-packages\openwakeword` 是 **0.6.0**。
`models/` 在 `.gitignore` 里（**不进 git**），但 `build_offline_pack.py` 的打包项是**整目录**
`models\wakeword\`（默认不打、`-Wake`/main 档要），而 `install-all.ps1` 的 main 档默认要唤醒模型
（`$wantWake = ($Profile -eq 'main') …`，缺了就 Warning 跳过）——
**一旦按 main/`-Wake` 打包，这个来路不明的 openWakeWord 权重会跟着交付包出去**（授权问题见 §5.3）。

## 2. "误识频率很高"的根因分析

先把两类症状分开（用户原话"误识"含义待定，这里两类都答）。

### 2.1 误唤醒（没叫它也触发）

**为什么"持续流式识别 + 文本匹配"天然容易误触发：**

1. **判定是"整段文本里出现过唤醒词"**，不是"独立说了一句唤醒词"。`kw in text` 是子串判定，
   而 `text` 是**约 1.6 秒累积**的识别结果 —— 只要这段里任何位置掠过相似音节就命中（实测：
   「这瓶汇声汇声挺贵」命中「回声回声」）。
2. **拼音匹配退化成"音节序列模糊包含"**：允许插入（`_subseq`）+ 音节编辑距离 ≤ 1（`_syl_match`）。
   中文音节只有 2~3 字母，编辑距离 1 的邻域极大 —— 实测「小李小李/小蜜小蜜」「很牛哦」全部命中（§1.3）。
3. **没有真正的 VAD，只有一个形同虚设的能量门**：RMS ≥ 60（≈ -54 dBFS）就喂 ASR。
   办公室里的电视、同事说话、键盘、空调都会被送进识别器，而识别器只会"尽力把它转成字"，转出来的字里就可能出现唤醒词。
4. **单帧命中即触发，多帧确认被代码绕过**：`wakeConfirmX/N` 读了不用，噪声导致的单次"幻觉转写"就足以触发。
5. **冷却只有 3 秒、且不说"必须重新起头"**：一旦命中，之后每次系统说话/环境相似音都可能再次触发。

### 2.2 漏唤醒（叫了它没反应）

1. **拼音容错层是死的**（§1.3 发现 1）：客户端缺 `pypinyin` 时只有"逐字全等"才算命中，
   「嘿尼欧」被转写成「嘿你哦」「黑牛哦」就全丢。
2. **唤醒词本身是叠词**：「回声回声」「小尼小尼」都是叠词。第三方一手经验与"唤醒词设计原则"
   都点名**叠词要避免**（识别难度翻倍）、**要有爆破音**（b/p/d/t/k）、**3~5 字**、**不要太常见**。
3. **能量门/流重置是二值的**：低于 60 RMS 的"小声喊"直接不进 ASR（第三方实测同类问题：
   安静环境小声喊识别不到，根因是噪声抑制把弱语音吞了，对策是 AGC + 软件增益）。
4. **KWS 路（`wakeEngine=kws`）另有三个可修的坑**：用了低精度的 chunk-8、阈值 0.5 偏严
   （一线标定是 0.1）、关键词行没写 boosting —— 这足以解释"KWS 对自然语音识别不了"。
   第三方一手记录里，"自然口语识别不了"的正解是**给同一个词多写几条音素变体**（见 §3.2）。

### 3.2 值得抄的三条实战结论（第三方一手，含中文）

来自一篇**中文 sherpa-onnx KWS 上线全记录**（2026-08-22，浏览器 wasm 场景，中文，含实测数据）：

1. **给同一个词写多条"发音变体"**，是解决"自然口语识别不了"的正解。它的关键词配置长这样：
   ```
   n iú l ái @牛来
   n ǐ y òu l ái @牛来A
   n ǐ y ǒu l ái @牛来B
   n iú y òu l ái @牛来C
   ```
   （主词一行 + 真实会有的口音变体三行）
2. **阈值是标定出来的，不是拍出来的**：它用 **threshold 0.1 / score 1.5**（对比 ECHO 的 0.5 / 1.0 且无 boosting）。
3. **代价要认**：音素变体的固有代价是**近音词会误触发**（「你又来」会命中「牛来」）；
   漏检集中在重口音与超速语音，**"加变体硬修"无效且抬高误报** —— 换个用户自己喊着顺的词更好。
   另外它实测"小声喊识别不到"，对策是 **AGC + 软件增益**（不是改模型）。

### 3.3 通用防误触发分层（行业做法，可对照自查）

第三方（厂商博客）给出的推理引擎内置**五层防误触发**，可作为 ECHO 自查清单：
**L1 连续帧确认 → L2 峰值/背景比 → L3 冷却时间 → L4 多关键词互斥 → L5 前后静音检测**。
ECHO 现状：L1 **被绕过**、L3 有（3 s）、L2/L4/L5 **基本没有**。openWakeWord 官方另推荐两条：
**阈值调参** 与 **custom verifier（只放行已知说话人的二次过滤）**。

## 4. 不换引擎、只调参（立即可做，按收益排序）

> 分三档：**【零代码】= 只改设置项**；**【小改】= ≤ 20 行、不动架构**；**【需配套】= 必须成对做，否则会更糟**。

| # | 动作 | 档位 | 预期收益 | 依据 / 代价 |
|---|---|---|---|---|
| 1 | **收紧拼音匹配**：`_subseq` 去掉"允许插入"，`_syl_match` 从"编辑距离 ≤ 1"改成**同音白名单**（只放行真同音字，如 汇声=回声），并**要求连续整句匹配** | 【小改】~15 行 | ★★★★★ 直接砍掉实测的「小李小李/小蜜小蜜/小李飞刀小李飞刀/很牛哦」这一整类 | §1.3 实测。**收益最大的一项**，且不引入任何新依赖 |
| 2 | **换掉叠词唤醒词**：`回声回声` → 3~4 音节、含爆破音、非日常用语（如「嘿尼欧」并把变体写进 `wakeKeywords`/`wakeAliases`） | 【零代码】 | ★★★★★ 叠词 + 常见词是误唤醒与漏唤醒的共同来源 | 唤醒词设计原则（第三方）；**注意**：现在 `wakeAliases` 是空的，「嘿尼欧」根本不在词表里 |
| 3 | **命中必须"起头"**：要求命中出现在识别文本的**开头 N 个音节内**，或命中后**紧接静音/句尾**才算 | 【小改】~15 行 | ★★★★☆ 消掉"一整句话里掠过相似音"（实测「这瓶汇声汇声挺贵」） | §2.1 第 1 条。这是"文本匹配架构"最有效的一味补药 |
| 4 | **VAD 前置**：只在"有人在说话"时才 `feed()` ASR（用**已在包里的** `silero_vad.onnx` + sherpa-onnx `VoiceActivityDetector`，或先用能量+过零率兜底） | 【小改】~20 行 / 零下载 | ★★★★☆ 消掉电视、键盘、空调、他人闲谈进 ASR 的整条通道 | §1.4：模型**已在交付包**、API 在现有依赖里；openWakeWord 官方也承认 VAD 能显著降误激活 |
| 5 | **真的启用 `wakeConfirmX/wakeConfirmN`**：命中后**不要立即 reset**，在 N 帧窗口内累计 X 次才触发 | 【小改】~15 行 | ★★★★☆ 单帧"幻觉转写"不再能触发 | §1.2：这两个设置现在是死设置 |
| 6 | **提高能量门 + 缩短累积窗口**：`wakeSilenceFloor` 60 → **200~400**；静音重置从 1.6 s 缩到 **0.6~0.8 s** | 【零代码】+1 行常量 | ★★★☆☆ 减少喂给 ASR 的垃圾；缓解"文本无限累积" | §1.1 / §1.2 |
| 7 | **冷却加大**：`wakeCooldownSec` 3 → **8~10** | 【零代码】 | ★★★☆☆ 抑制连续误触发 | §1.1 |
| 8 | **声明 `pypinyin` 依赖**（写进 `requirements-core.txt` / `requirements.txt`） | 【需配套】1 行 | ★★★☆☆ 让 dev 与客户行为一致，修复"容错层静默失效" | ⚠️ **必须与第 1 项同时做**：只装 pypinyin 而不收紧匹配器，会把漏唤醒换成**大量误唤醒**（§1.3 实测） |
| 9 | **KWS 路调参**（仅当决定用 KWS）：`wakeThreshold` 0.5 → **0.15~0.25**；给关键词行补 `:boost #thr`；模型从 **chunk-8 换成 chunk-16** | 【小改】1~3 行 | ★★★☆☆ 直接改善"KWS 对自然语音识别不了" | §1.3 发现 3；一线标定值 0.1/1.5（§3.2）；官方称 chunk-16 精度更高（延迟 320 ms） |
| 10 | **给每个唤醒词加 2~3 条口语变体**（KWS 路） | 【零代码】改关键词配置 | ★★★☆☆ 补齐口音/连读 | §3.2 一手记录；**代价**：近音词误触发会上升 |
| 11 | **二次校验**：命中后用同一段音频再跑一次整句 ASR，要求"重转写后仍含唤醒词"才放行 | 【中改】 | ★★★☆☆ 误唤醒可再降一截 | 属于"不改架构"的边界；等价于 openWakeWord 的 verifier 思路 |
| 12 | **小声喊要能进**（漏唤醒侧）：麦克风侧开 AGC 或加软件增益（tanh 软削波防爆音） | 【小改】 | ★★★☆☆ 修"安静环境小声喊识别不到" | §3.2 第三方实测的同类问题与对策 |

**只调参能改善多少？** 诚实回答：**没有可引用的百分比**（没有官方 FA/FR 曲线，也没做过 ECHO 自己的标注集）。
但**本机实测已经把误唤醒面量化了**：收紧第 1 项后，「小李小李/小蜜小蜜/小李飞刀小李飞刀/很牛哦/这瓶汇声汇声挺贵」
这些**确定会命中**的句子会全部失效 —— 也就是说这一类误唤醒是**可以归零**的，不是调参玄学。
**强烈建议**：动手前先建一个 **30~50 条的小语料集**（正样本：正常/小声/远场各 10 条；
负样本：办公室闲聊、电视、音乐、近音词各若干），改一项跑一次，把 4 个数字记下来
（正样本命中率、负样本误触发次数/小时、误触发最多的 3 句话、漏检最多的 3 句话）。
没有这个集子，后面所有"效果变好了"都无法验证。

## 5. 换引擎：推荐与迁移成本

### 5.1 推荐（按优先级）

1. **首选：不换引擎，把默认实现从"流式 ASR 文本匹配"改成"KWS 为主 + 文本匹配降级"**，
   并按 §4 第 1/3/4/5 项收紧。理由：**零新增依赖**（`sherpa-onnx` 已经是必装）、
   代码 Apache-2.0、`KeywordSpotter` API 已在、KWS 模型**已在包内且是 2025-12-20 最新版**、
   中文**开放词表免训练**、**全程 torch-free**。
   配合 §3.2 的"多音素变体 + boost/threshold 标定"，这是投产最快的路。
2. **次选（要更高准确率、愿意自训）**：**microWakeWord 模型 + `pymicro-wakeword`**。
   Apache-2.0、纯 Python、**不依赖 torch**、模型 **50~100 KB**（交付包几乎不涨），
   Home Assistant 官方生态在用（已进 Debian）。代价：**中文模型要自己训**，且要确认 Windows 上的 TFLite 轮子可用。
3. **明确否掉：Porcupine。** 不是效果问题，是**可用性问题**：免费档 2026-06-30 失效、
   厂商说**没有非商用档**、引擎**初始化即校验 AccessKey、无 Key 不运行**、按设备授权。
   把它做进交付包 = 给客户埋一个到期即失效的组件。
4. **明确否掉（本项目约束下）：openWakeWord。** 官方**只支持英文**，中文得自训且无官方支持；
   **官方预训练权重是 CC-BY-NC-SA-4.0（非商用）**，不能进交付包。
   本机那个 `niouniou.onnx` 是**自训分类头**（授权链另说，见 §5.3），但它引用了 openWakeWord 的共享骨干与训练管线。
5. **可观察**：`onnx-wakeword` + 听词（中文 ONNX 自训、五层防误触发、DSCNN ~130 KB）。
   但现有资料是**厂商博客口径**，落地前必须自行核实：引擎 LICENSE、模型授权、是否联网/计费。

### 5.2 迁移成本对照

| 目标方案 | 新增依赖 | 代码改动量 | 模型 / 下载 | 中文自定义唤醒词 | 授权风险 | 交付包体积变化 |
|---|---|---|---|---|---|---|
| 现状（流式 ASR 文本匹配） | 无 | — | 已在包（189 MB） | 改词表即可 | 低 | — |
| **→ sherpa-onnx KWS 为主**（推荐） | **无** | 中（`_make_detector` 默认值、匹配收紧、VAD 前置、多帧确认；~100 行） | **已在包（38 MB）** | ✅ 免训练、改配置 | 代码 Apache-2.0；**权重来源需确认**（§5.4） | **-150 MB**（可不再依赖流式模型） |
| → microWakeWord + `pymicro-wakeword` | `pymicro-wakeword` + TFLite 运行时（Windows 待确认） | 中大（新后端 + 模型加载） | 自训模型 **~50–100 KB** + 训练成本（Colab 管线） | ⚠️ 需自训中文 | 代码 Apache-2.0；模型授权取决于你的训练数据 | 几乎不变（可再 -189 MB） |
| → openWakeWord | `openwakeword`（+ onnxruntime，**已在 dev venv**） | 中 | 骨干 ~1–5 MB + 每词分类头 | ❌ 官方不支持 | ⚠️ **官方预训练模型非商用** | +几 MB |
| → Porcupine | `pvporcupine` | 小 | `.ppn` 小 | ✅ Mandarin | ❌ **2026-06-30 后不可用** | +几 MB，**但长期不可用** |

### 5.3 关于本机那个 `niouniou.onnx`（openWakeWord 自训产物）

- **事实**：它是 openWakeWord 训练脚本导出的分类头（`openwakeword.train.Model…Net`），输入 16 帧 × 96 维 embedding，
  输出 sigmoid；**代码里没有任何地方引用它**（全仓库 grep `niouniou` 只命中 `models/` 下的文件名）。
- **授权怎么算**（把已知事实摆清楚，别急着下结论）：
  openWakeWord **代码 Apache-2.0**；**官方预训练模型 CC-BY-NC-SA-4.0（非商用，因训练数据里有授权不明/受限的数据集）**；
  共享骨干 `embedding_model.onnx` 官方自述源自 Google `speech_embedding`（**Apache-2.0**）并手工重实现。
  → **自训分类头的授权，取决于你训练时用的正/负样本数据**；而它**依赖的骨干与管线**来自 openWakeWord。
  **结论：这条链不能默认"干净"，进交付包前需要有人为它负责**（至少写清：谁训的、用了什么数据、按什么许可证发布）。
- **建议**：要么把它从 `models/wakeword/` 移走（改名归档到 `dist/` 之外），要么在打包清单里显式排除；
  **别让 `-Wake`/main 档"整目录复制"把它顺手带出去**（§1.4）。

### 5.4 授权上仍需确认的两件事（不编，如实标注）

1. **sherpa-onnx KWS 权重的授权**：代码 Apache-2.0 已确认；但**模型卡没有明示权重许可证**，
   而它训练自 WenetSpeech / GigaSpeech（WenetSpeech 在 HF 上需要同意条款才能取用）。
   → **"Apache-2.0 代码 + 授权链条不明示的权重"不能自动等同于可商用**，交付前请确认模型卡的授权声明。
2. **Silero VAD 权重授权**：社区普遍按 MIT 引用，但**本次未能打开其仓库 LICENSE 原文核实 → 标记待确认**。

## 6. 给项目负责人的结论

1. **别换引擎**：sherpa-onnx 是当前约束下唯一"零新依赖 + Apache-2.0 + 中文开放词表 + torch-free + 模型已在包内（还是 2025-12-20 最新版）"的选择；Porcupine 免费档 2026-06-30 失效且无个人档，openWakeWord 官方只支持英文、预训练权重非商用，都不能进交付包。
2. **误唤醒的主因是匹配器太宽**：实测「小李小李」「小蜜小蜜」「小李飞刀小李飞刀」「很牛哦」「这瓶汇声汇声挺贵」**现在就会命中** —— 收紧 `_subseq`/`_syl_match`（去掉插入容忍、音节只放行真同音）是收益最大的一刀，且能归零这一整类。
3. **漏唤醒的主因是拼音层是死的**：`pypinyin` 从未写进依赖，`_pinyin` 把导入失败静默吞掉，客户端只剩"逐字全等"；补依赖**必须与收紧匹配器同时做**，否则会把漏唤醒换成大量误唤醒。
4. **另外两个白捡的修复**：`wakeConfirmX/wakeConfirmN` 现在是死设置（代码显式绕过），VAD 前置所需的 `silero_vad.onnx`（1.7 MB）**已经在交付包里**，接上即可用，零下载。
5. **先建 30~50 条小语料集再动手**：现在没有任何 ECHO 自己的正/负样本数字，改完无法证明变好了；同时**清理 `models/wakeword/` 里来路不明的 openWakeWord 权重**，别让它随 `-Wake` 打包出去。
