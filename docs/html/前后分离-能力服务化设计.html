ECHO 前后分离 · 能力服务化设计

源文件 docs/前后分离-能力服务化设计.md · 由 scripts/build-design-page.py 生成，勿手改

目标形态：客户端持有全部业务数据与状态，服务端只提供无状态算力能力。 本文回答的核心问题：在"服务端不存储业务数据 + 一服务端多客户端"的双重约束下， 指令转写、说话人分离、声纹识别应该切在哪里。

相关现状：ARCHITECTURE.md、app/audio/diarize.py、app/voiceprint.py、 app/meeting.py、app/providers/__init__.py、app/api.py

后续文档：docs/能力路由-三后端与轻客户端.md —— 本文 §2/§9 的展开： 本机 / ECHO 能力后端 / 内网公共 ASR 三后端的路由设计，以及"办公本可用"这一 性能与安装约束如何反向决定各能力的落点。

0. 结论速览

不要按"是否需要 GPU"来切。 按"是否需要 GPU"切出来的边界，会在三个地方立刻崩： 指令转写的可用性、说话人分离的跨段一致性、声纹库的隐私归属。

正确的三条切线是：

原则含义
算力外置，状态留内服务端只做「纯函数」：音频进 → 文本/嵌入/时间轴出。一切跨请求累积的状态（说话人身份、声纹库、会议、设置、历史）留客户端。判据不是"这个功能重不重"，而是"这个功能有没有跨请求状态"。
能力可降级客户端保留一份最小自给能力。服务端不可达时 ECHO 不瘫痪，只是变慢/变粗。
生物特征不出内网声纹库、原始音频、转写文本都不上行。上行的是"为了算而不得不给的音频"，且只在上行窗口内存在。

三个难点的答案：

能力切在哪一句话理由
指令转写可用性本地保证，准确率服务端增强交互延迟是硬约束，不能把"按热键有没有反应"交给网络
说话人分离切在 embedding 之后、clustering 之前"跨段是不是同一个人"= 小向量上的聚类决策 = 状态 = 客户端
声纹识别服务端只做 embed，匹配/库/阈值全在客户端库是敏感个人信息 + 阈值是私有调参 + 匹配是纯数学

1. 先把「服务端不存储业务数据」变成可验证的约束

这条是全局约束，必须先钉死定义，后面所有取舍都由它推出来。

业务数据（一律不许出现在服务端任何持久介质） 会议、录音、转写文本、纪要、说话人名、声纹库、命令历史、设置、业务日志。

运行状态（允许，但必须有界） 请求级临时缓冲、模型权重、内存中的解码状态、限流计数器。 要求：TTL 有界、进程重启即消失、不含用户内容。

1.1 要真正做到，必须同时管住 5 个地方（漏一个就破）

位置要求为什么容易漏
应用层音频只在内存；引擎非要文件路径时用内存盘（Linux /dev/shm；Windows 落 Temp 但 finally 必删 + 启动时清残留）funasr 要路径、pyannote 要文件/waveform，顺手写进 temp 就忘了删
日志只记 request_id / client_id / 端点 / 音频秒数 / 耗时 / 状态码；绝不记音频、文本、嵌入、原始请求体现在的 db.add_log 文化会不自觉把识别文本写进去（assistant.py 就在写 识别: {text[:60]}）
数据库服务端没有 DB，这条写成断言（CI 检查跑完后无 .db/.sqlite 生成）"先临时缓存一下"是最容易的滑坡
反向代理nginx proxy_request_buffering off、client_body_buffer_size 容下最大音频、proxy_temp_path 指内存盘、access_log 不记 body大请求体被 nginx 缓存到磁盘 = 服务端存了业务数据，而应用层完全看不见
崩溃转储关 core dump / 设 coredump_filter内存里的音频会随 core 落盘，静默且没人会想到

1.2 可验证性（最重要）

做一个自检：跑一遍完整请求（asr + diarize + embed）后断言

  1. 临时目录为空；
  2. 进程工作目录下无新增文件；
  3. 服务端日志里 grep 不到任何输入内容；
  4. 无新增 DB 文件。

这四条能直接写成测试。"不存储"必须是能被测试钉住的属性，而不是一句承诺 —— 否则半年后加个缓存就悄悄破了。

2. 服务端 API 形状

2.1 能力声明端点

GET /v1/capabilities 声明：能做什么、用什么模型、什么版本、什么限制。 客户端设置里的"服务端能力"选择器从它动态生成，服务端换模型不用改客户端。

{
  "protocol": 1,
  "server": {"id": "gpu-01", "version": "1.0.0"},
  "limits": {"maxAudioSeconds": 1800, "maxConcurrent": 4,
             "acceptedCodecs": ["pcm_s16le@16k", "wav", "opus"]},
  "capabilities": {
    "asr": [
      {"id": "sensevoice-small", "langs": ["zh","en","ja","ko","yue"],
       "modelVersion": "sensevoice-small-2024.07", "streaming": false, "rtf": 0.05},
      {"id": "qwen3-asr-0.6b", "modelVersion": "qwen3-asr-0.6b-2025.09", "rtf": 0.12}
    ],
    "diarize": [
      {"id": "pyannote-3.1", "dim": 256,
       "embeddingModelVersion": "wespeaker-voxceleb-resnet34-LM-v1",
       "returns": ["turns", "speaker_embeddings", "turn_embeddings"]}
    ],
    "embed": [
      {"id": "wespeaker", "dim": 256,
       "modelVersion": "wespeaker-voxceleb-resnet34-LM-v1"}
    ],
    "tts": [{"id": "edge-tts"}]
  }
}

modelVersion 必须存在且稳定 —— 它是声纹/说话人向量空间一致性的唯一依据（见 §4.4、§5.2）。

2.2 交互形态：只要两种

  1. 同步短请求 —— POST /v1/asr、/v1/embed、/v1/diarize。请求即全部上下文，响应即全部结果。
  2. 长请求 + SSE 进度 —— 长音频带 Accept: text/event-stream 边算边推进度。连接状态只在内存，断了客户端整段重试。

刻意不引入 job 队列（POST /jobs → 202 + job_id → 轮询）。理由：

  • job 表就是服务端状态，随之而来的是持久化、HA、粘性路由、清理策略 —— 与"不存储业务数据"背道而驰；
  • 客户端本来就持有全部业务上下文（会议目录、分段清单、哪些段已转写、失败重试），编排天然属于客户端。

代价：幂等责任在客户端。分段请求带 (meeting_id, segment_index, sha256)，服务端不缓存、重传即重算；客户端维护"已转写段"清单。这条要写进文档，别指望服务端去重。

收益：服务端真正无状态，多实例直接轮询即可水平扩，不需要共享存储。这就是"一个服务端支撑多个客户端"最容易扩展的形态。

2.3 编解码

16 kHz mono PCM s16le 为基准，10 分钟 = 19.2 MB。

  • 局域网：PCM 直传足够。
  • 广域/弱网：客户端 Opus 编码 → 1–2 MB/10min。
  • 服务端在 capabilities.acceptedCodecs 里声明，客户端按能力选（PCM 保底，Opus 可选）。
  • 服务端除了重采样不做任何转码 —— 少一个依赖。

2.4 端点清单（v1 建议）

方法路径语义状态
GET/v1/capabilities能力与版本声明无
GET/v1/health存活 + 队列深度 + 显存无
POST/v1/asr音频 → 文本（?variant=short|meeting、可选时间戳）无
POST/v1/diarize音频 → turns + 说话人嵌入（+ 可选逐 turn 嵌入）无
POST/v1/speaker/embed音频 → 一个或多个 256 维嵌入无
POST/v1/tts文本 → 音频（可选，客户端已有 edge-tts/SAPI）无

没有任何写端点。 没有 /voiceprints、没有 /enroll、没有 /meetings —— 这不是"暂时不做"，而是架构禁止（见 §5.1 的护栏测试）。

3. 指令转写：把「能不能用」和「准不准」分开

3.1 为什么不能整体上移

现在 assistant._capture_worker 的链路是 热键 → 录音 → 转写 → 意图分流 → 执行，全程本地，延迟 ~1–2 s。 把转写搬到服务端会同时引入三个问题：

  1. 可用性：断网 / 服务端重启 / GPU 排队 → "按热键没反应"。这是最高频、最伤体验的故障模式。
  2. 负载：命令是 10 s 级短音频、50–100 次/天/人。N 个客户端的高频小请求会把服务端 QPS 打满，挤掉会议转写这类长任务。
  3. 隐私：命令内容可能比会议更敏感（"把某某服务器的口令…"），上行面反而更大。

3.2 设计：本地保底 + 服务端增强 + 执行原子点

热键
 → 本地流式 ASR（sherpa zipformer，CPU，~50MB，边录边出草稿）
 → 录音结束，本地出稿 text_local（t=0 即可用）
 → 意图分流：
      命中本地意图（开始/结束录音、停止、开面板…）→ 直接执行，永不触碰服务端
      自由命令 → 按策略走：
         local-only    直接用 text_local（默认）
         server-ahead  同时上行，等 grace 窗口；窗口内到了就用服务端的
         race          同时上行，先到先用
 → 【执行原子点】不可逆
 → 结果写 commands 表，记 source=local|server、used=true|false

「执行原子点 + grace 窗口」是这条设计的核心。

  • 窗口（默认 0 ms，可配 300/800 ms）之前允许把结果替换成服务端返回；
  • 窗口之后命令已执行，服务端结果只用于修正历史记录（更新 commands.text，标 used=false），绝不重放。

这样：默认零额外延迟；追求准确率的用户开 300 ms，代价可量化、可自行选择；永远不会出现"命令执行两次"。

3.3 配套三条

  • 隐私开关 + 本地黑名单：commandUploadEnabled 默认关（首次显式询问）；命中本地关键词黑名单（口令/密码/身份证/账号…）的音频绝不上行。
  • 计量隔离：服务端给 asr.short 单独配额与队列，与会议转写分开，避免高频小请求饿死长任务。
  • 本地引擎不可省：客户端必须装 sherpa（CPU、无 torch、无 GPU 依赖）作为"最小自给能力"。这是整套方案的降级底线。

服务端侧：POST /v1/asr?variant=short 用一个小模型常驻显存，单请求 < 300 ms，不需要调度器介入。

4. 说话人分离：切在 embedding 之后、clustering 之前

4.1 看清 pyannote 流水线的三段

diarize.py 里 SpeakerDiarization 实际是三步：

步骤现状实现性质
分段 segmentationModel.from_pretrained(segmentation_dir())模型，GPU，依赖脏
嵌入 embeddingModel.from_pretrained(embedding_dir())（wespeaker 256 维）模型，GPU，依赖脏
聚类 clusteringSpeakerRegistry.map()：256 维余弦 + 贪心匹配，不到 40 行 numpy纯数学，小向量

再加上跨段状态：_centroids 累加，整场最多十几个质心 × 256 float ≈ 10 KB。

"同一场会议跨 10 分钟分段还是不是同一个人"这个判断，就是聚类。 它不是算力问题，是状态问题。 所以它必须留客户端。

4.2 切线

步骤放哪理由
分段 + 嵌入服务端模型 + GPU + 依赖地狱（_patch_speechbrain 那 60 行就是化石）
段内聚类（可选档）服务端无状态、省流量
跨段同一性 / 全局聚类客户端状态在小向量上
命名 / 改名 / 合并 / 落库客户端业务数据

4.3 两档返回

档 1（默认，省流） —— 服务端做段内聚类，返回 local speaker + 平均嵌入：

POST /v1/diarize → 200
{
  "modelVersion": "pyannote-3.1/wespeaker-voxceleb-resnet34-LM-v1",
  "dim": 256,
  "turns": [{"start": 0.31, "end": 4.92, "speaker": "S0"}, ...],
  "speakers": {"S0": [/* 256 floats */], "S1": [/* ... */]}
}

speaker 是 local label，只在本次响应内有意义。客户端拿 turns + speakers 喂给现有的 SpeakerRegistry.map() —— 现有代码几乎不用改，只是把嵌入来源从"本地 pyannote" 换成"服务端响应"。跨段一致性、改名、合并、声纹留存全部照旧。

档 2（精修，可选） —— 服务端返回逐 turn 嵌入，客户端做全场全局聚类：

{ "turns": [{"start":..,"end":..,"speaker":"S0","embedding":[/*256*/]}, ...] }

客户端对全部 turn 做一次 AHC / 谱聚类（几千个 256 维向量，毫秒级），得到全场一致的划分。

  • 用途：用户点"说话人分得不对/人数不对"时的一键精修；长会议接缝处认错人时。
  • 代价：流量从约 5 KB/段 → 约 100 KB/段（局域网无感，广域可接受）； 且上行的是逐 turn 嵌入 —— 生物特征衍生数据，隐私等级更高，要在 UI 明示。

4.4 铁律：嵌入必须带模型版本

speaker_embeddings 表现在只有 embedding + dim。必须补 modelVersion。

SpeakerRegistry 的 0.75 阈值和声纹的 0.65 阈值只在同一个模型的向量空间里有意义。 服务端换了 embedding 模型（哪怕同样 256 维），旧质心与新嵌入的余弦就变成噪声 —— 而且不会报错，只会"突然谁都认不出来"或"把两个人认成一个人"。

配套要求：

  • 跨段比较、声纹匹配前先比 modelVersion，不一致就拒绝并明说；
  • 提供"用新模型重算本场嵌入"的操作（不重新转写，只重跑 diarize 并替换 speaker_embeddings）；
  • 服务端在 capabilities 里声明版本；客户端升级服务端时要能感知并在 UI 提示。

4.5 整场一次性 diarize？v1 不做

分段长度影响分离质量。10 分钟对 pyannote 是舒服区间，但接缝处（一个人横跨两段） 只能靠客户端嵌入匹配兜。理论上"整场一次 diarize"质量更好，但那意味着：

  • 超长请求（2 小时会议 → 几百 MB 上行）；
  • 服务端要暂存几百 MB 音频（违背 §1）；
  • 失败重试成本极高。

结论：v1 用"分段 + 档 2 全局聚类"逼近同样效果，保持服务端无状态。

5. 声纹识别：服务端只当「向量化器」

这条只要坚持"服务端不存储业务数据"，其实最清楚。

5.1 切法

子步骤放哪理由
提嵌入服务端 POST /v1/speaker/embed要模型
余弦 + 阈值 + 间隔门客户端纯数学；阈值是每客户私有调参（不同麦克风/环境/人群最优值不同）
联系人库 / 入库 / 改名 / 删除 / 合并客户端敏感个人信息 + 业务数据
会议内"识别本场"客户端（用已落库的嵌入）服务端挂了也得能用

护栏测试：遍历服务端路由表，断言没有任何写端点。 POST /v1/voiceprints、PUT /v1/enroll 这类一旦出现就该让 CI 变红。

5.2 模型版本跟着样本走

voiceprints 表加 model_id / model_version 列；匹配只在同版本内做。 库里出现混合版本时 UI 提示"用新模型重新入库 N 条"。

这是换服务端模型时唯一会静默出错的地方 —— 余弦相似度不会崩，只会悄悄认错人。

5.3 声纹是敏感个人信息

按《个人信息保护法》口径，声纹属敏感个人信息。设计上要做到：

  1. 上行只为了"算"，算完即弃（§1 的内存盘 + 立即删）；
  2. 服务端日志里没有嵌入；
  3. 客户端 UI 明示"为提取声纹需上传这段音频"，并提供"只在本地提取"的降级 （客户端若装了 pyannote 就本地跑，没装才上行）；
  4. 声纹只用于"给说话人贴标签"，绝不用于身份认证/门禁。 现有代码已贯彻"宁可不认"（阈值 + 间隔双门），这条原则要写进文档， 避免以后有人拿它当鉴权 —— 声纹是可被录音重放的，不是可信凭据。

5.4 顺带解决的一个体验问题：现场注册联系人

现在声纹样本只能从会议分离结果里"改名为联系人"获得（enroll_from_meeting）， 前提是那场会议开了"区分说话人"。有了 /v1/speaker/embed，可以支持 对着麦克风念一段话直接注册联系人：

面板「新增联系人」→ 录 10s → /v1/speaker/embed → 客户端决定入哪个联系人的库

这让声纹库不再依赖会议分离，实用性明显提升，且依然满足"库不出客户端"。

5.5 可撤销性

库里只存归一化向量、不存原始音频；删除即物理删除。 可选加"客户端随机旋转"（cancelable biometrics）—— 但既然向量根本没出客户端， 收益有限，v1 不做。

能力服务端客户端状态归属服务端挂了会怎样

7. 多客户端与鉴权

7.1 身份模型

client_id + 凭据，三级递进：

  1. 内网 mTLS（最省心：证书即身份，无需自建凭据生命周期管理）
  2. client_id:secret → 短期 JWT（1 h），JWT 带 scopes 与 quota
  3. 每请求 HMAC 签名（仅在完全无法上 TLS 时兜底）

必须上 TLS，即使内网 —— 上行的是音频与声纹衍生数据。

现在的 api_keys 表是"单机自用"模型（全局一个开关 + 一串 token）。 多客户端要补：client_id 维度、凭据轮换、撤销、最后使用时间、轮换审计。

7.2 配额是服务端唯一的多租户关注点

因为没有数据要隔离，多租户问题只剩资源。需要：

  • 并发上限、队列上限、单请求最大音频秒数、每日音频分钟数；
  • 按能力分别限额与排队（asr.short 高频；diarize 吃 GPU；两者分开，避免互相饿死）；
  • GPU 调度：小模型常驻（embedding + short ASR），大模型按需 + LRU 卸载。 这与现在 boot.py 的 stt-cmd 常驻 / stt-meeting 按需是同一个思路， 可以直接复用那套组件状态机的心智模型。

7.3 隔离级别

不存数据 ≠ 无侧信道。不同法人/部门的客户端共用同一进程仍有 显存残留、模型缓存、日志串号的风险。按"信任域"分实例，同域内共享实例。

7.4 审计

服务端只记 client_id, request_id, 端点, 音频秒数, 耗时, 状态码。 客户端持全量业务日志。两边用 request_id 对齐 —— 排障能对上，服务端侧无内容。这是"不存储"与"可排障"的平衡点。

8. 可退化性：三种部署形态

必须都支持，这是"服务端运维出问题不能拖垮 ECHO"的保证。

形态场景价值
单机双进程同机跑 client + server，走 127.0.0.1第一步验证，先把协议和切面跑通，风险最低
部门一台 GPU + N 客户端目标形态无状态 server，随便加实例/加机器
客户端自给降级形态客户端保留本地引擎（sherpa + SenseVoice + 可选 pyannote），服务端不可达时会议转写照跑，只是慢

配套：

  • 客户端把"服务端能力"做成一级状态（现成挂点：boot.py 组件状态机 + GET /api/status）， UI 上服务端能力标灰 + 明确提示"当前走本地引擎"；
  • 离线队列：待转写分段排队，服务端恢复后补传。 比"转写失败"体验好得多，且天然契合无状态设计。

9. 落地路径：接口先行，双轨实现

不要一次性重写 api.py / meeting.py。

仓库里已有现成挂点：app/providers/（kind = asr / llm / tts， register() 可覆盖、active_id() / asr_if_configured() 已把"用哪个"收敛成一处判据）。 前后分离本质上就是：给 asr 和新增的 diarize、speaker-embed 各加一个 source="remote" 的 provider。

阶段内容验收
0定协议（capabilities + asr/diarize/embed）；抽出 CapabilityClient 接口，本地实现原样保留契约测试；客户端能在"本地/远端"之间切换而行为等价
1服务端只包能力（无 DB、无业务逻辑）；客户端加 remote provider自检：跑完整请求后无落盘、日志无内容（§1.2）
2明确划界：SpeakerRegistry / voiceprint 明令只在客户端；服务端路由表断言无写端点护栏测试（沿用本仓库"铁律 + 测试钉住"的做法）
3多客户端鉴权 / 配额 / 审计 / TLS两客户端并发压测；断网降级演练
4可选：本地重依赖（pyannote/torch）变成可选安装，安装包瘦身最小安装下会议转写仍可跑（走服务端）

阶段 0 的"行为等价"是关键：先用同一套接口把本地实现包起来，证明切面正确， 再动服务端。这样任何一步出错都能立刻回退到全本地。

10. 三个难点的"一句话版本"

  • 指令转写：本地保底，服务端只做可选增强；用「执行原子点 + grace 窗口」 避免"服务端延迟"与"命令重复执行"互相污染。可用性归本地，准确率归服务端。
  • 说话人分离：切在 embedding 之后、clustering 之前 —— 分段/嵌入上行（模型在这），跨段同一性与命名留本地（状态在这）。 嵌入必须带模型版本，否则换模型会静默认错人。
  • 声纹识别：服务端只当向量化器，匹配、阈值、库全在本地。 声纹库是敏感个人信息，任何"存到服务端"的变体都不该考虑。

11. 需要拍板的三个选择

  1. 服务端形态：内网自建 GPU 机器，还是接单位已有的推理平台？ 后者决定 capabilities 能不能自定义、modelVersion 由谁保证。
  2. 指令上行默认开还是关：建议默认关，首次使用时询问； 因为指令路径的隐私面比会议更大，而收益（准确率）是可选的。
  3. 是否引入 Opus：纯局域网可以不做（PCM 直传足够）； 有跨地域/弱网客户端则必须做（19 MB → 1–2 MB）。
