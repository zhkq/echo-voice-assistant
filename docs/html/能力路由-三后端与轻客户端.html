本文回答两个互相纠缠的问题：

  1. 客户端要能在本机 / ECHO 能力后端 / 内网公共 ASR 服务之间选择模型，怎么设计？
  2. 客户端安装要简单快捷、办公本可用，这个约束如何反向决定上面的设计？

前置文档：docs/前后分离-能力服务化设计.md（业务数据留客户端、服务端无状态） 后续文档：docs/ECHO能力后端-服务端设计.md —— 本文 §7 的展开： EnginePool 模型生命周期、并发与显存预算、临时文件政策、错误码契约、部署与护栏测试。 横向文档：docs/统一路由-模型能力与设备.md —— 把本文的能力路由与 LLM 提供商路由、采集设备路由、播放设备路由统一成一套"按优先级选资源"的设计。 相关现状：app/providers/__init__.py、app/components.py、app/modelinfo.py、 components/offline-pack.json、app/audio/stt.py、app/audio/diarize.py、dsh-failover/proxy.py

0. 结论速览

要建的不是"一个服务端"，而是"一层能力路由 + 三个后端"。 服务端只是其中一个后端。

新加的性能/安装约束把两件事同时钉死了：

  1. "本机"不是对等的第三个后端，而是保底后端。 它只提供 唤醒 + asr.text(命令) + tts，不提供 diarize / speaker.embed / 高精度 asr.text。
  2. torch 就是分界线。 默认安装不含 torch；所有 torch 系能力 （SenseVoice / Qwen3-ASR / pyannote）默认一律走 ECHO 能力后端，本机只作为 "离线增强包"选装。

一个漂亮的副产物："说话人分离切在 embedding 之后"这条设计，在办公本上不只是最优解， 而是唯一可行解 —— 因为办公本根本装不上 pyannote。

三条铁律（建议写进 AGENTS.md 的"铁律"区）：

铁律内容
L1默认安装 profile 不含 torch（也不含 CUDA、不含编译步骤）。
L2产生向量的能力（diarize.* / speaker.embed），只允许运行在能声明 vectorSpaceId 的后端上。内网公共 ASR 服务不满足，永久排除。
L3唤醒与指令转写必须有本机后端，且该后端不得依赖服务端可用性。

0.1 重要更正：sherpa-onnx 比本文初稿假设的强得多（2026-09-23 实测）

本文初稿写的是"办公本装不上 pyannote → diarize/speaker.embed 必须走服务端"。 实测后这条不成立 —— sherpa-onnx 1.13.6（整个包只有 27.4 MB）自带：

能力本机 API说明
唤醒KeywordSpotter已在用
流式命令转写OnlineRecognizer.from_transducer已在用
离线会议转写OfflineRecognizer.from_sense_voice / .from_whisper / .from_paraformer / .from_qwen3_asr无需 torch / funasr / ctranslate2 / transformers
声纹提取SpeakerEmbeddingExtractor（compute / create_stream / dim / is_ready）无需 torch
声纹库与匹配SpeakerEmbeddingManager（add / remove / search / verify / score / all_speakers / num_speakers / dim）原生实现，无需 numpy 手写余弦
说话人分离OfflineSpeakerDiarization + OfflineSpeakerDiarizationConfig + OfflineSpeakerSegmentationPyannoteModelConfig基于 pyannote 分割模型的 ONNX 版

所以正确的结论是：

  • diarize / speaker.embed 在办公本上可以做，只是质量低于 ECHO 后端的 pyannote 4.x + PLDA 流水线。 于是它从"可行性问题"变成质量/成本权衡 —— 而这恰恰正是能力路由要解决的问题。
  • 本文 §2 表格中 diarize.* / speaker.embed 的"❌ 装不上"应读作"默认档不装 torch 系实现； 可用 sherpa-onnx 轻量实现替代"；§5.1 路由表里 "ECHO 后端（唯一）" 应读作 "默认首选 ECHO 后端，可切换为 sherpa-onnx 本机轻量后端"。
  • vectorSpaceId 的重要性因此上升为必需（不再是"可选但很值"）： sherpa-onnx 的声纹模型与 pyannote 的 wespeaker 是两个不同的向量空间， 一旦允许两者并存，"同一场会议不得混用"就是硬约束，不是最佳实践。

模型体积尚未实测（本文不写未经核实的数字）。已确认存在的模型族： csukuangfj/speaker-embedding-models、 onnx-community/pyannote-segmentation-3.0、 sherpa-onnx 说话人分离模型清单。 接入前先实测体积与中文效果，再决定它进不进默认档。

1.5 实测：不要内置 faster-whisper，改用 sherpa-onnx 离线模型

components/offline-pack.json 里 stt-whisper-base 只声明了 141 MB 模型， 看起来是个便宜的兜底。实测后这个账算错了：

项实测备注
faster-whisper 模型 base141 MB声明值，准确
faster-whisper 依赖 ctranslate2795.2 MBPyPI wheel 捆了 CUDA
├ cublasLt64_12.dll637.7 MB纯 CUDA
├ cublas64_12.dll97.8 MB纯 CUDA
└ ctranslate2.dll（真核心）56.5 MB只有这点是有用的
sherpa-onnx（整个运行时）27.4 MBimport sherpa_onnx 实测

而且 -Profile offline 的默认组件集 （build-package.ps1:215：runtime-core, stt-sherpa, stt-whisper-base, wake-kws） 只打模型、不打 runtime —— runtime-core 装的是 requirements-core.txt， 里面没有 faster-whisper/ctranslate2。所以照现在的清单出一个"随包"版， 用户拿到手仍然要在首次使用时 pip 装那 795 MB。

正解：内置的离线会议转写改用 OfflineRecognizer.from_whisper（或 from_sense_voice / from_paraformer）—— 运行时已经在包里了（sherpa-onnx 本就是唤醒与流式命令转写的依赖）， 只多一份 ONNX 模型文件。代价：模型体积与中文效果需实测，且与 faster-whisper 的输出形态 （句级时间戳）可能有差异，要先对齐 _align_sentences() 的输入契约。

范围澄清（重要）：这条的适用范围只是客户端的"兜底档"。 现网已验证效果的两个引擎 —— sensevoice（命令档，常驻）与 qwen3asr（会议档，按需）—— 是服务端的主力，不换（见 docs/ECHO能力后端-服务端设计.md §4.5/§4.6）。 客户端换成 sherpa 离线模型，换的是"办公本在服务端不可达时的降级实现"， 不是"系统的主力转写质量"。

一个待验证的假设：funasr 的 SenseVoice 与 sherpa-onnx 的 from_sense_voice 很可能是同一份权重的两个运行时（PyTorch/funasr vs ONNX Runtime）， Qwen3-ASR 同理（from_qwen3_asr）。若成立，瘦身不一定牺牲质量。 但这是假设，必须用同一段真实会议音频实测对比才能定： 文本准确率、标点、繁简、时间戳形态、耗时、体积。

2. 每个能力槽在"办公本"上的可用性

把能力拆成槽（slot，见 §4），逐槽看本机能不能扛：

能力槽办公本本机需要装什么默认走向
wake✅ sherpa KWS，CPU，40 MB—本机（必须）
asr.text（指令）✅ sherpa 流式 int8，RTF ≈ 0.1–0.3—本机（L3：不可上移）
tts✅ SAPI / say / espeak（系统自带，零依赖）—本机；可选 edge-tts（纯 Python）
asr.text（会议）⚠️ 可选 whisper-base int8（141 MB + ctranslate2，torch-free，RTF ≈ 0.3–0.6）选装ECHO 后端；装了就本机兜底
asr.timestamps⚠️ whisper 可以给句级同上ECHO 后端；本地兜底
diarize.turns⚠️ 可（sherpa-onnx ONNX，见 §0.1），质量低于服务端轻量 ~几十 MBECHO 后端优先，可切本机轻量
diarize.embeddings⚠️ 同上同上同上
diarize.turn_embeddings⚠️ 同上（自算逐 turn 嵌入）同上同上
speaker.embed⚠️ 可（SpeakerEmbeddingExtractor），向量空间与服务端不同同上本机优先（隐私），需高质量时走服务端

这张表就是"办公本可用"的定义：唤醒、指令转写、播报全本地且秒级；会议转写、 说话人分离、声纹都可以本机跑（sherpa-onnx 轻量实现），但默认走 ECHO 后端拿质量。 服务端不可达时，命令链路完全不受影响，会议链路降级到本机轻量实现或排队。

3. 三后端的定位：不是对等的三选一

维度本机ECHO 能力后端内网公共 ASR 服务
部署进程内我们自己运维的服务别人的服务
协议函数调用我们定的 REST/SSE未知/厂商专有
能力唤醒 / asr.text / tts全部槽只有 asr.text（可能无时间戳、无说话人）
vectorSpaceId装了增强包才有✅ 我们声明❌ 无法声明 → L2 永久排除
模型版本可控是是否
可用性100%（装了就有）取决于我们自己取决于别人
隐私不出机出机到内网出机到内网第三方
额度免费无限我们自限别人限，可能收费
延迟最低（无网络）网络 + 排队网络 + 排队 + 更不可控

三类后端的能力是包含关系，不是并列关系：

本机        ⊂  只有 asr.text / tts / wake
内网公共    ⊂  只有 asr.text（质量高，但不可控、无向量）
ECHO 后端   =  全集（含向量类能力）

所以路由表不是"三选一"，而是"给每个槽找第一个能满足它的后端"。

4. 能力槽分解：核心抽象

4.1 现有代码里已经有雏形

app/meeting.py:_fallback_sv_rows() 现在干的是：

whisper 出时间戳骨架 + SenseVoice 出文本 → 按字符位置对齐切句 → 组合成句级时间戳行

这就是"拼装" —— 一次转写用了两个不同引擎，各出一个槽。设计上要做的事， 就是把这个写死的两路组合，一般化成 "槽 → 后端"的路由表 + 执行计划。

4.2 能力槽清单（v1）

槽语义产出
wake唤醒词检测事件
asr.text音频 → 文本text
asr.timestamps音频 → 时间轴骨架[(start,end)]
asr.streaming流式部分结果增量文本流

4.3 需求 → 执行计划

一个需求是一组槽 + 约束：

// 需求：会议转写
{
  "slots": {
    "asr.text":         {"need": "required",  "quality": "high"},
    "asr.timestamps":   {"need": "wanted"},
    "diarize.turns":    {"need": "optional"},
    "diarize.embeddings": {"need": "optional"}
  },
  "constraints": {
    "privacy": "lan",          // none(不出机) | lan(允许内网) | wan
    "latency": "batch",        // realtime | interactive | batch
    "lockVectorSpace": true    // 同一场会议必须同一个 vectorSpaceId
  }
}

路由结果是一份执行计划，每个槽可以落在不同后端：

// 计划示例：办公本 + 有内网公共服务
{
  "asr.text":            {"backend": "intranetASR", "reason": "quality=high 且 clock 允许出内网"},
  "asr.timestamps":      {"backend": "echoServer",  "model": "whisper-small"},
  "diarize.turns":       {"backend": "echoServer",  "model": "pyannote-3.1"},
  "diarize.embeddings":  {"backend": "echoServer",  "vectorSpaceId": "ws-resnet34-v1"}
}

→ 客户端按 _align_sentences() 现有的思路把三段结果合成句级转写行。 → 每一步都记 reason，面板能回答"这次为什么走了本机"。

4.4 拼装规则（要写死，别到时候各写一份）

规则内容
无时间戳兜底asr.text 后端不给时间戳，且 asr.timestamps 也不可用时，退回现有的按字数均摊（_split_provider_text），并在数据里标注 timestamps: "estimated"（现在这个信息只写在注释里，面板和导出看不出来）
向量必须同源同一场会议的所有 diarize.* / speaker.embed 结果必须来自同一个 vectorSpaceId（§6）
槽不可跨会议复用执行计划按会议生成一次并写进 meta.json，整场锁定
缺槽不等于失败diarize.* 拿不到时，会议照常产出无说话人的转写（现在是 meetingDiarize 开关，改成能力缺失自动降级 + 面板提示）

三行要特别记住：

  • asr.text（指令）刻意不参与降级 —— 它是 L3，链路里不允许出现网络后端作为主选 （服务端只能"增强"，见前置文档 §3）。
  • 会议相关的槽链上没有本机：后端全不可用时，行为是排队等待，不是降级为本机粗转写。
  • "不默认本机" ≠ "禁止本机"。 上面说的是默认档不装、不自动回落； 用户如果自己装了本机引擎（比如台式机有 GPU、想全本地不出网）， 允许显式把某个槽的后端设成本机 —— 那不是"兜底"，是他自己选的主选。两种要分清：
兜底（已取消）显式主选（保留）
触发后端不可用时自动回落用户主动配置
默认档装模型、在链上不装、不在链上
谁承担质量用户不知情地拿到粗结果用户明确知道自己在用本机

但有一条例外要留意：本机 asr.* 只是转写，不产生向量，安全； 而本机 diarize.* / speaker.embed 一旦启用，就引入了第二个 vectorSpaceId —— 此时 §6.3 的会议级锁定（同一场会议不得混用）必须重新生效。 这也是为什么下面把"客户端不产生向量"写成一条默认前提，而不是永久事实。

5.1.1 连带简化：客户端不产生向量 ⟹ 全系统只有一个 vectorSpaceId

会议不做本机兜底，就意味着 diarize.* / speaker.embed 在客户端没有任何本机实现。 于是：

  • 客户端永远不会产生嵌入 → 全系统只有一个 vectorSpaceId（后端声明的那个）
  • 前置文档 §6.3 的「会议级锁定不得混用向量空间」从硬约束降级为天然成立
  • §6.4 的「向量空间校准」也不必做了
  • §3 表里"内网公共无法声明 vectorSpaceId 所以永久排除（L2）"这条依然成立， 但它现在只是"防止未来有人接错"，不再是日常要防的混用风险

代价：服务端不可用时，会议彻底没有说话人与声纹（这是"不兜底"的直接后果，接受）。

唯一的例外口子（见 3.0 总览 §5.1）：如果将来允许本机注册联系人 （sherpa 的 SpeakerEmbeddingExtractor，模型仅几十 MB），那就必须让服务端也用同一个模型， 否则本机注册的样本与会议里认出的嵌入不可比。 这条要先实测"同权重跨运行时是否可比"才能开 —— 在那之前，注册与识别都走后端。

5.2 降级原因必须分类（沿用 stt.transcribe_ex 的思路）

现在 transcribe() 把所有失败吞成一个空串，transcribe_ex() 才区分 ok/empty/error/missing。 能力路由要把这个思路推到全链路，降级原因至少分：

unavailable       后端连不上
timeout           超时
quota             额度用尽 / 被限流
auth              鉴权失败
privacy-denied    约束不允许（例如 policy=lan 而目标是 wan）
unsupported       后端不支持这个槽（内网公共服务被问 diarize）
vector-mismatch   vectorSpaceId 与本次会议锁定的不一致
quality-rejected  结果不达标（空文本 / 说话人数异常）

每次降级写一条 source=capability 日志，含 slot / from / to / reason / 耗时。 面板「能力路由」页签按后端聚合成功率与最近降级原因。

5.3 熔断：直接复用现成的心智

dsh-failover/proxy.py 已经有成熟做法：主动探测 + 被动健康 + 连续失败摘除该通道 + 冷却。 能力路由是同一类问题，应该复用同一套（不要另写一份）：

  • 每个后端一个健康状态：online / degraded / offline
  • 连续失败 N 次 → 摘除 T 秒；期间所有槽跳过它
  • 主动探测：GET /v1/health（ECHO 后端）；内网公共服务用一次极短音频探测
  • 面板「能力路由」页签展示形态可参照 app/router_admin.py（注册态 / 成员 / 派发统计 / 熔断状态聚合）

6. 向量空间一致性：三后端把它放大了

6.1 vectorSpaceId 不等于模型名

不要用模型名判断两个嵌入是否可比，因为：

差异来源影响
精度（fp16 vs fp32）余弦差 ~1e-3，可忽略
预处理（重采样滤波器、归一化、VAD 切分）可能造成系统性偏移，不可忽略
模型权重 revision 不同完全不可比

所以判据是后端声明的 vectorSpaceId：同一 vectorSpaceId = 该后端保证其向量互相可比。 客户端只按这个值分组比较，永不按模型名猜。

好消息（轻客户端带来的简化）：默认安装下本机没有向量能力， 所以全系统只有一个 vectorSpaceId（ECHO 后端声明的那个）。 多向量空间问题只会在"用户额外装了离线增强包"时出现。

6.2 落库要加字段

speaker_embeddings / voiceprints 现在只有 embedding + dim。要补：

vector_space_id   后端声明的空间标识（比较的唯一依据）
backend_id        产生它的后端（排障 + 重算用）
model_version     展示用（"这库是用哪个模型建的"）

跨空间不比较；库里出现混合空间时 UI 提示"用新模型重新入库 N 条"。

6.3 会议级锁定

同一场会议的分段不能混用不同 vectorSpaceId 的 diarize 结果，否则跨段质心不可比。 规则：

  • 会议首次转写时锁定 vectorSpaceId + 后端，写进 meta.json；
  • 中途后端不可用 → 排队等待或整场重算，不允许"前 5 段用 ECHO、后 5 段用本机"；
  • 提供"换后端重算本场"（只重跑 diarize，不重新转写）。

6.4 空间校准（可选但很值）

首次把某个后端接入某个客户端时，用一段固定音频（或用户自己的样本）在两个后端各算一次嵌入，测余弦：

  • ≥ 0.9 → 视为同一空间，可互操作
  • < 0.9 → 标记为不同空间，拒绝混用

这个能做成面板上的一个「向量空间校准」按钮，把"能不能混用"从猜测变成实测。

7. ECHO 能力后端要建什么

7.1 接口清单

方法路径语义状态
GET/v1/capabilities能力 + 模型 + vectorSpaceId + 限制无
GET/v1/health存活 + 队列深度 + 显存无
GET/v1/ready就绪（模型池可服务则 200）无
POST/v1/pair配对：一次性码 → client_id + secret无
POST/v1/token换令牌：Basic client_id:secret → 短期 JWT无
POST/v1/asr音频 → 文本（?variant=short|long，可选时间戳）无
POST/v1/diarize音频 → turns + 嵌入（档 1 / 档 2）无
POST/v1/speaker/embed音频 → 嵌入无
POST/v1/tts文本 → 音频（可选）无

除了换凭据那两条，没有任何写端点（护栏测试见 §10）。 那两条写的是服务端自己的管理数据（设计 §8.5），不碰内容。 刻意不做 job 队列（理由见前置文档 §2.2）。

capabilities 必须含 vectorSpaceId，且它必须稳定 —— 换 embedding 模型就要换 id， 客户端据此拒绝混用而不是静默认错人。

7.2 实现要点：复用引擎层，剥掉业务层

现有 app/audio/stt.py 与 app/audio/diarize.py 实际上是干净的引擎层：

  • stt.py 只 import os/re/sys/threading + app.paths
  • diarize.py 只 import os/threading/wave + app.paths + numpy
  • 业务编排全在 meeting.py / assistant.py

所以服务端可以直接复用这两个模块，不 import db / meeting / assistant / api。

再加一条狠但有效的架构约束（呼应本仓库"服务端只认识槽，不认识业务"）：

服务端代码里不出现 meeting / command / summary 这些词。 它只认识 slot，不认识"会议/命令/纪要"。

这条能直接写成测试（grep 服务端目录），比任何口头约定都可靠。

7.3 服务端自己也要能选引擎

服务端内部也可能有多个模型（本机 GPU vs 多卡 vs CPU），但这是服务端内部的事，不暴露成客户端的复杂度： 客户端只传 variant=short|long 或 model=<id>，服务端自己调度。

服务端内部调度可以直接复用 boot.py 的心智：小模型常驻（embedding + short ASR）， 大模型按需 + LRU 卸载 —— 这与现在 stt-cmd 常驻 / stt-meeting 按需是同一个模型。

7.4 服务端复用客户端代码的边界

好消息：服务端和客户端是同一个仓库（echo-dev），引擎层可以直接共用， 不用维护两份 ASR/Diarize 实现。

代价：容易让服务端悄悄长出业务概念。所以 §7.2 那条"不出现 meeting/command/summary" 的门禁是必须的 —— 它保证"服务端不存储业务数据"不是靠自觉，而是靠代码结构。

8. 内网公共 ASR 服务的适配

8.1 它不受我们控制，所以必须按"不可控"设计

8.2 我们手上的那台内网 ASR 不是 OpenAI 兼容的（2026-09-24 更正）

这一节原来写的是"内网适配器 v1 = 直接复用 OpenAICompatAsrProvider"。那条路对我们 实际要连的那台服务不成立 —— 实测（10.100.0.24:10095，同事的 zysk-* 容器）：

事实与假设的差别
服务是 WebSocket 流式（wss://…/ws/，另带 /health、/ready）不是 POST /audio/transcriptions（一次性上传、一次性返回）
只走"连上去、喂音频块、收增量文本"这条路OpenAICompatAsrProvider 那套手工拼 multipart 的代码一行都用不上
拿不到"整段音频进、带句级时间戳出"的接口我们会议链路要的 asr.timestamps 可能根本没得给

app/providers/openai.py:OpenAICompatAsrProvider 仍然是别的对接方式的正解 （任何 OpenAI 兼容的在线转写都能用），只是它不是这台服务的适配器。 "能复用"这句写在这里快一个月了，属于设计里的假话，先改掉。

8.2.1 由此产生的一个真岔路：轻客户端要不要塞一个 WebSocket 库

stdlib 里没有 WebSocket 客户端。三条路，各有代价：

走法代价与铁律的关系
A. 引第三方 WS 库（websockets / websocket-client）客户端多一个依赖（含它的依赖树）撞 L1（默认档装机要短、不许有编译步骤）。websockets 是纯 Python，代价还算可控，但"为了一个可选后端"引依赖，方向不对
B. 手写 WS 客户端（stdlib：HTTP Upgrade 握手 + 帧的掩码/分片/关闭）约 150–250 行，且协议细节都得自己担（ping/pong、超时、重连、大帧）不撞 L1，但这是"自己养一个协议实现"，出错成本高
C. 当作可选组件（像"离线增强档"一样按需装，不进默认档）装了才有这个后端；没装就如实少一个后端（absent）最合 L1 的本意：默认档不做这件事，需要的人自己加一档

倾向 C + A：默认档不带它；在"增强档/可选组件"里带 websockets。 理由：内网公共 ASR 是锦上添花（质量高一点、但有 ECHO 后端与本机在）， 为它把默认档的装机时间与失败面撑大，与"办公本 3 分钟装完"是直接冲突的。 而 B 的 200 行协议代码，我们没有测试环境去验证（这台服务在同事的共享机器上， 用户 2026-09-24 明说"先不管测试环境了"）—— 没验证过的协议实现不该进主链路。

8.2.2 开工前要先问清楚同事的三件事

  1. 协议：是 funasr / sherpa 那套标准 WebSocket 协议吗？还是自家封的？ （帧格式、是否需要先发一条 JSON 配置、采样率与声道要求）
  2. 时间戳：给不给句级/字级时间轴？只给增量文本的话， 我们这条链路的 asr.timestamps 就只能标 estimated（见 §4.4 的拼装规则）—— 这件事直接影响会议纪要的质量，得先知道。
  3. 稳定性：并发几个？有没有配额？会不会被重启？（决定熔断与降级的默认值）

在那三条清楚之前，intranet 适配器不写。 写一个连不上、也没法验证的适配器， 只会让"配了却永远失败"变成一个谜 —— 这正是 build_default_router 现在 故意不造内网后端的理由（那段注释就是为这件事写的）。

9. 客户端落地

9.1 两个层次，别混在一起

层职责现状
app/providers/选一个实现（llm / tts / 整段 asr）✅ 已有 register() / active_id() / asr_if_configured()
app/capabilities/（新增）槽 → 后端链 → 执行计划 → 结果拼装❌ 待建

为什么分开：providers/ 是"从 N 个里挑 1 个"，而会议转写需要"从 N 个里挑 M 个并拼装"。 后者是 meeting.py:_fallback_sv_rows 一般化后的东西，放 providers/ 里会把那个抽象撑坏。

9.2 ProviderSpec 要扩两个字段

现有 ProviderSpec 已有 source（local/online）、egress（bool）、egress_note、ready() —— 挂点是对的，只需：

  1. source 取值扩展：local / echo-server / intranet / online
  2. egress 从 bool 升级为分级：none（不出机）/ lan（允许内网）/ wan（允许公网）

为什么必须分级：现在 egress=True/False 无法表达"可以出到内网、但不许出公网"， 而这正是 ECHO 能力后端与内网公共服务的共同定位。分三档后，路由的 privacy 约束（§4.3）才能落地成一道真实的拦截。

  1. 新增 provides 字段：声明这个后端能提供哪些槽。 有了它，"内网公共服务只能满足 asr.text"就是数据，不是散文。

阶段 0 落地时定的几件事（都在 app/capabilities/ 的注释里）：

  • 槽取交集，别搬服务端的槽名：服务端 capabilities.slots 里会出现 asr.long （那是它模型自己的主槽名），而客户端的词汇只有 base.SLOTS 那一套。取交集。
  • 降级原因用权威词汇，行为看 code：服务端坚持要分开 client_busy 与 server_busy（"合并了客户端就只能盲目重试"），而权威词汇里只有一个 busy —— 所以 reason 只回答"换不换后端"，retryable + code 回答"要不要再试"。 这个缺口记在 docs/3.0-PROGRESS.md 的待办里，没有擅自扩词汇表。
  • 说话人这一家子必须同源：diarize.turns 自己不产出向量，但它的标签只在同一次 分离里才有意义，所以它与 diarize.embeddings / speaker.embed 一起受 L2/L5 约束 （SAME_SOURCE_SLOTS）。设计 §4.4 的"向量必须同源"说的就是这条。

阶段 -1 的价值：它是纯收益、不依赖任何新架构 —— 即使前后分离最后没做， "默认档瘦身"这件事本身就已经解决了"办公本装不上"。 先做它，风险最低、见效最快。

阶段 3 的界面落点（2026-09-24 定，别再多开页签）

那块界面长在「能力」页签里（web/index.html 的 view-capabilities 里一张 capRouteCard），不新开「能力路由」页签。理由不是省事：用户 2026-09-19 明确要求过 "每个能力只在这一处出现" —— 当时模型页签 / 组件页签 / 设置里的 provider 卡片三处都在讲 同一件事，被合并成了一个页签。而"这个能力用哪个实现"与"用本机还是用那台 GPU" 是同一个问题的两半，再开一页就是走回那次合并之前。契约由 tests/test_capability_panel.py::test_the_card_lives_inside_the_capabilities_tab 钉住。

界面这一层只显示事实（每个后端自己 describe() 出来的东西 + 配置里选了哪个）， 不自己算"会选中谁"：那个答案只能由 router.plan 给出（会议主链路用的就是它）， 页签里再算一遍迟早会与主链路给出的不一样 —— 那时人看到的是一张 "说会走 GPU 其实走了本机"的表，比不显示更糟。

客户端侧新增的接口（app/api.py + app/capability_admin.py）：

方法路径干什么
GET/api/capability页签要的全部数据：配对状态 + 每个后端 + 每个用途选的哪个后端 + 那几行设置
POST/api/capability/probe立即重问所有后端（不吃 30 秒缓存）
POST/api/capability/pair{base_url, code} → 换凭据并落盘；失败回 400 + 一句人话
POST/api/capability/unpair忘掉本机凭据（服务端那本账归管理员）

那几行设置（capabilityEchoServerUrl / capabilityPrivacy / 三个"用哪个后端"） 在 config.py 里是 hidden=True，所以不出现在设置页；它们由 Settings.all(include_hidden=True) 出成与设置页同一形状的行，面板用同一个 renderSettingRow 渲染 —— 这样不会出现"设置页能改、卡片里少一项"这种漂移。
