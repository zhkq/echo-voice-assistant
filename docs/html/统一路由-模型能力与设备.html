统一路由：模型 · 能力 · 采集设备 · 播放设备

源文件 docs/统一路由-模型能力与设备.md · 由 scripts/build-design-page.py 生成，勿手改

用户需求（2026-09-23）：路由能力包含 asr/tts 等模型的路由、DSH 的大模型提供商路由， 再增加 mic 设备与播放设备的队列，按优先顺序连接 —— 例如开会录音时使用优先级最高的在线设备。

本文回答：把四处"按优先级选资源"统一成一套设计。

0. 结论速览

统一的是"选择"，不是"生命周期"。 四类候选资源共享同一个选择内核 （有序候选 + 排除判据 + 健康状态 + 降级原因），但租约与队列语义必须各自实现 —— 强行合并会把两个本质不同的东西套进一个抽象。

三个关键判断：

#判断依据
R1设备的本质是独占句柄，不是无状态服务模型/后端一次请求就走；设备被持有期间别人不能用，且持有者可能是两小时的会议录音线程
R2互斥分两级：泳道级 + 设备级现状 mic.py 是全局一把锁 → 配了"会议用全向麦 + 指令用耳机"也并行不了（AGENTS.md 记的待办）
R3只有播放需要真队列（可抢占）；采集要快速失败播报必须串行且高优先级要能打断长朗读；采集让用户干等一个麦克风是负体验
R4采集只有两条平级泳道（指令 / 会议），在明确需要时懒选设备，不做抢占去掉整个优先级/抢占子系统；不同设备天然并行，同设备后到者被拒

设备路由 100% 在客户端。 服务端没有麦克风，设备永远不会成为一个能力槽。 这条要明确写死，避免有人把它设计进 /v1/capabilities。

唤醒本次明确排除（不进候选链、不进泳道、不参与互斥设计）—— 见 §3.8。

1. 四类候选资源：共享什么，不共享什么

模型路由（LLM 提供商）能力路由（ASR/diarize/embed）采集设备（mic）播放设备
候选echo-auto 的通道们本机 / ECHO 后端 / 内网公共用途对应的有序设备链用途对应的有序设备链
顺序依据通道号路由表优先级用户排序用户排序
可用性判据主动探测 + 熔断健康 + 配额 + 隐私约束在位 + 黑名单 + 未被占用 + 实开成功在位 + 未被占用
生命周期无租约（请求级）无租约（请求级）独占租约（长持有）独占租约（短持有）
并发熔断跳过即可服务端有界队列 + 背压不可并发（同设备）不可并发（同设备）
排队？否服务端排队否 —— 快速失败 + 短重试是 —— 优先级队列 + 可抢占
降级方向下一通道下一后端下一设备 → 系统默认下一设备 → 系统默认

共享（做成内核）：有序候选 / 排除判据 / 健康状态与冷却 / 降级原因 / 选中理由日志。

不共享（各自实现）：租约、队列、抢占、释放。

已有先例：dsh-failover/proxy.py 的「主动探测 + 被动健康 + 连续失败摘除 + 冷却」 就是这套内核。能力路由与设备路由复用它，不要各写一份。

2. 选择内核

# app/routing/core.py（新增）
class Candidate(NamedTuple):
    key: str            # 稳定标识（设备名 / backend id / 通道 id）
    priority: int       # 越小越优先
    meta: dict

class Pick(NamedTuple):
    key: str
    reason: str         # "ok" | 具体为什么跳过别人
    skipped: list[tuple[str, str]]   # [(key, reason), ...] 全部候选的去向

def pick(candidates, *, eligible, health, pick_one) -> Pick | None:
    """按 priority 升序，逐个: eligible? → health? → pick_one() 成功即返回。

    关键：**永远返回 skipped 列表**。用户要知道"为什么没用我要的那个设备/后端"，
    而不是只看到一个"失败了"。这直接对应 §5 的面板与日志。
    """

skipped 里的 reason 取值必须在四处保持同一套词汇，否则面板和排障无法统一：

absent          不在位（设备拔了 / 后端没配）
blocked         被策略禁止（设备黑名单 / privacy 约束）
busy            被自己占用（租约表里有人持有）
offline         探测不通
circuit-open    熔断冷却中
quota           额度用尽
unsupported     不支持该需求（内网公共服务被问 diarize）
vector-mismatch vectorSpaceId 与本次会议锁定的不一致
open-failed     实开失败（设备）
error           其它失败（带 detail）

3. 采集设备路由

3.1 现状盘点：已经有的比想象多

已有位置说明
用途分级recorder.INPUT_DEVICE_KEYS = {command, meeting}指令与会议各有设备设置
三级优先解析recorder.resolve_input_device(purpose)该用途设置 → 通用 inputDeviceId → -1（系统默认）
设备名 = 稳定键recorder.find_input_device()注释明确写了"PortAudio 索引会随在位设备增减整体平移"——这个坑已经踩过并修好了
多 API 去重recorder.rank_hostapi()同名出现在 WASAPI/MME/DS 时，WASAPI 优先（WDM-KS 不做重采样，蓝牙免提端点常打不开）
设备清单缓存recorder.list_input_devices_cached(30s)录音路径不每次查 PortAudio
独占租约 + 抢占mic.py：_foreground / _yield_requested / background=前台采集抢占唤醒监听
崩溃隔离mic.py：_quarantined + _IsolatedStream 子进程macOS 上设备操作在可抛之子进程里跑，HAL 死锁时杀子进程而不杀 ECHO
缺设备回退策略resolve_input_device() 末尾回退系统默认 + 写 warn 日志（"宁可回退也不要打不开，但绝不静默"）

结论：底子很好，缺的正好是用户要的那三样。

3.2 缺口

缺口现状用户要的
① 有序候选链每个用途一个设备值"按优先顺序连接" —— 需要列表
② 「在线」判定解析到索引就直接尝试打开，失败才发现"优先级最高的在线设备" —— 需要先判定再选
③ 设备黑名单只有 AGENTS.md 里一条人读的铁律（"不要用 sd.default.device[下标]"）需要机制的 deny-list（见 §3.5）
④ 互斥粒度全局一把锁（mic.py:_lock / _foreground）两条泳道用不同设备时要能并行（见 §3.6）

3.3 设计：两条平级泳道，各一条有序候选链

只有两条泳道：指令 与 会议。 唤醒不进候选链（理由见 §3.8），麦克风测试沿用指令泳道。

// 只两条链；旧的单值设置全部保留为链尾兜底（零迁移）
"commandInputDevices": ["Jabra 耳机", "笔记本内置麦克风阵列"],
"meetingInputDevices": ["MAXHUB 全向麦", "笔记本内置麦克风阵列"]

解析顺序（完全兼容现状，只在前面插入"链"这一段）：

该泳道的候选链（按序探测）
  → 该泳道旧单值（commandInputDeviceId / meetingInputDeviceId）
  → 通用 inputDeviceId
  → -1（系统默认，永远可用，是兜底底线）

两条泳道之间没有优先级 —— 它们平级。谁在用什么设备由 §3.6 的两级互斥决定， 不由优先级数字决定。这样"抢占"这个概念就不需要存在了。

链尾重叠要留意：两条链的最后一档常常都是"内置麦"。若会议因为全向麦不在位 而落到了内置麦，此时下指令也会落到内置麦 → 被拒。这是正确行为， 但错误消息必须说清因果（"会议正在使用内置麦克风"），见 §3.6。

3.4 选中时机：在"明确需要"的那一刻懒选

泳道触发点持有期
指令assistant.capture() 被热键 / 媒体键 / 面板按钮触发时秒级（maxRecordMs 默认 30 s）
会议meeting.start_meeting() 被点「开始录音」时分钟到小时

三条推论：

  1. 不后台监听设备插拔，不维护"当前在线设备"缓存。 每次开麦现解析， 拿到的就是此刻真实的在位情况 —— 没有状态可以漂。
  2. 不做预测性选择（不提前占住最好的设备）：占住本身就是代价。
  3. known_bad_this_run 只是"本轮别再撞同一个坏设备"的记忆，不是状态机。

选中逻辑：

candidates = 该泳道解析出的有序链（含兜底）
for d in candidates:
    if denied(d):             skip  "blocked"        # 黑名单，见 §3.5
    if not present(d):        skip  "absent"
    if known_bad_this_run(d): skip  "open-failed"    # 本轮已失败过，不再试
    if held_by_other_lane(d): skip  "busy"           # 设备级互斥，§3.6
    if probe_open(d, timeout=1.5s):  → 选中，取租约
    else: mark_bad(d);        skip  "open-failed"
→ 全部失败：抛错，消息里列出每个候选的原因（不是一句"打不开麦克风"）

最后那句很重要：错误消息必须列出全部候选的去向。 现在的报错是 无法开始录音：打开麦克风超时（设备被占用或权限不足） —— 用户无从知道"我配的全向麦到底是不在位、被占用、还是被黑名单挡了"。

3.5 黑名单：把 AGENTS.md 的铁律变成机制

AGENTS.md 记着一个不可自愈的事故：

macOS 上打开 OrayVirtualAudioDevice / "iPhone"的麦克风 这类虚拟/接力设备， 可能把 CoreAudio HAL 锁死（HALB_Mutex::Lock() 卡在 HAL_CreateIOProcID）， 此时任何进程内麦克风操作都会永久超时，只能重启 ECHO。

现在的防线只有"默认输入用 device=None 交给 PortAudio 选"—— 这只挡住了默认路径， 用户手动指定一个虚拟设备时没有任何机制拦。

设计：默认 deny 模式（大小写不敏感的子串/通配匹配）

Oray*       *Virtual*    *虚拟*      iPhone*    *Relay*    *接力*    *VB-Cable*    *Loopback*

四条规则：

  1. 在枚举阶段过滤，不是"试失败后再记住" —— 因为试一次的代价是 HAL 死锁。
  2. 被 deny 的候选出现在面板上，标灰 + 说明原因 + 提供强制覆盖开关 （有人确实需要虚拟设备，比如要做录音回环测试）。
  3. 覆盖后如果 _quarantined 被置位 → 明确提示"请重启 ECHO"，并停止一切麦克风操作 （已有机制，mic.py:98）。
  4. deny 模式是客户端本地配置，可增删。

顺带把默认设备的取法也钉住：sd.default.device 是 (输入, 输出) 二元组， [0] 才是输入。任何地方都不许用 sd.default.device[下标] 硬取输入设备 —— 需要默认输入就传 device=None（wake.py:232 已是这个结论）。

3.6 两级互斥：泳道级 + 设备级（修掉那个待办）

现状：mic.py 的 _lock 与 _foreground 都是模块级全局一把。 所以即使把会议配到全向麦、指令配到耳机，第二个泳道照样被拒：

MicrophoneBusy: 麦克风正在录音或测试，请先结束当前操作

AGENTS.md 把这条记为待办："想让'会议用全向麦 + 指令用耳机'真正并行， 得让不同设备各自持有流"。

设计：互斥分两级。

级别键作用
泳道级lane（command / meeting）同一泳道同时只有一个持有者（保留现状的 busy 语义）
设备级device_key（名字 + hostapi；-1 → "default"）同一物理设备同时只有一个持有者（跨泳道）
# mic.py（改造）
_lane_holder:   dict[str, str] = {}   # lane       -> 持有者描述
_device_holder: dict[str, str] = {}   # device_key -> 持有者描述（含 lane）
_fallback_lock = threading.Lock()      # 仅覆盖 device_key == "default"

def claim(lane, device_key, who):
    if lane in _lane_holder:
        raise MicrophoneBusy(f"{lane} 已有采集在进行")
    if device_key in _device_holder:
        raise MicrophoneBusy(
            f"设备「{device_key}」正被 {_device_holder[device_key]} 占用")
    ...  # 登记两级，yield，finally 两级都释放

不做抢占。 设备选在"明确需要"的那一刻（§3.4），所以冲突只有两种，都是拒绝：

情况行为
两条泳道解析到不同设备直接授予，互不影响 ← 这就是那个待办的解法
两条泳道解析到同一设备后到者拒绝，消息说清"被谁占用、什么用途、什么时候开始"
同一泳道重复触发拒绝（沿用现状的 busy 锁与提示音）

为什么不做抢占：会议中途被一句误触打断是不可接受的（AGENTS.md 里那次 打断会议的事故就是这个类型的伤害），而指令抢占会议会直接断掉录音。 唯二的让出场景是唤醒监听（它本来就在后台跑，让出是常规操作）—— 这个机制保留，见 §3.8。

配套：_quarantined 语义不变（子进程杀不掉 → 全局停用麦克风，要求重启）。

3.7 设备标识的稳定性

候选链存设备名（稳定键）—— 这一点现有设计已经做对了，照用。补两条：

  • 同名设备出现在多套 hostapi 时，按 rank_hostapi() 选（已有）。
  • 候选链里允许写索引以兼容老配置，但面板上一律显示解析后的名字， 并在名字解析失败时提示"这个序号现在指向别的设备了，请重选"（索引会漂，名字不会）。

3.8 唤醒的处置（本次明确排除）

本设计不考虑唤醒：唤醒不进候选链、不构成第三条泳道、不进面板的设备路由表。

项处置
设备来源保持现状（inputDeviceId / 系统默认），不做候选链
持有方式保持现状：后台持有 + 可被前台采集让出（mic.py 的 _yield_requested）
与新设计的关系自动受益：互斥改成设备级后，唤醒占着内置麦不再挡住耳机上的指令

将来若要把唤醒纳入候选链，接口已经留好（lane 加一个 wake 即可）， 但要先想清楚"唤醒是否值得独占一个设备"—— 它 24 小时持有，代价与另外两条泳道不同。

4. 播放设备路由与队列

4.1 现状：完全空白

项现状
设备选择无 —— tts._play_wav_data() 直接 sd.play(data, sr)，用系统默认输出
串行靠 tts.py:34 的一把 _lock
优先级 / 抢占无 —— 一条长朗读播报时，错误提示音只能干等

4.2 设计：优先级队列 + 可抢占

这是四个域里唯一需要真队列的地方。

# app/audio/playback.py（新增）
优先级（数字越小越先播）：
  95  错误 / 告警提示音（"转写失败"）
  80  交互反馈（"没听清，请再说一次"）
  60  指令复述确认
  40  转写完成 / 状态提示音
  20  长内容朗读（会议纪要摘要）

规则：

规则说明
串行播放同一设备同一时刻只有一条在播（现在靠锁，改成显式队列）
高优先级抢占新任务优先级高于当前播放 → 立即停止当前、插队播放。被抢的任务丢弃（不重播 —— 一条被打断的朗读重播会很烦）
同级 FIFO保持顺序
队列有界满了丢最低优先级的，不是丢新来的（避免"提示音把正常播报挤掉"反过来）
可等待wait_until_idle(timeout) —— 会议开始时应该等播报结束再开麦，避免提示音被录进去

设备侧与采集对称：

"outputDevices": ["会议室音箱", "笔记本扬声器"]     // 有序候选链

同样三级回退：候选链 → 默认输出 → 系统默认。播放探测比采集安全得多 （打开输出设备不会锁死 HAL），所以"在线"判定可以直接尝试。

4.3 与已有提示音机制的关系

tts.py 已有 _beep_until / beep_pending() / wait_beep_done() 处理"提示音是异步播的、speak_async 紧随其后会打架"这个真实问题。

新队列要吸收这些语义，不要另起一套： play_beep 入队（优先级 40/95）、beep_pending() 变成"队列里还有提示音"、 wait_beep_done() 变成"等队列排空到该优先级以下"。否则会出现两套并行的播放状态。

6. 边界：什么该合，什么不该合

问题结论
设备路由放进 EnginePool？不。池管的是"可共享的模型实例"，设备是"独占句柄"。套一起会让两者都变形。
设备路由放进 /v1/capabilities？不。设备是本机资源，服务端没有麦克风。
四处共用一套代码？只共用 pick() 内核（§2）。租约、队列、抢占各自实现。
LLM 路由要不要改成用 pick()？建议改。dsh-failover/proxy.py 的健康/熔断逻辑与 pick() 同构，收拢后只有一处需要维护；但它是独立进程，要么提取成共享模块，要么用它现成的实现作为参考实现，v1 不强求。
设备优先级存哪？客户端 DB（settings 表）。这是业务配置，不出本机。

7. 落地顺序（按"独立性"排，不按"重要性"排）

阶段内容为什么这个顺序
D1两级互斥：泳道级 + 设备级（§3.6）独立、无新概念、直接修掉 AGENTS.md 里的待办。做完立刻能"会议用全向麦 + 指令用耳机并行"
D2黑名单机制（§3.5）独立、纯防御、把一条人读的铁律变成机制。防的是不可自愈的 HAL 死锁
D3两条泳道 + 有序候选链 + 懒选 + skipped 原因（§3.3/3.4）本次要的核心能力；依赖 D1 的设备级互斥表
D4播放设备 + 优先级队列（§4）相对独立，但要先吸收 tts.py 已有的 beep 状态机
D5pick() 内核收拢 + 统一面板等前三处都跑过一遍，才看得清哪部分真能共享

D1 和 D2 可以先做，它们不依赖能力路由，也不依赖前后分离 —— 纯收益，风险低。

8. 待拍板

  1. 候选链的设置项怎么放？ 新增 commandInputDevices / meetingInputDevices（列表）， 还是把现有单值直接改成列表？建议新增列表 + 保留单值作链尾，零数据迁移， 老配置行为一个字不变（沿用 inputDeviceId 那条"通用项兜底"的既有设计哲学）。
  2. 会议中途设备消失怎么办？（2 小时持有期内全向麦被拔 / 蓝牙断）这是"懒选"留下的 唯一长窗口。我倾向明确告警 + 不静默换设备（半场换设备会导致音质突变、时间轴要重新校准）； 但 ECHO 本来就按 meetingSegmentMinutes 分段，在分段边界换设备技术上是可行的。 要不要允许？还是就老实报"录音已中断"？
  3. 黑名单默认包含哪些？ 我列的 8 个模式来自 AGENTS.md 的实际事故 （Oray* / *Virtual* / iPhone* 等）。要不要更激进（默认 deny 一切非物理设备）？ 建议先用保守清单 + 命中时提示，观察一段时间再收紧 —— 误杀一个真需要的设备比漏放更烦人。
  4. 播放高优先级抢占时，被抢的任务丢弃还是重播？ 我倾向丢弃（被打断的朗读重播很烦）， 但"转写完成提示音"这种可能希望补播。要不要按用途细分？
