**续费设计（我给的建议，细则见 §4.6）**

1. **手动续费，不做自动扣款**：到期前 7 / 3 / 1 天面板提示；已配对用户点「续费」→ 带 JWT 下单 →
   支付成功**直接延长权益**（不发码、不换凭据），有效期从 `max(now, paid_until)` 起 +30 天
   （提前续费不吃亏）。
2. **到期处理**：立即停止新能力请求（402 `entitlement_expired`），但**保留配对与数据**、
   面板仍可打开并显示到期与续费入口；续费成功即时恢复。
3. **不给"免费继续用"的宽限期**（10 元/月的服务，宽限只会让续费率更差）——

4. **退款**：管理面手工退款；退款后按**剩余 `paid` 订单重算**权益（不是简单减 30 天），只剩退款单时失效；未兑付的码到期自动清理。
5. **试用**：可选的 7 天一次性试用（默认开、管理面可关），用于内部推广；不送就把开关关掉。
6. **重复支付/续费叠加**：同一订单只认一次；已有权益时往后累加，不并发叠加。

## 1. 目标与非目标

**目标**

1. 用户在 ECHO 面板的「后端」位置看到**可用套餐**并能完成支付（支付宝）。
2. 支付成功后，ECHO **自动完成配对**（等价于现在粘一张 `echo://pair?host=…&code=…`），并把
   **会议转写（ASR）+ 语音合成（TTS）路由到我的后端**。
3. 服务端按套餐管控权益（有效期 / 每日分钟数 / TTS 字数），到期或超额有明确提示与续费入口。

**非目标（本期不做）**

- 不做复杂的按 Token/按秒结算（先套餐制，按量计费放 M3）。
- 不做多商户/分销/发票系统（先管理面手工退款与对账）。
- 不改现有配对协议本身（`/v1/pair` 的一次性码语义保持不变，只是"码从哪来"多了一条：订单）。

**三条铁律**

1. **价格与权益只在服务端**：客户端只传 `planCode`，不传金额；订单金额、有效期、额度全部由服务端按套餐表决定。
2. **支付成功才发码**：配对码由订单驱动（`order_id` ↔ `pairing_code`），未支付订单不产生可用码。
3. **码仍是一次性 + 短 TTL**：沿用现有 `/v1/pair` 语义（用掉即删、失败退避），不新造一套配对协议。

## 3.5 用户身份层（补充：原设计只有"设备认证"，缺"人"）

### 3.5.1 缺口是什么

现有 `/v1/pair` 建立的是 **设备/客户端认证**（`client_id` + `secret` + JWT + TLS 证书固定），
**不是用户注册**。只做设备认证会带来四个问题：

1. **权益绑在设备上** → 重装系统/换电脑就"重新买一次"，用户一定骂；
2. **付款的人是支付宝账号、兑换的是设备**，两者对不上 → 退款、找回、客服"你买过什么"没有依据；
3. **一人多机 / 多人共用一张码** 无法治理；
4. **内部同事专用** 需要一道门：只允许自己人购买（邀请码/白名单），而不是谁都能扫。

### 3.5.2 设计原则

> **人（user）拥有权益，设备（client）只是登录/配对的一端。**

- `users`：`user_id`、姓名、工号（唯一）、手机号（可选）、`alipay_buyer_id`（支付回调带回）、状态、创建/更新时间。
- `user_devices`：`user_id` ↔ `client_id`、设备名、首次绑定/最近活跃、状态（**默认上限 3 台**，可配）。
- `invites`：邀请码（内部推广/防外部购买）、剩余次数、有效期、创建人。
- `orders.user_id`、`entitlements.user_id`：**权益主键从 client_id 改成 user_id**；设备通过 `user_devices` 关联。

### 3.5.3 注册 / 认证方式（三选一，推荐 A）

| 方案 | 做法 | 成本 | 适合 |
|---|---|---|---|
| **A. 邀请码 + 工号（推荐）** | 管理面生成邀请码（一次性/限量），客户端填邀请码 + 姓名 + 工号 → 注册；工号唯一、可查重 | 零短信费，人工可控 | 同事内部 |
| B. 手机号 + 验证码 | 接短信通道发码验证 | 短信费 + 合规 | 对外 |
| C. 支付宝账号即身份 | 不注册，支付回调的 `buyer_user_id` 当主键 | 最轻 | 极小规模（换支付宝就找不回） |

> 内部 10 元月卡建议 **A**：邀请码管"谁能买"，工号管"是谁"，支付宝 `buyer_user_id` 顺手记录下来做找回依据。

### 3.5.4 登录 / 会话 / 找回

- 注册成功发 **`user_token`**（JWT；30 天有效、可刷新），客户端本地存（与 `backend.json` 同级、DPAPI 加密）。
- 购买/续费/查权益/管设备都带 `user_token`；配对成功把 `client_id` 记入 `user_devices`。
- **换机/重装**：登录（工号 + 邀请码/验证码）→ 若已有有效权益 → 生成一张**设备绑定码**
  （一次性、10 分钟、只能绑到当前 user）→ 新设备配对后**继承权益，不重复收费**；
  设备数超限时先让用户解绑旧设备（面板可自助）。
- **找回**：管理面按工号 / 手机号 / 支付宝 `buyer_id` 查用户与订单，可重置设备绑定、
  补发绑定码 —— 这是"钱交了但机器换了"的唯一人工兜底。

### 3.5.5 认证与配对的关系（关键）

```
未注册用户点「购买」→ 先注册（邀请码+姓名+工号）→ 拿到 user_token → 才能建单
订单支付成功 → 发码（码里带 order_id + user_id）→ 客户端配对
/v1/pair 兑换时：校验码绑定的 user_id 与当前登录用户一致（首次即绑定）→ 记 user_devices
已登录的第二台设备：走「设备绑定码」（不是购买码），配对后沿用同一份 entitlements
```

### 3.5.6 治理与合规

- **设备上限**：默认 3 台/用户；超限要解绑（自助或管理面）。
- **防分享**：权益绑 `user_id`；日额度/1 QPS 也按 user 计；同一 user 多 IP 告警，不自动封。
- **个人信息最小化**：只收姓名 + 工号（手机号可选）；管理面访问受 admin 会话保护并记审计。
- **内部收费边界**：只对内部同事开放（邀请码控制），不是公开售卖；开票/合规按公司口径（见 §10）。

### 3.5.8 备选：用支付宝 `buyer_open_id` 代替注册（"支付即注册"）

**结论**：Vibe Pay 走支付宝收银台，异步通知/订单查询里**通常能拿到买家标识**，但新版接口
**不再返回老的 `user_id`（2088…），而是 `buyer_open_id`**：同一 `app_id` 下同一用户**稳定**、
跨应用不同、不可逆假名。`buyer_logon_id` 是脱敏登录名，**不能**做主键。

若沙箱实测确认有 `buyer_open_id`，可以**去掉注册流程**：

- `users` 表以 `alipay_open_id` 为唯一键；**首次支付成功自动建用户**（昵称可选，姓名/工号不强制收）；
- 订单/权益绑该 user；邀请码退化成"购买口令"（只做内部门槛，不计名）；
- 客户端「账户」卡没有注册表单，只有"已通过支付宝识别 · 设备 2/2 · 解绑/找回"。

**必须接受的五条边界**

1. **一个支付宝账号 = 一个用户**：家人/同事代付会把权益并到同一人；
2. **换机没有密码/验证码可证明身份**：只能 (a) 用同一支付宝再下一笔 ¥0.01 验证单
   （识别到同一 `open_id` 后自动退款/抵扣），或 (b) 管理面人工重置设备 —— 内部规模先做 (b)；
3. **换支付宝账号/注销** → 老权益找不回，只能人工兜底；
4. **`open_id` 是应用维度的**：换 `app_id`（重签约/换主体）会让所有 open_id 变 →
   记牢 app_id、订单/权益表同时存 `trade_no`，退款对账不依赖 `open_id`；
5. **字段可用性必须沙箱实测**：AI 支付产品可能只在订单查询里给，不保证回调一定带 →
   设计**保留「邀请码注册」作为 fallback**（两条路都实现，用配置开关切换）。

**推荐**：内部同事场景直接用这条（最省事、PII 最少）；邀请码只当可选的"购买口令"防外传。

### 3.5.9 扫码授权 → 白名单判定（**Phase 4：稳定后再上，本轮不实现**）

> 用户 2026-11-02："稳定后再考虑白名单。" 所以本轮**不做** `authorized_open_ids` 准入闸门：
> 扫码授权只用于**识别身份/登录**（拿 open_id），访问控制单纯靠"订阅是否有效"。
> 下面这段设计留档，等收费跑稳了再打开开关。
> 用户 2026-11-02 追问："有没有可能根据 vibe pay 这个 alipay_open_id，来决定是否在收费服务器内，
> 就是说支付宝扫码来确定他是否是授权用户。"

**可以，而且能把注册整个拿掉。** 但要先分清两种"扫码"：

| 扫码 | 用途 | 会不会扣钱 |
|---|---|---|
| 支付宝**收款码/收银台** | 支付 10 元 | 会 |
| 支付宝**网页授权登录**（`auth_userinfo`） | 只确认"你是哪个支付宝用户"，拿 `user_id`/`open_id` | **不会** |

**要做"扫码确认是否授权用户"，用第二种**：ECHO 面板里显示一张支付宝登录/授权二维码，
用户手机扫码并在支付宝里点"确认"→ 服务端拿到 `auth_code` → 换 `open_id` → **查白名单**。

### 判定模型（两道闸门，互不替代）

```
ECHO 请求（带 client JWT）
  → client_id → user（open_id）
  → ① 白名单 authorized_open_ids：在不在？（不在 → 403 "未授权，请扫码/联系管理员"）
  → ② 权益 entitlements：过期/超额？（过期 → 402 "续费后恢复"）
  → 放行（1 QPS + 日额度照旧）
```

- **白名单来源**三种：① 管理面手工预置（把同事的 open_id 录进去）；② 首次扫码后进"待审批"，
  你在管理面点通过；③ **支付成功自动加入**（付费即授权）。
- **管理员可随时撤销**：把 open_id 禁用 → 该用户立刻不能再用（比删 client 干净）。
- **扫码授权与收费解耦**：内部同事可以"只授权、不付费"（`internal`）；也可以"授权 + 买月卡"；
  外部人扫码后不在白名单 → 引导购买或拒绝。

### 扫码授权流程（面板内二维码）

```
ECHO 面板「后端」卡： [扫码验证 / 购买]
  → POST /v1/account/scan-session        （后端生成 state + 授权 URL + 二维码）
  → 面板显示二维码；用户手机支付宝扫码 → 点"确认"
  → GET  /v1/account/scan-callback?code&state   （支付宝重定向到后端）
        → alipay.system.oauth.token 换 token → alipay.user.info.share 取标识
        → 写 scan_session：open_id / 昵称（可选）
  → ECHO 轮询 GET /v1/account/scan-session/{id}
        → 已授权（白名单/已购）→ 返回设备绑定码 → 自动配对
        → 未授权 → 返回"可购买月卡 ¥10" → 走 §4.3-A 支付流程
```

### 关键校验点（必须先沙箱实测）

1. **授权登录返回的标识** 与 **支付回调里的 `buyer_open_id`** 必须是**同一个**（同一 `app_id` 维度）。
   如果授权只回 `user_id`、支付只回 `open_id`，两者对不上 → 这条路要改成"支付即授权"（单一路径），
   或找支付宝要标识转换接口。**这一点不确认，白名单就不能建。**
2. **权限**：网页授权登录需要应用签约"获取会员信息"（`auth_userinfo`）；个人主体能否开通要实测。
3. `redirect_uri` 必须公网 HTTPS 且与开放平台配置一致（复用 `echoserver.zhkq.online`）。

### 与前面几节的关系

- 有扫码授权 + 白名单 → **§3.5.3 的邀请码/工号注册可以完全不要**（管理面看 open_id + 昵称就够）；
- 没有扫码授权（权限拿不到）→ 回退"支付即注册"（§3.5.8）或"邀请码注册"（§3.5.3），设计三条路都保留、用开关切换；
- 无论哪条路，**权益始终绑 user（open_id）**，设备只是登录端，换机/解绑/找回规则不变（§3.5.4）。

### 3.5.10 一人多设备（多端）策略

> 用户 2026-11-02 补充："但是要考虑一个人有多台设备的情况。"

**原则：一份订阅覆盖同一个人的多台设备，不按设备收费；但设备数、并发、QPS、日额度都要有界。**

| 事项 | 规则（默认值，`plans` 表可配） |
|---|---|
| **设备上限** | `max_devices`，默认 **3 台**（办公机 + 家里 + 笔记本）；`internal` 用户可单独放宽 |
| **身份识别** | 每台设备独立 `client_id`+secret（现有配对机制）；`user_devices` 记 user↔device；**扫码登录只在"绑定新设备"时做一次**，日常请求靠 client JWT → user 映射 |
| **换新设备/重装** | 同 `open_id` 扫码登录 → 服务端发**设备绑定码**（一次性、10 分钟）→ 新设备配对 → **继承同一份权益**；已满 3 台则先解绑旧设备（页签设备列表可自助） |
| **设备列表** | 「我的」页显示：设备名（hostname）/ 最近活跃 / 状态；可重命名、解绑；管理面可强制解绑（找回兜底） |
| **1 QPS** | **同一 user 的所有设备共享一个令牌桶**（一台在刷 TTS，另一台也会被限） |
| **日额度** | ASR 分钟 / TTS 字符**按 user 累计**（`quota` 记账从 `client_id` 改成 `user_id`；否则换台设备又能用一遍） |
| **并发** | `max_concurrent`，默认 **1**：同一时刻只允许一台设备做 **ASR**（第二台收到 409 + "另一台设备正在转写"）；TTS 不占 GPU，只受 1 QPS |
| **多设备同时开会** | 默认不允许两台同时转写；确有需要（如两台机器各录一场）把该 user 的 `max_concurrent` 调到 2（成本上升，管理面单独放宽） |
| **解绑/撤销** | 解绑后该 client 的请求一律 `403 device_revoked`；**本机本地数据（录音/纪要）不受影响**；重新扫码可再绑 |
| **历史设备迁移** | 老 ECHO（无 user、已配对）首次扫码登录时，若该 client 未绑定 → 允许"认领本机"；多台走设备上限；认领不了的管理面人工 |
| **共享账号风险** | 一个支付宝账号 = 一个 user；同事共用账号会互相挤占设备数/并发/额度 → 建议每人用自己支付宝 |

### 3.5.11 登录方式与支付解耦（"微信登录 + 支付宝 Vibe Pay 支付"能不能做）

> 用户 2026-11-02："有可能微信用户登录，支付宝 vibe pay 支付吗，支付宝用户登录用户可能不喜欢。"

**结论：技术上可以——登录和支付本来就是两件事。** 登录只解决"你是谁"，支付只解决"谁付钱"：

```
微信/企业微信扫码登录 → openid/unionid（或企业微信 userid）→ 建 user
下单（user_id 已知）→ 支付宝 Vibe Pay 收款 → 回调带 buyer_open_id
→ 首次支付把 alipay_open_id 绑到当前 user（对账/退款/找回用），支付宝只负责收款、不承担登录
```

**但"微信登录"的资质门槛要看清：**

| 登录方式 | 资质要求 | 个人主体 | 适合 |
|---|---|---|---|
| 微信开放平台·网站应用扫码登录 | 企业主体 + 300 元认证 + 网站备案 | ❌ 个人基本做不了 | 对外产品 |
| 微信公众号网页授权（OAuth） | 认证服务号（企业） | ❌ | 对外/公众号内 |
| **企业微信扫码登录（OAuth）** | 企业微信管理员建应用 | 公司内部 ✅ | **同事内部（最顺）** |
| 钉钉扫码登录 | 企业钉钉管理员建应用 | 公司内部 ✅ | 同事内部 |
| 手机号 + 短信验证码 | 短信服务商（阿里云/腾讯云）实名 | ✅ 可 | 通用、不依赖微信/支付宝资质 |
| 支付宝网页授权（`open_id`） | 应用签约"获取会员信息" | 待实测 | 可选登录方式之一 |
| **不登录**（管理员发码/邀请码 + 支付） | 无 | ✅ | 内部小范围、最省事 |

**推荐顺序（按你的场景）：**

1. **同事内部**：有企业微信 → **企业微信扫码登录**；没有 → **不登录**（发码/邀请码 + 支付宝付款），
   权益靠订单/设备绑定；
2. **对外**：**手机号验证码登录** + 支付宝 Vibe Pay 收款（不依赖微信/支付宝登录资质）；
3. 有企业资质再上微信登录；支付宝扫码授权只当**可选登录方式**，不当唯一。

**设计调整（结构不变，只是把"身份来源"做成可插拔）**

- `users` 表加 provider 标识列：`wechat_openid`、`wechat_unionid`、`wework_userid`、`phone`、`alipay_open_id`（可空，支付回填）；
- 登录层抽象成 `IdentityProvider`（扫码/回调/取用户三件套），新增一种登录方式只加一个 provider，
  **不动**订单/权益/设备/续费逻辑；
- 支付回调只做"把 payment identity 绑到当前 user + 对账"，**不创建用户** ——
  登录与支付不是同一个人时也不会串号；
- 设备/换机/解绑规则不变（§3.5.10）。

**风险与边界**

- 微信登录拿不到手机号（需企业资质 + 额外授权）；个人拿不到微信登录；
- `unionid` 需要开放平台绑定同主体应用；企业微信 `userid` 是公司内唯一（离职回收）；
- 支付宝 `buyer_open_id` 在"微信登录 + 支付宝付款"的组合里只是**付款账号**，
  不能当登录主键 —— 否则"微信身份"和"支付宝身份"会打架；
- 企业微信/钉钉登录需要公司管理员配合建应用（走内部审批）。

### 4.4 权益执行（复用现有闸门）

- **ASR**：`routes.State._quota_limit_for()` 现在读 `clients.daily_audio_minutes`；改为
  `entitlements.daily_audio_minutes`（无权益 → 0；过期 → 402 `entitlement_expired`）。
  现有 `quota.check()` 的 429 路径保留（"今天用完了"），新增 402 分支（"套餐到期/未开通"）。
  **月卡 10 元的默认额度：每日 ASR 120 分钟**（后台可改，`plans.daily_audio_minutes`）。
- **TTS**：现在不计量（`server/routes.py:590 POST /v1/tts` 注释说明它是网络 IO，不占 GPU）。
  按**字符数**记 `entitlements.tts_chars`（**每日 5 万字符**，后台可改），超额 402；
  不占 GPU 也仍然有上游 edge-tts 成本与滥用风险，必须限。
- **QPS（本轮新增，单用户 1 QPS）**：按 **`user_id`** 的**令牌桶**限速 1 req/s（突发容量 1），
  请求进来先 `client_id → user_id`（`user_devices` 缓存），**多台设备共用同一份 1 QPS**；
  在 `/v1/asr`、`/v1/tts`、`/v1/diarize`、`/v1/speaker/embed` 的鉴权之后、准入之前判定；
  超限返回 `429 rate_limited` + `Retry-After: 1`。
  与现有 `per_client_concurrent=1` 的关系：**两个闸门并存**——并发 1 是"同一时刻只能一个请求"，
  1 QPS 是"起请求的速率"；会议分段转写天然 >1 秒，实际上并发闸门先起作用，QPS 闸门主要防脚本刷 TTS/短请求。
- **日额度也按人算**：`quota` 现在按 `client_id` 记账，改为 `client_id → user_id` 后按 **user** 累加
  （否则一台设备用完、换台设备又能用一遍）；`quota.check()` 的上限来自 `entitlements`。
- **并发（按人）**：`per_client_concurrent=1` 是**设备级**的；多设备场景还要加一道 **user 级并发**
  （`plans.max_concurrent`，默认 1）：同一 user 同时只允许一台设备做 ASR，第二台返回
  `409 client_busy` + "另一台设备正在转写"；TTS 不受此闸门（不占 GPU），只受 1 QPS。
  这样一台在家里录会，办公室那台不会同时抢 GPU。
- **到期/续费提示**：`GET /v1/capabilities` 里附
  `entitlement:{plan,paidUntil,dailyMinutes,ttsCharsLeft,qps,maxDevices,maxConcurrent,devices}`；客户端面板显示并提示续费。
  到期前 7 / 3 / 1 天同样带 `expiringSoon:true`，客户端弹一次提醒（不重复弹）。
- **到期策略**：到期不删配对/不删用户（保留凭据与设备绑定），只停能力并返回明确 402；续费即恢复。
- **退款**：退款成功 → 订单 `status=refunded`，再按剩余 `paid` 订单重算权益；只剩退款单时 `entitlements.status=refunded`、`paid_until=0`（见 `docs/后端收费-续费与退款规则.md`）。

### 4.5 续费规则（本轮定稿）

> 2026-11-06 补充：`projectedPaidUntil`、换套餐拒绝、退款重算与页面展示的完整口径见
> `docs/后端收费-续费与退款规则.md`；两者冲突以新文档为准。

| 场景 | 行为 |
|---|---|
| 提前续费（未到期） | 有效期从 `paid_until` 起 +30 天（不吃亏）；可连续续费叠加 |
| 到期后续费 | 从**支付成功时刻**起 +30 天（不补历史空档） |
| 续费是否再发配对码 | **不发**：已登录用户（userToken/JWT）下单，回调直接延长 `entitlements`；未注册/未配对的新用户才走"注册→支付→发码→配对" |
| 到期后用户还能看到什么 | 面板可打开、显示"套餐已到期，续费后恢复"；会议列表/纪要/本地功能照旧（只是会议转写与 TTS 停） |
| 提醒节奏 | 到期前 7/3/1 天各提示一次；到期当天再提示一次"已停，续费恢复" |
| 试用 | 7 天一次性试用（默认开）：`entitlements.plan_code=trial`，到期后转成"未开通"，续费买月卡即从当天起算 |
| 退款 | 管理面手工退款 → 订单 `refunded` → 按剩余 `paid` 订单重算权益；只剩退款单时 `status=refunded`、`paid_until=0`；已消费额度不退 |
| 换套餐 | 第一版**只支持同套餐续费**；有有效付费权益时买不同套餐 → `409 plan_change_unsupported`；过期/退款/试用状态下可按新购买任意上架套餐 |
| 自动续费 | **暂不做自动扣款**；若以后做，必须显式勾选、可随时取消、到期前提醒 |
| 换机/重装 | 登录后申请「设备绑定码」→ 新设备继承同一份权益，**不重复收费**；设备上限 3 台，超限先解绑 |
| 内部账号 | `plan_code=internal`：不过期、不收费、额度按配置（默认 9999 分钟/日），用于你本人与开发机 |

### 4.6 安全与防滥用

- **回调**：支付宝公钥验签；校验 `out_trade_no`/金额/卖家；`trade_status` 白名单；
  `trade_no` 唯一索引做幂等；通知与 `orders` 状态机只允许前进（paid→refunded 例外）。
- **订单**：orderId 用不可猜 ID；`GET /orders/{id}` 限频（IP+订单）；`status` 只暴露必要字段；
  `payUrl` 每次动态生成；`pairUrl` **只在 paid 后返回**，且同一订单只发一张码
  （重复请求返回同一张；码过期则重新发一张，**旧码作废**）。
- **发码防刷**：`/v1/pair` 已有 `PairThrottle`；billing 下单同样按来源限频（例如 10 次/小时/IP）。
- **权益防分享**：权益绑 `user_id`；设备上限 3 台（`user_devices`）；并发/日额度/QPS 都按 user 计；
  管理面可看"同一 user 多 IP / 多设备"告警（不改自动封禁）。
- **密钥**：支付宝应用私钥只在服务端（env / 挂载文件），绝不进客户端与日志；`admin_audit` 记录退款、改套餐。
- **隐私**：远程后端本来就是"音频离开本机"，`capabilityPrivacy` 的门保持不变；收费**不等于**放宽隐私档。

### 5.0 新增「我的」页面（收费功能独立页面；与老发码机制两路并存）

#### 5.0.0 两条路并存（A 老路 / B 新路）

| 路 | 谁用 | 配对方式 | 计费 | 本轮动作 |
|---|---|---|---|---|
| **A 老路（保留）** | 管理员发码给同事、本机自动配对、排障 | 设置 → 后端设置：贴 `echo://pair` 串 / 本机自动配对 | 沿用现有 `clients.daily_audio_minutes` 免费额度，**内测期照旧** | **一行不改** |

#### 5.0.2 行为规则（按用户口径逐条落）

1. **扫码登录**：用选定的身份来源（默认**支付宝网页授权**；若公司有企业微信/钉钉则改用企业微信/钉钉扫码，见 §3.5.11），
   只确认身份、不扣钱；登录态存 `user_token`（DPAPI，与 `backend.json` 同级）。
   **「我的」页不要求姓名/工号/邀请码**（除非走"不登录"档：由管理员发码/邀请码）。
2. **获取用户信息**：只保留 `open_id` + 可选昵称；页面显示"已识别：open_id 尾号 ······ab12"。
3. **判断购买是否在有效期**：进「我的」页即查 `GET /api/subscription/status`
   → `active / expired / none` + `paidUntil` + 今日剩余 + 设备数。
4. **有效期 → 自动配对服务端**：`active` 且本机未配对 → 服务端发**设备绑定码**（一次性、10 分钟）
   → 客户端调现有 `POST /api/capability/pair` → 成功后写：
   `capabilityMeetingAsrBackend=echo-server`、`dailyReviewSttBackend=echo-server`、
   `ttsEngine=echo-server`（`capabilityPrivacy=none` 时提示改 `lan`，不静默）+ 自检（ASR 一句 / TTS 一句）。
5. **超期就失效**：服务端 ASR/TTS 返回 `402 entitlement_expired`；「我的」页转 S1 显示"已过期"，
   配对凭据保留（不删），续费成功**立即恢复**，无需重新配对。
6. **扫码付款后授权 30 天、1 QPS**：订单金额由服务端 `plans` 表定（¥10/30 天）；
   支付回调 → `paid_until = max(now, 原到期) + 30 天`；`qps=1` 由服务端令牌桶执行；
   「我的」页只展示"1 QPS"，不可改。
7. **换机/多设备**：同一 `open_id` 扫码登录 → 设备管理里解绑旧设备/申请新设备绑定码；
   不重复收费（权益归 user），**默认上限 3 台**；满额先解绑；多台共享同一个 1 QPS 与日额度，
  ASR 默认同一时刻只允许一台（见 §3.5.10）。
8. **支付失败/取消/超时**：S4 转回 S1，文案说清（"已取消，未扣款" / "支付超时，可重试"）。

### 5.3 兼容与降级

- **已有配对的老用户（没有 user 账号）**：升级后首次打开面板，提示"免费额度继续用；要续费/换机需先注册"，

- 旧版 ECHO 看不到购买入口；服务端 billing 端点不存在也不影响它们（老路照走）。
- 服务端 `billing.enabled=false`：面板不显示购买；已配对客户端照旧按现有免费/内部额度跑。
- 新客户端连的是"没开 billing 的后端"：`GET /v1/billing/plans` 404 → 面板不显示购买（静默降级）。

| 回滚 | 关 `BILLING_ENABLED` 即停售；已支付订单仍可查、可退（管理面） |
| 监控 | `order_events` + `alipay_notify` 落库；管理面首页加"今日收入 / 待兑付码数量 / 到期 3 天内人数"；回调失败告警 |

## 7. 风险清单

1. **准入与合规**：支付宝 AI 支付产品需要签约/资质；个人 vs 企业对公；对外收费是否符合公司制度（需你确认）。
2. **费率与结算**：0 费率等政策以签约页为准；退款手续费与结算周期。
3. **回调可靠性**：通知可能重复/延迟/丢失 → 必须"主动查询 + 补偿任务"，不能只靠通知。
4. **支付页可达性**：公司网/内网机器打开支付宝页面可能失败；需要"复制链接到手机"的兜底。
5. **权益被分享**：一个 client_id 多机使用 → 已有并发/日额度第一道 + 告警，不自动封。
6. **成本**：GPU ASR / TTS 上游成本 → 套餐额度必须按成本设计，超量先降速/排队再拒绝。
7. **已配对冲突**：用户当前已配对到别人的后端 → 购买后要 `replace_pairing=true`，必须二次确认
   （面板已有"换一台后端先解除配对"的语义）。
8. **旧客户端/旧后端兼容**：新后端开 billing 不影响旧客户端；新客户端连旧后端要静默降级。
9. **个人信息**：姓名/工号/支付宝 `buyer_user_id` 属内部人事数据 → 只存必要字段、管理面访问受限、
   日志脱敏、不外发；需要在页面写清"收集什么、干什么用"。
10. **邀请码泄露**：一次性/限量/限期 + 可作废；同一个码出现多工号异常时告警。
11. **找回/解绑靠人工**：用户量上来会有客服成本；先在管理面提供"重置设备 / 补发绑定码"。

## 8. 沙箱与上线步骤（建议顺序）

0. **个人 Vibe Pay 开通**：支付宝账号实名 → 开放平台（open.alipay.com）建应用 → 签约

4. 到期 / 超额 / 1 QPS 超速 / 退款 四条负向用例；
5. 切生产网关、公网回调、对账跑一周。

## 10. 现在缺什么（材料 / 前置条件，不是设计了）

**已定（见 §0）**：个人 Vibe Pay；月卡 ¥10/30 天；1 QPS；`echoserver.zhkq.online`；
面向同事内部；续费=手动、不发码、直接延权益；到期停能力但保留配对；退款=手工全额+立即失效；
7 天试用（默认送、后台可关）；**权益归人（user），设备只是登录端**（§3.5）。

**开工前需要你给 / 确认的（1、2、3 是硬前置；4~8 是用户/登录口径）**

1. **支付宝材料**：个人实名账号是否已开通开放平台？能否签约 Vibe Pay 网页收款？
   签约后给 `APP_ID`；应用私钥你自己生成并放到服务端（**不要发给我/不要进聊天**）；
   支付宝公钥给我用于验签。沙箱先给沙箱应用的三件套。
2. **回调可达性**：`https://echoserver.zhkq.online:8900/v1/billing/alipay/notify` 从**公网**可达吗？
   （用手机 4G 打开这个地址应返回 200/405 之类，不是超时。）不可达就先做"前端轮询 + 服务端主动查询"
   兜底，但**上线前必须解决**，否则支付成功也不会自动发码。
3. **内部白名单**：哪些 `client_id` 要标 `internal`（你本机、同事开发机）？
   给我 `--list-clients` 输出，或授权我在管理面逐个标。
4. **认证方式**：用 §3.5.3 的 **A（邀请码 + 工号）** 可以吗？（推荐；零短信成本、只对内部开放）
   还是要手机号验证码（对外更通用，但要短信通道与费用）？
   **→ 更推荐先验证 §3.5.8：如果 Vibe Pay 回调/查询能拿到 `buyer_open_id`，直接"支付即注册"，
   连邀请码/姓名/工号都可以不填（邀请码降级成可选购买口令）——这个必须沙箱实测后才能定。**
5. **邀请码怎么发**：管理面生成后你私聊发同事？还是用一个固定内部码（`max_uses=50`、限期）？
   （若走"支付即注册"，这条变成可选的购买口令）
6. **设备上限**：默认 **3 台/用户** 可以吗？（你本机 + 家里/备用机）
7. **支付宝身份**：同意把回调里的 `buyer_open_id`（新版；老接口是 `buyer_user_id`，可能不再返回）
   记到用户档案（用于"钱交了换机器"找回）吗？
8. **登录方式（§3.5.11）**：同事内部用哪个？公司有没有**企业微信/钉钉**可建扫码登录应用？
   还是内测期"不登录（发码/邀请码 + 支付宝付款）"就够？
   **微信登录需要企业资质**（个人主体基本做不了），要做微信登录得先有企业/公众号/开放平台资质。
   支付宝扫码只当可选登录之一；支付统一走 Vibe Pay（登录和支付是两件事）。
9. **白名单（Phase 4，本轮不做）**：稳定后再决定是否采纳"支付宝扫码授权 → 查 `authorized_open_ids` 白名单
   → 通过才允许用这台后端"？如果采纳，还要定：
   - 内部同事是**免费**（`internal`，只扫码不付费）还是**都买 ¥10 月卡**？
   - 不在白名单的人：**直接拒绝**，还是"扫码后可购买"？
   - 白名单来源：你先录 open_id、还是首次扫码后进"待审批"你点通过？
   - **必须先沙箱确认**：扫码授权返回的标识与支付回调 `buyer_open_id` 是否同一个（§3.5.9 关键校验点）。
10. **「我的」页的支付形态**：付款二维码是**直接在面板里显示**（需要预下单/当面付那种二维码接口），
   还是**打开支付宝网页支付页**（Vibe Pay 网页收款，页面里再扫码）？
   面板内二维码体验更好，但产品接口不同；建议先按"网页支付页 + 面板内也展示链接/二维码"做兼容。
11. **内部同事的收费口径**：所有人都买 ¥10 月卡，还是"白名单免费（internal） + 外部/新同事才买"？
    （白名单延后到 Phase 4；本轮先按"订阅是否有效"准入）
12. **一人多设备的默认值**：设备上限 **3 台**、同一时刻只允许 **1 台做 ASR**（`max_concurrent=1`）可以吗？
    如果同事确实需要"两台机器同时各录一场"，要把他的 `max_concurrent` 单独调到 2（成本上升，管理面按人放宽）。
13. 额度确认：月卡默认 **每日 ASR 120 分钟 + TTS 5 万字符**（`plans` 一行可改，不影响代码）。
14. 试用 7 天送不送？（默认送）
15. 退款按默认（手工全额退、立即失效）可以吗？要按天折算就改一条规则。
16. 收款/开票：个人 Vibe Pay 收款要不要给同事开票？（开票可能需公司主体，个人不一定支持）
