# 先读我 —— ECHO 能力后端交付包（**老卡 / cu118**）

一句话：这是一套**容器化的 ECHO 能力后端**，给 `compute_cap <= 7.0` 的 NVIDIA 卡用
（Maxwell / Pascal / Volta：GTX 10xx、V100、M40、P4/P40/P100…）。你在一台装了 NVIDIA
驱动的 Linux GPU 机器上，照 §1 → §9 把命令抄一遍就能跑起来。

> **这不是最终用户装的那个 ECHO**（面板 + 本地模型那一套）。这是**服务端**：别的 ECHO
> 机器把"转写"这些活派给它干。所以它没有安装向导，只有命令。
>
> 你拿到的是**两个变体里的一个**：`cu118`（本包，老卡）与 `cu126`（新卡）。
> **选错了不会报错，只会得到一个"看不到这块 GPU"的 torch** —— 所以 §1 请务必先看一眼。
>
> ⚠️ 本包的能力**比新卡那包窄**，而且是**刻意的窄**（有些东西在这块卡上真的做不到）：
> 只有 **SenseVoice 转写**，**没有**说话人分离 / 声纹，也**不能**跑 qwen3asr。
> 原因都在 §1 / §10 写清楚了，别照新卡的文档配。

## ⚠️ 四个坑（都真踩过，先看这四条）

**坑 1：Docker Hub 可能被墙。**
不要只往 `/etc/docker/daemon.json` 里加 `registry-mirrors` —— 加了之后**裸名拉取**
（`docker pull python:3.11-slim`）有时反而会挂住，而且挂得没完没了。可靠的做法是
**显式前缀直拉，再 tag 回本来的名字**：

```bash
docker pull docker.1panel.live/library/python:3.11-slim
docker tag  docker.1panel.live/library/python:3.11-slim python:3.11-slim
docker images | grep python        # 确认 tag 真的在了
```

（`docker.1panel.live` 只是当前可用的一个加速站，换别的同理：**前缀 + `library/` 那一层都别丢**。
只有现场构建那条路才需要拉基础镜像；`docker load` 一个 tar 不需要网络。）

**坑 2：老卡必须 cu118，而且"镜像构建成功"不等于"这块卡能用"。**
torch 是**按卡**从不同 CUDA 源装的（`cu118` / `cu126` 是**镜像里 torch 那一层**决定的，
是构建期参数、不是运行时开关）。本包的 cu118 还**钉死了 torch 2.7.1**：
* cu118 源上目前最新就是 `torch-2.7.1+cu118`，它是**最后一个带 Pascal(sm_61) 的构建**；
* 不钉版本的话，装 funasr 等依赖时可能顺手把 torch 升到不含这块卡的版本 ——
  镜像照样构建成功、容器照样起来，只是它看不到 GPU。镜像里有一条校验会**让构建失败**，
  那是好意，别去删。

所以**验收必须看这一条**（§9 有）：

```bash
docker exec echo-backend python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_capability())"
# 期望：2.7.1+cu118 11.8 True (6, 1)   ← 第三个 True 是 is_available，必须是 True
```

**坑 3：模型不随镜像走，而且这块卡上"能跑的模型"和文档默认那套不一样。**
权重放在宿主上只读挂进容器（§4）。本变体**只需要 SenseVoice** —— 放了 qwen3asr 也不会被
加载（镜像里没有 qwen-asr 包），放了 pyannote 也没用（镜像里没有 pyannote.audio）。
摆错位置的症状是"看起来装了、其实加载不到"（转写一路 `model_failed`）。

**坑 4：管理面只发布在宿主回环（`127.0.0.1:8901`）。**
**别**把它改成 `"8901:8901"` —— 那等于把管理面（发授权、看客户端、看审计）摊给整个网段。
远程运维走 SSH 端口转发（§8）：

```bash
ssh -L 8901:127.0.0.1:8901 <gpu-host>     # 然后本地浏览器开 http://127.0.0.1:8901/admin/
```

## 1. ① 先确认你的卡：算力 → 该用哪个包

```bash
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv
```

看输出里的 **`compute_cap`**（例：`6.1`、`7.0`、`7.5`、`8.9`），然后对下面这张表：

| `compute_cap` | 架构 | 例子 | 用哪个包 | 转写 | 分离 / 声纹 | qwen3asr |
|---|---|---|---|---|---|---|
| **≤ 7.0** | **Maxwell / Pascal / Volta** | **GTX 1070 / 1080 Ti**、V100、M40、P4/P40/P100、GTX 9xx | **本包（cu118）** | **只有 SenseVoice ✅（无原生时间戳）** | ❌ | ❌ |
| 7.5 | Turing | RTX 2080 / 2080 Ti / 魔改 22G、Titan RTX、GTX 16xx、T4 | `backend-cu126` | SenseVoice ✅；qwen3asr ❌（无 bf16） | ✅ | ❌ |
| ≥ 8.0 | Ampere / Ada / Hopper / Blackwell | RTX 30/40/50 系、A100、H100 | `backend-cu126` | SenseVoice ✅ + **qwen3asr ✅（bf16 原生）** | ✅ | ✅ **原生句级时间戳** |

**判据一句话**：`<= 7.0` 用本包；`>= 7.5` 用 `backend-cu126`。
（分界线是 7.5 —— 7.0 与 7.5 之间，**7.5 走 cu126**；老卡那道线在"`sm_ < 7.5`"。）

### 1.1 为什么老卡上**不能**跑 qwen3asr（就用 SenseVoice）

这不是"慢一点"，是这条路根本走不通，两条原因各自都足以否掉它：

1. **本变体的镜像里没有 qwen-asr**。cu118 那一层只装 `funasr`（+ 依赖）——因为要装
   `pyannote.audio` / `qwen-asr` 就会把钉住的 `torch 2.7.1+cu118` 顶掉，而 2.7.1 是
   **最后一个带 Pascal(sm_61) 的构建**。二者不可兼得，所以镜像的选择是"保住这块卡"。
2. **这块卡没有 bf16**（bf16 要 `sm_80+`），而 qwen3asr 那条加载路径是按 bf16 请求的：

   ```python
   # app/audio/stt.py:342
   dtype = "bf16" if use_cuda else "fp32"      # 写死的
   ```

   退回 fp32 会把显存翻倍（qwen3asr 0.6B + 对齐器 0.6B 在 fp32 下约 4.8 GB + 激活），
   8 GB 卡上很容易踩回"溢出换页 → 慢十倍、600 秒音频只出几十个字"那个坑。
   **改成 fp16 是引擎层（`app/audio/stt.py`）的改动，本包没有做，也没在真机验过。**

**所以本变体的转写引擎只有一个：SenseVoice**（非自回归、不吃 bf16、显存小得多，
权重约 900 MB）。代价写在 §10：它**不给句级时间戳**。

## 2. ② 前置（宿主）

```bash
# 1) NVIDIA 驱动：能列卡就行（老卡用老驱动也行，但要能跑 CUDA 11.8 以上的容器）
nvidia-smi -L
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv

# 2) 容器 GPU 直通（**缺了这一步，compose up 会报
#    could not select device driver "" with capabilities: [[gpu]]**）
#    Debian/Ubuntu:
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker
#    RHEL / CentOS / Rocky:
#      sudo dnf install -y nvidia-container-toolkit && sudo systemctl restart docker
nvidia-ctk --version
docker info --format '{{json .Runtimes}}'      # 里面要有 "nvidia"

# 3) Docker + compose v2
docker version --format '{{.Server.Version}}'
docker compose version                          # 必须 v2；老的 docker-compose 没测过

# 4) 其它：openssl（生成 JWT 密钥）、python3（跑验收脚本）、rsync（从源机拷模型）
```

**磁盘**：建议**预留 ≥ 60 GB**。本变体的模型卷只要 ~1 GB（SenseVoice 权重 ~900 MB），
但镜像本体重 3~5 GB（`ECHO_EXTRA=1` 含 cu118 的 torch 那组），现场构建还要 10 GB 左右的
构建缓存与中间层。`df -h` 看一眼再动手。

**网络**：内网 registry 最好的情况是什么都不用拉；现场构建要能到 PyPI 与
`download.pytorch.org`（见坑 1 与 §3 方式 C）。

## 3. ③ 拿镜像（三种方式，挑一种）

### 方式 A：内网 registry（最快，推荐）

```bash
docker pull <registry>/echo-backend:0.1.0-cu118
docker tag  <registry>/echo-backend:0.1.0-cu118 echo-backend:0.1.0-cu118
```

或者干脆在 `.env` 里写 `ECHO_IMAGE=<registry>/echo-backend:0.1.0-cu118`，compose 就用它。
⚠️ **本地镜像的 tag 必须和 compose 用的那个一致**（默认 `echo-backend:0.1.0-cu118`）；
不一致时 compose 会以为"没有这个镜像"，转去**现场构建** —— 看起来像"卡住了"，其实是在编译。
⚠️ **别把 cu126 的镜像改个 tag 拿来用**：那个 torch 里没有这块卡的架构（坑 2）。
内网 registry 上如果只有 `cu126` 那个 tag，说明 cu118 镜像还没构建出来，走方式 C。

### 方式 B：`docker load` 一个 tar（别人 `docker save` 出来的）

```bash
docker load -i echo-backend-0.1.0-cu118.tar
docker images | grep echo-backend
# 如果 load 进来的 tag 不是 echo-backend:0.1.0-cu118，就 retag：
#   docker tag <load 进来的名字> echo-backend:0.1.0-cu118
```

tar 里已经含 cu118 的 torch 那一层，所以**不需要外网**，也**没有"装错 CUDA 源"的风险**。
拿 tar 之前问一句对方"这 tar 是 cu118 还是 cu126 出的" —— 名字里通常就有。

### 方式 C：现场构建（有一点外网/内网 pip 源时）

```bash
docker compose build        # 构建参数（ECHO_EXTRA=1 / ECHO_TORCH_INDEX=cu118 / TORCH_VERSION=2.7.1）已在 compose 里
docker compose up -d
```

* 基础镜像 `python:3.11-slim` 从 Docker Hub 拉 —— **被墙就按坑 1 显式前缀直拉再 tag**；
* 普通依赖默认走 PyPI。国内实测 PyPI 的 wheel 只有一二百 kB/s，而清华镜像同一时刻
  26 MB/s（差 170 倍）。想快就在 `compose.yaml` 的 `build.args` 里打开这一行：
  `ECHO_PIP_INDEX: "https://pypi.tuna.tsinghua.edu.cn/simple"`；
  ⚠️ **torch 不走它** —— torch 走 `ECHO_TORCH_INDEX`（= `cu118`）+ `ECHO_TORCH_VERSION`（= `2.7.1`），
  这两行**已经在 compose 里写好了，别动**；
* 构建完**必看日志最后那几行**：会打印实际装到的 torch / CUDA 版本，而且会**校验**
  它还是不是 2.7.1（被依赖顶掉时构建直接失败 —— 那是好意，见坑 2）；
* 想一条命令把模型、key、起容器、建管理员、验收全做了（**老卡记得加 `--asr-impl sensevoice`**）：
  `sudo bash scripts/prepare-backend.sh --from user@源机:/home/u/echo --extra --asr-impl sensevoice`。

## 4. ④ 放模型（权重**不随镜像走**；本变体**只要 SenseVoice**）

> **含权重的包**（包根有 `models/` 与 `MODELS-INCLUDED.txt`）到手时，这一节只剩一件事：
> 把 `.env` 里的 `ECHO_HOST_MODELS_DIR` 指向**解包后的 `models/`**。
> 下面这些"从哪拿权重"的步骤可以整段跳过（纯代码包才要走完整节）。

### 4.1 该放哪些

宿主上的根目录 = `.env` 里的 `ECHO_HOST_MODELS_DIR`（默认 `/srv/echo/models`），
容器里看到的就是 `/opt/echo/models`。下表路径都相对这个根：

| 放什么 | 落点（相对模型根） | 作用 | 必需？ |
|---|---|---|---|
| **SenseVoice** | `sensevoice/snapshots/master/`（`config.yaml` + `model.pt`） | **本变体唯一的转写引擎** | ✅ **必需** |

**不用放的**（放了也不会被加载，别浪费磁盘和拷贝时间）：

| 不用放 | 为什么 |
|---|---|
| `hub/models--Qwen--Qwen3-ASR-0.6B/` | 镜像里**没有装 qwen-asr**（§1.1），且这块卡没有 bf16 |
| `hub/models--Qwen--Qwen3-ForcedAligner-0.6B/` | 它是给 qwen3asr 配句级时间戳的；本变体不跑 qwen3asr |
| `pyannote/**` | 镜像里**没有装 pyannote.audio**（4.x 要 torch>=2.8，而这块卡上限 2.7.1；3.4.0 又缺 `app/audio/diarize.py` 要的 `plda=`） |

> 形状说明：SenseVoice 认 `{模型根}/sensevoice` 这个目录，并在它下面**递归**找 `model.*`。
> 所以 `sensevoice/snapshots/master/model.pt`（拷 ModelScope 缓存的标准形状）和
> `sensevoice/model.pt`（直接摊平放）**都认**。
> ⚠️ **不能只指望 ModelScope 缓存**：容器里的 `/root/.cache/modelscope/models`
> 既不在只读模型卷上、`read_only: true` 下也不可写。

### 4.2 三种来源

**① 从源机拷（推荐，内网快）** —— 源机 = 一台**已经跑起来过**、SenseVoice 已下好的 ECHO：

```bash
# 源机上 SenseVoice 一般在 models/sensevoice/（或 ModelScope 缓存里）
sudo rsync -aL --info=progress2 \
    user@源机:/home/user/echo/models/sensevoice/ /srv/echo/models/sensevoice/
```

`-L` 是**关键**：把符号链接实体化。缓存里大量文件是软链，而容器里的只读挂载看不到
链子的目标（那就是"白准备一场然后 model_failed"）。

或者让脚本一次拷齐并逐个校验权重真的在：

```bash
sudo bash scripts/prepare-backend.sh --models-only --from user@源机:/home/user/echo --asr-impl sensevoice
```

> 那个脚本默认还会去要 qwen3asr 与强制对齐器，**在你这块卡上找不到是完全正常的** ——
> 只要 SenseVoice 在位，它会把这批缺失**降级成警告**并提示你用 `--asr-impl sensevoice`。
> 输出的最后如果只有警告、没有 `[错误]`，就是对的。

**② 联网从 ModelScope 下**：

```bash
sudo python3 -m pip install modelscope        # 宿主上要有
# 单独下 SenseVoice（落进容器要的那个布局）：
sudo python3 -c "from modelscope import snapshot_download; \
  snapshot_download('iic/SenseVoiceSmall', local_dir='/srv/echo/models/sensevoice/snapshots/master')"
```

（`scripts/prepare-backend.sh --from-modelscope` 也会下 pyannote，那三件在本变体没用；
想省流量就照上面这一行单独下 SenseVoice。）

**③ 用现成的模型包**：别人给你的是一个目录（或 tar），里面已经是 `sensevoice/...` 的形状：

```bash
sudo rsync -aL 现成模型包/sensevoice/ /srv/echo/models/sensevoice/
```

### 4.3 摆完自检（30 秒，值得）

```bash
find /srv/echo/models/sensevoice -name 'model.*' -size +1k | head
du -sh /srv/echo/models/sensevoice          # 期望 ~900 MB 量级
```

容器起来之后再验一遍（这才是权威）：

```bash
docker exec echo-backend ls -R /opt/echo/models/sensevoice | head -20
docker inspect --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' echo-backend
```

⚠️ 宿主路径写错时 **Docker 不报错**，而是自己建一个空目录 —— 症状是转写一路
`model_failed`。看到 `Mounts` 里的 `Source` 不对，就是它。

## 6. ⑥ 起容器

```bash
docker compose up -d                    # 镜像已在本地（方式 A / B）
docker compose up -d --build            # 要现场构建（方式 C）
docker compose logs -f backend          # 看它起来
```

**期望看到的日志**：

```
echo-backend 0.1.0 起来了：listen=0.0.0.0:8900 models=1 并发上限=2
管理面在 http://0.0.0.0:8901/admin/ （**可写**：发授权 / 禁用 / 撤销 / ...）
```

（`models=1` 就是"只有 SenseVoice 一档"，那是本变体的**预期**形状。）

以及这两句**预期**的告警（别去消它们）：

```
管理面监听在 0.0.0.0:8901（不是回环）—— 那个网段里谁能连上谁就能看到模型/客户端/调用元数据。
管理面开着（0.0.0.0:8901），但**一个管理员账号都没有** —— 登录永远会失败。
```

第一句是实话（容器里确实绑在通配地址上），**挡住外部的是宿主这一侧的端口发布规则**
（`127.0.0.1:8901:8901`），不是进程的绑定地址。第二句在 §7 建完管理员、重启后就没了。

健康状态（`start_period` 是 60 秒，前 60 秒显示 `starting` 是正常的）：

```bash
docker inspect --format '{{.State.Health.Status}}' echo-backend
```

> 想"一条命令全自动"：`sudo bash scripts/prepare-backend.sh --from user@源机:/home/user/echo --extra --asr-impl sensevoice`。
> ⚠️ 那条路会用它自己的 `server/compose.yaml` 与生成出来的一份 `compose.local.yml`，
> 并**默认开容器内自签 TLS**；而本文件的 compose.yaml 默认是明文 http（隔离网内够用）。
> 两条路选一条走到底就行，别混着起两个容器（容器名都是 `echo-backend`）。

## 7. ⑦ 建管理员（**只能在命令行建**）

```bash
# 先看有没有（幂等：已经有账号就别再建 —— --new-admin 会**重置**同名账号的口令）
docker exec echo-backend python -m server.main --list-admins

# 建一个（口令只打印这一次，当场存进密码管理器；库里只有哈希）
docker exec echo-backend python -m server.main --new-admin ops
```

管理面**刻意不开账号管理**：面板里只有一份只读的管理员清单。改账号 = 改"谁能进这扇门"，
而面板本身就在这扇门里 —— 让面板改账号，等于给一次会话劫持配一个提权出口。

## 8. ⑧ 打开管理面 + 发一张配对码

管理面只发布在**宿主回环**上，所以：

* 在 GPU 机器本机上：直接开 `http://127.0.0.1:8901/admin/`；
* 在自己的电脑上（**推荐**，也是坑 4 的答案）：

```bash
ssh -L 8901:127.0.0.1:8901 <gpu-host>
# 保持这个 ssh 开着，然后本地浏览器开：
#   http://127.0.0.1:8901/admin/
```

登录（§7 建的那个账号）→ 左侧 **「客户端」** 页 → **发一张配对码** → 把配对串给客户端，
在客户端面板里粘一次即可（码默认 15 分钟有效）。

⚠️ 直接访问 `http://<宿主IP>:8901/admin/` 会**登录得进去、但写动作 403**（同站 Origin 判定
只认 `127.0.0.1` / `localhost` / `[::1]`）—— 这是有意的窄，不是坏了。

## 9. ⑨ 验收

```bash
# 1) 服务活着 + 探针期望值（免鉴权）
curl -s http://127.0.0.1:8900/v1/health | python3 -m json.tool

# 2) 冒烟自测（不加载模型：只验查询端点 + 拒绝路径 + 临时文件归零）
python3 scripts/smoke-echo-backend.py --base-url http://127.0.0.1:8900 --skip-inference

# 3) **这一条才是"模型真能用"的证据**（给一段 16k 单声道 wav，几秒就够）
python3 scripts/smoke-echo-backend.py --base-url http://127.0.0.1:8900 --wav /path/to/16k.wav

# 4) 镜像里的 torch 真的认识这块卡（坑 2）—— **必须 True**
docker exec echo-backend python -c \
  "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_capability())"
```

**`/v1/health` 的期望值**（老卡这边 `models` 只有一条，是新卡的一半）：

| 字段 | 期望 | 说明 |
|---|---|---|
| `ok` | `true` | 挂了才 false |
| `version` | `0.1.0` | 与镜像 tag 对得上 |
| `uptimeSeconds` | 递增 | |
| `busy` | `{"active":0,"maxConcurrent":2,"perClientConcurrent":1}` | 并发闸门快照 |
| `vram` | `budgetMb=7000`（或你改的值）、`usedMb=0` | **空转时 `usedMb=0` 是对的**：模型按需加载 |
| `tmp` | `files=0, bytes=0` | **不为 0 就是泄漏信号** |
| `models` | **只有 `asr-long`**，空转时 `absent` | **没有** `diarize` / `speaker-embed` 两条 —— 那是本变体的预期形状，不是少配了 |
| `metrics` / `quota` | 数字 | |

`--skip-inference` **不会加载模型**，所以它证明不了权重是对的 —— 第 3 条才算。
第 3 条跑过之后再看一次 `/v1/health`：`vram.usedMb` 会变成 SenseVoice 的真实占用，
把它抄回 `server.yaml` 的 `est_vram_mb`（那里现在是占位估算 1200）。

## 10. 能力边界表（本变体 = `compute_cap <= 7.0`）

| 能力 | 能不能跑 | 说明 |
|---|---|---|
| 转写（SenseVoice，`/v1/asr`） | ✅ | 本变体唯一的转写引擎 |
| **原生句级时间戳** | ❌ | SenseVoice 不产出时间戳，`supports` 里**没有** `asr.timestamps`；服务端**不编**时间戳，会议时间轴由客户端按字数均摊、并如实标为**估算** |
| 转写（qwen3asr） | ❌ | 镜像里没装 qwen-asr；这块卡也没有 bf16（§1.1）。**不是"不建议"，是跑不了** |
| 说话人分离（`/v1/diarize`） | ❌ | 镜像里没有 pyannote.audio（4.x 要 torch>=2.8，而这块卡上限 2.7.1+cu118；3.4.0 又缺 `plda=`）。配置里**刻意不宣告**这一档 |
| 声纹嵌入（`/v1/speaker/embed`） | ❌ | 同上 |
| 并发 | 2 路（`ECHO_MAX_CONCURRENT`） | **按卡校准**：老卡算力弱，用真机压测决定 |

**客户端那边的表现是"诚实的降级"，不是故障**：后端不宣告 `diarize.turns` 这一档时，
客户端会显示 **「说话人分离未执行：<真原因>」** 并照常产出文字（这是设计行为 ——
宁可明说没做，也不假装做了）。

**需要分离 / 声纹 / 原生时间戳怎么办**：换 `compute_cap >= 7.5` 的卡，用 `backend-cu126`
那个包（Turing 上 qwen3asr 仍然不可用，但分离/声纹与 SenseVoice 都在）。

**实测参考**（2026-09-28 更新：本变体**已经在真机上跑过**了）：
宿主 GTX 1070 8 GB / Ubuntu 26.04 / Docker 29.1.3，`torch 2.7.1+cu118`、`cap (6,1)`；
`/v1/health` 用过之后 **`usedMb=1800`**；**90 秒真会议音频**：冷 **9.7~15.7 s**、
热 **1.17 s（RTF 0.013）**、490 字、`timestamps=none`、**显存峰值 1701~1737 MiB**。
所以下面那句"1200 是估算"只对 `server.yaml` 里那个**占位值**成立 —— 真机峰值约 **1.7 GB**，
把它抄回注释里。完整记录（含当时发现并修掉的 7 个问题）见仓库 `docs/后端容器部署.md` §13。
**在别的卡上跑完请把你这台的 `vram.usedMb` 与一段真音频的耗时也写回注释里**，
下一个人就不用猜了。

## 11. 排错五条（按现象查）

| 现象 | 真因 | 怎么办 |
|---|---|---|
| `compose up` 阶段就报 `could not select device driver "" with capabilities: [[gpu]]` | 宿主没装/没配 nvidia-container-toolkit | §2 第 2 条那两行命令，然后 `docker info --format '{{json .Runtimes}}'` 里要能看到 `nvidia`；再试 `docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi` |
| 容器起来了，日志有"`models.device=cuda` 但本机看不到可用的 CUDA"，随后转写 `model_failed` | **GPU 没直通进容器**（或驱动太老） | 同上；再跑 §9 第 4 条 —— `torch.cuda.is_available()` 必须是 `True`（坑 2）。**"装了个看不到 GPU 的 torch"不算成功** |
| 容器起来、`/v1/health` 200，但客户端"配对成功"之后换令牌回 **503 `auth_misconfigured`** | `ECHO_AUTH_ENABLED=true` 而 `ECHO_JWT_SECRET` 没进容器 | `docker exec echo-backend env \| grep ECHO_` 看有没有它；确认 `.env` 里填了、且 `docker compose up` 用的是本目录（`.env` 与 `compose.yaml` 同级）。留空的话 compose 本会直接报错退出，所以这一条多半是有人手工 `docker run` 起的 |
| 转写 `model_failed`，日志里是 `No such file` / `Can't load`；或 `/v1/health` 里 `asr-long` 长期 `absent` 而调用报错 | **模型卷摆错了**（宿主路径不存在时 Docker 会建空目录；或 SenseVoice 没放进 `sensevoice/`） | §4.3 那两条 `docker exec … ls` 与 `docker inspect … Mounts`；对着 §4.1 那张表核一遍落点 |
| 日志里说"没有 `diarize` 这个槽"，客户端显示「说话人分离未执行：…」 | **正常**：本变体的 `server.yaml` 刻意不宣告分离/声纹（§10） | 不需要修。确实要分离就换 sm_75+ 的卡用 cu126 包 |
| `docker pull` / `docker compose build` 卡住、超时；或构建**失败**在 torch 版本校验那一步 | **镜像源被墙**（Docker Hub）/ PyPI 太慢；版本校验失败 = 有依赖把 torch 顶掉了 | 坑 1 的显式前缀直拉 + `docker tag`；构建慢就打开 `ECHO_PIP_INDEX`（§3 方式 C）。**版本校验失败别绕过去**（那是"这块卡跑不了"的哨兵），改用 `docker load` 那条路拿一个现成的 cu118 tar |
| 宿主上 `curl 127.0.0.1:8901/admin/` 拒绝；或浏览器打不开管理面 | 8901 只发布在**宿主回环**，或者 `ECHO_ADMIN_LISTEN` 没配 | 必须**在 GPU 机器上**访问，或走 §8 的 `ssh -L`；`docker exec echo-backend env \| grep ADMIN_LISTEN`、`docker compose config \| grep -A3 ports` 各看一眼（坑 4） |
| 容器一直 `unhealthy` 而服务其实是好的 | 容器里启用了 TLS，而探针还在打 http | 在 `.env` 里写 `ECHO_HEALTH_SCHEME=https`，重新 `up -d` |

## 12. 进阶：TLS / 显存预算 / 停止与回滚

**开容器内 TLS**（默认是明文 http，隔离实验网内够用；一旦客户端跨网段就该开）：
没有环境变量能设 `server.tls.*`，所以要挂一份配置。在本目录加一个 `compose.override.yaml`：

```yaml
services:
  backend:
    volumes:
      - /srv/echo/tls/server.crt:/etc/echo/tls/server.crt:ro
      - /srv/echo/tls/server.key:/etc/echo/tls/server.key:ro
```

同时把 `server.yaml` 里补上 `server.tls.certfile/keyfile`（**两个都要填**，只填一个服务端
**启动就报错** —— 刻意不静默降级成 http），并在 `.env` 里把 `ECHO_HEALTH_SCHEME` 改成
`https`，否则容器会一直显示 `unhealthy` 而服务其实是好的。自签证书生成可以借
`scripts/prepare-backend.sh --tls self-signed`（它会写 `/srv/echo/compose.local.yml`）。
客户端**不需要**装自签根：配对串里带证书指纹，客户端按指纹固定。

**改显存预算 / 并发**：`server.yaml` 里的 `vram_budget_mb`（默认 7000）与 `.env` 里的
`ECHO_MAX_CONCURRENT`。**这两个要按卡校准，别照抄。**

**停止 / 回滚**（**卷留着**：客户端凭据、审计都在 state 卷里）：

```bash
docker compose down                       # 停掉，卷留着
docker compose logs --tail=200 backend    # 出事了先看日志
docker compose up -d                      # 再起来
```

**换包**：换镜像就改 `.env` 的 `ECHO_IMAGE`（或 `docker load` 新 tar 后 retag），
再 `docker compose up -d`。**state 卷不要删** —— 删了所有客户端都要重新配对一遍。
