# 先读我 —— ECHO 能力后端交付包（**新卡 / cu126**）

一句话：这是一套**容器化的 ECHO 能力后端**，给 `compute_cap >= 7.5` 的 NVIDIA 卡用
（Turing / Ampere / Ada / Blackwell）。你在一台装了 NVIDIA 驱动的 Linux GPU 机器上，
照 §1 → §9 把命令抄一遍就能跑起来。

> **这不是最终用户装的那个 ECHO**（面板 + 本地模型那一套）。这是**服务端**：别的 ECHO
> 机器把"转写 / 说话人分离 / 声纹"这些活派给它干。所以它没有安装向导，只有命令。
>
> 你拿到的是**两个变体里的一个**：`cu126`（本包，新卡）与 `cu118`（老卡）。
> **选错了不会报错，只会得到一个"看不到这块 GPU"的 torch** —— 所以 §1 请务必先看一眼。

---

## ⚠️ 四个坑（都真踩过，先看这四条）

**坑 1：Docker Hub 可能被墙。**
不要只往 `/etc/docker/daemon.json` 里加 `registry-mirrors` —— 加了之后**裸名拉取**
（`docker pull python:3.11-slim`）有时反而会挂住，而且挂得没完没了。可靠的做法是
**显式前缀直拉，再 tag 回本来的名字**：

```bash
docker pull docker.1panel.live/library/python:3.11-slim
docker tag  docker.1panel.live/library/python:3.11-slim python:3.11-slim
docker images | grep python        # 确认 tag 真的在了
```

（`docker.1panel.live` 只是当前可用的一个加速站，换别的同理：**前缀 + `library/` 那一层都别丢**。
只有现场构建那条路才需要拉基础镜像；`docker load` 一个 tar 不需要网络。）

**坑 2：这块卡必须用对应的变体，而"构建成功"不等于"卡能用"。**
torch 是**按卡**从不同 CUDA 源装的（`cu126` / `cu118` 是**镜像里 torch 那一层**决定的，
是构建期参数，不是运行时开关）。装了一个不含这块卡架构的 torch，镜像照样构建成功、
容器照样起来 —— 只是它看不到 GPU。所以**验收必须看这一条**（§9 有）：

```bash
docker exec echo-backend python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_capability())"
# 期望：True (8, 9) —— 前一个必须是 True，后一个必须和 nvidia-smi 报的算力一致
```

**坑 3：模型不随镜像走，而且"缺强制对齐器"不是降级一点。**
权重放在宿主上只读挂进容器（§4）。摆错位置的症状是"看起来装了、其实加载不到"
（每个模型 `model_failed`）。更隐蔽的是**缺强制对齐器**：服务端宣告的
`supports: [asr.text, asr.timestamps]` 会变成**假话** —— 时间戳一路退化成 `none`，
而 `/v1/health` 照样是绿的。所以 §4 那张清单要摆齐。

**坑 4：管理面只发布在宿主回环（`127.0.0.1:8901`）。**
**别**把它改成 `"8901:8901"` —— 那等于把管理面（发授权、看客户端、看审计）摊给整个网段。
远程运维走 SSH 端口转发（§8）：

```bash
ssh -L 8901:127.0.0.1:8901 <gpu-host>     # 然后本地浏览器开 http://127.0.0.1:8901/admin/
```

## 1. ① 先确认你的卡：算力 → 该用哪个包

```bash
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv
```

看输出里的 **`compute_cap`**（例：`8.9`、`7.5`、`6.1`），然后对下面这张表：

| `compute_cap` | 架构 | 例子 | 用哪个包 | 转写 | 分离 / 声纹 | qwen3asr |
|---|---|---|---|---|---|---|
| **≥ 8.0** | Ampere / Ada / Hopper / Blackwell | RTX 30/40/50 系、A100、H100 | **本包（cu126）** | SenseVoice ✅ + **qwen3asr ✅（bf16 原生）** | ✅ | ✅ **原生句级时间戳** |
| **7.5** | **Turing** | RTX 2080 / 2080 Ti / 魔改 22G、Titan RTX、GTX 16xx、T4 | **本包（cu126）** | SenseVoice ✅；**qwen3asr ❌** | ✅ | ❌ —— **见 §1.1** |
| **≤ 7.0** | Maxwell / Pascal / Volta | GTX 1070 / 1080 Ti、V100、M40、P4/P40/P100 | `backend-cu118` | **只有 SenseVoice ✅（无原生时间戳）** | ❌ | ❌ |

**判据一句话**：`>= 7.5` 用本包；`<= 7.0` 用 `backend-cu118`。
（分界线是 7.5 —— 7.0 与 7.5 之间，**7.5 走本包**。老卡那道线在"`sm_ < 7.5`"。）

拿不准自己属于哪一类：`scripts/prepare-backend.sh` 会在宿主上读 `compute_cap`，
并在 `sm_ < 7.5` 时**自动**把 torch 源换成 cu118（读不到算力就按型号名兜底）。

### 1.1 Turing（`compute_cap = 7.5`）必读：qwen3asr 现在跑不了，请换 SenseVoice

Turing **没有 bf16**（bf16 要 `sm_80+`），而 qwen3asr 那条加载路径是按 bf16 请求的：

```python
# app/audio/stt.py:342
dtype = "bf16" if use_cuda else "fp32"      # 写死的
```

* 请求 bf16 → 要么报错、要么走低效路径，两种都不该拿去上生产；
* 退回 fp32 会把显存**翻倍**（qwen3asr 0.6B + 对齐器 0.6B 在 fp32 下约 4.8 GB + 激活），
  8 GB 卡上很容易踩回"溢出换页 → 慢十倍、600 秒音频只出几十个字"那个坑；
* **改成 fp16 是引擎层（`app/audio/stt.py`）的改动，本包没有做，也没在真机验过。**

**所以 Turing 的正解是 SenseVoice**（非自回归、不吃 bf16、显存小得多）。三步：

1. 把 SenseVoice 权重放进模型卷（§4 清单里那一行"可选"）：
   `{模型根}/sensevoice/snapshots/master/{config.yaml,model.pt}`；
2. 打开 `server.yaml`，把 `- id: asr-long` 那一条（8 行）**整条替换成**：

   ```yaml
       - id: asr-long
         slot: asr.long
         impl: sensevoice
         resident: false
         max_concurrency: 1
         est_vram_mb: 1200          # 占位估算：跑一段真音频后按 /v1/health 的 vram.usedMb 校准
         modelVersion: sensevoice-small
         supports: [asr.text]       # 注意：**没有** asr.timestamps
   ```

   （`server.yaml` 里那段注释就是同一份片段，可以直接对照。）
3. 重启容器：`docker compose up -d --force-recreate`。

代价：SenseVoice **不给句级时间戳**，所以 `supports` 里刻意没有 `asr.timestamps`。
会议的时间轴会退化成客户端按字数均摊的**估算**（面板会如实标明是估算，不是后端编的）。
其余能力（分离 / 声纹）在 Turing 上仍然可用 —— 那是 pyannote，与 bf16 无关。

## 2. ② 前置（宿主）

```bash
# 1) NVIDIA 驱动：能列卡就行（驱动要够新，至少支持 CUDA 12.x）
nvidia-smi -L
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv

# 2) 容器 GPU 直通（**缺了这一步，compose up 会报
#    could not select device driver "" with capabilities: [[gpu]]**）
#    Debian/Ubuntu:
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker
#    RHEL / CentOS / Rocky:
#      sudo dnf install -y nvidia-container-toolkit && sudo systemctl restart docker
nvidia-ctk --version
docker info --format '{{json .Runtimes}}'      # 里面要有 "nvidia"

# 3) Docker + compose v2
docker version --format '{{.Server.Version}}'
docker compose version                          # 必须 v2；老的 docker-compose 没测过

# 4) 其它：openssl（生成 JWT 密钥）、python3（跑验收脚本）、rsync（从源机拷模型）
```

**磁盘**：建议**预留 ≥ 60 GB**。其中模型卷约 6 GB（qwen3asr 0.6B + 对齐器 0.6B + pyannote
三件套），镜像本体重 3~5 GB（`ECHO_EXTRA=1` 含 torch 那组），现场构建还要 10 GB 左右的
构建缓存与中间层。`df -h` 看一眼再动手。

**网络**：内网 registry 最好的情况是什么都不用拉；现场构建要能到 PyPI 与
`download.pytorch.org`（见坑 1 与 §3 方式 C）。

## 3. ③ 拿镜像（三种方式，挑一种）

### 方式 A：内网 registry（最快，推荐）

```bash
docker pull <registry>/echo-backend:0.1.0-cu126
docker tag  <registry>/echo-backend:0.1.0-cu126 echo-backend:0.1.0-cu126
```

或者干脆在 `.env` 里写 `ECHO_IMAGE=<registry>/echo-backend:0.1.0-cu126`，compose 就用它。
⚠️ **本地镜像的 tag 必须和 compose 用的那个一致**（默认 `echo-backend:0.1.0-cu126`）；
不一致时 compose 会以为"没有这个镜像"，转去**现场构建** —— 看起来像"卡住了"，其实是在编译。

### 方式 B：`docker load` 一个 tar（别人 `docker save` 出来的）

```bash
docker load -i echo-backend-0.1.0-cu126.tar
docker images | grep echo-backend
# 如果 load 进来的 tag 不是 echo-backend:0.1.0-cu126，就 retag：
#   docker tag <load 进来的名字> echo-backend:0.1.0-cu126
```

tar 里已经含 torch 那一层，所以**不需要外网**，也**没有"装错 CUDA 源"的风险** ——
前提是给你 tar 的人用的是对应这块卡的变体（新卡才用 cu126）。

### 方式 C：现场构建（有一点外网/内网 pip 源时）

```bash
docker compose build        # 构建参数（ECHO_EXTRA / ECHO_TORCH_INDEX=cu126）已经写在 compose 里
docker compose up -d
```

* 基础镜像 `python:3.11-slim` 从 Docker Hub 拉 —— **被墙就按坑 1 显式前缀直拉再 tag**；
* 普通依赖（funasr / qwen-asr / transformers / pyannote.audio / speechbrain）默认走 PyPI。
  国内实测 PyPI 的 wheel 只有一二百 kB/s，而清华镜像同一时刻 26 MB/s（差 170 倍）。
  想快就在 `compose.yaml` 的 `build.args` 里打开这一行：
  `ECHO_PIP_INDEX: "https://pypi.tuna.tsinghua.edu.cn/simple"`；
  ⚠️ **torch 不走它** —— torch 走 `ECHO_TORCH_INDEX`（= `cu126`，已写好，**别改**）；
* 构建完**看一眼日志最后几行**：会打印实际装到的 torch / CUDA 版本；
* 想一条命令把模型、key、证书、起容器、建管理员、验收全做了：
  `sudo bash scripts/prepare-backend.sh --from user@源机:/home/u/echo --extra`（见 §4 与 §6）。

## 4. ④ 放模型（权重**不随镜像走**）

> **含权重的包**（包根有 `models/` 与 `MODELS-INCLUDED.txt`）到手时，这一节只剩一件事：
> 把 `.env` 里的 `ECHO_HOST_MODELS_DIR` 指向**解包后的 `models/`**。
> 下面这些"从哪拿权重"的步骤可以整段跳过（纯代码包才要走完整节）。

### 4.1 本变体该放哪些（**照这张表摆，位置是固定的**）

宿主上的根目录 = `.env` 里的 `ECHO_HOST_MODELS_DIR`（默认 `/srv/echo/models`），
容器里看到的就是 `/opt/echo/models`。下表路径都相对这个根：

| 放什么 | 落点（相对模型根） | 作用 | 必需？ |
|---|---|---|---|
| Qwen3-ASR 0.6B | `hub/models--Qwen--Qwen3-ASR-0.6B/snapshots/master/`（`config.json` + `model.safetensors`） | 转写（qwen3asr） | ✅ 必需（sm_80+） |
| Qwen3 强制对齐器 0.6B | `hub/models--Qwen--Qwen3-ForcedAligner-0.6B/snapshots/master/`（`config.json` + `model.safetensors`） | **句级时间戳** | ✅ **必需**（缺了 `asr.timestamps` 是假话，见坑 3） |
| pyannote 分割 | `pyannote/pyannote-segmentation-3.0-local/pytorch_model.bin` | 说话人分离 | ✅（要用 `/v1/diarize`） |
| pyannote 声纹 | `pyannote/pyannote-wespeaker-local/pytorch_model.bin` | 声纹嵌入 / 分离后处理 | ✅ 同上 |
| pyannote PLDA | `pyannote/pyannote-plda-local/plda/{plda.npz,xvec_transform.npz}` | 分离的聚类 | ✅ 同上 |
| SenseVoice（可选） | `sensevoice/snapshots/master/{config.yaml,model.pt}` | **Turing 的转写退路**（§1.1） | 仅 Turing 需要 |

两条容易踩的：

* **Qwen 那两份必须在 `hub/` 下**，目录形状是
  `hub/models--<owner>--<name>/snapshots/<任意子目录>/`（`master` 只是跟 ModelScope 的命名对齐，
  目录名本身不参与判断）。放错一层（比如直接放 `models/Qwen3-ASR-0.6B/`）就是加载不到。
* **容器里的 ModelScope 缓存不可用**（`/root/.cache/modelscope/models` 既不在只读模型卷上、
  `read_only: true` 下也不可写），所以 SenseVoice 也必须显式放进模型卷。

### 4.2 三种来源

**① 从源机拷（推荐，内网快）** —— 源机 = 一台**已经跑起来过**、模型已下好的 ECHO：

```bash
sudo rsync -aL --info=progress2 \
    user@源机:/home/user/echo/models/hub/models--Qwen--Qwen3-ASR-0.6B/ \
    /srv/echo/models/hub/models--Qwen--Qwen3-ASR-0.6B/
```

`-L` 是**关键**：把符号链接实体化。HF / ModelScope 缓存里大量文件是软链，而容器里的只读
挂载看不到链子的目标（那就是"白准备几 GB 然后 model_failed"）。pyannote 三件套同理。

或者让脚本一次拷齐（含对齐器、pyannote，并逐个校验权重真的在）：

```bash
sudo bash scripts/prepare-backend.sh --models-only --from user@源机:/home/user/echo
```

**② 联网从 ModelScope 下**：

```bash
sudo python3 -m pip install modelscope        # 宿主上要有
sudo bash scripts/prepare-backend.sh --models-only --from-modelscope
```

**③ 用现成的模型包**：别人给你的是一个目录（或 tar），里面已经是上面那张表的形状：

```bash
sudo rsync -aL 现成模型包/hub/        /srv/echo/models/hub/
sudo rsync -aL 现成模型包/pyannote/   /srv/echo/models/pyannote/
# 拷完按下面 4.3 自检一遍；顺序/来源不重要，"落点对不对"才重要。
```

### 4.3 摆完自检（30 秒，值得）

```bash
ls /srv/echo/models/hub/ | grep Qwen                  # 期望看到两个 models--Qwen--*
ls /srv/echo/models/pyannote/*/ | head                # 期望看到三件套的权重文件名
find /srv/echo/models -name '*.safetensors' -o -name 'pytorch_model.bin' | wc -l
```

容器起来之后再验一遍（这才是权威）：

```bash
docker exec echo-backend ls /opt/echo/models/hub
docker inspect --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' echo-backend
```

⚠️ 宿主路径写错时 **Docker 不报错**，而是自己建一个空目录 —— 症状是每个模型
`model_failed`。看到 `Mounts` 里的 `Source` 不对，就是它。

## 5. ⑤ 填 .env

```bash
cp .env.example .env
openssl rand -hex 32          # 把结果填进 .env 的 ECHO_JWT_SECRET
$EDITOR .env
```

最少要动一处：**`ECHO_JWT_SECRET`**（留空的话 `docker compose up` 会直接报错退出 ——
这是故意的，宁可起不来也不要静默起一个不鉴权的服务）。卷路径不对才需要改另外三项。
**给同事用就再多动一处**：`ECHO_ADVERTISED_HOST=<同事能访问到的那个 IP>` ——
不填的话发出去的配对串里会是 **Docker 网桥地址**，同事连不上（见 §8.1）。
⚠️ `.env` 里有密钥：别提交到 git、别转发。

## 6. ⑥ 起容器

```bash
docker compose up -d                    # 镜像已在本地（方式 A / B）
docker compose up -d --build            # 要现场构建（方式 C）
docker compose logs -f backend          # 看它起来
```

**期望看到的日志**：

```
echo-backend 0.1.0 起来了：listen=0.0.0.0:8900 models=3 并发上限=6
管理面在 http://0.0.0.0:8901/admin/ （**可写**：发授权 / 禁用 / 撤销 / ...）
```

（`并发上限` 打的是**此刻真正生效**的值：全新部署（还没在管理面配过）就是出厂 **6**；
在管理面「运行参数」里改过之后，这里打的是**管理面那个值** —— 不是 `.env` 里的。）

以及这两句**预期**的告警（别去消它们）：

```
管理面监听在 0.0.0.0:8901（不是回环）—— 那个网段里谁能连上谁就能看到模型/客户端/调用元数据。
管理面开着（0.0.0.0:8901），但**一个管理员账号都没有** —— 登录永远会失败。
```

第一句是实话（容器里确实绑在通配地址上），**挡住外部的是宿主这一侧的端口发布规则**
（`127.0.0.1:8901:8901`），不是进程的绑定地址。第二句在 §7 建完管理员、重启后就没了。

健康状态（`start_period` 是 60 秒，前 60 秒显示 `starting` 是正常的）：

```bash
docker inspect --format '{{.State.Health.Status}}' echo-backend
```

> 想"一条命令全自动"（建目录 / 拷模型 / 生成密钥 / 自签 TLS / 写配置 / 起容器 / 建管理员 /
> 验一遍）：`sudo bash scripts/prepare-backend.sh --from user@源机:/home/user/echo --extra`。
> ⚠️ 那条路会用它自己的 `server/compose.yaml` 与生成出来的一份 `compose.local.yml`，
> 并**默认开容器内自签 TLS**；而本文件的 compose.yaml 默认是明文 http（隔离网内够用）。
> 两条路选一条走到底就行，别混着起两个容器（容器名都是 `echo-backend`）。

## 7. ⑦ 建管理员（**只能在命令行建**）

```bash
# 先看有没有（幂等：已经有账号就别再建 —— --new-admin 会**重置**同名账号的口令）
docker exec echo-backend python -m server.main --list-admins

# 建一个（口令只打印这一次，当场存进密码管理器；库里只有哈希）
docker exec echo-backend python -m server.main --new-admin ops
```

管理面**仍然不开账号管理**：面板上那份管理员清单**是只读的**，新建 / 删除 / 禁用 / 启用、
改**别人**的口令都只在命令行。改账号 = 改"谁能进这扇门"，而面板本身就在这扇门里 ——
让面板改账号，等于给一次会话劫持配一个提权出口。
唯一的例外（2026-09-29 起）是**改"自己"的口令**：面板上可以改，但**必须先给出当前口令**
（所以"一次会话劫持"不足以改掉它），改成功后别的会话失效、当前会话保留。
面板上那句话是后端下发的（`GET /admin/api/admins` 的 `note` / `selfServiceNote`），
不是 HTML 里另抄的一份。

## 8. ⑧ 打开管理面 + 发一张配对码

管理面只发布在**宿主回环**上，所以：

* 在 GPU 机器本机上：直接开 `http://127.0.0.1:8901/admin/`；
* 在自己的电脑上（**推荐**，也是坑 4 的答案）：

```bash
ssh -L 8901:127.0.0.1:8901 <gpu-host>
# 保持这个 ssh 开着，然后本地浏览器开：
#   http://127.0.0.1:8901/admin/
```

登录（§7 建的那个账号）→ 左侧 **「客户端」** 页 → **发一张配对码** → 把配对串给客户端，
在客户端面板里粘一次即可（码默认 15 分钟有效）。

⚠️ 直接访问 `http://<宿主IP>:8901/admin/` 会**登录得进去、但写动作 403**（同站 Origin 判定
只认 `127.0.0.1` / `localhost` / `[::1]`）—— 这是有意的窄，不是坏了。

### 8.1 ⚠️ 发码之前先定形态：**共享后端**还是**本机后端**（两种都别漏这一步）

配对串里那个 `host` 是**服务端写进去**的 —— 而服务端在容器里**自己探测**时拿到的
是 **Docker 网桥地址**（实测 `172.18.0.2`），于是串长这样：

```
echo://pair?host=http://172.18.0.2:8900&code=…      ← 同事照它连必然连不上
echo://pair?host=http://10.100.0.24:8900&code=…     ← 这才是同事连得到的
```

**"同事连得到哪台机器"只有你知道**，所以这一项要人来填。两种形态**选一种**，
别混着来（差别不只是一个地址，还有"要不要对局域网开放"）：

| | **共享后端**（本包默认，同事要连） | **本机后端**（后端与客户端同一台机器） |
|---|---|---|
| `ECHO_LISTEN` | `0.0.0.0:8900`（对网段开放） | **`127.0.0.1:8900`（只回环）** |
| 端口发布（`compose.yaml` 的 `ports:`） | `"8900:8900"` | 改成 **`"127.0.0.1:8900:8900"`** |
| 对外公布地址 | **要填**：`ECHO_ADVERTISED_HOST=10.100.0.24`（你这段局网的 IP） | **不用填**（下面有"为什么"） |
| 怎么配对 | 管理面发码、手工粘串 | 客户端点「检测本机后端」读状态卷里的 `local-pair.json`，**全自动** |
| 局域网里的人能不能用 | 能连上端口（所以**鉴权必须开着**） | **根本连不到**这个端口 |

**共享后端（同事要连）—— 在 `.env` 里加一行就够**：

```bash
ECHO_ADVERTISED_HOST=10.100.0.24        # 换成**你这台**的局域网 IP；端口不写就用 8900
# 等价写法：ECHO_ADVERTISED_HOST=10.100.0.24:8900
#           ECHO_ADVERTISED_HOST=http://10.100.0.24:8900
docker compose up -d                    # 改了 .env 要重新 up 才进容器
```

填完**再发码**（或重发一张），串里的 host 就是它了。也可以不改 `.env`、
直接在**管理面**的「客户端 / 发授权」页签里填那张「**对外公布地址**」卡 ——
保存**立刻生效**（不用重启容器）、存在 state 卷、重启后还在；
**管理面配过的值优先于 `.env` 里的 `ECHO_ADVERTISED_HOST`**（页面与日志都会如实说）。
**怎么确认？** 管理面那张卡上会显示"**此刻发码会用的地址**"与它的**来源**
（管理面配置 / 环境变量 / 配置文件 / 本机探测）—— 来源写着「本机探测」就是还没配。

**本机后端（这台机器自己用，不对外）为什么不需要公布地址**：

* 监听改 `127.0.0.1:8900` 之后，**局域网里的人根本连不到这个端口** ——
  这是比"靠鉴权挡住"更强的隔离（本机自用不必先跟凭据较劲）；
* 配对走本机那份 `local-pair.json`（后端启动时写在**状态卷**里），客户端点
  「检测本机后端」读它即可，**地址是构造出来的 `127.0.0.1:<端口>`** ——
  与"同事能不能连到这台机器的局域网 IP"是两个不相干的问题，所以**不需要**
  `ECHO_ADVERTISED_HOST`，也不要求手填任何地址；
* 所以这一档**不要**在 `.env` 里填局域网 IP：本机客户端该走回环
  （换网络、IP 变了都不受影响）。而**即使你填了**，本机配对文件里的地址仍然是
  `127.0.0.1`（那条路刻意不走这一项）。

**同一台后端两边都服务**（既有本机客户端、又有同事）：保持 `0.0.0.0:8900` +
`ECHO_ADVERTISED_HOST=<局域网 IP>`，发码时**各写各的** —— 管理面发码那张卡上有一个
「这一张公布的地址」输入框：给本机那张填 `127.0.0.1`、给同事那张留空（用全局那一项）。
串本身带 host，**两张码互不影响**；串就是一段文本（没有签名/校验），
**手改 host 也能直接用**。

> 忘了配会怎样？启动日志里会有一句告警（"没有配 `server.advertised_host` ——
> 配对串里的地址只能本机探测：容器里探测到的是 Docker 网桥地址，同事连不上"），
> 配对串本身也会附一句同样的提示。**不会静默给你一个错地址。**

## 10. 能力边界表（本变体 = `compute_cap >= 7.5`）

| 能力 | sm_80+（Ampere/Ada/Blackwell） | sm_75（Turing） | 备注 |
|---|---|---|---|
| 转写 SenseVoice（`/v1/asr`） | ✅ | ✅ | 需另放 SenseVoice 权重；**不给句级时间戳** |
| 转写 qwen3asr（`/v1/asr`） | ✅ | ❌ | Turing 无 bf16，见 §1.1；sm_80+ 上带**原生句级时间戳** |

| 原生 `asr.timestamps` | ✅ | 仅 SenseVoice 时 ❌ | 对齐器在位才有；Turing 走 SenseVoice 时时间轴是**估算** |

* 本机 RTX 5060 Laptop（Ada，`sm_8.9`）：qwen3asr **600 秒音频 30~45 秒**、**峰值显存 4.6 GB**
  （2026-09-27 实测，数据据以定的 `est_vram_mb: 4700` 就是它）；
* ⚠️ **这条数字来自开发机上的"后端进程"**（不是容器），而且**这个交付包还没有在任何真机上
  按它从零跑过一遍**。你这次跑完把 `/v1/health` 的 `vram.usedMb` 与一段真音频的耗时写回
  `server.yaml` 的注释里，下一个人就不用猜了。

**这个变体跑不了什么**：`compute_cap <= 7.0` 的卡（Maxwell/Pascal/Volta）—— 请换
`backend-cu118` 包；那边只有 SenseVoice，而且**没有**分离/声纹（原因写在那份文档里）。

## 11. 排错五条（按现象查）

| 现象 | 真因 | 怎么办 |
|---|---|---|
| `compose up` 阶段就报 `could not select device driver "" with capabilities: [[gpu]]` | 宿主没装/没配 nvidia-container-toolkit | §2 第 2 条那两行命令，然后 `docker info --format '{{json .Runtimes}}'` 里要能看到 `nvidia`；再试 `docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi` |
| 容器起来了，日志有"`models.device=cuda` 但本机看不到可用的 CUDA"，随后每个模型 `model_failed` | **GPU 没直通进容器**（或驱动太老） | 同上；再跑 §9 第 4 条 —— `torch.cuda.is_available()` 必须是 `True`。**"装了个看不到 GPU 的 torch"不算成功**（坑 2） |
| 容器起来、`/v1/health` 200，但客户端"配对成功"之后换令牌回 **503 `auth_misconfigured`** | `ECHO_AUTH_ENABLED=true` 而 `ECHO_JWT_SECRET` 没进容器 | `docker exec echo-backend env \| grep ECHO_` 看有没有它；确认 `.env` 里填了、且 `docker compose up` 用的是本目录（`.env` 与 `compose.yaml` 同级）。留空的话 compose 本会直接报错退出，所以这一条多半是有人手工 `docker run` 起的 |
| `model_failed`，日志里是 `No such file` / `Can't load`；或 `/v1/health` 里 `models` 长期是 `absent` 而调用报错 | **模型卷摆错了**（层数/目录名不对；宿主路径不存在时 Docker 会建空目录） | §4.3 那两条 `docker exec … ls` 与 `docker inspect … Mounts`；对着 §4.1 那张表核一遍落点 |
| 日志有 `[stt] 强制对齐器 … 不在本机`，`timestamps` 一路 `none`（而 `/v1/health` 是绿的） | **缺强制对齐器** —— 服务端宣告的 `asr.timestamps` 是假话 | 把 `Qwen3-ForcedAligner-0.6B` 放到 `hub/models--Qwen--Qwen3-ForcedAligner-0.6B/snapshots/master/`（坑 3） |
| `docker pull` / `docker compose build` 卡住、超时 | **镜像源被墙**（Docker Hub）或 PyPI 太慢 | 坑 1 的显式前缀直拉 + `docker tag`；构建慢就打开 `ECHO_PIP_INDEX`（§3 方式 C）；`docker load` 那条路完全不需要网络 |
| 宿主上 `curl 127.0.0.1:8901/admin/` 拒绝；或浏览器打不开管理面 | 8901 只发布在**宿主回环**，或者 `ECHO_ADMIN_LISTEN` 没配 | 必须**在 GPU 机器上**访问，或走 §8 的 `ssh -L`；`docker exec echo-backend env \| grep ADMIN_LISTEN`、`docker compose config \| grep -A3 ports` 各看一眼（坑 4） |
| 容器一直 `unhealthy` 而服务其实是好的 | 容器里启用了 TLS，而探针还在打 http | 在 `.env` 里写 `ECHO_HEALTH_SCHEME=https`，重新 `up -d` |
| 客户端"配对成功"却一直连不上，而串里是 `host=http://172.1x.x.x:8900` | **没配对外公布地址** —— 串里是容器自己探测到的 **Docker 网桥地址**（同事那头当然没有这个网段） | 见 §8.1：在 `.env` 里填 `ECHO_ADVERTISED_HOST=<同事能访问到的 IP>`（或在管理面「对外公布地址」卡里填），然后**重新发一张码**。手改串里的 host 同样能用 |

## 12. 进阶：TLS / 显存预算 / 停止与回滚

**开容器内 TLS**（默认是明文 http，隔离实验网内够用；一旦客户端跨网段就该开）：
没有环境变量能设 `server.tls.*`，所以只能走配置 —— 本变体的 `server.yaml` 已经挂进容器了
（`/etc/echo/server.yaml`），**只要在它里面补两行**（两个都要填；只填一个服务端**启动就报错**，
刻意不静默降级成 http）：

```yaml
server:
  tls:
    certfile: /etc/echo/tls/server.crt
    keyfile: /etc/echo/tls/server.key
```

再把证书挂进容器（在本目录加一个 `compose.override.yaml`，它会与 `compose.yaml` 合并）：

```yaml
services:
  backend:
    volumes:
      - /srv/echo/tls/server.crt:/etc/echo/tls/server.crt:ro
      - /srv/echo/tls/server.key:/etc/echo/tls/server.key:ro
```

最后在 `.env` 里把 `ECHO_HEALTH_SCHEME` 改成 `https` —— 否则容器会一直显示 `unhealthy`
而服务其实是好的（这是已知的真实风险点：探针打的是容器自己的 8900）。
自签证书的生成可以借 `scripts/prepare-backend.sh --tls self-signed`
（它会一并写好 `/srv/echo/compose.local.yml`，那条路更省事）。
客户端**不需要**装自签根：配对串里带证书指纹，客户端按指纹固定。

**改显存预算**：`server.yaml` 里的 `vram_budget_mb`（默认 7000，8 GB 卡实测值；
24 GB 卡可以给 20000）—— 要按卡校准，改完**要重起容器**。

**改并发**（出厂 6 路）：**在管理面里改** —— 登录后进「性能」页签，那张「运行参数」卡里直接填。
**改完即时生效，不用重启、也不用动 `.env`**；写的值存在 state 卷里，重启后还在。
`.env` 里的 `ECHO_MAX_CONCURRENT` **只在管理面没配过时**（空 state 卷首启）当起点 ——
配过之后**以管理面那份为准**（优先级：**管理面配置 > 环境变量 > 出厂默认**，见 `server/limits.py`；
env 在场面却被管理面盖住时，管理面接口与启动日志都会如实说一句）。
**显存预算与并发这两个数都要按卡校准，别照抄。**

**停止 / 回滚**（**卷留着**：客户端凭据、审计都在 state 卷里）：

```bash
docker compose down                       # 停掉，卷留着
docker compose logs --tail=200 backend    # 出事了先看日志
docker compose up -d                      # 再起来
```

**换包**：换镜像就改 `.env` 的 `ECHO_IMAGE`（或 `docker load` 新 tar 后 retag），
再 `docker compose up -d`。**state 卷不要删** —— 删了所有客户端都要重新配对一遍。
